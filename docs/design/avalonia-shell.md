# Avalonia shell

`src/Steward.Desktop` is the Avalonia 12 app, the same views, styles and view models on Windows, Linux and macOS. It is a self-contained `WinExe` on `net10.0-windows10.0.26100.0` (`win-x64`, `win-arm64`) and on `net10.0` (`linux-x64`, `linux-arm64`, `osx-x64`, `osx-arm64`, published with `-f net10.0 -r linux-x64`; a Windows build of the solution also emits `bin\<config>\net10.0\win-x64\Steward.Desktop.exe`, which carries the Unix stubs, cannot read the DPAPI session and shares `state.json` with the installed app, so it is never launched on Windows) on Avalonia 12.1.3 and FluentAvaloniaUI 3.1.0 (`FluentAvaloniaTheme` replaces `Avalonia.Themes.Fluent`), with compiled bindings by default. `app.manifest` declares PerMonitorV2 DPI awareness, so the window opens at 980x720 logical pixels scaled for its monitor. `appsettings.json`, `Steward.ico`, the in-app PNGs, the Store logo images and `Assets/Products/*.png` live in `src/Steward.Desktop` (`src/Steward.Desktop/Assets/Steward.ico`): the icon and PNGs are `AvaloniaResource` under `avares://Steward.Desktop/Assets/` (the window, tray and `_NET_WM_ICON` all load it from there), and `appsettings.json` is the embedded resource `Steward.Desktop.appsettings.json`, read through `AddJsonStream`, so a single-file publish needs no settings or icon file beside the exe; the font licence texts under `Assets/Fonts` are `Content` and sit beside it, and so do the native libraries (`libSkiaSharp`, `libHarfBuzzSharp`, and `av_libglesv2.dll` on Windows) unless the publish sets `IncludeNativeLibrariesForSelfExtract`, which the Windows zip build does (see Releases), so .NET extracts them to its bundle folder on first start. No file beside the exe overrides it, so the app has the one embedded source. `AVLN3001` is suppressed because every view takes its view model through its constructor and is never loaded by URI. `Program.BuildAvaloniaApp` sets `Win32PlatformOptions`: rendering `AngleEgl` then `Software`, composition `WinUIComposition`, `DirectComposition`, then `RedirectionSurface`; under Wine (`AppInfo.IsWine`) `Software` rendering into a `RedirectionSurface` only, and the window keeps Wine's own frame (`ExtendClientAreaToDecorationsHint` off), since an extended client area under Wine 11 sat 30px above the window Wine reported and clipped the title bar row; the title row there hides the app's own icon and title (`TitleArea`), which Wine's frame already shows, and keeps the install picker. `--curseforge-link=` and a bare `curseforge:` or `steward:` argument are read in `Program.ActivationLink`, and a packaged build without either falls back to the WinRT `Windows.ApplicationModel.AppInstance.GetActivatedEventArgs()` protocol arguments (`WindowsShell.ProtocolActivationUri`; no Windows App SDK `AppInstance`); the named mutex, events and link pipe are the shared `InstanceCoordination`.

A Windows publish (the Windows TFM and a `win` RID) renames the apphost to `Steward.App.exe` (MSBuild target `NameWindowsExeStewardApp` in `Steward.Desktop.csproj`, after `Publish`), since installed builds start `Steward.App.exe` from the HKCU Run value, user pins, the MSI's `taskkill /im Steward.App.exe`, its Start menu shortcut and `LaunchSteward`, and the Store manifest, so an update needs no migration code. The apphost still loads `Steward.Desktop.dll`. `dotnet build` output keeps `Steward.Desktop.exe` (Debug: `src\Steward.Desktop\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Steward.Desktop.exe`), and the Linux and macOS executable is `Steward.Desktop`.

The app is packaged as an MSIX by `scripts/Build-DesktopMsix.ps1` (PowerShell 7) from `packaging/windows/Package.appxmanifest`: identity `Hoobi.Steward` with publisher `CN=D74C026B-1081-4787-BDE6-0CFA2F1EDD71` and `ProcessorArchitecture="x64"`, `Executable="Steward.App.exe"` with `EntryPoint="Windows.FullTrustApplication"`, the `StewardStartup` startup task with `--tray`, the `curseforge` and `steward` protocols, `runFullTrust`, the `10.0.17763.0`/`10.0.26226.0` device family and `Resource Language="en-US"`. The script publishes `Steward.Desktop` for `net10.0-windows10.0.26100.0` `win-x64` self-contained and not single-file (an MSIX holds loose files) into `<OutputDirectory>\layout`, copies the manifest's visual assets from `src/Steward.Desktop/Assets`, stamps the version into `AppxManifest.xml`, builds `resources.pri` with `makepri` (a config from `createconfig /dq en-US` with its `packaging` element removed, so the scale-200 logos stay in the one PRI rather than a `resources.scale-200.pri` split meant for bundles, indexing only the assets), packs `Steward-<version>-x64.msix` with `makeappx pack` and zips and renames it to `Steward-<version>-<Identity>-x64.msixupload`, as `build.yaml` does. `makeappx` and `makepri` come from `Microsoft.Windows.SDK.BuildTools` at the `Directory.Packages.props` version (10.0.26100.9169) when it is in the NuGet cache, else from the newest installed Windows SDK (the runner's 10.0.26100). `-Identity Store` (default) builds with `GitHubRelease=true` and a version of `<major>.<minor>.<GITHUB_RUN_NUMBER>.0`; `-Identity Dev` stamps `Hoobi.Steward.Dev`, `CN=Hoobi Dev` and "Steward (Development)" and builds without `GitHubRelease`, with `<version.txt>.<git rev-list --count HEAD>`; `-Version` overrides either, which is how `build.yaml` passes its release-PR-based number, `-StoreDisplayVersion` passes through, and `-PreRelease` passes `StorePreRelease=true`. Nothing is signed. The package is self-contained and needs no Windows App Runtime. Packaged, the app takes the packaged paths shared in Presentation: `AppInfo.IsPackaged` from `GetCurrentPackageFullName`, the `StewardStartup` task in place of the Run key, `WindowsShell.DisplayDataFolder` and, with the real `%LocalAppData%\Steward` absent, its first writes virtualised to `%LocalAppData%\Packages\<PFN>\LocalCache\Local\Steward`. `AppUpdateTitle` and `AppUpdateChangelogUri` follow `UpdateSource` rather than `IsPackaged` (see Self-update). `PackageManifestTests` checks the manifest's Store identity, that the application and startup task start the literal `Steward.App.exe` with `StartupRegistration.TrayArgument`, that the protocols are `CurseForgeLinks.Scheme` and `AddonSettingsPayload.Scheme` (and the Linux desktop entry and macOS plist register both) and that every `Assets\` reference has a file.

`AvaloniaPlatform` (`Services/AvaloniaPlatform.cs`) implements `IUiPlatform` over `Dispatcher.UIThread` and `DispatcherTimer`. A URI image is a `DrawingImage` returned at once, whose `Drawing` is replaced by an `ImageDrawing` of the bitmap (replacing it is what invalidates the `Image`) when the download (on the `Addon` client, `AvaloniaPlatform.Http`, set after the host is built) has decoded to the requested width times the window's render scaling, cached per URI and width. The image is a `PlatformImage` (a `DrawingImage` with `HasFailed` and a `Failed` event): a failed download or decode marks it failed and drops it from the cache, as undecodable bytes do, and `Views/IconImage` (an `Image` with a `Failed` event, raised at once for a source that has already failed) is how a view sees it, so the Addons table sets `AddonRowViewModel.ManifestIconFailed` and loads the local `FallbackIcon` as WinUI does from `Image.ImageFailed`; a missing `Http` client leaves the image empty rather than failed. Every decode goes through one helper that turns the `NullReferenceException` Avalonia.Skia 12.1.3 throws for bytes no codec recognises into an `ArgumentException`, which the shared callers already catch. An `avares:` URI or packaged asset and encoded bytes decode to a `Bitmap` at once, premultiplied BGRA goes through a `WriteableBitmap`, and `DecodeBgraAsync` decodes and scales through Skia and un-premultiplies to straight BGRA. The clipboard and folder picker go through the main window's `TopLevel.Clipboard` and `StorageProvider`, and `OwnerWindowHandle` is `TryGetPlatformHandle()`.

The shell (`Views/MainWindow.axaml`) is custom rather than `FANavigationView` (a headless probe of FA 3.1.0's `LeftCompact` measured the same item, indicator and pane metrics as WinUI, so this is a choice for direct control of the pane, not a metric gap): a 48px title bar row (app icon, title, the install picker centred on the window and clamped 8px from the title and from the 144px caption-button area, right-aligned in its column when too narrow; the title bar carries `WindowDecorationProperties.ElementRole` `TitleBar` and the picker `User`), then a 48px pane of WinUI `NavigationView` `LeftCompact` metrics taken from `generic.xaml` (items 36px high with a 4,2 margin, a 40px icon column, 16px glyphs, a 3x16 accent indicator with 2px corners, `-1,3` pane margin; the account button above Settings at the AGENTS.md Navigation metrics) and the page host. With the client area extended, Avalonia 12.1.3 on Win32 always asks for a managed title bar (`WindowImpl.RequestedDrawnDecorations` returns `TitleBar`), and FluentAvalonia's `WindowDrawnDecorations` theme draws its own 12px title and four 46px caption buttons, a full-screen one included, over the app's title bar. `MainWindow.WindowDecorationsTheme` is `StewardWindowDecorations` (`Styles/Controls.axaml`), based on FluentAvalonia's, whose template keeps the drag, border and shadow parts and draws only minimise, maximise and close, 48px wide (`CaptionButtonWidth`) as the WinUI baseline measures, in `CaptionButtonTheme` (FluentAvalonia's glyphs, the `CaptionButton*` brushes in `Resources.axaml`: hover `#191919` and close hover `#E81123`, the system caption colours the baseline's hover captures show, from a rest of `#00191919` so the fade never passes through a lighter colour, press `SubtleFillColorTertiary`, the inactive glyph `#666666` sampled from the baseline). Avalonia 12.1.3 hovers a drawn caption button from `WM_NCMOUSEMOVE`, but moving onto one from the client area also ends client tracking with a `WM_MOUSELEAVE` that clears the hover a few milliseconds later, and Windows resends the move only 0.6s (maximise) to 1.7s (minimise, close) after that (measured 16 Oct 2026), so `MainWindow`'s window procedure hook posts a `WM_NCMOUSEMOVE` for the cursor's position whenever a `WM_MOUSELEAVE` arrives over a caption button (`Native.RepostCaptionButtonMove`), and the hover shows on the first frame, as on WinUI. FluentAvalonia binds a caption button's `inactive` class to an ancestor `Window`, which the decorations layer, the window's sibling under its host, never has, so `MainWindow.UpdateCaptionButtons` sets it on activation, deactivation and open. WinUI keeps the 1px top resize border outside its client area, so `Root` sits 1px down (not under Wine) and every element lands on the WinUI baseline's screen row; the title bar icon is 14px from the left with the title 15px after it, as measured. Pages are DI singletons swapped into `PageHost` by `ShowPage`, with the 220ms fade-and-rise entrance on every page change except the first. Dialogs subclass `FAContentDialog` and are shown through `Services/AppDialogs.cs` (one at a time, the `Steward` class, the accent primary button unless the caller already themed it, as the close confirmation's critical button is, the dialog hover brushes, open popups closed first). `Styles/Dialogs.axaml` holds the dialog frame as the WinUI baseline measures it: a `#99000000` scrim (WinUI transmits 0.40 of the ground with no tint, not the WinUI build's `#B3000000` override), one 24px gap between the content and the buttons with no separator (the command row is padded `24,0,24,24`), and `StewardDialogResources`, which `AppDialogs` copies into each dialog: WinUI draws a dialog's text boxes and combo boxes with generic.xaml's fills and edges rather than the app's page overrides (text box rest `#0FFFFFFF` with a `#3A404D` top and `#9FA1A8` bottom edge, focused `#B31E1E1E` with a 2px `#73D0FF` bottom drawn inside the box so the text does not move, disabled `#0BFFFFFF`; combo box rest `#0FFFFFFF`). `AppDialogs` gives each dialog's panel (`BackgroundElement`, not the scrim, which still covers the whole window) the shell's 1px top margin plus 0.01, so the panel centres on the same client area as WinUI's, which excludes the top resize border, and a half pixel rounds up as on WinUI rather than to even; without it every panel sat 1px higher, and with it every dialog panel starts on WinUI's row at 100% and 150% except Get addons at 150% (1px low). After a dialog opens, `AppDialogs` focuses the first focusable control in its content, else keeps the dialog's own focus, else the first command button, so the first input is focused as on WinUI, Tab stays inside the dialog and Escape cancels it. A dialog hidden while it still waits in that queue (the RestedXP sign-in dialog hides itself on sign-in) has its `Closing` cancelled and is never shown, returning `None`, since FluentAvalonia 3.1.0's close path throws `ArgumentNullException` on a dialog that was never shown. FluentAvalonia 3.1.0's close path also turns the dialog's `IsHitTestVisible` off and its show path never turns it back on, so `AppDialogs` sets it before every show: without that, a dialog instance shown a second time (the addon folders dialog after the changelog it handed over to) let every click through to the window behind and could not be closed from its buttons. The close path's 167ms fade also leaves the template's `LayoutRoot` with `IsVisible` false as a local value; the next show's open animation hides it until the animation ends 83ms later, when `LayoutRoot` reads false for one frame, and Avalonia clears keyboard focus from inside an element that turns invisible, so focus fell to the window: Escape no longer closed the dialog and Tab moved to the install picker behind it. `AppDialogs` clears that value before every show, so a dialog shown again behaves as a fresh one (`DialogReshowTests`). A dialog's Primary or Secondary result is accepted only from a deliberate press on that button (`Services/DialogIntent.cs`, attached for each show and removed after it): a left pointer press and release on the button while the dialog is open, or an Enter or Space key-down while the dialog is open and visible and its window is active, followed for Space by its key-up, or a UI Automation Invoke of the button while the dialog is open (Narrator and other assistive technology, and `tools\UiDriver.psm1`, press buttons through the Invoke pattern), whatever window is active. The Invoke is recognised by the button type: `Styles/Dialogs.axaml` gives `FAContentDialog.Steward` FluentAvalonia 3.1.0's template with Primary and Secondary as `DialogCommandButton` (`Services/DialogCommandButton.cs`, styled as `Button`), whose automation peer re-implements `IInvokeProvider.Invoke` to mark the button for the length of the click, since Avalonia 12.1.3's `ButtonAutomationPeer.Invoke` calls the internal `Button.PerformClick` and leaves no other trace. A key-up whose key-down the dialog did not accept, a repeated key-down, a key that was already held when the dialog opened or its window was activated again (`AppDialogs.IsKeyHeld`, `GetAsyncKeyState` on Windows and never held elsewhere), and a press before the dialog opened are swallowed when they would reach the Primary or Secondary button or, for Enter, FluentAvalonia's default-button path. Any other click on those buttons (an access key, a click raised from code) is cancelled and the dialog stays open, and `ShowAsync` returns `None` for any Primary or Secondary result that no accepted press chose, which covers `Hide(Primary)` and the stale result FluentAvalonia 3.1.0 keeps on a dialog shown again and then closed with Escape. This was needed because Avalonia 12.1.3's `Button.OnKeyUp` clicks a focused button on a Space key-up with no matching key-down, and FluentAvalonia's `SetupDialog` focuses the first button, Primary, when `DefaultButton` is `None`: on 16 Oct 2026 a `curseforge://` link installed DBM with no Install press, and the close confirmation went to the tray on its own twice, while other keyboard input was reaching the desktop (the exact keystroke is unproven; `DialogIntentTests` reproduces the mechanism). `AppDialogs.FocusFirstInput` therefore never leaves focus on a Primary button that is not the default: it moves to the Close button, else the first other focusable element, while a caller's own choice of the Secondary button (the close confirmation) is kept. WinUI's `ContentDialog` also focuses the first command button when there is no default and no focusable content (`SetInitialFocusElement` in microsoft-ui-xaml's `ContentDialog_Partial.cpp`). The addon folders dialog (`Views/AddonFoldersDialog.axaml.cs`) differs from WinUI's on purpose: a sub-addon row shows its version over that sub-addon's own "Released n days ago" line (`FolderEntry.Released` and `ReleasedTip`, from its row's `ReleasedText` and `ReleasedTip`, left out while the release date is unknown, the table's rule), right-aligned in one column beside the channel (24px between that column's right edge and the channel), stacked with the table's 4px gap and centred vertically on the row rather than pinned to the name and folder lines; WinUI's dialog has no release line. FluentAvalonia completes `ShowAsync` 200ms after `Hide()`, and never if the window closes within those 200ms, which in this app happens only at quit. The tray icon is an Avalonia `TrayIcon` with Open Steward, Check for updates and Quit; close and minimise to tray, `--tray`, `--no-activate`, every preview switch and the session-end hook (`Win32Properties.AddWndProcHookCallback`) behave as on WinUI. A start never shows the window before its first frame is composed: `InitializeCommand` runs first (its synchronous session restore decides gate or shell), then the window is shown DWM-cloaked and uncloaked two animation frames later (`MainWindow.ShowRendered`); a `--tray` start constructs the window, so every view model delegate is wired, and shows it the same way on its first restore. `--tray` and `--no-activate` show with `ShowActivated` off and no `Activate`; only a normal start and a tray restore take the foreground (`Native.ForceForeground`). Such a start also holds `MainWindow.ForegroundGate` (`Services/ForegroundGate.cs`), set in `App.OnFrameworkInitializationCompleted` before `InitializeCommand` runs and released only by `ShowFromTray` (a tray click, the tray's Open Steward, a same-train relaunch's show signal) or the window's first `Activated`, which is logged; while it is held, `AppDialogs.ShowAsync` waits before showing any dialog (the guild prompt, a CurseForge link confirmation, and every other dialog), since a dialog on a window the user did not activate is a prompt they never asked for. A second launch of the same train carrying `--tray` or `--no-activate` sends its CurseForge link but no show signal (`InstanceCoordination.TryAcquire`'s `showRunning`, false only from `Steward.Desktop`'s `Program`), so it never brings the running window forward. In Avalonia 12.1.3 on Win32, `Window.Activate`, `Show` with `ShowActivated` on, a `WindowState` change to Normal or Maximized while visible (`WindowImpl.ShowWindow(state, activate: true)`, `SW_RESTORE`) and the close of a `ShowDialog` child (`owner.Activate()`) all call `SetForegroundWindow`; `Control.Focus()` and `FAContentDialog`'s default-button focus do not touch Win32 focus, and Win32 popups show with `SW_SHOWNOACTIVATE`.

A GPU driver reset (TDR) on Windows left the window fully transparent and the tray menu unable to open, so the process had to be killed (21 Oct 2026, an RTX 4090 that resets every few days). Avalonia 12.1.3 recreates its ANGLE context and the WinUI composition device after a loss (`PlatformRenderInterfaceContextManager`, `WinUiCompositedWindowSurface`), but its render thread can stop ticking: `WinUiCompositorConnection` schedules the next tick only from a commit that completes, and its 1-second watchdog acts only while a commit is in flight. The UI thread then blocks in `SyncCommit` on the next paint, and the tray menu is a `TrayPopupRoot` window on the same thread and compositor. This path is read from the source and not proven. `Services/UiWatchdog` runs on Windows outside Wine from the end of `App.OnFrameworkInitializationCompleted`: a background thread posts a beat to the UI thread every 5 seconds, and the beat awaits `Compositor.TryGetCompositionGpuInterop()`, a render-thread job that runs only once the graphics context is valid, so one beat proves both threads alive. After 6 missed checks in a row (30 seconds of the watchdog's own running time, so sleep and resume do not count), with no debugger attached, it logs which thread stalled, starts `Environment.ProcessPath` with `--no-activate` (window visible) or `--tray` (hidden) and `--restart-after=<pid>`, and kills its own process. `Program.Main` waits up to 15 seconds for that pid to exit before `InstanceCoordination.TryAcquire`, since a launch while the old process runs hands over to it and exits. A process started with `--restart-after` that stalls again within 5 minutes logs it and does not restart, so a GPU that stays broken does not cause a loop. A killed process leaves its tray icon until the pointer passes over it. `Services/AvaloniaLogSink` (`Logger.Sink`) writes Avalonia's Warning and higher lines for the `Visual`, `Win32Platform`, `OpenGL` and `WinUIComposition` areas to the app log, so the next reset shows what Avalonia saw.

`Styles/Resources.axaml` holds every key of the WinUI build's app resource dictionary with the same value, plus each system key a view or view model uses, resolved through that dictionary's overrides and otherwise taken from WinUI's dark theme (`microsoft.windowsappsdk.winui` 2.3.9, the dependency of Microsoft.WindowsAppSDK 2.5.1, `lib\net6.0-windows10.0.17763.0\Microsoft.WinUI\Themes\generic.xaml`, `Default` dictionary): `SubtleFillColorTransparent/Secondary/Tertiary/Disabled` (`#00FFFFFF`, `#0FFFFFFF`, `#0AFFFFFF`, `#00FFFFFF`), `MenuFlyoutItemBackground*` and `NavigationViewItemBackground*` (those subtle fills), `DividerStrokeColorDefault` and `MenuFlyoutSeparatorBackground` (`#15FFFFFF`), `CardBackgroundFillColorTertiary` (`#12FFFFFF`), `ControlAltFillColorQuarternary` (`#12FFFFFF`, the avatar fill), `TextOnAccentFillColorPrimary` (`#000000`), `TextFillColorInverse` (`#E4000000`), `AccentTextFillColorPrimaryBrush` and `SystemFillColorAttentionBrush` (`SystemAccentColorLight3`/`Light2`, both `#73D0FF` under the app's override), the InfoBar severity backgrounds (`SystemFillColor*Background`: success `#393D1B`, caution `#433519`, critical `#442726`, attention `#08FFFFFF`) and icon fills (generic's own `SystemFillColor*`, since its InfoBar aliases them through `StaticResource` as it does the text brushes: warning `#FCE100`, measured on the Guides page's session-expired bar, critical `#FF99A4`, success `#6CCB5F`; the banners and the error bar are the app's own controls and keep `#FFD580` and `#F28779`), and the text sizes (caption 12, body 14). WinUI's `generic.xaml` aliases its control brushes to its own `TextFillColorPrimaryBrush` (`#FFFFFF`) through `StaticResource`, which resolves inside `generic.xaml`, so the app's `#FFCBCCC6` override reaches only the keys the app dictionary overrides by name (`ButtonForeground*`, `TextControlForeground*`) and explicit `ThemeResource TextFillColorPrimaryBrush` uses (the views and the CommunityToolkit `SettingsCard` and `Segmented`); everything else measures `#FFFFFF` in the baseline: page, window, section and dialog titles, dialog text, plain `TextBlock`s, ComboBox text and items, radio, check box and On/Off labels, menu items, tooltips, InfoBar text and the nav glyphs. A plain `TextBlock` is also 14px, where controls use the app's 13px `ControlContentThemeFontSize`. The global `:is(TopLevel)` style therefore sets `DefaultTextForegroundThemeBrush` (`#FFFFFF`) and 14px, `views|SettingsCard` keeps `TextFillColorPrimaryBrush` and draws its title and the On/Off labels beside its toggles at 13px (`ControlContentThemeFontSize`, the CommunityToolkit card's size: the WinUI tree's title boxes are 18px high at 100% and 26 device pixels at 150%), `RadioButton`, `CheckBox`, `ToggleSwitch`, `ToggleButton`, `ComboBox` and `MenuItem` take `ControlContentThemeFontSize`, a `ComboBoxItem` takes 14px, and the nav items take `NavigationViewItemForeground` (`#FFFFFF`) with the `NavigationViewSelectionIndicatorForeground` (`#73D0FF`, generic's Light2 accent) indicator. Inside a `ContentDialog` WinUI resolves the visual-state brushes (pointer over, pressed, checked, disabled) from `generic.xaml` too, so the accent button hovers `#E673D0FF`, presses `#CC73D0FF` and disables to `#28FFFFFF` with `#87FFFFFF` text, and check boxes use the `#73D0FF` fill, black tick and `#8BFFFFFF` ring (the Forever sync wizard, whose options centre the glyph's 32px template row on their two-line label in `TemplateApplied`, as the WinUI wizard does in `Loaded`, which moves each glyph 2px down onto the row WinUI's baseline capture shows at 100%), while on a page they keep the app's `#409FFF`; `Styles/DialogResources.axaml` holds those keys and `Styles/DialogResourceScope` copies them into every `FAContentDialog`'s own `Resources` when it loads. Radio buttons appear only in dialogs, so their keys in `Resources.axaml` are generic's (unchecked `#19000000` fill and `#8BFFFFFF` ring, checked `#73D0FF` with a black dot). `Styles/Controls.axaml` also removes the HyperlinkButton underline (WinUI's template has none; FluentAvalonia's template underlines the TextBlock it makes for string content through a style inside its `ContentPresenter`, which outranks an app style without an activator, so the app's selector ends in `TextBlock:not(.Underlined)` to take StyleTrigger priority), shrinks a pressed RadioButton's dot to WinUI's 10px (FluentAvalonia scales it to 8.5), draws a checked CheckBox's tick as a stroked `Path` (1.3px, flat caps, mitred) fitted pixel for pixel to WinUI's `AnimatedAcceptVisualSource` tick in the baseline at 100% and 150%, in place of FluentAvalonia's thinner font glyph, which is hidden while checked, draws the banner and error-bar close buttons' X as `Path.CloseGlyph` (11px, 1.4px stroke, WinUI's 11px ChromeClose ink; Fluent's `dismiss` glyph inks only 0.6 em and measured 7px) and the Settings "Close to the tray" card's icon as a 20px `Path.CloseGlyph` with a 2px stroke (WinUI's 20px ChromeClose inks 20x20, where `dismiss` measured 14x14), spaces dialog buttons 12px apart (the app's `ContentDialogButtonSpacing`; FluentAvalonia uses 8; the WinUI baseline measures the two buttons 193px wide and 4px apart with a square-cornered close button, which neither the app dictionary's 12 nor generic.xaml's 8 explains, so the spacing stays 12), and holds `SegmentedStyle` and `FieldHeader` (see Design system). The accent button's `#FF1F2430` SemiBold text on `#FF409FFF` and the dialog's 438px inner width (a 1px transparent border inside 440, so 390px of content) are WinUI's own values. Flyout and menu presenters (`MenuFlyoutPresenter` and `FlyoutPresenter.Tinted`) take hoobi-design's Mirage flyout through `Styles/Acrylic` (below), and so does every ComboBox list (the template's `Border#PopupBorder`, at 8px corners with `ComboBoxDropdownBorderThickness` 0), on pages and in dialogs alike. A menu sits 4px lower than Avalonia places it (`MenuFlyoutPresenter` is drawn 4px down inside a 4px bottom margin, since Avalonia positions a popup by its content and ignores a top margin), as does the install picker's flyout (its presenter's `Below` class; a `VerticalOffset` of 4 on that flyout left the first click after a start opening nothing); a menu's empty input gesture column is hidden, so menus are as wide as WinUI's, and the first item is not highlighted on open unless keyboard focus is visible. A tooltip opens centred on the pointer with its bottom edge 20px above it (`Styles/PopupPlacement`, a custom placement set on every control that gets a `ToolTip.Tip`), and a ComboBox list opens over the box with the selected item centred on it. The tooltip anchor is a 40px-tall rect around the pointer with the offset cleared (Avalonia's `ToolTip.VerticalOffset` defaults to 20 and a flip keeps it), so a tooltip with no room above opens 20px below the pointer instead of under it, where it took the next click (the install picker then needed two clicks). A tooltip also takes no pointer input, as on WinUI: `PopupPlacement` sets `IsHitTestVisible` false on every `Popup` whose child is a `ToolTip`, which Avalonia 12.1.3 passes to the overlay popup host and to a native popup window (`IPopupImpl.SetHitTestVisible`: `HTTRANSPARENT` from `WM_NCHITTEST` on Win32, an empty XFixes input shape on X11, the native call on macOS), so a click on a control under an open tooltip reaches that control at once and the press closes the tooltip (Avalonia's `ToolTipService` clears it on any button down); before this the first click on the addon folders dialog's changelog icon under a "Released" tooltip only closed the tooltip. A ScrollViewer's scroll bars fade out after 2s with no scroll or pointer movement over it and back in on either (`Styles/ScrollIndicator`, the `ScrollActive` class), as WinUI's indicator does, and the collapsed vertical thumb sits 1.75px further right, on WinUI's column. Avalonia rounds a half device pixel to even (`Math.Round`) where WinUI rounds it up, so at 150% the Settings card's 15px padding (22.5px) lost 1px a side per card; the card theme uses 15.01. `Styles/Acrylic` is switched on by the presenter styles and draws the same tinted blur on every OS, asking the OS for no blur: when a presenter attaches, and again whenever its screen rectangle or the main window's activation changes, it renders what is behind it (each `TopLevel` from the main window down to the popup's parent: that window's `Background`, then its `Content` through `RenderTargetBitmap.Render`, then each child of its `OverlayLayer` below the one that holds the popup, so an open parent flyout shows under its submenu and a ComboBox list in a dialog blurs the dialog rather than the page, and never the popup's own layer, so an overlay popup takes the same path), and applies hoobi-design's Mirage flyout blur (`.mirage-flyout` in `D:\hoobi-design\styles.css`: `blur(24px) saturate(1.4)`; its tint, `--color-bg` `#1F2430` at 72%, is this window's own ground, so a flyout over plain page could not be told from it, and the tint here is darker): Avalonia's `BlurEffect` at `Acrylic.BlurRadius`, which is a sigma of 24 since Avalonia.Skia 12.1.3 maps a radius to a sigma as `0.288675 * radius + 0.5`, pushed over a rect inflated by three sigma so the popup's edges sample the page beyond them, with the main window's `Background` filling that whole rect, as CSS repeats the backdrop's edge; then, since Avalonia has no saturate effect, the CSS `saturate()` matrix on the sRGB pixels (`Acrylic.Saturate`) and `FlyoutAcrylicTintColor` (`#13161D`) at `TintOpacity` 0.575 (`#9313161D`, `Acrylic.Composite`), and sets the result as the presenter's `Background` through an `ImageBrush`, so the presenter's own rounded corners clip it and the menus' 4px offset shows the page itself; a page that animates under an open popup is shown still, and a popup that overhangs the window shows `FlyoutAcrylicFallbackColor` there. Avalonia's `AcrylicBlur` is not asked for: on Windows it is WinUI's own Gaussian blur of the host backdrop at a standard deviation of 30 device pixels (`WinUIGaussianBlurEffect` in Avalonia.Win32, 12.1.3), which averages a dark page of 13px text and 36px rows to one flat tone, so the WinUI baseline's flyouts measured a flat `#232834` (sd under 0.5 per channel) and the first Avalonia build under that blur read as a flat fill at every tint opacity tried (0.96, 0.80, 0.50; 21 Oct 2026); it also filled the whole popup window, which needed a `SetWindowRgn` clip to the presenter. The popup window keeps `PopupRoot`'s default `Transparent` level on every OS, and no Win32 call is made for it. While the main window is not active, the presenter is the solid `FlyoutAcrylicFallbackColor` (`#181B23`), as `DesktopAcrylicController` shows on WinUI; Avalonia closes a light-dismiss flyout when its window deactivates and its popups never take activation, so this is seen only for an overlay presenter, and WinUI's case of keyboard focus inside the popup does not arise. The popup windows have no drop shadow of their own, where WinUI's carry one; whether DWM now draws one for the unclipped window was not checked on screen. Dialogs keep FluentAvalonia's own shadow, which fades out about 29px from the panel's side where WinUI's reaches about 40px.

The window on Linux and macOS is set in `Views/MainWindow.Unix.cs` (`ConfigurePlatformWindow`, a partial method that the Windows target does not implement), so the Windows title bar, tray and session-end code are unchanged. `Root` has no 1px offset on either OS. On Linux, Avalonia 12.1.3's X11 backend ignores `ExtendClientAreaToDecorationsHint` unless `X11PlatformOptions.EnableDrawnDecorations` is set (`X11Window.SetExtendClientAreaToDecorationsHint`), and without it the window manager draws its own frame above the app's title row. `Program.BuildAvaloniaApp` sets it (the option is marked experimental, `AVALONIA_X11_CSD`, suppressed at that one call). With it, Avalonia sets `_MOTIF_WM_HINTS` decorations to 0, so a window manager that honours Motif hints (openbox, xfwm4 and WSLg's Weston were tested) draws no frame, and the app draws the same `StewardWindowDecorations` minimise, maximise and close buttons as on Windows. X11 asks for every drawn part (title bar, border, shadow, resize grips); the drawn shadow band is opaque without a compositor, so Linux uses a theme based on `StewardWindowDecorations` with no shadow and a 4px frame, which is the resize grip around the edge (the frame's border is under `Root` and does not show). X11 starts a window-manager move on every press over a `TitleBar` role before the app receives it, and that move takes the second click of a double-click, so on Linux the title row has the `User` role and moves the window itself: a press records the point, a move of 4px or more first moves the window by the pointer's travel since the press and then calls `BeginMoveDrag`, and a double-click toggles maximise (`TitleBarTests`, skipped off Linux). Avalonia 12.1.3's X11 `BeginMoveDrag` sends `_NET_WM_MOVERESIZE` with the pointer's current position, so without that first move the window trailed the pointer by the 4px threshold; verified 16 Oct 2026 under Xvfb with openbox, a press then a 50,30 pointer move moved the window from 310,153 to 360,183. `X11PlatformOptions.WmClass` is `Steward`, so the main window's `WM_CLASS` is the process name and `Steward` (`steward`, `Steward` when started as `/usr/bin/steward`), which the packaged desktop entry's `StartupWMClass=Steward` matches. The folder picker is titled "Choose the World of Warcraft folder" off Windows (Windows keeps the system title); the GTK chooser takes its own `WM_CLASS` from the GTK program name, which Avalonia does not expose (`Steward.Desktop`, `Steward.Desktop` when started as `Steward.Desktop`). X11 raises `Activated` before `IsActive` changes, so on Linux `UpdateCaptionButtons` also runs once each `Opened`, `Activated` and `Deactivated` handler has completed. Avalonia 12.1.3's X11 activation tracker (in `_NET_ACTIVE_WINDOW` mode, openbox's) only reacts to a change of the root `_NET_ACTIVE_WINDOW` and never reads it for a newly shown window, and a restarted Steward's window reuses the XID the window manager left in that property, so after a normal start the window stayed inactive (grey caption glyphs, solid `#2B3140` menus, `ForegroundGate` held) until focus left and came back (16 Oct 2026); each time the window is shown on Linux `X11ActiveWindow.ActivateIfActive` reads `_NET_ACTIVE_WINDOW` through libX11 and, when it names this window and `IsActive` is false, calls Avalonia's own `X11Window.SetActiveSpeculatively` (by reflection; `ShellTests` fails if Avalonia drops it), which raises `Activated` and sets `IsActive`, so every reader of window activity follows and the next active-window change re-verifies it. The maximise and minimise buttons show only when the window manager lists `_NET_WM_ACTION_MAXIMIZE_*` and `_NET_WM_ACTION_MINIMIZE` in `_NET_SUPPORTED`; WSLg lists neither, so there only close shows. With no window manager the buttons are drawn but move, maximise and minimise do nothing. Without a compositor a native popup window's transparent rounded corners show white, so `Program.BuildAvaloniaApp` sets `X11PlatformOptions.OverlayPopups` when no client owns the `_NET_WM_CM_S<screen>` selection (`Services/X11Compositor.cs`, a one-shot `libX11.so.6` check before Avalonia starts; no display or no libX11 keeps native popups), and popups are then layers inside the window, as under Wine; with a compositor they stay native windows. Verified 16 Oct 2026 under Xvfb with openbox: the install picker opened inside the one 980x720 window with no compositor, and as its own 268x196 window with `xcompmgr` running. A screenshot under a compositor is taken with `import -window root`, never `xwd -root`: `xwd` reads each 32-bit window's own premultiplied pixels without compositing them, so the transparent corners of every native popup (install picker, account flyout, row menu, ComboBox) read black there, while `import`, `xcompmgr` and `picom` all show the window behind (16 Oct 2026; a 50% `_NET_WM_WINDOW_OPACITY` showed in `import` and not in `xwd`). The window icon is the bundled `Steward.ico` set as `_NET_WM_ICON`, which xfce4-panel's task list shows. On macOS the native traffic-light buttons stay (Avalonia.Native requests no drawn decorations), the content extends under the title bar, the title row starts 78px from the left to clear them and the 144px caption column is 0. Avalonia.Native 12.1.3 keeps the traffic lights in AppKit's standard 28px title bar whatever `ExtendClientAreaTitleBarHeightHint` says (`SetExtendClientArea` sets no toolbar and the hint only sizes the title bar material), so they centre 14px below the window's top edge, 10px above the 48px row's centre; the app icon and title are top-aligned in a 28px box on macOS to sit on the lights' row, and the install picker stays centred in the 48px row. The desktop-preview tour on `macos-26` and `macos-26-intel` (16 Oct 2026) measured the red light 13.5px below the top edge with the icon 10px lower before this; centring the lights on the 48px row needs an `NSToolbar` or moved standard buttons, which AppKit lays out again on resize and full screen, and is not done. Avalonia.Native moves the window, and zooms it on a double-click, when a press lands on a visual whose own role is `TitleBar` (`WindowImpl.ChromeHitTest`), which the transparent `AppTitleBar` is, so macOS needs no handler of its own. This is read from the Avalonia.Native source and not tested on a Mac. The macOS app menu takes its title from `Application.Name` (Avalonia's default is "Avalonia Application"), set to `Steward` in `App.axaml`; with no application `NativeMenu` Avalonia.Native adds "About Avalonia", so on macOS `App.Initialize` sets one holding "About Steward" (shows the window on Settings, where the About card is; its `Click` is wired in `OnFrameworkInitializationCompleted`). It is set there because Avalonia.Native exports the app menu once in its `AfterSetup` callback, after `Initialize` and before `OnFrameworkInitializationCompleted`, and adds the standard items only to that first export; after it Avalonia.Native appends Services, Hide Steward, Hide Others, Show All and Quit (`AvaloniaNativeMenuExporter.PopulateStandardOSXMenuItems`).

Avalonia's Linux `TrayIcon` is a StatusNotifierItem on the session bus and has no XEmbed fallback, so it shows only when a `org.kde.StatusNotifierWatcher` exists (KDE, Xfce 4.18's panel, Cinnamon; GNOME only with the AppIndicator extension). `Services/TrayHost.Unix.cs` lists the session bus names at every check, through `Tmds.DBus.Protocol` (in the package closure through `Avalonia.FreeDesktop`), with a 2-second limit; no bus, no watcher or a timeout is "no tray host". It is checked at each hide to the tray, each close-to-tray decision and each Settings page load, so a panel started after Steward is used from then on; Avalonia's `DBusTrayIconImpl` watches the watcher's bus name and registers the visible icon with a watcher that appears later (16 Oct 2026, Xvfb with openbox: Steward started with no panel, xfce4-panel started after it listed `org.kde.StatusNotifierItem-<pid>-0`, and a click on that icon showed the window again). `TrayHost.Windows.cs` is always true, and macOS is always true (the menu bar). With no tray host, `MainWindow.HideToTray` minimises the window instead of hiding it, so a `--tray` start begins minimised, Close to the tray behaves as off (the close confirmation offers "Minimize" in place of "Minimize to tray"), and the two Settings cards are disabled with "Not available: no system tray is running on this desktop" (enabled again on the next page load that finds a tray), while the stored settings are kept. On macOS, closing the window hides it with no confirmation, so the Close to the tray card is hidden there, and a Dock icon click (`IActivatableLifetime` `ActivationKind.Reopen`) shows it through `ShowFromTray`. On both OSes `ForceForeground`, cloaking and the efficiency-mode calls are no-ops, so a restore is `Activate()` behind the same `ForegroundGate`, and the session-end hook is the lifetime's `ShutdownRequested` (an X11 session-manager save-yourself, or macOS Quit), which lets the windows close without the close-to-tray or confirmation path.

Every button-anchored flyout and menu is the button's own `Button.Flyout`, never `FlyoutBase.AttachedFlyout` opened from a `Click` handler, so a second click on the button closes it. Avalonia 12.1.3's `Button` closes its open flyout on the press itself (`OnPointerPressed` with the flyout open calls `OnClick`, which hides it). A press anywhere else hits the `LightDismissOverlayLayer` and closes the flyout without reaching what is under it. An `OverlayInputPassThroughElement` is left out of that overlay's hit test, so its press never closes the flyout, and a hand-written `Click` that only shows it finds it still open, where `ShowAt` with the same target does nothing; the install picker's hand-written `Click` that showed its flyout, with a 300ms reopen guard, could not close it, and it is the button's own `Button.Flyout` now. The account button sets the flyout's `VerticalOffset` in `Opening`, which `ShowAtCore` raises before it positions the popup. A style in an element's own `Styles` also applies to that element's flyout content, which is its logical child, so such a selector names the element (`Button#InstallPicker:pointerover`). Avalonia's `BrushTransition` lerps straight, not premultiplied, alpha, so a fade between a clear brush and an opaque one of a different RGB passes through a lighter colour; the install picker's unscoped `Button:pointerover` override (`LayerFillColorAltBrush`, `#FF2B3140`) reached every row of its flyout and faded each from `#00FFFFFF`, the white flash on hover. `FlyoutTests` walks the shell, every page, the install and account flyouts and a gallery of every control type and button theme the app uses, applies `:pointerover` and `:pressed` to each templated control, and fails when any `BrushTransition` pair composited over `#1F2430` reaches a frame lighter than both ends. Motion follows WinUI's `generic.xaml` storyboards, measured with real pointer input: nav items change at once (FluentAvalonia's button fade is removed on `Button.Nav`), a toggle switch's off-state track fades over `ControlFasterAnimationDuration` (83ms) into pointer-over and pressed and snaps back (its on-state colours snap both ways), set by selectors with a pseudo-class because FluentAvalonia's template sets its own 167ms transitions, which outrank a plain style, a `HyperlinkButton` fades its background over 83ms both ways (WinUI's `BackgroundTransition`), and a dialog fades in over 83ms while it scales from 1.05 over 250ms: `AppDialogs` shortens FluentAvalonia's 250ms opacity animation in its `ContentDialog` theme once, since a second app animation on the same `Opacity` fights the theme's (two fades ran one after the other).

An indeterminate ring is `Views/ProgressRing` (`IsActive`, `Foreground`, accent by default, 32px default and 16px minimum as WinUI's style), not `FAProgressRing`: FluentAvalonia 3.1.0 draws a 4-unit stroke on a 30-unit radius in an 80-unit box, 0.7px at 14px, where WinUI's `ProgressRingIndeterminate` Lottie draws 7.5 on 35, and its arc starts at zero sweep, so a headless frame shows a dot. `ProgressRing.Frame` follows that Lottie: over 2 seconds the head runs 0 to 180 degrees while the tail holds, then the tail catches up, turning 900 degrees, on its 0.167/0.833 bezier, redrawn each animation frame while active and visible. With WinUI's 16px minimum, a ring the views size at 14px renders at 16, as on WinUI.

The window ground is `WindowGroundBrush` under the two corner glows, `GroundGlowTopLeft` and `GroundGlowTopRight` from `Resources.axaml` with WinUI's colours, stops and radii, each drawn by `Views/DitheredRadialGradient` rather than a `Rectangle`. Skia draws an Avalonia gradient brush in 8 bits without dithering, and these glows change by about 20 levels across 900px, so a plain brush showed flat bands 45 to 100px wide (headless, 1280x820 and 1920x1230). The control draws the brush through an `ICustomDrawOperation` on the leased `SKCanvas` (`ISkiaSharpApiLeaseFeature`) as an `SKShader` radial gradient with `SKPaint.IsDither`, which is Skia's ordered dither on both the GPU and the software raster path, so the same draw covers Wine. The shader is built once per size and brush, and the draw is one rectangle. Along a line through either glow the longest flat run fell to 4 to 18px with 10 to 40 times as many colour changes, and region means sit within 0.2 of a level of the WinUI baseline, where the plain brushes sat about 0.5 above it (`BackgroundBandingTests`). The headless renderer is the software raster path; the AngleEgl GPU path was not measured.
