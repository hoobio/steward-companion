# Addon sources and channels

The manifest for an addon+channel is `{ManifestBaseUrl}latest-{channel}.json`; the release zip resolves relative to that manifest URI, so an absolute `zip` URL is used as-is. A CurseForge manifest may carry a structured `changelog` (`ChangelogBlock` headings, paragraphs and depth-indented items whose `ChangelogRun`s may hold an http(s) `href`), which `ChangelogDialog` renders; a manifest without one shows its plain `notes` lines as depth-0 items (`Changelogs.For`). A manifest fetch sends `Cache-Control: no-cache` only from a manual Refresh (`RefreshAsync` passing `noCache` through `CheckAsync` to `AddonUpdater.ProbeChannelsAsync`), never from startup, the background pass or a retry; steward-server serves a CurseForge manifest from its 15-minute cache otherwise, and on `no-cache` refetches one 60 seconds old or more. Manifest fetches are conditional: `AddonUpdater.FetchManifestAsync` keeps the `ETag` and the parsed manifest per manifest URL in a `ManifestCache` (in memory; one per `AddonUpdater`, `AddonUpdater.ManifestCache`, and one inside `AppUpdater` for the MSI manifest), sends `If-None-Match` on the next fetch and reuses the stored manifest on a `304`, the literal `null` of an empty channel included. A response without an `ETag` drops the entry, so a server that sends none is fetched in full every time, and a `304` with nothing stored is refetched without the header. The 404 refetch in `InstallRefetchingOn404Async` never revalidates (`revalidate: false`), since a stored protected manifest names a signed zip URL that may have gone, and the cache is cleared on sign-out and when the signed-in user changes. SHA-256 verification and the zip-slip guard are unchanged from the single-addon version, except that a TukUI release is installed without a hash (see TukUI below). A row installs through `AddonUpdater.InstallRefetchingOn404Async`: a 404 on the zip refetches the manifest once and retries with the build it names, since a publish after the manifest fetch can delete the zip (steward-server keeps a replaced protected zip for an hour). An existing addon folder is deleted and replaced whatever it holds, per Hoobi on 12 Nov 2026, since requiring its own TOC refused QuestieTrace, which ships only `QuestieTrace-Camelot.toc` and `-Classic.toc`; `AddonUpdater.RemovalRefusal` refuses only a name that is not a single folder (empty, `.`, `..`, or holding `/`, `\` or `:`), which would delete outside it. `LocalAddons.FlavourTocs` lists both flavour separators, `<Folder>_<flavour>.toc` and `<Folder>-<flavour>.toc`, for every TOC lookup. After every install or update, and on startup and Refresh for every installed, unhidden managed row (configured, GitHub-mirrored and CurseForge alike), `InGameIcon.EnsureAsync` gives the primary folder an in-game icon when none of its top-level TOCs carries a `## IconTexture:` line: the row's own icon URL is fetched with the `Addon` client (a row with no `icon_url` behind a session manifest, `ManagedAddon.IconNeedsSession`, such as BugGrabber, is skipped, since its `icon.png` answers only with the session cookie and logged a 401 on every start), scaled to 64x64 and written as `StewardIcon.tga` through `AvatarTga.Encode` (the bottom-left-origin layout `Avatar.tga` and StewardGuides' `Icon.tga` already load with in the Forever client), and `GeneratedAddonIcon` (Core) adds `## IconTexture: Interface\AddOns\<Folder>\StewardIcon` after the last `##` line of every top-level TOC byte for byte, so encoding and line endings are kept; Local and unadopted folders are never touched, since CurseForge fingerprint matching hashes the TOC, and a failed fetch or decode is logged and skipped.

CurseForge is a second addon source, built to `docs/design/curseforge.md` (the source of truth for it) and gated on the user-level `addons` feature and the "Enable CurseForge addon management" setting (`AppState.CurseForgeEnabled`, `curseforge_enabled` in `state.json`, on by default, shown on the Settings page only while `addons` is held), together `MainViewModel.IsCurseForgeEnabled`; the app reads no `curseforge` feature from steward-server. With the setting off there are no CurseForge rows, no Get addons button, no match route call and no Adopt button, recorded folders show as plain Local rows, every Local row is hidden whenever `IsCurseForgeEnabled` is false, the `addons` feature missing included (shown only under the Hidden segment, `WowInstallViewModel.IsHiddenRow`), and `provider_addons.json` is left untouched (`ReconcileProviderAddons` returns without dropping records), so turning it back on restores the rows; toggling it takes effect at once through `ReconcileFeatureGating`, a rescan of every install and a manifest probe of every visible CurseForge addon, the catalogue's BugSack and BugGrabber as well as the recorded ones (turning it on once probed only the recorded ones, so the catalogue rows had no channel, release line or changelog until a Refresh). Every CurseForge call goes through steward-server's `/api/addons/curseforge/*` routes (`src/Steward.Integrations/CurseForgeRoutes.cs`) (`StewardClient.GetCurseForgeDiscoverAsync`, `SearchCurseForgeAsync`, `MatchCurseForgeAsync`, `GetCurseForgeIconUrlAsync`); the API key never reaches the app. A CurseForge addon is persisted per install in `%LocalAppData%\Steward\provider_addons.json`, loaded and saved through `AppStateStore` the same way `CharacterSyncState`/`character_sync.json` is: kept out of `state.json` on save and merged in on load, so an older build sharing `state.json` (which lacks the key) cannot drop them; a `provider_addons` key still in `state.json` from before this split is migrated in on first load and no longer written there. It maps flavour path to a list of `ProviderAddonRecord` (id `curseforge-{modId}-{versionType}`, primary folder, name, `Source: "CurseForge"`, mod id, version type, the mod's folders, its icon URL and, once matched, its CurseForge project URL) and becomes a `ManagedAddon` through `CurseForgeAddons.ToManagedAddon`, with `Features: ["addons"]` and `ManifestBaseUrl` steward-server's `/api/addons/curseforge/{modId}/{versionType}/`, so its rows go through the same `SyncAddons`, channels, Ignore, Hide, sort, filter, Update all and auto-apply as a configured addon. `MainViewModel.AddonsFor(flavourPath)` is `VisibleAddons()` plus that install's CurseForge addons (none while `IsCurseForgeEnabled` is false), and `AllVisibleAddons()` adds every install's for the manifest check, feature reconciliation and `AddonChannels`. `AddonUpdater` fetches a CurseForge manifest with the `Steward` `HttpClient` (the `gg_session` cookie), everything else with the unauthenticated one; a 401 on any manifest throws `SessionExpiredException` and signs out. CurseForge manifests are checked on startup, on Refresh (with `no-cache`, so the answer is at most a minute old), when an addon is newly recorded, and at most every 30 minutes from the background pass (`_lastCurseForgeCheck`). That check of recorded CurseForge addons (`ProbeProviderAddonsAsync`, `ProbeChannelsAsync(direct: true)`) goes direct first: `AddonUpdater` reads curseforge.com's public website API (`/api/v1/mods/{modId}/files`, newest 50 by `dateCreated`) with the unauthenticated client and a 10-second timeout, and `CurseForgeDirect` picks the newest file per channel by the server's rules (release type 1 for `release`, 2 or 3 for `pre-release`, the install's version type in `gameVersionTypeIds`, `status` 4 or 10 (a missing or other value is unavailable) standing in for the missing `isAvailable`, an unconfirmed mapping; items without a positive `id`, a safe `fileName`, `dateCreated` or `gameVersionTypeIds` are skipped) and builds an `AddonRelease` with `Direct` set: version `displayName` else `fileName`, the edge CDN zip URL, `fileLength` as size, no hash, folders or changelog. steward-server is not called while that works. A channel with no eligible file asks steward-server for that channel unless the list is complete (`pagination.totalCount` within the page). A row install of a direct release first reads `/dependencies` (`AddonUpdater.WithDirectRequiresAsync`) and takes its `RequiredDependency` entries one level deep as `requires`, which the install record keeps as `requires` so the row's "required by" guard (`AddonRequirements.Of(addon, release, installed)`, `AddonRequirements.Requires`) survives later direct checks and restarts. The endpoint is unsupported (robots.txt disallows `/api/*`), so a failure falls back to the steward-server manifest, a failed direct install included (`InstallRefetchingOn404Async` refetches the proxy manifest and installs that). A network-level failure (no status, a timeout, 403, 429, 5xx, a body that is not JSON or has no `data[]` array) skips direct calls for every addon for an hour (in memory, logged once at Information), and a direct release still held then installs from steward-server without a download attempt; a per-mod problem (no usable items, another status, a dependencies failure, a size or CRC mismatch, which sends no download-failure report) falls back for that addon only. When a direct install fails and steward-server's build is a different version, that direct file id is remembered for the session and that channel asks steward-server instead. Only recorded addons (`CurseForgeAddons.IsRecorded`) go direct, and `AddonRequirements.Matches(ManagedAddon, id)` also matches a requirement to a known CurseForge addon by the mod id in its `ManifestBaseUrl`, so a `curseforge:13344` requirement resolves to the catalogue BugGrabber. Catalogue CurseForge addons, Get addons, links and requirement probes still use steward-server. A manifest with `distributable: false` gives the row `Get on CurseForge` or `Update on CurseForge`, opening the manifest's `website`, and keeps it out of the Updates count, Update all and auto-apply. `appsettings.json`'s `CurseForge:GameVersionTypes` maps a product code to CurseForge's version type (`wow_classic_beta` to `88568`); an install with no mapping has no CurseForge rows and no Get addons button. When a CurseForge addon's zip download fails (a non-success status, a network failure or timeout) or fails its size or CRC check, `AddonUpdater.InstallAsync` reports it once per addon id and version per run through `StewardClient.ReportCurseForgeDownloadFailureAsync` (`POST /api/addons/curseforge/download-failure`, `CurseForgeDownloadFailure`), fire-and-forget on the `Steward` client so the owner hears about CDN blocking; a failed report (including a 401 or 404) is logged at Warning and never touches the install error, `StatusMessage` or sign-in state, and user cancellation, manifest fetches and folder guard refusals are not reported.

The Local scan (`WowInstallViewModel.RescanLocalAsync`) excludes every recorded CurseForge folder whenever the setting is on, whether or not `addons` is currently held (so a steward-server outage does not turn them into Local rows), and while `IsCurseForgeEnabled` holds it then sends every remaining folder to steward-server's `match` route off the UI thread (`CurseForgeAddons.MatchRequest`: the top-level TOC's `## X-Curse-Project-ID` as a declared id where there is one, and every folder's `CurseForgeFingerprint`, since an exact fingerprint match needs all of a mod's module fingerprints in one request). `CurseForgeAddons.Adopt` folds each matched mod's modules present on disk into one record, a declared-id match winning over a fingerprint match for the same folder, named by `CurseForgeAddons.PrimaryFolder`, the module that prefixes the most others (`Questie` over `QuestieDB`, `AtlasLootClassic` over `AtlasBIStooltips`, the first listed when none prefixes another), the same rule a link or Get addons install names its record by and that `AppStateStore` re-applies on load to a recorded addon whose primary folder differs while the new one is on disk, and titled from the match's own CurseForge `name` when steward-server's `match` route returns one, falling back to that folder's TOC title (Questie's plain `Questie.toc` is a stub reading "game client not supported", so the match's `name` is what shows instead); the match's `websiteUrl`, when present, is kept on the record too and used as the row's project link before a manifest has ever been fetched. Nothing is recorded automatically: the scan keeps each install's matches in memory, `CurseForgeAddons.Adoptable` drops the ones already recorded, and `CurseForgeAddons.MatchFor` gives a Local row the match holding any of its folders, so that row shows the match's CurseForge name and icon and an amber Adopt button (`CautionButtonBackground` brushes in `Styles/Resources.axaml`) in its status column. While the selected install has an adoptable, unhidden row not kept local, the Update all slot in the table toolbar is an "Adopt all" split button whose dropdown holds "Adopt none". Adopt, Adopt all and the overflow menu's "Adopt from CurseForge" all go through `WowInstallViewModel.Adopt`, which passes that `CurseForgeAddons.Adopt` output to `MainViewModel.ReconcileProviderAddons` in one call: it records the matches, resyncs the rows and fetches their manifests at once, and the install rescans. "Adopt none" records each adoptable row's `AppStateStore.Key(flavourPath, primaryFolder)` in `kept_local_addons` in `state.json` (pruned by `AppStateStore.RemoveInstall` like `ignored_addons`); a kept-local row has no Adopt button, is left out of Adopt all, and offers "Adopt from CurseForge" in its overflow menu, which adopts it and drops the key. Before any adopt, `MainViewModel.ConfirmAdoptAsync` runs `AddonManagerApps.Detect` (Core) off the UI thread: CurseForge, WowUp and WowUp-CF count when a process of that exe name is running, or when an enabled startup entry (HKCU/HKLM `Run`, the 32-bit `Run`, or a startup-folder shortcut, each honouring its `StartupApproved` byte, `02` or absent meaning enabled) points at that exe and the exe exists, so an app that is not installed is never reported; any hit shows an "Adopt from CurseForge?" confirm naming what was found, with "Adopt anyway"; on Windows it says an app "starts with Windows" and points at Windows Settings > Apps > Startup, and off Windows "starts when you log in" and "your desktop's startup applications settings". Run value names are matched by exe filename rather than by name, since none of the three documents theirs; WowUp-CF was seen running from `%LocalAppData%\Programs\wowup-cf\WowUp-CF.exe` on 29 Sep 2026. Every scan still calls `ReconcileProviderAddons` with no matches, so it drops any record whose primary folder has gone from disk (after a CurseForge uninstall or a manual delete). A recorded CurseForge addon is only un-adopted by the row's "Unmanage addon" overflow item (`MainViewModel.UnmanageProviderAddon`), which drops its record, install record and ignore key and records its `kept_local_addons` key, so the folder comes back as a Local row with no Adopt button and "Adopt from CurseForge" in its overflow menu. Configured addons keep their configured source: their folders are excluded from the scan, so BugSack and RXPGuides are never sent to the match route. A matched row with no install record whose TOC carries no `## Version` reads `unknown` rather than Not installed, since its folder is on disk. The row's folder line reads `Questie + 1 folder` for a multi-folder addon, and Uninstall removes every folder in the manifest's `folders` (else the recorded folders, else `FolderName`), plus every folder the last install recorded, through `AddonUpdater.Uninstall`, which refuses before deleting anything when any folder fails the TOC guard. The install record keeps the manifest's `sha256` and `folders`, what `AddonUpdater.InstallAsync` returned; a `sha1` key in an older `state.json` is ignored on load and dropped on save. A CurseForge install is verified by size (the zip's length equals the manifest's `size`) and by every entry's CRC-32, checked before anything is deleted, never by a hash: the server still sends `sha1` for older builds and the app ignores it, while every other source but TukUI still requires `sha256`. It takes every top-level folder of its zip as well as the manifest's `folders`, since CurseForge's module list can omit one the zip ships (EllesmereUIForeverEssentials, 29 Sep 2026), and a direct release takes only the zip's top-level folders that hold a `.toc`; those recorded folders are excluded from the Local scan like the record's own. A root-level file in the zip is still refused, as is any entry whose path has a `.` or `..` segment, an empty segment, a drive colon or a leading separator (`AddonUpdater.EntryParts`, checked before anything is deleted or extracted). On every install and update of a CurseForge addon, from a row's Update, a requirement install or a link, `AddonUpdater.InstallAsync` checks the final folder set (manifest folders plus the zip's top-level folders) against `MainViewModel.ExcludedFoldersForOthers(install, addonId)`, the folders of every other catalogue addon, StewardGuides and every other recorded CurseForge addon with its install record's folders, and fails with "ships X, which belongs to another addon" before touching disk.

TukUI is a second recorded source, for ElvUI (project `-2`) and Tukui (project `-1`), and it uses the same gate as CurseForge management (`IsCurseForgeEnabled`), with no setting of its own. Identification is local only: `LocalAddons.ReadDeclaredIds` also reads `## X-Tukui-ProjectID` and the comma list `## X-Tukui-ProjectFolders` from the top-level TOC it picks, and `TukUiAddons.Identify` (Core) makes one `ProviderAddonRecord` per project from the folder that declares the id: id `tukui-{projectId}`, `Source: "TukUI"`, `ModId` the project id, `VersionType` 0, the declaring folder as the primary folder, the listed folders that are on disk, the TOC title without colour codes, and the cached TukUI list's `logo_square_url` and `web_url` as the icon and website when a list is loaded (`TukUiAddons.WithListing`). `MainViewModel.IdentifyProviderAddonsAsync` runs it on every Local scan before the CurseForge match, and the folders it claims are not sent to the match route, so a TOC that declares both `X-Tukui-ProjectID` and `X-Curse-Project-ID` is adopted from TukUI; an ElvUI already recorded as a CurseForge addon stays one, since recorded folders never reach the scan. A TukUI match gives its Local row the Adopt button, Adopt all includes it, and adoption, `kept_local_addons`, the Local-scan exclusion, `ExcludedFoldersForOthers` and Unmanage are the CurseForge paths; the confirmation reads "Adopt from TukUI?" and the overflow item "Adopt from TukUI". `TukUiAddons.ToManagedAddon` makes the row: `Features: ["addons"]`, source label "TukUI", `manifest_auth` none, not `curseforge`, so it never goes direct to curseforge.com, never reports a download failure and works on every client. TukUI is handled entirely in the app, with no steward-server route: `TukUiSource` (Core, owned by `AddonUpdater` as `AddonUpdater.TukUi` on the cookie-less `Addon` client) reads `https://api.tukui.org/v1/addons`, a JSON array of every project (`TukUiAddon`), and keeps it 15 minutes; a manual Refresh (`noCache`) refetches a list 60 seconds old or more, as steward-server's CurseForge cache does. `AddonUpdater.GetLatestAsync` answers a row for which `TukUiAddons.ProjectId` holds (source `TukUI` and id `tukui-{projectId}`) from that list: `release` is `TukUiSource.ToRelease` (the version without its `v`, `released` from `last_update` at midnight UTC, `folders` from `directories`, `website` from `web_url`, `notes` from the newest `### ` section of `changelog_url`'s markdown, `TukUiSource.Notes`, cached per project and version), every other channel has no build, and a project the list no longer holds reads as no release. A list that cannot be fetched or parsed throws, so the row's check fails and is reported like any manifest failure; a failed changelog gives no notes for that check, logged at Warning, and is fetched again on the next. The `url` in the list is a download token: each list fetch issues a new one, and a token answered 403 by 16 minutes old (26 Oct 2026), so `AddonUpdater.InstallAsync` takes the zip URL from `TukUiSource.ZipUriAsync`, a list at most 60 seconds old, and fails when that list names another version. TukUI publishes no hash, so a release that `TukUiSource` built (`AddonRelease.TukUiProjectId`, which is `[JsonIgnore]` and never read from a manifest) installs without `sha256`; any other release with no `sha256` is still refused, a `TukUI` row's included. The row's `ManifestBaseUrl` is the list URL and is never fetched as a manifest. A record from before this, whose `icon_url` is steward-server's `/api/addons/tukui/{projectId}/icon.png`, needs no migration step: `ProviderAddons` builds its row through `TukUiAddons.ToManagedAddon`, which drops that icon URL, and the first successful TukUI check rewrites every TukUI record's `icon_url` and `website_url` to the list's (`MainViewModel.RefreshTukUiListings`). `ForeverCopy.CarryState` carries a TukUI record to the live install without the CurseForge version type check.

`Get addons` in the Addons page header (`GetAddonsDialog` and `GetAddonsViewModel`, shown only with the feature and a mapped game version) lists steward-server's discover route, `popular` then `recentlyUpdated` de-duplicated, with an empty query, and searches with a query, debounced 300ms. A `503 search_unavailable` from the search route shows "CurseForge search is not enabled for Steward yet. Showing popular addons." and keeps the list on discover for the rest of the dialog. Every new result set (a search or discover) scrolls the list back to the top, as WinUI's does: the Avalonia dialog resets `ResultsScroller` whenever `Results` is cleared. `Install` resolves the manifest first, refuses a folder already owned by a configured addon or another CurseForge record, records the addon, adds its row behind the dialog and runs that row's own `UpdateCommand`, so the install path, size check and install record are the row's; the result then reads Installed. A result with `allowDistribution: false` shows `Available on CurseForge`, linking to its project page. TukUI's addons lead the list: Popular starts with every TukUI project whose `patch` list holds a version with the install's client major version (`TukUiSource.RunsOn`; a project with no `patch` list, or an install with no client version, always shows), and a search starts with the ones whose `name` or `slug` contains the query, case-insensitive, both from `AddonUpdater.TukUi`'s cached list. A TukUI row uses the same row look with "TukUI ·" before the version where a CurseForge row reads "CurseForge ·" (`CurseForgeResultViewModel.Source`), and its Install is `MainViewModel.InstallTukUiAsync`, which records `TukUiAddons.Record` (the record TOC adoption makes: id `tukui-{projectId}`, `CurseForgeAddons.PrimaryFolder` of `directories`, the logo and website) through the same path as a CurseForge install (`InstallProviderAsync`: the gates, the folder-ownership refusal, then the row's own `UpdateCommand`). TukUI and CurseForge are fetched independently, so one failing shows its error ("Could not reach TukUI: ..." or the CurseForge message) above the other's results. The Source ComboBox is not bound to the list.

The Install button on a curseforge.com addon page launches `curseforge://install?addonId=<modId>&fileId=<fileId>`, and `Package.appxmanifest` registers the `curseforge` protocol (beside `steward`, the addon settings import link, see Addon settings), so the Store, flight and dev packages receive it (with the CurseForge app also installed, Windows asks which app opens it). `Program.ActivationLink` reads the URI from `AppInstance.GetCurrent().GetActivatedEventArgs()` on a packaged build, or from a bare `curseforge:` argument or `--curseforge-link=<uri>` on any build; the unpackaged Debug build registers no protocol, so the switch is how the path is exercised there. `MainViewModel.ReceiveCurseForgeLinkAsync` waits for `InitializeCommand` to finish (sign-in restore and the first pass), parses the link with `CurseForgeLinks.Parse` (two positive integers, anything else logged and ignored), shows "CurseForge installs are not enabled for your account." as a dismissible local banner when signed out or without the `addons` feature, "CurseForge addon management is turned off in Settings." when the setting is off, and otherwise fetches steward-server's `GET /api/addons/curseforge/{modId}/files/{fileId}` (`StewardClient.GetCurseForgeFileAsync`, `CurseForgeModFile`: the mod's name, icon, website and distribution flag, that file as a manifest, its `releaseType` and `gameVersionTypeIds`). `CurseForgeLinks.State` picks the outcome for the selected install. Install, and Update (installed, and `CurseForgeLinks.IsNewer` finds the linked file released after the installed one, or after it was installed when the installed file's date is unknown), first show an "Install {name}?" confirmation (`CurseForgeLinks.ConfirmBody`: name, author when the files route returns one, file version and the game install; Install or Cancel, and Cancel installs nothing), then navigate to Addons and install that exact file through `InstallCurseForgeAsync`; a link from a web page therefore never installs on its own. Already installed navigates to Addons with a dismissible "{name} {version} is already installed." local banner; only available on CurseForge (an older server) keeps its Open on CurseForge dialog. A file for another client (`NotBuilt`) asks the same confirmation, then probes the install's own manifests and installs `CurseForgeLinks.Alternative` (release, else pre-release) with an "Installed the {game version} build {version} of {name} instead of the linked file." banner; with none, `MainWindow.ChooseLinkFileAsync` shows "{name} has no build for {game version}." with a `ComboBox` of steward-server's `GET /api/addons/curseforge/{modId}/latest-files` (`StewardClient.GetCurseForgeLatestFilesAsync`; a 404 leaves the linked file alone, `CurseForgeLinks.Choices`), the linked file preselected (`CurseForgeLinks.Preselect`), Install and Skip, and Install fetches the chosen file through the files route; an install with no mapped version type still gets a Close-only dialog. `InstallCurseForgeAsync` pins the installed file on the channel `CurseForgeLinks.Channel` maps from `releaseType` (`pre-release` for 2 and 3, else `release`) and stores that channel, so the row shows a newer build on the next CurseForge check. On a packaged build where `IsCurseForgeEnabled` holds, `MainViewModel.EvaluateCurseForgeDefaultHandlerAsync` (after every `/api/me` recheck, on sign-out and on window activation, debounced 500ms) shows a dismissible local banner "Open CurseForge links with Steward" (`dismissed_banners` key `curseforge-default-handler`) unless this package is the default for `curseforge:`: `CurseForgeDefaultQuery` calls `IApplicationAssociationRegistration.QueryCurrentDefault("curseforge", AT_URLPROTOCOL, AL_EFFECTIVE)`, resolves the ProgId through `HKCR\<ProgId>\Application\AppUserModelID` and compares it with the package family name plus `!App` (`CurseForgeDefaultHandler.IsOurs`); no association counts as not default and a query exception shows nothing. Windows forbids setting the default programmatically (UCPD, Store policy 10.2.8), so "Set as default" opens Windows' own app picker for the scheme (`Launcher.LaunchUriAsync("curseforge://")` with `DisplayApplicationPicker`, where choosing Steward with Always sets the default and launches Steward with a bare link it ignores) while no app is the default yet (`QueryCurrentDefault` answers `Undecided`), and `ms-settings:defaultapps?registeredAUMID=<AUMID>` once any app is, since the picker then offers only "Just once" (seen 29 Sep 2026 with the Store build as the default) and when the picker call throws.

On Linux the .deb and .rpm install `/usr/share/applications/steward.desktop` with `MimeType=x-scheme-handler/curseforge;x-scheme-handler/steward;` and an `Exec` ending in `%u`, so a link arrives as the bare `curseforge:` or `steward:` argument `Program.ActivationLink` already reads. The default-handler banner shows there only while `xdg-mime` is on `PATH` and `steward.desktop` exists under `$XDG_DATA_HOME/applications` or an `applications` folder of `$XDG_DATA_DIRS` (`/usr/local/share:/usr/share` when unset; `XdgMime.ApplicationDirs`), probed once per run, so a tarball or Debug build never points the scheme at a desktop file that does not exist. The query is `xdg-mime query default x-scheme-handler/curseforge` compared with `steward.desktop` (`XdgMime.IsDefault`), and "Set as default" runs `xdg-mime default steward.desktop x-scheme-handler/curseforge` (`CurseForgeDefaultQuery.TrySetDefault`, `false` on Windows) and then records the banner as dismissed, since xdg-utils 1.1.3's generic query skipped the `mimeapps.list` default it had just written (Ubuntu 24.04, 16 Oct 2026); a failed set shows on the status bar. Every `xdg-mime` and `xdg-open`/`open` call passes an argument list, never a shell string (`WindowsShell.Unix.cs`, where the app-picker launch is the plain open). Every folder and link the app opens goes through `ShellOpen.Open` (Presentation): the Open folder commands (the install picker's Open AddOns folder, a row's Open folder, a Local row's Open folder), the Settings page's folder and link buttons, the account menu's Guild panel, the sign-in browser launch, the release and Store pages, a non-distributable row's or CurseForge link's project page and every `WindowsShell.LaunchUriAsync` off Windows: on Windows it is the same `UseShellExecute` start as before; off Windows it starts `xdg-open` (`open` on macOS) and waits for its exit off the UI thread, since `UseShellExecute` returns once `xdg-open` starts and `xdg-open` reports a missing handler only through its exit code. A non-zero exit (3 reads "no application is set up to open it") or an opener that cannot start raises `ShellOpen.Failed`, which `MainViewModel` logs at Warning and shows as "Could not open <path>: <reason>." on the status bar (an http or https target through `LogRedactor.PathOnly`, so no query string is shown or logged); a failed sign-in launch instead sets `BrowserOpenFailed`, the gate's own copy-the-link notice, since the status bar is not on the gate (the Addons page error bar, as for every other `StatusMessage`); verified 16 Oct 2026 under Xvfb with no handler for `inode/directory`, for Open AddOns folder and Open data folder. On macOS the `.app` declares `CFBundleURLTypes` for `curseforge` and `steward`, the link arrives as an Apple Event rather than an argument, and `App.OnFrameworkInitializationCompleted` hands every `ProtocolActivatedEventArgs` with that scheme from Avalonia's `IActivatableLifetime.Activated` to `ReceiveCurseForgeLinkAsync`; the macOS default-handler banner never shows (`CurseForgeDefaultQuery.Aumid` is null there).

Two release channels, named after what produces them in `hoobio/addons`: `release` (a tagged GitHub release of the addon) and `pre-release` (every push to the addon's `main`). The `develop` channel (every push to an addon's `develop` branch) was removed on 26 Sep 2026: the download site no longer publishes it, so probing it is pointless and it is gone from `AddonChannelStatus.Ordered`; an addon repo's own `develop` branch is unaffected. RestedXP has `release` and `pre-release` only, mapped to the GitHub release and prerelease flags steward-server's mirror reads. The channel is per addon, stored in `Channels` alongside the install-state records in the same `state.json`, defaulting to the first channel that has a release in the order `release`, `pre-release` (`AddonChannelStatus.Ordered`, also the picker order). When a more stable channel holds a build released after the one on the chosen channel, the row shows a notice naming it, so being on `pre-release` while a newer `release` exists is visible without switching. The rename from `stable`/`beta`/`unstable` was not migrated: a stored old channel name falls back with the "No releases on X any more" notice. A stored `development` or `develop` value is migrated to `pre-release` on load: `AppStateStore.MigrateDevelopChannel` rewrites it, alongside the `LegacyChannel` seed; if that addon has no `pre-release` build, the ordinary `Resolve` fallback drops to `release` instead and says so in the row's notice.

Each WoW install + addon pair records what was actually installed (version, channel, and the manifest's `sha256` when it has one), keyed by flavour path plus addon id. With no record, the addon's own `.toc` version is the fallback, which is the manual-install case. Update availability is plain string inequality between that recorded/TOC version and the channel manifest's version, not a semver comparison: versions like `0.5.0-beta.1` and `0.5.0-unstable.219da29` don't parse as `System.Version`, and switching channels has to be able to move the installed version in either direction.
