# Managed addons

The managed addon list is steward-server's: `/api/me` carries a top-level `addons` array (`DesktopAddons` in `src/Steward.Auth/Me.cs`), already filtered to what the caller may see and in display order, each entry `{ id, name, folder_name, manifest_base_url, source, auto_install, features, parent?, icon_url? }` (`CatalogueAddon` in `Steward.Core`, mapped to `ManagedAddon`). It is cached as `addon_catalogue` in `state.json` and loaded at startup, so rows appear before the first `/api/me`; a successful `/api/me` carrying the field replaces it (saved only when it changed), one without it clears it, as do sign-out, a 401, a lost-access answer and a start with no session to restore, and it is kept while steward-server is unreachable or answers `client_outdated`, so addon.hoobi.io updates continue through an outage (`client_outdated` itself disables every row). An entry missing `id`, `folder_name` or `manifest_base_url` is dropped in `StewardClient.GetMeAsync` rather than failing the whole `/api/me`, and a null `source` or `auto_install` reads as `Steward` and false. Every folder in the server list is excluded from the Local scan, the CurseForge match route, adoption and the Get addons "already managed" guard, the same as a configured addon's, and a changed list rescans every install's Local rows. An install or update also deletes, in the same `AddOnsWriteLock` step, each folder in that addon's install record (`installs` `folders`) that the new release does not ship, so a changed `folder_name` or folder list leaves no old folder behind; a recorded folder that another addon now uses, a name `AddonUpdater.RemovalRefusal` refuses and a junction or symlink are kept. An older build sharing `state.json` drops the key on its next save, and the next successful `/api/me` restores it. Adding an addon is a steward-server catalogue row plus its addon.hoobi.io manifests, with no app release. `appsettings.json`'s `Addons` array of `{ Id, FolderName, ManifestBaseUrl, AutoInstall?, Features?, Source? }` (`ManagedAddon`) is kept only as the fallback for a server that sends no `addons`, rendered in array order; `ManifestBaseUrl` is required. `Source` defaults to `Steward` and names where the addon's release zip comes from, shown as-is in the table's Source column: `Steward` for the `addon.hoobi.io` manifests, `GitHub` for steward-server's RestedXP mirror (the mirror serves RestedXP only), and `CurseForge` for BugSack (mod 6273) and BugGrabber (mod 13344), whose `manifest_base_url` is steward-server's `/api/addons/curseforge/{modId}/88568/` with the Forever beta's version type baked in, and BugSack's `icon_url` is the CurseForge logo, since that route's `icon.png` needs the session cookie and row icons load without it, while BugGrabber has no CurseForge logo and carries none. A `CurseForge`-sourced catalogue entry is visible only while `IsCurseForgeEnabled` holds and its folder is excluded from the Local scan only while the setting is on, so with CurseForge off an installed BugSack is a Local row; it is a catalogue row rather than a `ProviderAddonRecord`, so it has no Unmanage item (`CurseForgeAddons.IsRecorded`) and its download failures are not reported. Five fallback entries ship today: `steward` (`AutoInstall: true`, `Features: ["sync"]`, so anyone holding the character-sync flag also gets the addon auto-installed, since it is what writes and reads the guild data that flag unlocks), `hoobiscripts` (`Source: "Protected"` at steward-server's protected route, since addon.hoobi.io no longer hosts it; `Features: ["hoobiscripts"]`, a flag held only by explicitly granted individuals rather than any officer default), and `restedxp`, `bugsack` and `buggrabber` (`Features: ["addons"]` each, a grantable flag held by officers by default and derived server-side for anyone holding `sync` or `hoobiscripts`, so the diagnostic and RestedXP rows show for the same population without each naming its own flag; the RestedXP row moving to `addons` is separate from the Guides page and sign-in entry point, which stay gated on `guides`). A configured addon with no manifest on any channel renders as "No releases yet" rather than as an error. `AddonUpdater` takes the `ManagedAddon` and channel as parameters rather than hardcoding a folder name or manifest URL, and the UI iterates the visible list per WoW install.

`Features` applies to the fallback list only and defaults to empty, so a configured addon without it is never visible. It names which of the signed-in user's `/api/me` features make the addon appear at all: it is visible when the user holds any one of them. `MainViewModel.VisibleAddons()` (`AddonCatalogue.Visible` in Core) is the one place the visible list is chosen: the server list as-is whenever one is known, fresh or cached, with no client-side feature filter (`features` on a server entry is informational, and `_features` is empty while steward-server is unreachable), else the configured `Addons` filtered by the user's feature set; every addon-list iteration (the manifest/release check, auto-apply, Update all, the Hidden addons toggle, `AddonChannels`) goes through it. Per-install rows are not fixed at construction: `WowInstallViewModel.SyncAddons` reconciles `AddonRows` against a given addon list, keeping the row instance for an addon still visible, adding one for an addon newly visible in its config-order position, and removing and unsubscribing one for an addon no longer visible; that removal only drops the row and its event subscription, never the addon's own folder on disk, since `AddonUpdater.RemoveExistingInstall` runs only from inside `InstallAsync`, itself only reachable through a visible row's own `UpdateCommand`. `MainViewModel.ReconcileFeatureGating` calls it on every install, prunes `_status`/`_releases` to the addons still visible and rebuilds `AddonChannels`, whenever `RecheckAuthorizationAsync` finds the feature set or the server addon list changed from the previous check; that covers a feature gained or lost mid-session, an addon added or withdrawn server-side, and a start where steward-server was unreachable and the set was still empty, since the next successful check is a change from empty. Each row's own `ensureAuthorized` (`MainViewModel.EnsureAuthorizedForAddonAsync`) rechecks `/api/me` and reconfirms the addon is still in that install's visible list before an update runs, so an update queued just as access drops refuses rather than applying. It passes on `Authorized`, and on `Unreachable` for a `Steward`-sourced addon in the cached server list (`AddonCatalogue.UpdatesWhileUnreachable`), whose manifest and zip live on addon.hoobi.io; a 401, lost access or `client_outdated` refuses, and a CurseForge or GitHub-mirrored row needs `Authorized`, since its manifest comes through steward-server. While steward-server is unreachable with a cached list, those rows stay enabled (`MainViewModel.IsAdminFor`), each manifest is probed on its own so one failing addon does not stop the rest, and the background pass still runs the manifest check and auto-apply (`CheckAsync` with no roster pull); Update all stays gated on `IsAuthorized`. Auto-apply and Update all only ever iterate `Installs[].AddonRows`, so a feature-hidden addon, having no row there at all, is never auto-installed, updated or touched by either.

A server entry may carry `parent` (the parent addon's id, `ManagedAddon.Parent`; today only `hoobiscripts-actionbars` under `hoobiscripts`), and `appsettings.json` entries carry none. `AddonGroups.FoldedInto` (Core) maps each visible sub-addon whose parent is also visible to that parent, one level deep. Every visible addon keeps its own `AddonRowViewModel`, so install, status, manifest, TOC guard and install records are unchanged, but `WowInstallViewModel.SyncAddons` marks a folded one `IsFolded` and hands it to the parent row (`AddonRowViewModel.SetChildren`), and `WowInstallViewModel.TopRows` (the table, the Updates count, Update all, Update all installs and `AutoApplyAsync`) leaves it out. The parent row rolls the group up: `AddonGroups.NeedsUpdate` reads Update available when the parent or a sub-addon has an update or a sub-addon is missing while the parent is installed, so granting a sub-addon's flag delivers it through Update or auto-update, skipping a sub-addon that is hidden, ignored or not distributable in its own right (`AddonGroups.IsRolledUp`); its Update installs the parent first when it needs it, then each sub-addon that does, and a sub-addon failure fails the row with that sub-addon's message; busy, Ignore, Hide and Uninstall cover the group (one `AddonUpdater.Uninstall` over every member's folders, so one TOC guard refusal refuses the lot); the changelog is the parent's followed by a heading per sub-addon with content, naming it and the version it would install (`Changelogs.Combine`). A sub-addon follows its parent's stored channel (`AddonGroups.StoredChannel`), falling back through the ordinary `Resolve` order when it has no build there, with the notice kept off the parent row; the channel dialog edits the parent only. A sub-addon whose parent is not visible gets an ordinary row.

`AutoInstall` marks an addon the background pass installs when it is missing, under the same admin gate as auto-update; it cannot be hidden. No addon is sourced from the GitHub API from this app any more: RestedXP moved to steward-server's own mirror of `RestedXP/RXPGuides`'s GitHub releases, served at its `ManifestBaseUrl` in the same `latest-{channel}.json` shape every other manifest-host addon uses, so `AddonUpdater` and `GetLatestAsync` have one code path for every addon. The mirror (`src/Steward.Integrations/GitHubMirror.cs` in `D:\steward-server`) applies the selection rules the list of GitHub releases needs: `release` is the non-draft entry without the `prerelease` flag that has the latest `published_at` and `pre-release` the one with the flag that has the latest `published_at`, because the GitHub API's list order is not date order (on 20 Sep 2026 it returned `.95, .94, .92, .102, .100`, and taking the first entry reported the installed build as up to date). The `.zip` asset is the release and its `sha256` digest is the checksum, and the tag name is the version (RXPGuides stamps the same `v4.11.4` form into its TOC); a release lacking a `.zip` asset or a digest is skipped by the mirror rather than surfaced here. There is no `develop` channel for RestedXP: the mirror only ever answers `release` and `pre-release`, so a `develop` request 404s and reads as no release the same way an empty channel does for any other addon. The icon comes from the mirror's own `icon.png` route, which redirects to the repo owner's GitHub avatar, so a manifest-host addon's icon logic covers it without a branch.

A manifest (`AddonRelease.Requires`) or a catalogue row (`CatalogueAddon.Requires`, mapped to `ManagedAddon.Requires`) may carry `requires`, the field steward-server's `DesktopAddons` catalogue defines: each entry is a catalogue id string or an object `{ id, name, folder_name, manifest_base_url, requires }` (`AddonRequirement`, read by `AddonRequirementConverter`, which drops an entry with no id rather than failing the manifest); steward-server's CurseForge manifests list a file's required dependencies as `curseforge:<modId>` objects. Before a row installs its own build, `AddonRowViewModel.InstallSelfAsync` runs `MainViewModel.InstallRequirementsAsync`, which walks both lists through `AddonRequirements.InstallAsync` (Core) depth-first, dependencies before dependants, to depth 3, skipping an id already on the walk: each entry resolves to a visible row by id (`AddonRequirements.Matches`, so `curseforge:<modId>` matches that install's `curseforge-<modId>-<versionType>` record) or folder, else to a new CurseForge record or a bare `ManagedAddon` from the object; one whose folder is already on disk with its own TOC, at any version, or whose key is in `ignored_addons`, is skipped; the rest fetch their manifest on the dependant's channel (the ordinary `AddonChannelStatus.Resolve` fallback), install with the row's progress bar and "installing <name> (needed by <addon>)" as its status, and are recorded like any install, a CurseForge one also as a `ProviderAddonRecord` so it becomes a normal row. A requirement that cannot be resolved, has no build or fails to install fails the dependant with "Could not install <name> (needed by <addon>): ..." (`AddonRequirementException`). `WowInstallViewModel.RefreshRequired` sets `AddonRowViewModel.RequiredBy` on every row an installed row requires, which hides Uninstall, Ignore and Hide on it as `AutoInstall` does. A curseforge:// link install asks steward-server's files route with `?versionType=` so the file's own manifest carries `requires`.

A catalogue row's behaviour comes from declarative fields steward-server fills on every row (its `AGENTS.md`, "Protected addons"), read onto `ManagedAddon` and resolved there, rather than from the `source` string: `manifest_auth` (`session` fetches the manifest with the `Steward` client, `ManifestNeedsSession`), `zip_auth` (parsed and unused; always `none`, since a signed zip URL carries its own token), `zip_relative` (whether a relative `zip` resolves against the manifest URL; an absolute `zip` is used as given either way, and a relative one on a row that is not `zip_relative` fails the install, `AddonUpdater.ZipUri`), `auto_install`, `updates_while_unreachable` (`MayUpdateWhileUnreachable`, read by `AddonCatalogue.UpdatesWhileUnreachable`), `source_label` (the Source column, `DisplaySource`) and `curseforge` (the CurseForge gate, the Local-scan exclusion, the zip folder union, the unknown-version read and download-failure reporting, `IsCurseForge`), plus `requires` above and `notice` (`{ icon, text }`, both optional, `AddonNotice`, cached in `state.json` and omitted when null), which `AddonRowViewModel` draws as a small icon button after the addon name on the Addons table row, with `text` as its tooltip: `icon` `lock` is the Fluent lock glyph (`E72E`) and any other value the info glyph (`E946`), so the wording is steward-server's to change. `products` is a list of product codes the row is offered on, `"*"` for every client (`ManagedAddon.RunsOn`); a row without it, from an older server or the cached catalogue, is offered on Forever (`wowf` and `wow_classic_beta`) only, since Steward rows auto-install. `MainViewModel.AddonsFor(install)` filters the visible list by it for each install (recorded CurseForge addons are per install already), and `ExcludedFoldersForOthers` excludes a catalogue folder, and the `StewardGuides` folder, only on an install the row is offered on, so on another client those folders are Local rows and a CurseForge install of them is not refused. The configured `Addons` fallback takes the same `Products` key, and only `restedxp` sets it (`["*"]`). After every install or update of a row that `AddonThemeFile.AppliesTo` (it has a `notice`, `manifest_auth` `session` or the `Protected` source), `AddonRowViewModel.WriteThemeFile` writes `Core/Theme.lua` in each of that row's folders that already has one (the zips ship a placeholder with `ns.themeId = nil`) as exactly `local _, ns = ...` and `ns.themeId = "<Discord user id>"` (LF, UTF-8 without BOM, temp file then move, never outside the addon's own folder), using the signed-in user's `/api/me` `user.id`; it writes nothing when signed out and rewrites every row when `MainViewModel` sees the account change. The id identifies who fetched a protected addon if a copy is shared, which the catalogue `notice` text says to users; no UI, log line or state key names it beyond the file. A row without a field falls back to its `source` string as before, so an older server changes nothing; a `Protected` row without them reads as `manifest_auth` session, not `zip_relative`, `source_label` "Steward", no `updates_while_unreachable` and not `curseforge`. `Protected` is the source of every HoobiScripts addon served from steward-server's gated `/api/addons/protected/<id>/` routes, whose manifest needs the session and whose `zip` is an absolute signed URL fetched with the cookie-less `Addon` client and hash-verified like any other. This is the release after which a catalogue change needs no client update: a new kind of row is expressed in these fields, and a behaviour they cannot express is a client change that extends them rather than adding a `source` string.

`docs/design/addon-manager.md` is the built Addons page: one table per selected WoW install, listing every configured addon `VisibleAddons()` passes plus a Local row for every other folder in that install's `AddOns` holding its own TOC. A folder whose TOC names another unmanaged folder as a dependency folds into that folder's row instead of getting one of its own, resolved through chains to the root, so a DBM-style suite of folders reads as one row; a folder depending only on a configured addon still gets its own row. A folder's top-level TOC is picked by the install's client interface (`TocFile.InterfaceNumber(ClientVersion)`): among `<Folder>.toc` and every `<Folder>_*.toc`, the first whose `## Interface:` list holds that number wins, suffixed before base, and with no match or an unknown client interface the base TOC (else the first suffixed) is used (`LocalAddons.TopLevelToc`), since Questie's base TOC is an interface-0 stub and the client loads `Questie_Camelot.toc`. `LocalAddons.Scan` in `Steward.Core` builds the list and `WowInstallViewModel.RescanLocal` rebuilds it on startup, on Refresh, and after an install or uninstall on that install, never on the background pass. The table's rows are in a plain `StackPanel`, not a virtualising panel, so every row is realised and the column widths do not change when the table scrolls (`ColumnFitTests`). The table's column widths, `IsCompact` (the Channel column dropped) and `IsVersionStacked` are computed only from widths that do not change with those modes (`HomePage.MeasureVersionCell`): a managed row's Version need is its current version or "No releases yet", its "Released {relative}" line measured off the tree whether or not it shows, and its Channel cell, while the version pair's own width comes from `VersionFloor`; the mode-dependent elements (the released line, the folded channel chip, the wide and stacked pair) are never measured live. The cell measured as a whole made the released line count only outside compact mode, so at one width the table switched between the two layouts on every layout pass (`ColumnFitTests` sweeps the window width 1px at a time and fails on that).

An install added by hand whose folder is gone is kept and shown greyed as "Folder not found" rather than dropped (`docs/design/addon-manager.md`, Missing installs). `MissingInstalls.Detect` (Core) runs on startup and Refresh only, recording `missing_since` per path, and reports a path due for removal after 14 days when its drive root still exists; a path on an absent drive is never auto-removed. Whether the drive is present is `InstallVolume.IsPresent` (Core): the path root on Windows and macOS, and on Linux, where the root is always `/`, the deepest mount in `/proc/self/mountinfo` holding the path: the drive counts as absent when an `/etc/fstab` mount point deeper than that holds the path (a configured disk that is not mounted), or when only `/` holds a path under `/media`, `/run/media` or `/mnt` (an unmounted removable or hand-mounted disk), with mount points matched on whole segments and their octal escapes decoded. A disk mounted by hand outside those folders and not in `fstab` reads as on `/`, so its install can still be removed 14 days after it was unmounted. `MainViewModel.DetectMissingInstalls` removes the due ones through `RemoveInstall(path)`, the one removal path, which calls `AppStateStore.RemoveInstall` (every per-path key and both side files). A missing install (`WowInstall.IsMissing`, built by `WowInstalls.MissingFromPath`) gets no addon rows, no local scan, no `StewardSync.lua` write, no character push and no RestedXP card; selecting it shows a centred message with Remove, and a once-per-episode local banner (dismissal recorded in `dismissed_banners` under `missing-install|{path}|{missing_since ticks}`) offers Remove too. User-driven removals confirm through `AppDialogs` first.

A user can ignore updates for a configured addon on one install, from the row's overflow menu. The key is `AppStateStore.Key` (flavour path plus addon id) in `ignored_addons` in `state.json`; an installed ignored row reads "Updates ignored" in amber in its status column, with "Update available" beneath it when there is one, and is excluded from the Updates count, Update all and `AutoApplyAsync`. A user can also hide an addon they manage through CurseForge or WowUp, from the same menu. Hidden ids live in `hidden_addons` in `state.json`, global rather than per install, and hidden rows are excluded from counts, auto-apply, Update all and the default and Updates views; the Hidden segment in the table's toolbar shows them again with a Hidden pill so they can be unhidden. Neither Ignore nor Hide is offered on an `AutoInstall` addon. Release channels are edited in the row's own channel dialog rather than on the Settings page.
