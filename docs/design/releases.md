# Releases

`build.yaml` runs on every push to `main` that touches something other than Markdown, `docs/`, `tools/`, `.githooks/` and `scripts/Install-DevBuild.ps1` (`paths-ignore` on both `push` and `pull_request`), and on `workflow_dispatch`; a release-please merge always runs, since it changes `version.txt` and the manifest alongside `CHANGELOG.md`. `PROJECT_PATH` is `src/Steward.Desktop/Steward.Desktop.csproj` and `AVALONIA_TELEMETRY_OPTOUT` is `1`. `lint-and-test` is a matrix: on Windows it builds the solution in Release and runs the Core and Desktop suites on both TFMs, and on Linux it builds the `net10.0` target of the two test projects with `-p:EnableWindowsTargeting=true` and runs the Desktop suite under `xvfb-run`. `build-msi` publishes `Steward.Desktop` for `net10.0-windows10.0.26100.0` `win-x64`, self-contained and not single-file, with `GitHubRelease=true`, and wraps it with `installer/Steward.wxs`, whose `UpgradeCode` is the earlier MSIs', so a WinUI MSI install upgrades in place; the `Icon` reads `$(sys.SOURCEFILEDIR)..\src\Steward.Desktop\Assets\Steward.ico`, since the Avalonia publish has no `Assets\Steward.ico` file (the icon is an `AvaloniaResource`). A push runs release-please and lint and tests; `build-msix` and `store-flight` run only on a dispatch or when release-please cut a release on that run, and `store-submit` only on the latter. A newer run cancels the one still in progress in its group (`concurrency` with `cancel-in-progress`); the group carries the event name, so a push never cancels a dispatched flight build, and a release-please merge (`chore(main): release ...`) sits in its own group, so a push behind it can never cancel the run that cuts the release. release-please runs first, and `build-msix` reads its version as described under Microsoft Store. Merging the release PR has release-please create the release as a draft (`draft: true` in `release-please-config.json`), the notes are stacked back to the last minor, and only then, with the MSIX, the `.msixupload`, the MSI, the `desktop` assets and the two HTML reports (`virus-scan-report.html`, `certification-report.html`) attached, is the draft published through `publish-github-release`; `store-submit` runs alongside it rather than behind it. On a release run only, the `desktop` job calls `.github/workflows/desktop-builds.yaml` (the one definition of the Windows zip, Linux packages and macOS dmg builds and their launch smokes, which `desktop-preview.yaml` calls too) with the release version as both `version` and `display-version` and `preview: false`, so it builds `Steward-<version>-win-x64.zip` (`PortableZip`, build name and train `portable`), `Steward-<version>-linux-<x64|arm64>.<deb|rpm>` and `Steward-<version>-macos-<arm64|x64>.dmg`; `release` requires that call to succeed, smokes included, attaches every `desktop-*` asset to the draft with `gh release upload`, and the Store jobs do not wait on it. The release-please job exposes the release version (`tag_name` without its `v`) as its `version` output for that call. The MSI is still the only `.msi` asset, so steward-server's mirror (`GitHubMirror.PackageAsset`, `EndsWith(".msi")`) and `hoobio/addons`' `mirror-github-releases.sh` (`endswith($suffix)` with `.msi`) still pick it, checked 17 Oct 2026. After `release` publishes, `linux-feed` calls `.github/workflows/linux-feed.yaml` (see the feed below). The notes end, below the changelog, with the macOS quarantine note and the Linux feed note linking the README's `#linux` section. release-please matches the latest release by exact manifest version string. The notes step builds a trust header above the changelog with `.github/scripts/New-TrustHeader.ps1`: a row of linked badges (Get it from Microsoft to the Store listing, CodeQL to its workflow runs, ClamAV to `virus-scan-report.html`, the Windows App Certification Kit result to `certification-report.html`, the commit, the workflow run and the privacy policy), then bullet lines for the Store's certification, the open-source commit and run that built the release, code analysis (`codeql.yaml`, C# buildless and Actions, `security-extended`, on push, pull request and weekly), the virus scan with a link to its report, the certification kit result and `PRIVACY.md`. `virus-scan` runs on `ubuntu-latest` whenever `build-msix` succeeds, a dispatch included, through `.github/scripts/Invoke-VirusScan.ps1`: it scans the MSIX, the `.msixupload`, the MSI and, on a release run, the `desktop-*` assets with the size limits raised and an exceeded limit counted as a detection, writes a self-contained `virus-scan-report.html` (the ClamAV engine and signature database version and date, every file's SHA-256, size and result, the limits and the run link), and fails on a detection or an unscanned file; a failure skips `release`, and the Store jobs do not wait on it. `certify` (`windows-latest`) runs `.github/scripts/Invoke-AppCert.ps1` on the MSIX: it signs a copy with a throwaway certificate whose subject is the manifest publisher, trusts it, runs `appcert.exe reset` and `appcert.exe test -appxpackagepath <msix> -reportoutputpath <xml>`, and writes a self-contained `certification-report.html`. The result is Passed, Passed with warnings, Failed or Not run with the reason, and the job never fails and never blocks the release. The Settings page's About group links to `PRIVACY.md`, which is kept in step with what the app reads, stores and sends. Pull requests run lint and tests only; nothing is built for the release PR beyond that. The `release: published` trigger is gone, since nothing downstream listens.

`.github/workflows/desktop-preview.yaml` (Desktop Preview) builds the app only on a manual `workflow_dispatch` (`gh workflow run desktop-preview.yaml --ref main`), with `AVALONIA_TELEMETRY_OPTOUT` set, so the Linux, macOS and Windows zip pre-releases come from `main` when one is wanted. Its `version` job reads the next release version the way `build.yaml`'s "Read version" step does (the open release-please PR's `release X.Y.Z` title, else `version.txt` with its patch plus 1, `0.24.1` while `version.txt` is `0.24.0` and no release PR is open), so a preview sorts above the last release and below the one it leads to. The Windows zip, Linux and macOS builds and their smokes are the `desktop` job, a call of `.github/workflows/desktop-builds.yaml` with `version` the next version, `display-version` `<next>-preview.<run number>` and `preview: true`, the same reusable workflow `build.yaml` calls for a release, so the two never differ; its first step fails when the display version is not `<version>-preview.<n>` for a preview or `<version>` for a release, since the zip's build name and every build's update channel are read from it. Every build passes `-p:GitHubRelease=true` and that `StoreDisplayVersion`, so the version label shows the preview number, the update source follows `AppUpdateSources.Resolve` (`ReleasePage` for the zip on Windows, Linux and macOS, because the Windows job also passes `-p:PortableZip=true`; `AppUpdateSourceTests`), and the build name is `preview` for the Windows zip, `linux` on Linux and `macos` on macOS. The Windows job publishes `win-x64` as one self-contained exe (`PublishSingleFile`, `IncludeNativeLibrariesForSelfExtract`, `EnableCompressionInSingleFile`) named `Steward.App.exe` by the Windows publish rename, fails when a DLL is left beside it, signs it when `SIGNING_CERTIFICATE` and `SIGNING_CERT_THUMBPRINT` are set, and ships it as `Steward.exe` in `Steward-<version>-win-x64.zip` with the font licence texts in `licences/`: OFL 1.1 and MIT require the licence with each copy, and a resource inside the exe is not one the user can read. The exe was 59.6 MB on 16 Oct 2026 and ran under Wine 11 from a fresh data folder to the sign-in gate, extracting `av_libglesv2.dll`, `libHarfBuzzSharp.dll` and `libSkiaSharp.dll` to `%TEMP%\.net\Steward\<hash>` on first start. The Linux job publishes `linux-x64` and `linux-arm64` with `-p:EnableWindowsTargeting=true` and builds a .deb and an .rpm of each with nfpm 2.47.0 (`packaging/linux/nfpm.yaml`; the tarball is checked against its SHA-256): the publish folder goes to `/opt/steward`, `/usr/bin/steward` links to `/opt/steward/Steward.Desktop`, `steward.desktop` (`StartupWMClass=Steward`, `Categories=Game;`) to `/usr/share/applications`, the PNG icons to `hicolor` at 16, 24, 32, 48 and 256px and the licence texts to `/usr/share/doc/steward`, and `postinstall.sh` (also the post-remove script) refreshes the desktop database and the icon cache. The x64 .deb is then installed into a clean `ubuntu:24.04` container, since `ubuntu-latest` already carries every library it depends on, and must run 10 seconds under `xvfb-run`; the x64 .rpm is installed in a `fedora:44` container (`rpm --import packaging/linux/steward.asc`, `rpm --checksig`, `dnf install`) and must run 15 seconds under `xvfb-run` with a `starting (linux,` log line. Verified 16 Oct 2026 in WSL Ubuntu 24.04 from `git archive HEAD`: `apt-get install` of the .deb resolved its dependencies, `/usr/bin/steward` started under Xvfb as a fresh user on the sign-in gate with `WM_CLASS` `steward`, `Steward` and a `steward-linux-*` log, `xdg-mime query default x-scheme-handler/curseforge` answered `steward.desktop` after the post-install `update-desktop-database`, `dpkg -r` removed every file and the mime entry, and `rpm -qRp` listed the Fedora dependency names. The macOS job publishes `osx-arm64` and `osx-x64` into `Steward.app` (`packaging/macos/Info.plist`, the version stamped with `plutil`, an `.icns` built from `Steward-256.png`, and an ad-hoc signature, since Apple silicon runs no unsigned Mach-O) inside a `.dmg`; the builds are not notarised, and the release notes say how to clear the quarantine flag. NuGet restore gets three attempts in each publish, as in `build.yaml`. Launch smoke jobs run the published artifacts and gate `pre-release`, so a build that cannot start is never published. The Windows and macOS smokes launch the app 21 times in sequence: once with no switch, then once per preview switch (`--banners-preview`, `--update-progress-preview`, `--client-outdated-preview`, `--forever-install-preview`, `--live-preview=reconnecting` and `--guides-preview=` with each of `current`, `downloading`, `written`, `failed`, `newer`, `unfinished`, `expired`, `none`, `loading`, `signin`, `signin-error`, `signin-busy`, `mfa`, `mfa-error` and `mfa-busy`), each on a deleted data folder, so every launch starts fresh and writes its own log; each launch waits for the window, captures the screen 5 seconds later, checks the process is still running, stops it and waits for it to exit before the next, since a launch while the previous instance is still running hands over to it and exits. A launch fails on an early exit, no window within 60 seconds or no startup line in its log, and the job fails after the last launch when any did. `windows-smoke` (`windows-latest`) unzips the win-x64 zip, starts `Steward.exe` on the runner's empty profile, waits for its `MainWindowHandle` and captures the screen with `Graphics.CopyFromScreen`. `macos-smoke` runs on `macos-26` (arm64) and `macos-26-intel` (x64; `macos-13` is retired and the app needs macOS 15): it attaches the dmg, copies `Steward.app` to a temporary Applications folder, clears the quarantine flag, records `codesign --verify --deep --strict`, starts `Contents/MacOS/Steward.Desktop` under the runner's own (fresh) home, since with `HOME` pointed at a temporary folder (16 Oct 2026) the app wrote no log under it, waits for a layer-0 window of that process through `CGWindowListCopyWindowInfo` (a small Swift program compiled once in the step) and captures it with `screencapture -x`. The x64 Linux .deb smoke runs Steward 15 seconds under `xvfb-run` at 1280x800 and captures the root window with ImageMagick's `import`; that screenshot is uploaded as `login-screen-linux-x64` and the macOS default launch's as `login-screen-macos-<arch>`. Each smoke uploads `smoke-<os>-<arch>` (the screenshots, `<os>-<arch>-<launch>.png` on Windows and macOS, stdout where captured, the app's `logs` folder per launch, and on macOS `codesign.txt`) and fails when no log file holds the `INF Steward.Desktop.App: Steward <version> starting (<build name>, <OS>, <arch>)` line `App.OnFrameworkInitializationCompleted` writes on every start, so a silent logging failure fails CI; the upload, the `desktop-*` pattern of `pre-release` leaves out. `windows-msix` (`windows-latest`) builds the Store-identity package with `scripts/Build-DesktopMsix.ps1` (version `<major>.<minor>.<run number>.0` from this workflow's own run counter, so it is a test package and not a valid update of the live Store build) and uploads the unsigned `.msix` and `.msixupload` as `msix-test-x64`, outside the `desktop-*` pattern, so `pre-release` attaches neither: both release mirrors take only an asset ending `.msi` (`GitHubMirror.PackageAsset`'s `EndsWith` in steward-server and `endswith($suffix)` in `hoobio/addons`' `mirror-github-releases.sh`, read 16 Oct 2026), so neither file would be picked. It then signs a copy with a self-signed certificate whose subject is the manifest's `Publisher`, made in the job and trusted in `LocalMachine\TrustedPeople`, installs it with `Add-AppxPackage`, checks through `Get-AppxPackageManifest` that the `curseforge` protocol and the `StewardStartup` task are registered, launches it through `shell:AppsFolder\<PFN>!App`, waits for a `Steward.App` window from the package's install folder and the `starting (store,` line in the real or the virtualised log folder, captures the screen, starts `curseforge://install?addonId=1&fileId=1` and waits for the running app to log `CurseForge link received: mod 1, file 1` (or the ignore line), captures again, then stops the app, removes the package and both certificates, runs the certification kit and uploads `certification-report`, and uploads `smoke-windows-msix` (screenshots and both log folders); it gates `pre-release`. `windows-msi` (`windows-latest`) publishes and builds the MSI as `build.yaml` does and runs `.github/scripts/Test-MsiUpgrade.ps1`: it installs the latest GitHub release's MSI (the WinUI build until a release carries this one), sets the Run value to its `Steward.App.exe --tray`, upgrades to the new MSI and checks a new `Steward.App.exe` window from `%LocalAppData%\Steward`, one Steward entry in Apps, no `Microsoft.WinUI.dll` left, the Run value's file still existing, the Start menu shortcut targeting `Steward.App.exe` and a `starting (msi,` log line. It gates `pre-release` and attaches nothing. A `virus-scan` job runs `Invoke-VirusScan.ps1` over every pre-release asset (the win zip, .deb, .rpm and .dmg) and gates `pre-release`. The `pre-release` job creates the draft release `desktop-preview-<run number>` with every asset plus `virus-scan-report.html` and `certification-report.html`, since a published immutable release takes no asset, publishes it as a pre-release that is never Latest, and deletes every `desktop-preview-*` release but the newest 3 with its tag, since both release mirrors read only the newest 20 releases and older previews would push the latest MSI release off that page. The pre-release body opens with the same trust header as a release (`New-TrustHeader.ps1`, the certification result from the `windows-msix` job), followed by the Windows, macOS quarantine and Linux feed notes.

The Linux releases and previews are also served as a signed package feed on GitHub Pages, `https://hoobio.github.io/steward-companion/` (build type `workflow`, no `gh-pages` branch; the `github-pages` environment allows `main` to deploy). nfpm signs each `.rpm` with the Steward Linux packages key (`rpm.signature` in `nfpm.yaml`, key id `E6ED105810B41C42`, the primary key since it has no subkey); the `.deb` files are unsigned, and apt verifies the signed `InRelease` instead. The feed is `.github/workflows/linux-feed.yaml`, a reusable workflow called by `desktop-preview.yaml` after `pre-release` and by `build.yaml` after `release`, with job-level `concurrency` `linux-feed` (not cancelled in progress), so the deploys of a release merge, which runs both workflows, take turns and the last one holds the full state. Every deploy rebuilds both channels from the release list: `packaging/linux/build-feed.sh <site> <version>` reads `repos/<repo>/releases?per_page=100` through `gh api`, keeps the non-draft releases with a `.deb` or `.rpm` asset, and downloads the `.deb` and `.rpm` assets of the newest 3 that are not pre-releases (`stable`) and the newest 3 `desktop-preview-*` pre-releases (`preview`, the kept previews after the prune). `/apt/` is a Debian repo with suites `stable` and `preview`, component `main` and architectures amd64 and arm64, built with `apt-ftparchive` (each `.deb` is copied as `<package>_<version>_<arch>.deb`, into `pool/stable` for a release and `pool/main` for a preview, since `apt-ftparchive --arch` selects by that file name; `stable` lists `pool/stable` and `preview` the whole pool) and each suite signed as `InRelease` and `Release.gpg`; `/rpm/stable/<x86_64|aarch64>/` holds the release `.rpm` files and `/rpm/preview/<x86_64|aarch64>/` the previews and the releases, each with `createrepo_c` metadata and a detached `repodata/repomd.xml.asc`. The `preview` channel carries the releases so that a preview install upgrades to the next release from its own source, which is the only source the in-app apt and dnf upgrade refreshes. `/steward.asc`, `/steward.gpg` (dearmored, for `signed-by`), `/steward.repo` (`[steward]`, `rpm/stable`) and `/steward-preview.repo` (`[steward-preview]`, `rpm/preview`, the content `steward.repo` had before 0.24.1, which existing installs keep as their local copy) sit at the root, both with `gpgcheck=1` and `repo_gpgcheck=1`. The script skips an unsigned `.rpm` from an older build with a warning, fails when an `.rpm` named `Steward-<version>-linux-*` is unsigned, and fails when the `preview` suite or repo has no package for an architecture; `stable` may be empty (an empty signed suite and empty rpm metadata), as it is until a release carries Linux packages, since v0.24.0 attached none.
