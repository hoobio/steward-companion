# WoW install discovery

`WowInstalls` walks `.flavor.info` (product code) joined against the root `.build.info` (product to version) to find each flavour without a hardcoded product-to-folder map. The Blizzard registry key (`HKLM\...\World of Warcraft`) is not used as a discovery root by itself: on the dev machine it is hijacked by an unrelated Ascension install, so it is one candidate root among several, never the only one trusted.

The candidate roots differ per OS. On Windows they are the registry `InstallPath` and `World of Warcraft`, `Program Files\World of Warcraft` and `Program Files (x86)\World of Warcraft` on every fixed drive. On macOS they are `/Applications/World of Warcraft` and `~/Applications/World of Warcraft`, then the same drive scan. On Linux WoW runs only through Wine, so `WinePrefixes.WowRoots` (Core) adds `drive_c/Program Files (x86)/World of Warcraft` and `drive_c/Program Files/World of Warcraft`, each folder name matched ignoring case, in every one of these prefixes: `$WINEPREFIX` and `~/.wine` (Wine's default); the `prefix:` value of each Lutris game config in `$XDG_CONFIG_HOME/lutris/games/*.yml`, `$XDG_DATA_HOME/lutris/games/*.yml` (Lutris falls back to the data folder when the config one is missing) and the Flatpak `~/.var/app/net.lutris.Lutris/{config,data}/lutris/games/*.yml`; each folder one level under `~/Games` (where Lutris installs `battlenet` by default, an unconfirmed default), `~/Games/Heroic/Prefixes/default`, `~/Faugus`, `$XDG_DATA_HOME/bottles/bottles` and the Flatpak `~/.var/app/com.usebottles.bottles/data/bottles/bottles`; and `steamapps/compatdata/*/pfx` under `~/.steam/steam`, `$XDG_DATA_HOME/Steam` and the Flatpak Steam's `data/Steam` and `.local/share/Steam`. Nothing below those levels is searched. On Linux a flavour folder's `Interface/AddOns` is also matched ignoring case (`WowInstalls.AddOnsPath`, through `WinePrefixes.FindIgnoringCase`), both to accept the flavour folder and as the install's `AddOnsPath`, since a Wine prefix keeps whatever case the copy or tool wrote; with no such folder yet the path is the plain `Interface/AddOns`. Confirmed from each project's source or docs: Wine's default, the Lutris config folders and its wine runner's `game_config.get("prefix")`, the native Bottles folder, `~/Games/Heroic/Prefixes/default`, `~/Faugus` and the Flatpak Steam `data/Steam` compatdata. Unconfirmed and probed only because a miss costs nothing: the per-game folder layout under Heroic, Faugus and the Bottles Flatpak, the native Steam roots, the Flatpak Steam `.local/share/Steam` form and the macOS paths. A hand-added install takes a POSIX path as is. On 16 Oct 2026 a read-only bind of the Windows install at `~/Games/battlenet/drive_c/Program Files (x86)/World of Warcraft` in WSL showed the beta with its client version, the held live install and the beta's Local rows.

`WowClient` finds a running client per OS too. On Windows and macOS it reads `Process.MainModule` of a process named `Wow*` (on macOS also `World of Warcraft*`). On Linux the process is the Wine preloader (`comm` reads `wine`), so `WowClient.WineClients` reads `/proc/<pid>/cmdline` for the first argument whose file name is `Wow*.exe` and maps a Windows path through the process's own `WINEPREFIX`, else `STEAM_COMPAT_DATA_PATH/pfx`, else `$HOME/.wine` (`WinePrefixes.ToUnixPath`: `C:` to `drive_c`, `Z:` to `/`, other letters through `dosdevices`), falling back to `/proc/<pid>/cwd`; verified 16 Oct 2026 with Wine 11.0, where the argument was `C:\Program Files (x86)\World of Warcraft\_forever_\Wow.exe` and `WaitForExitAsync` returned for the non-child process. On Linux `AddonManagerApps` reads `$XDG_CONFIG_HOME/autostart/*.desktop` (skipping `Hidden=true` and `X-GNOME-Autostart-enabled=false`, and requiring the `Exec` file to exist) and each process's first argument and `APPIMAGE` variable, comparing names with the version, `.AppImage`, case and hyphens removed (`AddonManagerApps.AppKey`), so `WowUp-CF-2.24.0.AppImage` is WowUp-CF and never WowUp (WowUp's AppImage asset name and its `auto-launch` autostart are from its source; the running process names of CurseForge, WowUp and WowUp-CF on Linux are not confirmed); macOS checks running processes only. The "Open Battle.net" button runs `BattleNet.Launcher` (Core): the `battlenet:` handler's exe on Windows, `/Applications/Battle.net.app` on macOS (unconfirmed path), and `lutris:rungame/battlenet` on Linux when a Lutris `battlenet-<id>.yml` exists, which `xdg-open` hands to Lutris's `x-scheme-handler/lutris` (the button was seen on 16 Oct 2026; the launch itself was not run); with none it is hidden.

Discovery is filtered to `SupportedProducts` in `appsettings.json`, a product code to display name map. It holds the live client `wowf` (`_forever_`, "World of Warcraft: Forever", `Wow.exe`) and the beta `wow_classic_beta` (`_classic_beta_`), both at interface 16001 and both mapped to CurseForge version type 88568, and the other clients: `wow` (retail, `_retail_`, version type 517), `wow_classic` (Mists of Pandaria Classic, `_classic_`, 79434), `wow_classic_era` (`_classic_era_`, 67408) and `wow_anniversary` (`_anniversary_`, 73246), each with an icon in `Assets/Products`. A steward-server product entry (see Products) may rename a code already in `SupportedProducts` and nothing else, so server data never adds a client to discovery; the cached names apply before the first discovery, and a changed fetch renames the installs in place (`WowInstallViewModel.RefreshProduct`: the picker, the flyout, the Settings installs, the game version options and `WowInstall.DisplayName`). The product codes come from each flavour folder's `.flavor.info` (read 24 Oct 2026). PTRs are not listed, since a PTR can run another game version than its product code suggests (the era PTR ran 2.5.6). `ForeverLaunch.IsForever` is true for `wowf` and `wow_classic_beta` only. An install of another client gets CurseForge management (Local rows, adopt, Get addons, recorded CurseForge addons) and the catalogue rows whose `products` name it (today the RestedXP and Steward: Guides rows), and no sync of any kind; `docs/forever-release.md` lists every value and what the beta's retirement touches. From 21 Oct 2026 (`ForeverLaunch.Date`, local date) `MainViewModel.EnsureSelection` moves a selection still on a beta install to a present `wowf` install once (`ForeverLaunch.MoveFromBeta`, recorded as `forever_selection_moved` in `state.json`), so a user who picks the beta again afterwards stays on it.

While a beta install is present and no live install is found, a dismissible local banner, "Install World of Warcraft: Forever" (`dismissed_banners` key `forever-install`), points at the Battle.net app, where the live client is listed as "Stress Test". Its "Open Battle.net" action starts the exe named by the `battlenet:` protocol handler (`HKCR\battlenet\shell\open\command`, so a non-default install location is found), since a `battlenet://` link leaves a tray-minimised Battle.net hidden; with no handler or no exe at that path the banner has no button. `--forever-install-preview` shows the banner whatever the installs, and a dismissal in it records nothing. A detected live install always shows, beta or no beta. The Addons page header shows "Sync from beta" while the live install is selected and a beta install is present, which opens the copy wizard (`MainWindow.ShowForeverCopyAsync` through `AppDialogs`) with Sync and Cancel. Sync runs `ForeverCopy.Sync`, a newer-wins sync that never deletes anything on the live install: a beta AddOns folder missing on live is copied whole (staged as `<Folder>.steward-copy` and moved into place), a folder on both that Steward does not manage on live (not a configured or catalogue folder, not StewardGuides, not a recorded CurseForge folder or a folder in any live install record) is updated file by file where the live file is missing or has an older `LastWriteTimeUtc`, and managed folders are left to Steward's own updates. `WTF\Account` is synced the same way at account level only, through a map from each beta account folder to a live account folder (`ForeverCopy.DefaultAccountMap`, shown in the wizard as an "Forever accounts" block with one row per live account, "<account> copies from" over a combo box of "Don't copy" and the beta accounts, each labelled with up to three of its character names; a live account fed by the beta account of the same name, and a numbered live account nothing copies to, has no row). Beta account folders are all `<bnetId>#<n>`, but a live account folder can carry the player's old WoW account name (`JIMMYBOBOZ`, 22 Oct 2026), and a copy into a folder the live client never reads is lost. The default pairs folders of the same name (case-insensitive) and, when exactly one beta account and one live account are left unpaired, pairs those two, else when exactly one classic-named live folder is left unpaired, pairs it with the first unpaired beta account whose name ends `#1` (the Battle.net account's first game account); every other beta account is "Don't copy". Forever creates the classic-named folder only at the first login, so while the live install has no classic-named folder of its own, `ForeverCopy` also scans every directory beside the live flavour folder (the WoW install root, whatever its name, except the live and beta flavour folders) for a `WTF\Account` folder and offers each classic-named account found there (not `SavedVariables`, deduplicated case-insensitively, first casing kept) as a live account with `FoundIn` set to the directory name. A candidate takes part in the default pairing exactly as a free classic-named live folder does and is never stale, its row reads "<account> (from classic) copies from" (`FoundIn` without underscores), the copy creates `WTF\Account\<name>` on live with its `cache.md5`, and the migration banner ignores candidates. That Forever uses the same classic account name as the other game versions is assumed from one player (22 Oct 2026) and not confirmed. A live `<digits>#<digits>` folder with no realm folder (no subfolder besides `SavedVariables`) beside a folder named after an old WoW account is stale, one an earlier Steward copy created and the client never reads (`ForeverCopy.IsLegacyAccountName`): it stays in the live account list but is never a same-name match or a free folder for the pairing, so the legacy folder is the default, and nothing on live is deleted. `ForeverCopy.NeedsAccountMigration` is true when a stale folder shares its name with a beta account; while it holds for a live install with a present beta, a dismissible local banner, "Choose a beta account for your Forever settings" (key `forever-account-names|{live path}` in `dismissed_banners`), names the first legacy folder and offers "Sync from beta". It clears on dismissal and after a Sync whose account map targets a legacy-named folder and copies at least one saved variable or settings file; `MainViewModel.ApplyForeverBanners` re-evaluates it on startup and Refresh. Only live account folders that exist, and the classic-name candidates below, are targets, so with neither (Forever never logged in and no classic name beside it) both account options read "Log in to World of Warcraft: Forever once first". A live account is chosen for at most one beta account, and the plan, the copy and the `cache.md5` stamp all use the mapped live folder. The options are: "Account saved variables" (`<account>\SavedVariables\*`, `*.bak` excluded, and `Steward.lua`, which holds the beta's characters that the live install would then push as its own) and "Account settings" (`config-cache.wtf`, `bindings-cache.wtf`, `macros-cache.txt`, `tts-cache-account.txt` and `edit-mode-cache-account.txt` directly in `<account>`, offered when their contents differ, since the client rewrites them at every login, and checked by default only when one is newer on the beta); realm and character folders are never copied, since they are named after the beta's realms and characters. The client keeps each of those files' MD5 and save time in `<account>\cache.md5` (ten 24-byte slots: MD5, little-endian unix save time, 4 zero bytes, in the order config, bindings, macros, TTS, flagged, edit mode, unused, character list order, unused, unused), and at login downloads the server's copy over any file whose slot time differs from the server's save time, later or earlier, and loads the file when they are equal (`Logs\AccountData.log`, "Requesting Data Download" or "Loading Data From File"); on 22 Oct 2026 that replaced copied bindings with an empty file and the edit mode layout with the default, and a slot stamped with the current time, two hours after the server's, was downloaded over too. A copied settings file therefore gets only its slot's MD5 rewritten (`ForeverCopy.StampAccountData`), keeping the time the client last agreed with the server. "Graphics, sound and narration" merges the beta's video, sound and screen narration CVars (an allowlist in `ForeverCopy`: `graphics*`, `raidGraphics*`, `RAID*`, `Sound_*`, `Gx*`, `maxFPS*`, `shadow*`, `lodObject*`, `accessibility*`, `showScreenNarrationDialog` and named video CVars) into the live `WTF\Config.wtf` line by line, replacing a differing value in place and appending a missing one, temp then move, and leaves every other line (portal, locale, cache counters, `hwDetect`, `videoOptionsVersion`) as it is. Its count is the CVars whose value differs, since the client rewrites `Config.wtf` on every exit and its date says nothing, and it starts checked only when the beta's file is newer. With no live `Config.wtf` it is disabled with "Start Forever once first" and nothing is written, since a file of graphics lines alone lacks the client's own detection markers. Each option shows its count, computed off the UI thread before the dialog opens, and an option with nothing newer is disabled and unchecked. The dialog's CheckBox glyphs are re-centred against their two-line labels in `Loaded`, since the template top-aligns them. The copy refuses while either client is running or a row on either install is busy, checked before the plan and again before the copy, which holds `AddonUpdater.AddOnsWriteLock` for the AddOns part. Afterwards `ForeverCopy.CarryState` re-keys the beta's state to the live path for whatever is now on the live install, never replacing a live key: CurseForge records whose primary folder is on live and whose version type matches the live install's mapping, and the `installs`, `ignored_addons` and `kept_local_addons` keys for those addons and folders. `channels` and `hidden_addons` are global and need nothing; the other per-install keys (`restedxp_guides*`, `guild_roster_sync`, `person_avatars`, `character_sync*`, `install_labels`, `install_products`, `missing_since`, `lost_access`) describe that install's own disk or server state and are not carried. Each failed file is logged and counted, and the rest continue; the result shows as a toast over the page for 6 seconds (`MainViewModel.ShowToast`), "Synced from the beta: {n} addons copied, {m} updated, {k} saved variable files, {j} game settings files.", leaving out the zero parts.
