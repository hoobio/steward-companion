# Roster and character sync in the app

`docs/design/roster-sync.md` is the agreed contract between this app, steward-server and the Steward addon, and it is the source of truth for how the three interact. Read it before touching anything that crosses a repo boundary. It carries the direction of travel, the identity and linking rules, the steward-server endpoints in use, the confirmed Forever client API facts, and the per-repo branch rules.

The short version. steward-server holds the people, the addon holds the characters, and this app is the only party that can talk to both. steward-server defines the whole `StewardSync.lua` payload and serves it as one JSON document, `GET /api/addons/sync/{guild_id}`; `AdminMe.Guilds` supplies the guild id. `StewardGuildSyncApi.PullAsync` fetches it through `StewardClient.GetSyncDocumentAsync`, `SyncDocument` converts it to Lua with no knowledge of the keys, and `StewardGuildSyncApi.LoadImagesAsync` loads the images it names. `docs/design/roster-sync.md` has the converter rules, the file overlay, sign-out and the triggers. `StewardGuildSyncApi` is the only implementation and is registered directly, with no interface between it and its callers.

Pulls are event-driven. While signed in, a guild selected and the `steward` feature held (the same gate as the pull it drives), `MainViewModel` keeps one connection to `GET /api/admin/{guild_id}/events` (`StewardClient.StreamGuildEventsAsync`, a `text/event-stream` read line by line by `ServerSentEventReader` in Core), restarted on a guild switch and stopped on sign-out or loss of `steward`, and kept reconnecting while the API is unreachable. `ready` and each `roster-changed`, `members-changed` or `characters-changed` event queue `SyncFileAsync` (`QueueGuildPull`), debounced 2 seconds and never overlapping a pull already queued from the stream. A dropped or ended connection reconnects after 1, 2, 4, 8 and 16 seconds, then every 30, each plus up to 10 seconds of jitter (`TransientHttp.StreamBackoff`), reset only when the dropped stream had lived at least 2 minutes; neither server honours `Last-Event-ID`, so a reconnect resumes through the full pull that `ready` already queues; 60 seconds with no line at all, pings included, counts as a dropped connection. A 404 means the server in front of the app predates the route, and the stream stays off for the rest of the run; a 403 stops it for that guild; a 401 signs out as everywhere else. None of these touch the error bar or `StatusMessage`. The 1-minute background pass keeps the character push as the fallback: every pass while the stream is not connected, and at most every 15 minutes (`_lastGuildSync`, wall-clock) while it has received `ready` and is alive. The sync document is pulled on the background pass at most every 15 minutes (`_lastDirectorySync`), never on every pass. This guild stream is scoped to `steward` holders and to roster/member/character changes only; the separate access-change stream every signed-in user gets, whatever its role, is under Auth, and its `syncChanged` frame queues the same pull for every user.

The existing `RosterMember` record is the WoW guild roster the addon observes, not the steward-server roster of people. The two are different datasets and the names are deliberately distinct.

## Character sync

`docs/design/character-sync.md` is the agreed contract for this and the source of truth. `StewardSavedVariables` reads `StewardDB.characters` (or, when the addon packed it at logout, the `packedCharacters` string through `PackedSavedVariables.Decode`: base64, then DEFLATE, read as zlib or gzip when the bytes carry that header, then CBOR), `professions` and `gear` (nested under each `characters[guid]` from 31 Oct 2026, top-level before; both are read), `catalogue` and `guildRanks` through the `LuaSavedVariables` parser into `CharacterObservation`, `CharacterProfessions`, `ProfessionCatalogue` and `GuildRanks` records. `realm` on a character and on `guildRanks` is the guild's realm as a compact key (`ClassicBetaPvP2`), and the optional `realmName` display name (`CharacterObservation.RealmName`, `GuildRanks.RealmName`, JSON `realmName`, omitted when null) is forwarded on `CharacterSyncEntry` and `GuildRanksSync` and included in the push-gate fingerprint like `realm`. While a `sync` feature is held, `MainViewModel` gzip-compresses each install's batch and posts it to `POST /api/sync/{guild_id}/characters` (steward-sync's canonical prefix; builds before it posted to `/api/guild/{guild_id}/characters/sync`, still served as a temporary alias) through `StewardClient`, gated by a fingerprint over the canonical data with `observedAt` and `scannedAt` stripped out; the signed `fp` values cover those timestamps, so a `/reload` that restamps them still pushes. Push records live in `%LocalAppData%\Steward\character_sync.json`, a file separate from `state.json` because an older Store build rewrote `state.json` without the sync key, verified 26 Sep 2026. Each `/api/me` guild entry may carry `sync_guild_names` (`AdminGuild.SyncGuildNames`), the WoW guild names that Discord guild accepts. One push routes each install's characters to every Discord guild they belong to rather than only the selected one: `CharacterPushRouting.Route` (Core, via `MainViewModel.CharacterRoutes`) takes every `/api/me` guild whose own resolved features (`StewardClient.ResolveGuildFeatures`) hold `sync`, in that guild's own mode (officer with `steward`, professions-only without), and for each one whose `sync_guild_names` is a non-empty list runs `CharacterSyncMapping.Scope`, which keeps characters whose trimmed `guild` matches a listed name case-insensitively, keeps `guildRanks` only for an officer guild listing its guild, and fingerprints only what it kept. A WoW guild on several lists goes to each, and a character on no list, a guildless one included, is skipped. The Sync page, its "Your characters" row and Sync now show whenever any guild can be pushed to (`MainViewModel.CanPushCharacters`), not only when the selected guild holds `sync`, and the row's last push time and error cover only the guilds the install's characters route to. A `/api/me` recheck that finds any guild's `sync_guild_names` or push mode changed queues a push and reloads the Sync page. When the selected guild's entry carries no `sync_guild_names` at all (an older server), everything goes to the selected guild only, as before. Every routed guild is pushed in turn inside the one in-flight push; a 403, 404 or 429 for one guild is handled as before for that guild and the rest still run, a 401 signs out, and the directory pull that follows a post stays on the selected guild. Push records, batch ids, per-character outcomes and the catalogue fingerprint are keyed by Discord guild id plus install (`AppStateStore.CharacterSyncKey`), so each guild's gate and diff are independent. A rejection reading `guild not allowed` (`CharacterSyncRejectionCopy.GuildNotAllowedReason`) counts as skipped, never as rejected (`CharacterPushRouting.StateOf`). A push runs on startup, on Refresh, from Sync now, whenever an install's `WTF\Account\**\Steward.lua` is written (the Sync page's `SavedVariablesWatcher`, debounced 1.5 seconds, calls `MainViewModel.SavedVariablesWrittenAsync`, which pushes and then reloads the page), and on the background pass as described under Roster sync. Pushes never overlap: a request made while one is in flight runs once more after it finishes, forced if any queued request was.
A `sync` holder with no officer seat (`MainViewModel.IsProfessionsOnlySync`) gets a narrower push: `CharacterSyncMapping.FilterToProfessionsOnly` keeps only the characters that have a `StewardDB.professions` entry, the request's `guildRanks` is left null, and the push is a per-character diff (`ProfessionsPushSelection` in Core): each character's professions fingerprint (`CharacterSyncMapping.ProfessionsFingerprint`, `observedAt`/`scannedAt` excluded) is recorded with its outcome in `character_sync.json`, and a push sends only characters whose fingerprint differs from the recorded one, plus the catalogue only when its fingerprint differs from the last accepted one. A rejected character is resent only when its data changes or, for a "not linked to you" rejection, when the pulled member roster now links that guid to the signed-in user; with nothing to send no request is made, and Sync now sends every character. Only the selected guild's push resends a "not linked to you" rejection on its own when the roster changes, since the roster pull is the selected guild's; another guild's resends when the character's data changes or on Sync now, and its rejection reads with the plain copy rather than the roster-based text. The catalogue itself still rides along, since a seatless caller's captured recipes may be new to the guild: steward-server inserts only the catalogue rows that do not already exist for such a caller and never modifies an existing row. Roster fields still ride along on each sent `CharacterSyncEntry`, since the server's validation requires them; steward-server ignores them for a seatless `sync` holder along with the guild ranks, and keeps professions only for guids linked to that user. No separate `professions` flag exists. The Sync page has one layout for an officer and a seatless `sync` holder alike; only the data behind each row differs. `SyncViewModel` builds, for the selected install, a "Guild roster" row (the selected guild's `roster` feature, or `steward`, where it also covers the admin roster, members and Discord pull) and a "Guild professions" row (`professions`, or `steward`, where it also covers the admin recipe catalogue), both pulls whose tick means `StewardSync.lua` on disk carries the last written fingerprint, then a "Your characters" push row that expands to the per-character states, collapsed by default and remembered per install for the session. The row reads "{n} characters synced to {m} servers" (singular forms for one), or "{n} characters for {m} servers, sending shortly" while any is unsent, where n counts distinct characters routed to at least one guild and m the guilds routed to; with no character on any guild's list it reads "No characters on a server's guild list". Across routed guilds a character is synced when every guild it went to accepted it, pending when any is pending, and rejected only for a real rejection (`CharacterPushRouting.Combine`). The expanded list shows the characters routed in professions-only mode with each one's professions-fingerprint state, and otherwise only the signed-in user's own characters, matched by Discord link rather than by name (`CharacterSyncMapping.IsOwnCharacter`: the pulled roster pin `DirectoryCharacter.LinkedUserId` for that guid when a roster pull is available, else the character's own `StewardDB.characters[guid].linkedUserId`, compared against the signed-in user's id), while the row's own count and status cover every routed character; an officer with no own characters on an install sees "No characters of yours on this install yet." in the expanded row. Loot and attendance have no rows: nothing syncs them yet. The generated-file card shows for both, since a non-officer's `StewardSync.lua` still holds `me` and whatever the server put in their document. The row counts come from the last document (`MainViewModel.LastDirectory`, described under Keys the app reads in `docs/design/roster-sync.md`). The saved-variables watcher and Sync now still push on the same triggers as the officer path.

`StewardDB.guildEvents` (optional, absent or empty when the addon saw no invite) is a list of `{ inviter, invitee, at }` guild invites, `at` in unix seconds. `StewardSavedVariables` maps it into `SavedVariablesSnapshot.GuildInvites`: entries missing a name or `at` count as skipped, identical entries across files collapse, and the list is ordered by `at`. The officer push carries it as `guildInvites: [{ inviter, invitee, at }]` on the characters request, only on a route that also carries `guildRanks` (so only for an officer server listing the guild), omitted when empty and never sent on the professions-only push. It is part of the push-gate fingerprint, so a new invite triggers a push. The returned `StewardSync.lua` `invites` field (invitee to `{ by, at }`, officers only, rendered by steward-server) needs no app code: `StewardSyncFile` writes the server's entries verbatim and its fingerprint hashes them as they come.

Until the Forever launch (`ForeverSchedule.Launch`), a live `wowf` install reads no Steward saved variables (`ForeverLaunch.HasNoCharacters`, applied by `MainViewModel.ReadStewardSavedVariables` for the push, the Sync page and the routed-guild count), since nobody can play that client yet and any `Steward.lua` there is a copy of the beta's; its Sync page shows "World of Warcraft: Forever is not out yet" (`SyncViewModel.NotReleasedVisibility`) in place of the cards, the addon-missing and never-exported states and the journey row, and the install pushes no characters and uploads no journeys. An install of a client other than Forever never reads Steward saved variables (`ForeverLaunch.ReadsCharacters`, which is false unless `ForeverLaunch.IsForever`), so it pushes no characters and uploads no journeys, even when the Steward folder was copied there, and `GuildRosterSync.WriteIfChanged` writes no `StewardSync.lua` or avatar files to it. Until the launch no install uploads journeys at all (`UploadJourneysAsync`), since steward-server stores none before it, and after it a journey is uploaded only with an hour of active play and 3 or more subzones (`JourneyQuality.IsWorthUploading`); one below that is recorded as `too_short` and looked at again when its file changes. Packed chunks that end before the launch are never sent (`JourneyFile.FromLaunch`; a file left with no rows is recorded as `too_short`), since a character reusing a beta namesake's folder carries them and steward-server drops them anyway. steward-server answers each stored upload with the SHA-256 of every chunk's decoded `data` and of the stored file (`chunks` and `sha256`, kept per file in `journey_uploads`). While every listed chunk is still in the file, the next upload leaves them all out and puts one `{ ["ref"] = "<stored file sha>" }` in `packed` with `X-Journey-Refs` (`JourneyFile.WithRef`), which steward-server replaces with that stored file's chunks, looked up only among that user's current files for the character. A file missing a listed chunk (a logger merge or `/route clear`) goes whole, since the server would otherwise bring the chunk back. A `resend` answer means it no longer holds that file, so the list is dropped and the next pass sends the whole file. A server that sends no `chunks` gets whole files, and the file is re-serialised as Latin1 only when a chunk is dropped or replaced. An install with several WoW accounts has one `Steward.lua` per account: a duplicate guid across files resolves to the newest `observedAt`, and a guild's character observations (other players seen in a guild scan) are dropped from any file whose own scan of that guild (`guildRanks.observedAt` for that guild, else its newest character `observedAt`; guild matched by name plus the realm id in its characters' guids (`Player-<realmId>-<hex>`, stable across addon realm spellings such as `Classic Beta PvP` and `ClassicBetaPvP2`), falling back to the compact realm key or `realmName` when no guid carries one) is more than 24 hours older than the newest scan of it in any file, so a stale account never resends roster rows the server skips. A character with a `professions` or `gear` entry in that file is kept, as is every character of a guild only one file has seen (`StewardSavedVariables.Read`).

`StewardDB.professions[guid].fp` is a keyed integrity fingerprint the addon computes in game (every sync field, timestamps included, is signed this way, and a new sync field ships with its fingerprint in the same change; see "Integrity" in `docs/design/character-sync.md` for the formats, test vectors and what is still unsigned); `StewardSavedVariables` parses it into `CharacterProfessions.Fp` and the app forwards it untouched as `professions.fp` on that character's `CharacterSyncEntry`, and left out of the push-gate fingerprint like every other `fp`, since each signs a timestamp and would otherwise push on every restamp. See "Integrity" in `docs/design/character-sync.md`. `StewardDB.catalogue[profession].fp` is the same kind of fingerprint, one per profession's catalogue entry rather than per character; `StewardSavedVariables` parses it into `ProfessionCatalogue.Fp` and it is forwarded untouched as `fp` on that profession's entry in the push's `catalogue` object, on both the officer and professions-only push, and is left out of the push-gate fingerprint the same way. `StewardDB.characters[guid].fp` (`o1`) and `StewardDB.guildRanks.fp` (`r1`) sign the roster fields and guild ranks, `observedAt` included; `StewardSavedVariables` parses them into `CharacterObservation.Fp` and `GuildRanks.Fp`, and they are forwarded untouched as `fp` on the `CharacterSyncEntry` and on `GuildRanksSync`, left out of the push-gate fingerprint like the rest. Each recipe list and the bank carry their own signature: `recipeScans[profession]` (`{scannedAt, fp}`, `p1`) beside the professions entry, parsed into `CharacterProfessions.RecipeScans`, and `bank.fp` (`k1`), parsed into `GearBank.Fp`, both forwarded untouched in the same shape. Since every version now signs its timestamp (`v3`, `p1`, `g3`, `k1`, `c3`, `o1`, `r1`), a restamp changes each `fp`, so the push gate leaves every `fp` out alongside `observedAt` and `scannedAt` (`recipeScans` and the bank's `observedAt` included), and a `/reload` that changes no data pushes nothing. A fingerprint is computed only at the moment of observation, over only what that observation read from the game, and stored data is never re-signed: the addon never fingerprints data read back from `StewardDB`, a migration or merge drops or carries a fingerprint and never recomputes one, data carried over from an earlier observation keeps the `fp` and timestamp of its own capture, and a new synced field is signed at its capture point. The app keeps to the same rule by forwarding every `fp` and the values it signs exactly as read, never recomputing, merging or normalising them. The addon also writes `addonVersion` (its TOC `## Version`) on each of those entries; `StewardSavedVariables` parses it onto the same models and it is forwarded untouched as `addonVersion` on the character, `guildRanks`, professions, gear and catalogue objects (omitted when null), left out of the push-gate fingerprint like `fp`. steward-server names it in the rejection it gives a character whose fingerprint is missing (`written by an older Steward addon (<version>); log in on this character to refresh`, shown verbatim on the Sync page) and in the mismatch DM; a missing fingerprint raises no DM.

`StewardSavedVariables.ForwardedKeys` (`talents`, `notes`, `linkSet`) lists the per-character sub-records that are forwarded as read: `StewardDB.<key>[guid]` or `StewardDB.characters[guid].<key>` becomes a JSON object on that character's push entry, with every field, `fp` and `observedAt` included, and no value is recomputed, trimmed or normalised. Text keeps its bytes (quote, backslash, `|` and UTF-8 survive), a Lua `false` stays JSON `false` (`linkSet.userId` of an unlink) and a whole number is an integer. Duplicates across account folders are ranked by `observedAt`, and `linkSet.observedAt` equals its `at`. The push-gate fingerprint drops `observedAt`, `fp` and `addonVersion` from each record, so a change to the note text, `officerNote`, `userId`, `at` or `by` pushes and a restamp does not. `notes` is the guild roster public and officer note and `linkSet` is an officer's Discord link or unlink made in game; steward-server verifies each `fp` and applies them from the officer push only (`docs/design/sync.md` in steward-server, "In-game notes and link edits"). `StewardSync.lua` carries `companion = { forwards = { ... } }` with the same list, which the addon reads to show its Link Discord button only when `linkSet` is listed.

Every signed-in user whose install has the Steward addon gets a `me` table in `StewardSync.lua`, officer or not, from the server's document. `RecheckAuthorizationAsync` queues a pull whenever the signed-in user, role or feature set of a user without `steward` changes (comparing against the values captured before that check overwrites them). `SignOutTo` is the one sign-out path (the `SignOut` command delegates to it): it rewrites the file from the last document with `SyncPayload.SignedOut`, which drops `me` and keeps the rest for `dropMe` and writes the overlay only for `clear` or when no document was pulled. `Steward.Sync.Me()`/`Steward.IsOfficer()` in `hoobio/Steward`'s `Core/Sync.lua` are the addon-side readers; `me.role` is a display gate only; it is not enforced client-side.

The server gates each part of the document on the selected guild's features, so the app calls one route whatever the user holds. The app's own reads of the directory (the people, the character links and the counts) come from `SyncDirectory`, read from the last document's `payload.directory`, `members` and `catalogue`. Each image in the document's `images` becomes `Avatar.tga` or `Avatars\<id>.tga` in the addon folder, and an `avatar` key on the matching `discord[]` or `directory.people[]` table, written only when the file exists after the write; `PersonAvatars` (Core) decides what to download and `StewardSyncFile.Write` writes and prunes the files, as `docs/design/roster-sync.md` describes. The last written URL per install and user id is `person_avatars` in `state.json`.

steward-server pins every character link (guid to Discord user id) rather than deriving it live, so an officer's re-map, unlink or reset shows up in `directory.characters[].linkedUserId` and in the top-level `links` on the next pull the same way a fresh match would. `hoobio/Steward`'s `Core/Sync.lua` reads `links` in preference to note matching. The other payload keys (`rankTargets`, `rankLocked`, `kos`, `attunements`, `gearSets` and the rest) are listed under Payload keys in `docs/design/roster-sync.md`; their content and order are the server's.
