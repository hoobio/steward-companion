# Microsoft Store

The MSIX package identity, reserved in Partner Center, is `Hoobi.Steward` (PFN `Hoobi.Steward_thayxpy3eqg0g`), publisher `CN=D74C026B-1081-4787-BDE6-0CFA2F1EDD71`, Store ID `9PBKMZFKZHKX`. `packaging/windows/Package.appxmanifest` carries that identity directly rather than a Dev/Release pair, because the Store build is release-only: there is no channel-identity stamping to do. The `desktop:StartupTask` extension (`TaskId="StewardStartup"`, `uap10:Parameters="--tray"`) covers Start with Windows for a Store install, the counterpart to the registry-based toggle the MSI build uses.

`build.yaml`'s `build-msix` job runs on a release-please release run and on a manual `workflow_dispatch` of the workflow (the tester build), never on an ordinary push, running `scripts/Build-DesktopMsix.ps1 -Identity Store -Version <the job's computed version> -StoreDisplayVersion <display-version> -PreRelease:<true on a non-release run>`, which publishes `Steward.Desktop` with `GitHubRelease=true` (and `StorePreRelease=true` for `-PreRelease`) and stages `Steward-<version>-x64.msix` and, by zipping and renaming it (the documented manual method), `Steward-<version>-Store-x64.msixupload`. The job uploads the latter as the `msixupload-x64` workflow artifact and the bare `.msix` as `msix-x64`. The MSIX is self-contained and needs no Windows App Runtime. `release` attaches both to the draft release beside the MSI. Neither is signed: the Store re-signs on submission, so the `.msix` the `release` job attaches to a release's draft carries the Store publisher and installs only through the Store or with a matching certificate. On a release run only, `build-msi` publishes an unpackaged self-contained build (`GitHubRelease=true`), wraps it with `installer/Steward.wxs` (WiX 5, per-user, the bridge MSI's `UpgradeCode`) through `build-msi-wix`, signs it when `SIGNING_CERTIFICATE` and `SIGNING_CERT_THUMBPRINT` are set, and `release` attaches it to the draft beside the MSIX before publishing, since the repo's immutable releases take no asset once published; `store-submit` never waits on the MSI or on the GitHub release. Every run stamps the manifest `<major>.<minor>.<run number>.0`, release and flight alike, and exposes it as the job's `version` output. On a release run the major.minor is `version.txt`'s own; on a non-release run it comes from the open release-please PR's title (`chore(main): release 0.12.0` gives `0.12`), falling back to `version.txt`'s major.minor when no release PR is open. The fourth part is always `0`, since the Store reserves it and requires it be `0` at build time, and every part is capped at 65535. `GITHUB_RUN_NUMBER` makes each package version strictly higher than every earlier one, release or flight, which the Store requires for a device to see it as an update: a release stamped with its plain `0.13.2.0` would sit below a tester's `0.13.248.0` flight, and the Store never downgrades. The plain release version (`version.txt`) is the job's separate `release-version` output, which `store-submit` uses to find the previous release and the changelog section; the app's own version label reads the assembly's informational version, also `version.txt`, so it shows `0.13.2` whatever the package version, except on a flight, where the "Read version" step's separate `display-version` output (the release-please PR's next full version plus `-pre.<run number>`, e.g. `0.14.1-pre.260`, falling back to `version.txt`'s version with the same suffix when no release PR is open) is stamped as a `StoreDisplayVersion` `AssemblyMetadata` and shown instead: `InstalledVersion` itself stays the plain numeric `version.txt` value on every build, since `BannerFilter.Active` parses it as a 3-part version and a `-pre` suffix would break that; the sync User-Agent instead reads `AppInfo.StoreDisplayVersion` when set, falling back to `InstalledVersion` otherwise, so steward-server's logs show the flighted `-pre` version rather than the last release's. `version.txt` itself is untouched by a non-release run. `AppInfo.IsPreRelease` reads a matching `StorePreRelease` `AssemblyMetadata`, set to `true` only on a non-release `build-msix` run (mirroring how `GitHubRelease` is set), and the window title, tray tooltip and version label append " (Pre-release)" for a flighted build the same way they append " (Development)" for a packaged non-`GitHubRelease` build and " (Debug)" for the unpackaged one (`AppInfo.BuildName == "debug"`), all through `AppInfo.BuildSuffix`. The window title and tray tooltip (`AppInfo.WindowTitle`) also append " (Linux)" while `AppInfo.IsLinux` holds: under Wine (`AppInfo.IsWine`, true when `ntdll.dll` exports `wine_get_version`) or on native Linux (`OperatingSystem.IsLinux()`); the version label does not. The package manifest's `DisplayName` stays "Steward" either way, since the Store listing name does not change per flight.

The `store-submit` job runs only when release-please cut a release on that run, in parallel with the `release` job once lint and tests and `build-msix` pass, and only when the `AZURE_CLIENT_ID` repo variable is set, using `microsoft/microsoft-store-apppublisher@v1.4` and the `msstore` CLI. The Store credentials live in the homelab Key Vault `hbicfgkvtaus01` as `msstore-tenant-id`, `msstore-client-id`, `msstore-client-secret` and `msstore-seller-id` (the client is the "Partner Center Uploads" Entra app with the Manager role), so any repo that publishes to the Store reads the same four; the job signs in through GitHub OIDC as the `github-hoobio-msstore` Entra app (repo variables `AZURE_CLIENT_ID` and `AZURE_TENANT_ID`, no subscription), which holds `Key Vault Secrets User` on those four secrets only and trusts `main` of each repo it has a federated credential for. The job masks each value, runs `msstore reconfigure`, then a delete-pending-submission, `msstore publish <msixupload> -id 9PBKMZFKZHKX --noCommit`, a release-notes and mandatory-update patch, `msstore submission publish` sequence, checking `$LASTEXITCODE` after every `msstore` call except the delete (which resets it deliberately, since a missing pending draft is not a failure). Before that delete, `scripts/Wait-StoreSubmissionClear.ps1`'s `Wait-StoreSubmissionClear` polls `msstore submission status 9PBKMZFKZHKX` every 2 minutes for up to 60 minutes while the status is `CommitStarted`, `PreProcessing`, `PendingPublication`, `Publishing` or `Release`, since a delete against a submission still in one of those refuses rather than clearing it; a `PendingCommit` draft or a submission in `Certification` is deleted straight away (a flight submission in `Certification` was refused with "cannot be deleted" on 14 Oct 2026 while the plain submission was replaced in the same run, so the delete's "cannot be deleted" answer is what the wait follows; every `msstore` call whose output is matched captures stderr with `2>&1`, since `msstore` writes its progress and errors there), the newest push replacing it (observed 28 Sep 2026, run 259: `msstore flights submission delete` printed "Submission in its current state cannot be deleted" and then a false "✅ Existing submission deleted!" anyway, because `msstore`'s delete helper only treats the Ingestion API's own "created in Partner Center" error as a real failure and reports success for every other case regardless of what the API actually did). The same helper treats "cannot be deleted" in the delete output as not deleted and goes back to waiting, and stops the job immediately with `::error::` naming the submission id (`msstore` prints `Found ... Submission with Id '<id>'`) whenever any `msstore` output says a submission "can only update, delete, and commit ... created through the API", since only a human deleting it in Partner Center clears that one. `msstore publish` itself is retried up to 3 times, 60 seconds apart and re-running the wait first, when it fails with "Error while creating submission". The patch reads the submission through `Get-StorePendingSubmission` (same script), which polls `submission get` (or `flights submission get`) every 30 seconds, up to 10 times, until it lists the uploaded `.msixupload` by `FileName`, and fails the job otherwise: on 4 Oct 2026 (0.20.2) `get` answered right after the upload with the last published submission, and patching and committing that shipped the previous release's package. The file-path form of `msstore publish` (a `.msixupload`/`.msixbundle` passed as the positional argument, not `-i <directory>`) is confirmed working: `hoobio/command-palette-bitwarden`'s `store-publish` job uses the identical `msstore publish $bundle -id $env:PRODUCT_ID --noCommit` form against a `.msixbundle` and succeeded (run 31148741706, job "Publish to Microsoft Store"). The patch goes through `msstore submission update`, not `submission updateMetadata`, because `updateMetadata` sends only availability, properties and listings (`MSStore.API/Models/UpdateMetadataRequest.cs` in `microsoft/msstore-cli`) and drops `PackageDeliveryOptions`, while `update` PUTs the whole submission. Both take their JSON inline as a positional argument with no file-input flag, so the patched submission JSON is read from disk and passed as `(Get-Content -Raw patched.json)`. Every release and flight submission sets `PackageDeliveryOptions.IsMandatoryUpdate` with `MandatoryUpdateEffectiveDate` at submission time, merged into the existing delivery options so rollout settings are kept. The Store does not enforce the flag: it only sets `StorePackageUpdate.Mandatory` for the app's own `Windows.Services.Store` code to act on. Pre-releases never reach the Store. `msstore` only updates an app that is already live in the Store, so the first submission has to be made by hand in Partner Center: submit a pre-release `.msixupload` there manually, and only publish the bridge GitHub release (the one that triggers `store-submit`) once that manual listing is live, since `store-submit` clones the live submission rather than creating the app's first one.

The "What's new in this version" listing field is filled from the being-released version's own `CHANGELOG.md` section, keeping only the Features and Bug Fixes entries and dropping every other conventional-commit type; `scripts/Get-StoreWhatsNew.ps1` strips each entry down to its plain description (scope, gitmoji and commit-hash link removed) and truncates at a bullet boundary to the Store's 1500-character `ReleaseNotes` limit, replacing the dropped entries with a closing "and N more changes" line. A version whose changelog section holds neither section returns "Minor improvements and fixes." rather than leaving the listing untouched. Every `feat` and `fix` commit therefore reaches Store users, so a commit that changes nothing a user of the installed app sees (the workflow, packaging, Store submission, the dev build) is typed `ci`, `build` or `chore`.

The listing screenshots are the PNGs in `docs/screenshots`, which the README also shows. They are captured from a Debug build started with `--screenshot`, at the default 980x720 window centred on a 1366x768 canvas (the Store's minimum) of the desktop wallpaper, and they replace the listing's screenshots through `scripts/Update-StoreScreenshots.ps1`, run locally with `AZURE_CONFIG_DIR` on the Hoobi profile. The script reads the same four `msstore-*` secrets, creates a submission from the published one through the Partner Center submission API, marks every existing `Screenshot` image `PendingDelete`, adds each PNG as `PendingUpload` with a caption from its file name, uploads the images as a zip to the submission's `fileUploadUrl` and commits it. The `msstore` CLI uploads no listing images. The script refuses to run while another submission is pending, and its submission holds the next `store-submit` until certification finishes, so it runs only after the last release's submission is published.

The `store-flight` job runs after every `build-msix` (a manual dispatch, and a release-please release run), because flight testers only ever receive flight packages and never the non-flighted submission (Partner Center's package flight ranking), so a release reaches them only as a flight too. On a release run it submits the same package `store-submit` does, built with `StorePreRelease` off, so the tester's build carries no " (Pre-release)" suffix. It runs only when both the `STORE_FLIGHT_ID` and `AZURE_CLIENT_ID` repo variables are set (the same Key Vault OIDC login, credential masking and `msstore reconfigure` steps as `store-submit`). It waits out and deletes any pending flight submission through the same `Wait-StoreSubmissionClear` helper `store-submit` uses, pointed at `msstore flights submission status/delete 9PBKMZFKZHKX <flightId>` instead of the plain `submission` form, publishes the flight build (`msstore publish <msixupload> -id 9PBKMZFKZHKX --flightId <flightId> --noCommit`, retried up to 3 times 60 seconds apart and re-running the wait first when it fails with "Error while creating flight submission"), marks it mandatory through `msstore flights submission get` and `msstore flights submission update`, and commits it (`msstore flights submission publish 9PBKMZFKZHKX <flightId>`), checking `$LASTEXITCODE` after every call except the delete. It patches no release notes. A run cancelled mid-sequence (a newer dispatch cancels an older dispatched run) leaves at worst a pending flight draft; the next run's wait-and-delete clears it before publishing again, so a flighted tester never sees a half-submitted build linger. Flight testers are a known user group managed by hand in Partner Center; this repo has no record of who is in it. The submission API only updates, deletes and commits submissions it created itself, so a draft started in Partner Center (including the empty one Partner Center makes alongside a new flight) makes the delete and `msstore publish` answer "created through the API" instead of clearing normally; `Wait-StoreSubmissionClear` stops the job immediately with `::error::` naming that submission's id rather than looping on it, since only a human can delete it in Partner Center before either Store job can run again. Both jobs carry a 90-minute `timeout-minutes` to give the 60-minute wait room alongside the rest of the job.

A named mutex (`Local\Steward.App`, acquired in `Program.Main` before `Application.Start`) enforces one running instance across every train, so the name is shared between the Store build and an MSI install still in the wild rather than stamped per channel. `InstanceCoordination` decides what a second launch does with it: a launch of the SAME train (Store/flight, MSI, the dev package, Debug, `AppInfo.Train` is `BuildName` with `prerelease` folded into `store` since a Store flight is the same package; the trains are `store`, `msi`, `preview`, `portable`, `dev` and `debug` on Windows and `linux`, `macos` and `debug` elsewhere) signals the running instance to come to the foreground (`Local\Steward.App.Show.<train>`, an `EventWaitHandle` the running instance waits on from a background thread and marshals to `MainWindow.ShowFromTray` on the UI thread) and exits without showing anything; a launch of a DIFFERENT train signals the running instance to quit (`Local\Steward.App.Quit`), waits up to 15 seconds for the global mutex, and on success shows a dismissible "Closed the &lt;train&gt; build automatically" info bar through the same banner mechanism as a server banner. Each running instance also holds `Local\Steward.App.Running.<train>`, probed with `EventWaitHandle.TryOpenExisting` rather than any file, since a file a packaged build newly creates lands in per-package virtualised storage that another train's process does not see. The signalled instance quits through its own tray Quit path (`MainWindow.QuitFromAnotherBuildAsync`), waiting up to 10 seconds for a busy addon row to finish first so it never blows the newcomer's 15-second budget. A same-train launch carrying a `curseforge://` link first writes the URI as one line to the running instance's per-train named pipe (`Steward.App.Link.<train>`, `PipeOptions.CurrentUserOnly`, a 5-second connect timeout, logged and skipped on failure) and then sets the show event; the running instance reads it on a background loop and hands it to `MainViewModel.ReceiveCurseForgeLinkAsync` on the UI thread. A different-train launch carries its link through the quit-and-take-over path and handles it as a cold start. Windows App SDK `AppInstance` redirection is not used, since the named events already decide which instance keeps running. `InstanceCoordination.Windows` also probes the old preview trains `store-avalonia`, `msi-avalonia`, `dev-avalonia` and `debug-avalonia`, so a pre-cutover preview still running is closed by the first current build that starts. On Linux and macOS (`InstanceCoordination.Unix.cs`) named events do not exist and `Local\` names one login session (two terminals each acquire it, verified 16 Oct 2026), so the mutex is `Steward.App` with `NamedWaitHandleOptions { CurrentUserOnly = true, CurrentSessionOnly = false }` (a lock under `/tmp/.dotnet-uid<uid>`, separate per user, freed when its owner is killed), and every signal goes through one Unix domain socket per train, `<train>.sock` in `$XDG_RUNTIME_DIR/steward`, else `<LocalApplicationData>/Steward/run`, a folder kept at mode 0700. A launch connects to its own train's socket and, when it answers, writes `link <uri>` (when it carries one) and `show` (unless started with `--tray` or `--no-activate`) as UTF-8 lines and exits; otherwise it sends `quit` to the first other `*.sock` that answers, waits up to 15 seconds for the mutex, then binds its own socket, deleting the file first, since a killed instance leaves it behind and a refused connection reads as not running. The running instance accepts on a background loop, reads each connection's lines within 10 seconds, ignores unknown lines and a link over 64 KB (`AddonSettingsPayload.MaxLinkLength`, which also caps the Windows link pipe), and marshals show, quit and link to the same UI-thread handlers as on Windows; lines sent before `ListenForSignals` wait in the listen backlog. Verified 16 Oct 2026 under Xvfb in WSL: a same-train second launch with a link exited in 0.06 seconds and the first logged the link and the show, a relaunch after `kill -9` started and answered, and an MSI-train launch closed the running Debug train and bound its socket in 0.1 seconds. `Mutex.WaitOne` throwing `AbandonedMutexException` counts as already acquired, since a Store update force-kills the old process without releasing it. A `WM_QUERYENDSESSION`/`WM_ENDSESSION` subclass on the window (`MainWindow`'s `Native.HookSessionEnd`) always quits outright, bypassing Close to tray, so a Store update's forced shutdown does not wait out a 30-second kill timeout.

`MainViewModel.CheckStoreUpdateAsync` catches every exception from the `StoreContext` call itself and routes it to `StatusMessage`, rather than relying on the caller's typed catch clauses, since a WinRT failure there is not guaranteed to be a `COMException`.

Every Store, package and startup-task WinRT call lives in `WindowsStore` (`StoreContext` and its update and queue APIs, `AppInstallManager`, `PackageManager`, `StartupTask`, `RegisterApplicationRestart`), and the launcher and data-folder calls in `WindowsShell` (`Launcher`, `ApplicationData`); `CurseForgeDefaultQuery` keeps the `IApplicationAssociationRegistration` call. `MainViewModel` keeps the orchestration, the progress reporting and every `StatusMessage`, and `WindowsStore.ToProgress` maps a `StorePackageUpdateStatus` to Core's `StoreUpdateProgress` (`UpdateProgressPreview` goes through it). Under Wine (`AppInfo.IsWine`) the Store scan, the Store update check and the startup task are skipped entirely. A creation step (`StoreContext.GetDefault`, `new AppInstallManager()`, `new PackageManager()`, `StartupTask.GetAsync`, or the association COM object) that fails with a `TypeLoadException`, `DllNotFoundException`, `EntryPointNotFoundException` or a `COMException` of `REGDB_E_CLASSNOTREG` (`0x80040154`) or `CLASS_E_CLASSNOTAVAILABLE` (`0x80040111`) (`WindowsStore.IsActivationFailure`) is logged once and turns that feature off for the run, with no `StatusMessage`; any other failure is reported and retried as before: a Store failure goes to `StatusMessage` and the next check tries again, and a startup task read failure shows "Could not read the Start with Windows setting". With the startup task off the toggle is disabled and reads "Start with Windows is not available on this system".

When packaged, "Open data folder" prefers `Windows.Storage.ApplicationData.Current.LocalCacheFolder.Path\Local\Steward` over the literal `%LocalAppData%\Steward` when that folder exists, through the shared `WindowsShell.DisplayDataFolder` helper: a packaged process's newly created files under `%LocalAppData%\Steward` land in that virtualised location, so pointing Explorer at the literal path would not show them; where the real folder already exists (the usual case, see Development install) no such folder is created and the literal path is shown. The About card shows the version and, on the line beneath, the update state; it does not show the install path. Every successful `StoreContext` or MSI manifest check records its outcome in `app_update_check` in `state.json` (the displayed version, whether an update was found, when), so a later launch of the same version reads "Up to date" or "An update is available" before its own check finishes; a different version reads "Not checked for updates yet" until one does. The dev and Debug builds never check for an update and say so on that line instead. The real `%LocalAppData%\Steward` path is unchanged for `state.json` and `update.log`, which the packaged and unpackaged builds still share.

The Start with Windows toggle shows distinct, disabled text for each locked `StartupTaskState`: `EnabledByPolicy` reads on with "Turned on by your organisation's policy", `DisabledByPolicy` reads off with "Turned off by your organisation's policy", and `DisabledByUser` reads off with "Turned off in Windows Settings > Apps > Startup".

A WinUI install that updates to this build sees the Avalonia rebuild's window chrome, menus and fonts (the bundled Hanken Grotesk, Cascadia Mono and Fluent UI System Icons in place of Segoe), and its MSIX no longer depends on the Windows App Runtime. The train, the data folder (`state.json`, the DPAPI secrets, the logs, `provider_addons.json`, `character_sync.json`), the session, the Run value, the Start menu shortcut, the `StartupTask` and the `curseforge` protocol carry over: the executable is still `Steward.App.exe`, the train names are those the WinUI build used, `SecretProtection` is the same `ProtectedData` call for the current user with no entropy, and the MSI keeps its `UpgradeCode`, so it upgrades in place.

0.11.0 was the MSI release that bridged existing installs across to the Store, through a Switch-to-Store banner since removed; releases after 0.20.2 attach an MSI again, and an MSI build updates itself from those releases as described under Self-update.
