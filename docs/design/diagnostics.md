# Memory and diagnostic logging

Task Manager's Memory column is the private working set, which `Native.TrimWorkingSet` lowers: a blocking, compacting `GCCollectionMode.Aggressive` collection with the large object heap compacted, then `SetProcessWorkingSetSizeEx(-1, -1)` on Windows. It runs 3 seconds after the window hides to the tray or loses focus (when it is still not active then), once after `InitializeCommand` when the window is hidden, and after every background pass (`MainViewModel.BackgroundPassCompleted`) while the window is not active, so the 1-minute pass's garbage (the RestedXP guide strings of up to 1.3M characters, `state.json`) does not stay resident. Measured 27 Oct 2026 on a Debug build in the tray: 4 to 15 MB between passes against 128 MB for the Store build before it, with a GC pause of 7 to 14 ms per trim. `Steward.Desktop.csproj` also turns concurrent GC off and sets `System.GC.ConserveMemory` to 5. Committed private bytes (about 100 MB, mostly Skia, ANGLE and the runtime) are unchanged.

## Diagnostic logging

The app writes a daily-rolling diagnostic log to `%LocalAppData%\Steward\logs\steward-<build>-YYYYMMDD.log` (the same folder for a packaged build, which modifies the existing real folder in place), through `FileLoggerProvider` in `Steward.Core` (`src/Steward.Core/Diagnostics`), registered as an `ILoggerProvider` in `StewardServices.AddStewardServices` alongside the existing `Microsoft.Extensions.Hosting`/`Logging` setup. `<build>` (`AppInfo.BuildName`, derived from `IsPackaged`/`IsGitHubRelease`/`IsPreRelease`) is one of `prerelease`, `store`, `dev`, `msi`, `preview`, `linux`, `macos` or `debug`, so the Store release, a Store flight, the side-by-side dev package, an unpackaged MSI install and a Debug build never contend for the same file lock when several run at once. Each line is `<UTC ISO timestamp> <level> <category>: <message>`, with an exception's full `ToString()` (stack included) on the following line; writes are single-threaded behind a lock and flushed per line. `LogFileRetention.DeleteOlderThan` runs at startup and drops any `steward-*.log` file older than 14 days, across every build name. Minimum level is Information for `Steward.*` categories and Warning for `Microsoft.*`/`System.*` (`builder.Logging.AddFilter`).

Instrumented through `ILogger<T>` injected where the class is already resolved through DI (`MainViewModel`, `SessionService`, `AddonUpdater`, `RestedXpService`, `StewardGuildSyncApi`) or passed as a parameter to the one static call site that needs it (`GuildRosterSync.WriteIfChanged`): every start (one `Steward <version> starting (<build name>, <OS>, <arch>)` line, without which a signed-out start on a fresh profile wrote no line and so no file, since the file opens on the first write), sign-in (start, browser launch, callback received, code exchange, completion or failure), every `/api/me` recheck (authorized/401/unreachable, role, feature count), sync document pulls (key and image counts, a repeated failure logged once, 403 quiet, 401), character pushes (accepted/rejected counts, 403/429/unreachable), both SSE event streams (connect, ready, drop with reason and backoff, give-up), banner fetches, Store update checks, addon manifest probes and installs (per addon and install path), `StewardSync.lua`/`StewardGuides` writes (written/skipped-unchanged/failed) and RestedXP session refresh failures. `Dispatcher.UIThread.UnhandledException`, `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` are hooked in `App.OnFrameworkInitializationCompleted` to log at Critical without changing how they are otherwise handled.

Never logged: the `gg_session` cookie/token, the sign-in code or PKCE verifier, RestedXP tokens or password, and any DPAPI blob; the sign-in URL is logged through `LogRedactor.PathOnly`, which drops its query string (the challenge and callback port) entirely rather than judging what in it is sensitive.
