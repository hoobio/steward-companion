# Steward

.NET 10 Avalonia desktop app for Windows, Linux and macOS, public repo. Windows ships through the Microsoft Store (x64 only), with an unpackaged self-contained MSI and the bare MSIX attached to every GitHub release; an MSI install updates itself from those releases. Every release from 0.24.1 also attaches a portable Windows zip, a deb and an rpm for Linux x64 and arm64 and a dmg for macOS arm64 and x64, and the same builds ship as previews; Linux installs come from a deb and rpm feed with a `stable` and a `preview` channel. The desktop half of Steward, a guild toolkit for World of Warcraft: it keeps the Steward addon current and will carry guild roster, loot history and attendance between the game and steward-server, combining several officers' records into one view.

Updating is the whole of it today. It manages a set of addons rather than one, against their published release channels, reading admin state from steward-server.

## Project layout

`src/Steward.Core` holds the domain logic with no UI. `src/Steward.Presentation` holds the view models (`ViewModels/`), the UI-neutral services (`Services/`), `AppInfo` (build flags, train, `IsPackaged`, `IsWine`, `IsLinux`, `WindowTitle`) and `StartupRegistration`, and references no UI stack, and keeps the `Steward.App.*` namespaces (its `RootNamespace`).

`Steward.Core`, `Steward.Presentation`, `Steward.Desktop` and both test projects target plain `net10.0` (Linux and macOS) beside their Windows TFM: `net10.0-windows` for Core and its tests, `net10.0-windows10.0.26100.0` (the WinRT projection) for Presentation, Desktop and the Desktop tests. Per-OS code is chosen by file name: `Directory.Build.targets` compiles `*.Windows.cs` only for the Windows TFM and `*.Unix.cs` only for the others, each pair declaring the same public type and members, so callers need no `#if`; today the pairs are `WindowsStore`, `WindowsShell`, `CurseForgeDefaultQuery`, `InstanceCoordination` (the Windows file holds the named events and the link pipe; the Unix file uses a per-user mutex and a Unix domain socket per train, since named events do not exist off Windows) and `SecretProtection` (DPAPI on Windows; AES-GCM under a per-user key held in a keyring or an owner-only file off Windows, see Auth). A `*.Unix.cs` stub turns its feature off and logs it rather than throwing, and `.editorconfig` turns CA1822 off for those stubs, which keep an instance API. Code in a type that exists on every TFM (the registry, a P/Invoke) is guarded with `OperatingSystem.IsWindows()` instead; CA1416 is never suppressed, and it does not flag a P/Invoke or a named `EventWaitHandle` constructor, so those are confined by hand. `src/Steward.Desktop` is the one app: the views, `App.axaml`, `Program`, the tray icon and the Avalonia services (`AppDialogs`, `AvaloniaPlatform`). Every UI-neutral service registration (configuration, logging, the `Steward` and `Addon` HTTP clients, `AppStateStore`, `StewardClient`, `SessionService`, `AddonUpdater`, `AppUpdater`, the RestedXP services, `DiscordImage`, `StewardGuildSyncApi`, `MainViewModel` and `IUiPlatform`) is `StewardServices.AddStewardServices(platform, dataFolder)` in `src/Steward.Presentation/Hosting`, which the app calls with `StewardServices.DefaultDataFolder` (`%LocalAppData%\Steward`, holding `state.json` and `logs\`); that folder, and every default path under it (`AppStateStore`, `ManifestIcon`, `SecretProtection`, the instance socket folder and the pre-host log), is `LocalData.Folder` in Core: `Steward` under `SpecialFolder.LocalApplicationData`, which off Windows is read with `SpecialFolderOption.Create`, since .NET answers an empty string for a folder that does not exist yet and the data folder was then relative to the working directory. On Linux that is `$XDG_DATA_HOME` when it is absolute, else `~/.local/share` (created when missing); on macOS .NET 10 answers `NSApplicationSupportDirectory`, `~/Library/Application Support`, the platform convention, so nothing differs there; the app adds only its window, its pages and its concrete platform type. Presentation makes its internals visible to `Steward.Desktop` and `Steward.Desktop.Tests`.

A view model reaches the UI stack only through `IUiPlatform` (`src/Steward.Presentation/Services/IUiPlatform.cs`): the owner window handle, `HasThreadAccess` and `TryEnqueue` for the UI thread, `CreateTimer` (a `UiTimer` with `Interval`, `IsRepeating`, `IsRunning`, `Tick`, `Start` and `Stop`), images from a URI, a packaged asset, encoded bytes or premultiplied BGRA pixels, whether a packaged asset exists (`HasAsset`, which `ProductIcon` checks), `DecodeBgraAsync` (straight BGRA, optionally scaled to a square, for `DiscordImage` and `InGameIcon`), the clipboard and the folder picker. `AvaloniaPlatform` implements it (see Avalonia desktop app); `MainViewModel` passes it to every view model it builds. An image property on a view model is typed `object` and is the platform's own image type. A visibility property is a `bool`, a brush or style is a resource key string, an initials tile colour is an ARGB `uint` and a hairline is a `bool`; the views convert them through `Views/BindConvert.cs` in `Steward.Desktop` (`Brush`, `Theme`, `ColorBrush`, `TopHairline`, `Image`, `Glyph`, `Initials`), where a null brush key is a transparent brush. A glyph on a view model (`BannerViewModel.IconGlyph`, `AddonRowViewModel.NoticeGlyph`, `FolderEntry.NoticeGlyph`, the four `*SortGlyph` headers) is a neutral name from `ViewModels/Glyphs.cs` (`Info`, `CheckMark`, `Warning`, `Error`, `Lock`, `ChevronUp`, `ChevronDown`, or empty for none), which `BindConvert.Glyph` maps to the icon font. `InstanceCoordination.ListenForSignals` takes the platform and the show, quit and link callbacks rather than the window.

## Avalonia desktop app

`src/Steward.Desktop` is the Avalonia 12 app, the same views, styles and view models on Windows, Linux and macOS. It is a self-contained `WinExe` on `net10.0-windows10.0.26100.0` (`win-x64`, `win-arm64`) and on `net10.0` (`linux-x64`, `linux-arm64`, `osx-x64`, `osx-arm64`, published with `-f net10.0 -r linux-x64`; a Windows build of the solution also emits `bin\<config>\net10.0\win-x64\Steward.Desktop.exe`, which carries the Unix stubs, cannot read the DPAPI session and shares `state.json` with the installed app, so it is never launched on Windows) on Avalonia 12.1.3 and FluentAvaloniaUI 3.1.0 (`FluentAvaloniaTheme` replaces `Avalonia.Themes.Fluent`), with compiled bindings by default. `app.manifest` declares PerMonitorV2 DPI awareness, so the window opens at 980x720 logical pixels scaled for its monitor. `appsettings.json`, `Steward.ico`, the in-app PNGs, the Store logo images and `Assets/Products/*.png` live in `src/Steward.Desktop` (`src/Steward.Desktop/Assets/Steward.ico`): the icon and PNGs are `AvaloniaResource` under `avares://Steward.Desktop/Assets/` (the window, tray and `_NET_WM_ICON` all load it from there), and `appsettings.json` is the embedded resource `Steward.Desktop.appsettings.json`, read through `AddJsonStream`, so a single-file publish needs no settings or icon file beside the exe; the font licence texts under `Assets/Fonts` are `Content` and sit beside it, and so do the native libraries (`libSkiaSharp`, `libHarfBuzzSharp`, and `av_libglesv2.dll` on Windows) unless the publish sets `IncludeNativeLibrariesForSelfExtract`, which the Windows zip build does (see Releases), so .NET extracts them to its bundle folder on first start. No file beside the exe overrides it, so the app has the one embedded source. `AVLN3001` is suppressed because every view takes its view model through its constructor and is never loaded by URI. `Program.BuildAvaloniaApp` sets `Win32PlatformOptions`: rendering `AngleEgl` then `Software`, composition `WinUIComposition`, `DirectComposition`, then `RedirectionSurface`; under Wine (`AppInfo.IsWine`) `Software` rendering into a `RedirectionSurface` only, and the window keeps Wine's own frame (`ExtendClientAreaToDecorationsHint` off), since an extended client area under Wine 11 sat 30px above the window Wine reported and clipped the title bar row; the title row there hides the app's own icon and title (`TitleArea`), which Wine's frame already shows, and keeps the install picker. `--curseforge-link=` and a bare `curseforge:` argument are read in `Program.ActivationLink`, and a packaged build without either falls back to the WinRT `Windows.ApplicationModel.AppInstance.GetActivatedEventArgs()` protocol arguments (`WindowsShell.ProtocolActivationUri`; no Windows App SDK `AppInstance`); the named mutex, events and link pipe are the shared `InstanceCoordination`.

A Windows publish (the Windows TFM and a `win` RID) renames the apphost to `Steward.App.exe` (MSBuild target `NameWindowsExeStewardApp` in `Steward.Desktop.csproj`, after `Publish`), since installed builds start `Steward.App.exe` from the HKCU Run value, user pins, the MSI's `taskkill /im Steward.App.exe`, its Start menu shortcut and `LaunchSteward`, and the Store manifest, so an update needs no migration code. The apphost still loads `Steward.Desktop.dll`. `dotnet build` output keeps `Steward.Desktop.exe` (Debug: `src\Steward.Desktop\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Steward.Desktop.exe`), and the Linux and macOS executable is `Steward.Desktop`.

The app is packaged as an MSIX by `scripts/Build-DesktopMsix.ps1` (PowerShell 7) from `packaging/windows/Package.appxmanifest`: identity `Hoobi.Steward` with publisher `CN=D74C026B-1081-4787-BDE6-0CFA2F1EDD71` and `ProcessorArchitecture="x64"`, `Executable="Steward.App.exe"` with `EntryPoint="Windows.FullTrustApplication"`, the `StewardStartup` startup task with `--tray`, the `curseforge` protocol, `runFullTrust`, the `10.0.17763.0`/`10.0.26226.0` device family and `Resource Language="en-US"`. The script publishes `Steward.Desktop` for `net10.0-windows10.0.26100.0` `win-x64` self-contained and not single-file (an MSIX holds loose files) into `<OutputDirectory>\layout`, copies the manifest's visual assets from `src/Steward.Desktop/Assets`, stamps the version into `AppxManifest.xml`, builds `resources.pri` with `makepri` (a config from `createconfig /dq en-US` with its `packaging` element removed, so the scale-200 logos stay in the one PRI rather than a `resources.scale-200.pri` split meant for bundles, indexing only the assets), packs `Steward-<version>-x64.msix` with `makeappx pack` and zips and renames it to `Steward-<version>-<Identity>-x64.msixupload`, as `build.yaml` does. `makeappx` and `makepri` come from `Microsoft.Windows.SDK.BuildTools` at the `Directory.Packages.props` version (10.0.26100.9169) when it is in the NuGet cache, else from the newest installed Windows SDK (the runner's 10.0.26100). `-Identity Store` (default) builds with `GitHubRelease=true` and a version of `<major>.<minor>.<GITHUB_RUN_NUMBER>.0`; `-Identity Dev` stamps `Hoobi.Steward.Dev`, `CN=Hoobi Dev` and "Steward (Development)" and builds without `GitHubRelease`, with `<version.txt>.<git rev-list --count HEAD>`; `-Version` overrides either, which is how `build.yaml` passes its release-PR-based number, `-StoreDisplayVersion` passes through, and `-PreRelease` passes `StorePreRelease=true`. Nothing is signed. The package is self-contained and needs no Windows App Runtime. Packaged, the app takes the packaged paths shared in Presentation: `AppInfo.IsPackaged` from `GetCurrentPackageFullName`, the `StewardStartup` task in place of the Run key, `WindowsShell.DisplayDataFolder` and, with the real `%LocalAppData%\Steward` absent, its first writes virtualised to `%LocalAppData%\Packages\<PFN>\LocalCache\Local\Steward`. `AppUpdateTitle` and `AppUpdateChangelogUri` follow `UpdateSource` rather than `IsPackaged` (see Self-update). `PackageManifestTests` checks the manifest's Store identity, that the application and startup task start the literal `Steward.App.exe` with `StartupRegistration.TrayArgument`, that the protocol is `CurseForgeLinks.Scheme` and that every `Assets\` reference has a file.

`AvaloniaPlatform` (`Services/AvaloniaPlatform.cs`) implements `IUiPlatform` over `Dispatcher.UIThread` and `DispatcherTimer`. A URI image is a `DrawingImage` returned at once, whose `Drawing` is replaced by an `ImageDrawing` of the bitmap (replacing it is what invalidates the `Image`) when the download (on the `Addon` client, `AvaloniaPlatform.Http`, set after the host is built) has decoded to the requested width times the window's render scaling, cached per URI and width. The image is a `PlatformImage` (a `DrawingImage` with `HasFailed` and a `Failed` event): a failed download or decode marks it failed and drops it from the cache, as undecodable bytes do, and `Views/IconImage` (an `Image` with a `Failed` event, raised at once for a source that has already failed) is how a view sees it, so the Addons table sets `AddonRowViewModel.ManifestIconFailed` and loads the local `FallbackIcon` as WinUI does from `Image.ImageFailed`; a missing `Http` client leaves the image empty rather than failed. Every decode goes through one helper that turns the `NullReferenceException` Avalonia.Skia 12.1.3 throws for bytes no codec recognises into an `ArgumentException`, which the shared callers already catch. An `avares:` URI or packaged asset and encoded bytes decode to a `Bitmap` at once, premultiplied BGRA goes through a `WriteableBitmap`, and `DecodeBgraAsync` decodes and scales through Skia and un-premultiplies to straight BGRA. The clipboard and folder picker go through the main window's `TopLevel.Clipboard` and `StorageProvider`, and `OwnerWindowHandle` is `TryGetPlatformHandle()`.

The shell (`Views/MainWindow.axaml`) is custom rather than `FANavigationView` (a headless probe of FA 3.1.0's `LeftCompact` measured the same item, indicator and pane metrics as WinUI, so this is a choice for direct control of the pane, not a metric gap): a 48px title bar row (app icon, title, the install picker centred on the window and clamped 8px from the title and from the 144px caption-button area, right-aligned in its column when too narrow; the title bar carries `WindowDecorationProperties.ElementRole` `TitleBar` and the picker `User`), then a 48px pane of WinUI `NavigationView` `LeftCompact` metrics taken from `generic.xaml` (items 36px high with a 4,2 margin, a 40px icon column, 16px glyphs, a 3x16 accent indicator with 2px corners, `-1,3` pane margin; the account button above Settings at the AGENTS.md Navigation metrics) and the page host. With the client area extended, Avalonia 12.1.3 on Win32 always asks for a managed title bar (`WindowImpl.RequestedDrawnDecorations` returns `TitleBar`), and FluentAvalonia's `WindowDrawnDecorations` theme draws its own 12px title and four 46px caption buttons, a full-screen one included, over the app's title bar. `MainWindow.WindowDecorationsTheme` is `StewardWindowDecorations` (`Styles/Controls.axaml`), based on FluentAvalonia's, whose template keeps the drag, border and shadow parts and draws only minimise, maximise and close, 48px wide (`CaptionButtonWidth`) as the WinUI baseline measures, in `CaptionButtonTheme` (FluentAvalonia's glyphs, the `CaptionButton*` brushes in `Resources.axaml`: hover `#191919` and close hover `#E81123`, the system caption colours the baseline's hover captures show, from a rest of `#00191919` so the fade never passes through a lighter colour, press `SubtleFillColorTertiary`, the inactive glyph `#666666` sampled from the baseline). Avalonia 12.1.3 hovers a drawn caption button from `WM_NCMOUSEMOVE`, but moving onto one from the client area also ends client tracking with a `WM_MOUSELEAVE` that clears the hover a few milliseconds later, and Windows resends the move only 0.6s (maximise) to 1.7s (minimise, close) after that (measured 16 Oct 2026), so `MainWindow`'s window procedure hook posts a `WM_NCMOUSEMOVE` for the cursor's position whenever a `WM_MOUSELEAVE` arrives over a caption button (`Native.RepostCaptionButtonMove`), and the hover shows on the first frame, as on WinUI. FluentAvalonia binds a caption button's `inactive` class to an ancestor `Window`, which the decorations layer, the window's sibling under its host, never has, so `MainWindow.UpdateCaptionButtons` sets it on activation, deactivation and open. WinUI keeps the 1px top resize border outside its client area, so `Root` sits 1px down (not under Wine) and every element lands on the WinUI baseline's screen row; the title bar icon is 14px from the left with the title 15px after it, as measured. Pages are DI singletons swapped into `PageHost` by `ShowPage`, with the 220ms fade-and-rise entrance on every page change except the first. Dialogs subclass `FAContentDialog` and are shown through `Services/AppDialogs.cs` (one at a time, the `Steward` class, the accent primary button unless the caller already themed it, as the close confirmation's critical button is, the dialog hover brushes, open popups closed first). `Styles/Dialogs.axaml` holds the dialog frame as the WinUI baseline measures it: a `#99000000` scrim (WinUI transmits 0.40 of the ground with no tint, not the WinUI build's `#B3000000` override), one 24px gap between the content and the buttons with no separator (the command row is padded `24,0,24,24`), and `StewardDialogResources`, which `AppDialogs` copies into each dialog: WinUI draws a dialog's text boxes and combo boxes with generic.xaml's fills and edges rather than the app's page overrides (text box rest `#0FFFFFFF` with a `#3A404D` top and `#9FA1A8` bottom edge, focused `#B31E1E1E` with a 2px `#73D0FF` bottom drawn inside the box so the text does not move, disabled `#0BFFFFFF`; combo box rest `#0FFFFFFF`). `AppDialogs` gives each dialog's panel (`BackgroundElement`, not the scrim, which still covers the whole window) the shell's 1px top margin plus 0.01, so the panel centres on the same client area as WinUI's, which excludes the top resize border, and a half pixel rounds up as on WinUI rather than to even; without it every panel sat 1px higher, and with it every dialog panel starts on WinUI's row at 100% and 150% except Get addons at 150% (1px low). After a dialog opens, `AppDialogs` focuses the first focusable control in its content, else keeps the dialog's own focus, else the first command button, so the first input is focused as on WinUI, Tab stays inside the dialog and Escape cancels it. A dialog hidden while it still waits in that queue (the RestedXP sign-in dialog hides itself on sign-in) has its `Closing` cancelled and is never shown, returning `None`, since FluentAvalonia 3.1.0's close path throws `ArgumentNullException` on a dialog that was never shown. FluentAvalonia 3.1.0's close path also turns the dialog's `IsHitTestVisible` off and its show path never turns it back on, so `AppDialogs` sets it before every show: without that, a dialog instance shown a second time (the addon folders dialog after the changelog it handed over to) let every click through to the window behind and could not be closed from its buttons. The close path's 167ms fade also leaves the template's `LayoutRoot` with `IsVisible` false as a local value; the next show's open animation hides it until the animation ends 83ms later, when `LayoutRoot` reads false for one frame, and Avalonia clears keyboard focus from inside an element that turns invisible, so focus fell to the window: Escape no longer closed the dialog and Tab moved to the install picker behind it. `AppDialogs` clears that value before every show, so a dialog shown again behaves as a fresh one (`DialogReshowTests`). A dialog's Primary or Secondary result is accepted only from a deliberate press on that button (`Services/DialogIntent.cs`, attached for each show and removed after it): a left pointer press and release on the button while the dialog is open, or an Enter or Space key-down while the dialog is open and visible and its window is active, followed for Space by its key-up, or a UI Automation Invoke of the button while the dialog is open (Narrator and other assistive technology, and `tools\UiDriver.psm1`, press buttons through the Invoke pattern), whatever window is active. The Invoke is recognised by the button type: `Styles/Dialogs.axaml` gives `FAContentDialog.Steward` FluentAvalonia 3.1.0's template with Primary and Secondary as `DialogCommandButton` (`Services/DialogCommandButton.cs`, styled as `Button`), whose automation peer re-implements `IInvokeProvider.Invoke` to mark the button for the length of the click, since Avalonia 12.1.3's `ButtonAutomationPeer.Invoke` calls the internal `Button.PerformClick` and leaves no other trace. A key-up whose key-down the dialog did not accept, a repeated key-down, a key that was already held when the dialog opened or its window was activated again (`AppDialogs.IsKeyHeld`, `GetAsyncKeyState` on Windows and never held elsewhere), and a press before the dialog opened are swallowed when they would reach the Primary or Secondary button or, for Enter, FluentAvalonia's default-button path. Any other click on those buttons (an access key, a click raised from code) is cancelled and the dialog stays open, and `ShowAsync` returns `None` for any Primary or Secondary result that no accepted press chose, which covers `Hide(Primary)` and the stale result FluentAvalonia 3.1.0 keeps on a dialog shown again and then closed with Escape. This was needed because Avalonia 12.1.3's `Button.OnKeyUp` clicks a focused button on a Space key-up with no matching key-down, and FluentAvalonia's `SetupDialog` focuses the first button, Primary, when `DefaultButton` is `None`: on 16 Oct 2026 a `curseforge://` link installed DBM with no Install press, and the close confirmation went to the tray on its own twice, while other keyboard input was reaching the desktop (the exact keystroke is unproven; `DialogIntentTests` reproduces the mechanism). `AppDialogs.FocusFirstInput` therefore never leaves focus on a Primary button that is not the default: it moves to the Close button, else the first other focusable element, while a caller's own choice of the Secondary button (the close confirmation) is kept. WinUI's `ContentDialog` also focuses the first command button when there is no default and no focusable content (`SetInitialFocusElement` in microsoft-ui-xaml's `ContentDialog_Partial.cpp`). The addon folders dialog (`Views/AddonFoldersDialog.axaml.cs`) differs from WinUI's on purpose: a sub-addon row shows its version over that sub-addon's own "Released n days ago" line (`FolderEntry.Released` and `ReleasedTip`, from its row's `ReleasedText` and `ReleasedTip`, left out while the release date is unknown, the table's rule), right-aligned in one column beside the channel (24px between that column's right edge and the channel), stacked with the table's 4px gap and centred vertically on the row rather than pinned to the name and folder lines; WinUI's dialog has no release line. FluentAvalonia completes `ShowAsync` 200ms after `Hide()`, and never if the window closes within those 200ms, which in this app happens only at quit. The tray icon is an Avalonia `TrayIcon` with Open Steward, Check for updates and Quit; close and minimise to tray, `--tray`, `--no-activate`, every preview switch and the session-end hook (`Win32Properties.AddWndProcHookCallback`) behave as on WinUI. A start never shows the window before its first frame is composed: `InitializeCommand` runs first (its synchronous session restore decides gate or shell), then the window is shown DWM-cloaked and uncloaked two animation frames later (`MainWindow.ShowRendered`); a `--tray` start constructs the window, so every view model delegate is wired, and shows it the same way on its first restore. `--tray` and `--no-activate` show with `ShowActivated` off and no `Activate`; only a normal start and a tray restore take the foreground (`Native.ForceForeground`). Such a start also holds `MainWindow.ForegroundGate` (`Services/ForegroundGate.cs`), set in `App.OnFrameworkInitializationCompleted` before `InitializeCommand` runs and released only by `ShowFromTray` (a tray click, the tray's Open Steward, a same-train relaunch's show signal) or the window's first `Activated`, which is logged; while it is held, `AppDialogs.ShowAsync` waits before showing any dialog (the guild prompt, a CurseForge link confirmation, and every other dialog), since a dialog on a window the user did not activate is a prompt they never asked for. A second launch of the same train carrying `--tray` or `--no-activate` sends its CurseForge link but no show signal (`InstanceCoordination.TryAcquire`'s `showRunning`, false only from `Steward.Desktop`'s `Program`), so it never brings the running window forward. In Avalonia 12.1.3 on Win32, `Window.Activate`, `Show` with `ShowActivated` on, a `WindowState` change to Normal or Maximized while visible (`WindowImpl.ShowWindow(state, activate: true)`, `SW_RESTORE`) and the close of a `ShowDialog` child (`owner.Activate()`) all call `SetForegroundWindow`; `Control.Focus()` and `FAContentDialog`'s default-button focus do not touch Win32 focus, and Win32 popups show with `SW_SHOWNOACTIVATE`.

A GPU driver reset (TDR) on Windows left the window fully transparent and the tray menu unable to open, so the process had to be killed (21 Oct 2026, an RTX 4090 that resets every few days). Avalonia 12.1.3 recreates its ANGLE context and the WinUI composition device after a loss (`PlatformRenderInterfaceContextManager`, `WinUiCompositedWindowSurface`), but its render thread can stop ticking: `WinUiCompositorConnection` schedules the next tick only from a commit that completes, and its 1-second watchdog acts only while a commit is in flight. The UI thread then blocks in `SyncCommit` on the next paint, and the tray menu is a `TrayPopupRoot` window on the same thread and compositor. This path is read from the source and not proven. `Services/UiWatchdog` runs on Windows outside Wine from the end of `App.OnFrameworkInitializationCompleted`: a background thread posts a beat to the UI thread every 5 seconds, and the beat awaits `Compositor.TryGetCompositionGpuInterop()`, a render-thread job that runs only once the graphics context is valid, so one beat proves both threads alive. After 6 missed checks in a row (30 seconds of the watchdog's own running time, so sleep and resume do not count), with no debugger attached, it logs which thread stalled, starts `Environment.ProcessPath` with `--no-activate` (window visible) or `--tray` (hidden) and `--restart-after=<pid>`, and kills its own process. `Program.Main` waits up to 15 seconds for that pid to exit before `InstanceCoordination.TryAcquire`, since a launch while the old process runs hands over to it and exits. A process started with `--restart-after` that stalls again within 5 minutes logs it and does not restart, so a GPU that stays broken does not cause a loop. A killed process leaves its tray icon until the pointer passes over it. `Services/AvaloniaLogSink` (`Logger.Sink`) writes Avalonia's Warning and higher lines for the `Visual`, `Win32Platform`, `OpenGL` and `WinUIComposition` areas to the app log, so the next reset shows what Avalonia saw.

`Styles/Resources.axaml` holds every key of the WinUI build's app resource dictionary with the same value, plus each system key a view or view model uses, resolved through that dictionary's overrides and otherwise taken from WinUI's dark theme (`microsoft.windowsappsdk.winui` 2.3.9, the dependency of Microsoft.WindowsAppSDK 2.5.1, `lib\net6.0-windows10.0.17763.0\Microsoft.WinUI\Themes\generic.xaml`, `Default` dictionary): `SubtleFillColorTransparent/Secondary/Tertiary/Disabled` (`#00FFFFFF`, `#0FFFFFFF`, `#0AFFFFFF`, `#00FFFFFF`), `MenuFlyoutItemBackground*` and `NavigationViewItemBackground*` (those subtle fills), `DividerStrokeColorDefault` and `MenuFlyoutSeparatorBackground` (`#15FFFFFF`), `CardBackgroundFillColorTertiary` (`#12FFFFFF`), `ControlAltFillColorQuarternary` (`#12FFFFFF`, the avatar fill), `TextOnAccentFillColorPrimary` (`#000000`), `TextFillColorInverse` (`#E4000000`), `AccentTextFillColorPrimaryBrush` and `SystemFillColorAttentionBrush` (`SystemAccentColorLight3`/`Light2`, both `#73D0FF` under the app's override), the InfoBar severity backgrounds (`SystemFillColor*Background`: success `#393D1B`, caution `#433519`, critical `#442726`, attention `#08FFFFFF`) and icon fills (generic's own `SystemFillColor*`, since its InfoBar aliases them through `StaticResource` as it does the text brushes: warning `#FCE100`, measured on the Guides page's session-expired bar, critical `#FF99A4`, success `#6CCB5F`; the banners and the error bar are the app's own controls and keep `#FFD580` and `#F28779`), and the text sizes (caption 12, body 14). WinUI's `generic.xaml` aliases its control brushes to its own `TextFillColorPrimaryBrush` (`#FFFFFF`) through `StaticResource`, which resolves inside `generic.xaml`, so the app's `#FFCBCCC6` override reaches only the keys the app dictionary overrides by name (`ButtonForeground*`, `TextControlForeground*`) and explicit `ThemeResource TextFillColorPrimaryBrush` uses (the views and the CommunityToolkit `SettingsCard` and `Segmented`); everything else measures `#FFFFFF` in the baseline: page, window, section and dialog titles, dialog text, plain `TextBlock`s, ComboBox text and items, radio, check box and On/Off labels, menu items, tooltips, InfoBar text and the nav glyphs. Text centring is tested in `tests/Steward.Desktop.Tests`. `TextCentringTests` renders each text-bearing control type the app uses (`TextBox` typed and placeholder at each real size, `Button`, accent `Button`, `ToggleButton`, `HyperlinkButton`, `ComboBox`, `ComboBoxItem`, the segmented `ListBoxItem`, `CheckBox`, `RadioButton`, `ToggleSwitch`, `MenuItem`, `ToolTip`, `FAInfoBar`, and a `TextBlock` and a `SelectableTextBlock` in a 32px box) with `HXE`, and asserts that the ink gap above equals the gap below within 1px, that a placeholder sits on typed text's row, that the caret and the selection span the text, and that accent buttons render SemiBold; it reports `weakauras gjpqy` too. `TextCentring.Verify`, called by every page and dialog render test, swaps every visible single-line text in the frame for `HXE`, takes its box (the nearest `Button`, `ListBoxItem`, `ComboBox`, `MenuItem`, `TextBox`, `ToolTip` or `FAInfoBar`, a template `LayoutRoot`, or the nearest filled ancestor; a check box's or radio button's glyph, a toggle switch's track, also for a label in the same panel as the switch, an InfoBar title's icon) and asserts the same gaps, so a new control or view is checked with no new test. Mouse-wheel scrolling is smoothed by `Styles/SmoothScroll.cs`, which the global `ScrollViewer` style switches on: each notch scrolls the system's `SPI_GETWHEELSCROLLLINES` lines of 16px (48px at the default 3, a page when the setting is "one screen", and 3 lines off Windows; Wine answers the system call itself) and eases out over 250ms (cubic), a notch during the animation adds to the pending target, a fractional delta (a precision touchpad) scrolls at once without animation, and the target is clamped to the live extent every frame. The handler runs on the tunnel route, so an outer viewer leaves a notch to the innermost viewer that can still move that way, and a viewer at its end lets the notch chain outward; any offset change it did not write (keyboard, the scroll bar, bring-into-view) ends the animation. DirectManipulation's own curve is not published, so the 250ms ease-out is a choice, and the 16px line is taken from WinUI's per-notch distance of about 48px at 3 lines, which was not measured here.

## Managed addons

The managed addon list is steward-server's: `/api/me` carries a top-level `addons` array (`DesktopAddons` in `src/Steward.Auth/Me.cs`), already filtered to what the caller may see and in display order, each entry `{ id, name, folder_name, manifest_base_url, source, auto_install, features, parent?, icon_url? }` (`CatalogueAddon` in `Steward.Core`, mapped to `ManagedAddon`). It is cached as `addon_catalogue` in `state.json` and loaded at startup, so rows appear before the first `/api/me`; a successful `/api/me` carrying the field replaces it (saved only when it changed), one without it clears it, as do sign-out, a 401, a lost-access answer and a start with no session to restore, and it is kept while steward-server is unreachable or answers `client_outdated`, so addon.hoobi.io updates continue through an outage (`client_outdated` itself disables every row). An entry missing `id`, `folder_name` or `manifest_base_url` is dropped in `StewardClient.GetMeAsync` rather than failing the whole `/api/me`, and a null `source` or `auto_install` reads as `Steward` and false. Every folder in the server list is excluded from the Local scan, the CurseForge match route, adoption and the Get addons "already managed" guard, the same as a configured addon's, and a changed list rescans every install's Local rows. An older build sharing `state.json` drops the key on its next save, and the next successful `/api/me` restores it. Adding an addon is a steward-server catalogue row plus its addon.hoobi.io manifests, with no app release. `appsettings.json`'s `Addons` array of `{ Id, FolderName, ManifestBaseUrl, AutoInstall?, Features?, Source? }` (`ManagedAddon`) is kept only as the fallback for a server that sends no `addons`, rendered in array order; `ManifestBaseUrl` is required. `Source` defaults to `Steward` and names where the addon's release zip comes from, shown as-is in the table's Source column: `Steward` for the `addon.hoobi.io` manifests, `GitHub` for steward-server's RestedXP mirror (the mirror serves RestedXP only), and `CurseForge` for BugSack (mod 6273) and BugGrabber (mod 13344), whose `manifest_base_url` is steward-server's `/api/addons/curseforge/{modId}/88568/` with the Forever beta's version type baked in, and BugSack's `icon_url` is the CurseForge logo, since that route's `icon.png` needs the session cookie and row icons load without it, while BugGrabber has no CurseForge logo and carries none. A `CurseForge`-sourced catalogue entry is visible only while `IsCurseForgeEnabled` holds and its folder is excluded from the Local scan only while the setting is on, so with CurseForge off an installed BugSack is a Local row; it is a catalogue row rather than a `ProviderAddonRecord`, so it has no Unmanage item (`CurseForgeAddons.IsRecorded`) and its download failures are not reported. Five fallback entries ship today: `steward` (`AutoInstall: true`, `Features: ["sync"]`, so anyone holding the character-sync flag also gets the addon auto-installed, since it is what writes and reads the guild data that flag unlocks), `hoobiscripts` (`Source: "Protected"` at steward-server's protected route, since addon.hoobi.io no longer hosts it; `Features: ["hoobiscripts"]`, a flag held only by explicitly granted individuals rather than any officer default), and `restedxp`, `bugsack` and `buggrabber` (`Features: ["addons"]` each, a grantable flag held by officers by default and derived server-side for anyone holding `sync` or `hoobiscripts`, so the diagnostic and RestedXP rows show for the same population without each naming its own flag; the RestedXP row moving to `addons` is separate from the Guides page and sign-in entry point, which stay gated on `guides`). A configured addon with no manifest on any channel renders as "No releases yet" rather than as an error. `AddonUpdater` takes the `ManagedAddon` and channel as parameters rather than hardcoding a folder name or manifest URL, and the UI iterates the visible list per WoW install.

`Features` applies to the fallback list only and defaults to empty, so a configured addon without it is never visible. It names which of the signed-in user's `/api/me` features make the addon appear at all: it is visible when the user holds any one of them. `MainViewModel.VisibleAddons()` (`AddonCatalogue.Visible` in Core) is the one place the visible list is chosen: the server list as-is whenever one is known, fresh or cached, with no client-side feature filter (`features` on a server entry is informational, and `_features` is empty while steward-server is unreachable), else the configured `Addons` filtered by the user's feature set; every addon-list iteration (the manifest/release check, auto-apply, Update all, the Hidden addons toggle, `AddonChannels`) goes through it. Per-install rows are not fixed at construction: `WowInstallViewModel.SyncAddons` reconciles `AddonRows` against a given addon list, keeping the row instance for an addon still visible, adding one for an addon newly visible in its config-order position, and removing and unsubscribing one for an addon no longer visible; that removal only drops the row and its event subscription, never the addon's own folder on disk, since `AddonUpdater.RemoveExistingInstall` runs only from inside `InstallAsync`, itself only reachable through a visible row's own `UpdateCommand`. `MainViewModel.ReconcileFeatureGating` calls it on every install, prunes `_status`/`_releases` to the addons still visible and rebuilds `AddonChannels`, whenever `RecheckAuthorizationAsync` finds the feature set or the server addon list changed from the previous check; that covers a feature gained or lost mid-session, an addon added or withdrawn server-side, and a start where steward-server was unreachable and the set was still empty, since the next successful check is a change from empty. Each row's own `ensureAuthorized` (`MainViewModel.EnsureAuthorizedForAddonAsync`) rechecks `/api/me` and reconfirms the addon is still in that install's visible list before an update runs, so an update queued just as access drops refuses rather than applying. It passes on `Authorized`, and on `Unreachable` for a `Steward`-sourced addon in the cached server list (`AddonCatalogue.UpdatesWhileUnreachable`), whose manifest and zip live on addon.hoobi.io; a 401, lost access or `client_outdated` refuses, and a CurseForge or GitHub-mirrored row needs `Authorized`, since its manifest comes through steward-server. While steward-server is unreachable with a cached list, those rows stay enabled (`MainViewModel.IsAdminFor`), each manifest is probed on its own so one failing addon does not stop the rest, and the background pass still runs the manifest check and auto-apply (`CheckAsync` with no roster pull); Update all stays gated on `IsAuthorized`. Auto-apply and Update all only ever iterate `Installs[].AddonRows`, so a feature-hidden addon, having no row there at all, is never auto-installed, updated or touched by either.

A server entry may carry `parent` (the parent addon's id, `ManagedAddon.Parent`; today only `hoobiscripts-actionbars` under `hoobiscripts`), and `appsettings.json` entries carry none. `AddonGroups.FoldedInto` (Core) maps each visible sub-addon whose parent is also visible to that parent, one level deep. Every visible addon keeps its own `AddonRowViewModel`, so install, status, manifest, TOC guard and install records are unchanged, but `WowInstallViewModel.SyncAddons` marks a folded one `IsFolded` and hands it to the parent row (`AddonRowViewModel.SetChildren`), and `WowInstallViewModel.TopRows` (the table, the Updates count, Update all, Update all installs and `AutoApplyAsync`) leaves it out. The parent row rolls the group up: `AddonGroups.NeedsUpdate` reads Update available when the parent or a sub-addon has an update or a sub-addon is missing while the parent is installed, so granting a sub-addon's flag delivers it through Update or auto-update, skipping a sub-addon that is hidden, ignored or not distributable in its own right (`AddonGroups.IsRolledUp`); its Update installs the parent first when it needs it, then each sub-addon that does, and a sub-addon failure fails the row with that sub-addon's message; busy, Ignore, Hide and Uninstall cover the group (one `AddonUpdater.Uninstall` over every member's folders, so one TOC guard refusal refuses the lot); the changelog is the parent's followed by a heading per sub-addon with content, naming it and the version it would install (`Changelogs.Combine`). A sub-addon follows its parent's stored channel (`AddonGroups.StoredChannel`), falling back through the ordinary `Resolve` order when it has no build there, with the notice kept off the parent row; the channel dialog edits the parent only. A sub-addon whose parent is not visible gets an ordinary row.

`AutoInstall` marks an addon the background pass installs when it is missing, under the same admin gate as auto-update; it cannot be hidden. No addon is sourced from the GitHub API from this app any more: RestedXP moved to steward-server's own mirror of `RestedXP/RXPGuides`'s GitHub releases, served at its `ManifestBaseUrl` in the same `latest-{channel}.json` shape every other manifest-host addon uses, so `AddonUpdater` and `GetLatestAsync` have one code path for every addon. The mirror (`src/Steward.Integrations/GitHubMirror.cs` in `D:\steward-server`) applies the selection rules the list of GitHub releases needs: `release` is the non-draft entry without the `prerelease` flag that has the latest `published_at` and `pre-release` the one with the flag that has the latest `published_at`, because the GitHub API's list order is not date order (on 20 Sep 2026 it returned `.95, .94, .92, .102, .100`, and taking the first entry reported the installed build as up to date). The `.zip` asset is the release and its `sha256` digest is the checksum, and the tag name is the version (RXPGuides stamps the same `v4.11.4` form into its TOC); a release lacking a `.zip` asset or a digest is skipped by the mirror rather than surfaced here. There is no `develop` channel for RestedXP: the mirror only ever answers `release` and `pre-release`, so a `develop` request 404s and reads as no release the same way an empty channel does for any other addon. The icon comes from the mirror's own `icon.png` route, which redirects to the repo owner's GitHub avatar, so a manifest-host addon's icon logic covers it without a branch.

A manifest (`AddonRelease.Requires`) or a catalogue row (`CatalogueAddon.Requires`, mapped to `ManagedAddon.Requires`) may carry `requires`, the field `docs/upcoming/protected-addons.md` in steward-server defines: each entry is a catalogue id string or an object `{ id, name, folder_name, manifest_base_url, requires }` (`AddonRequirement`, read by `AddonRequirementConverter`, which drops an entry with no id rather than failing the manifest); steward-server's CurseForge manifests list a file's required dependencies as `curseforge:<modId>` objects. Before a row installs its own build, `AddonRowViewModel.InstallSelfAsync` runs `MainViewModel.InstallRequirementsAsync`, which walks both lists through `AddonRequirements.InstallAsync` (Core) depth-first, dependencies before dependants, to depth 3, skipping an id already on the walk: each entry resolves to a visible row by id (`AddonRequirements.Matches`, so `curseforge:<modId>` matches that install's `curseforge-<modId>-<versionType>` record) or folder, else to a new CurseForge record or a bare `ManagedAddon` from the object; one whose folder is already on disk with its own TOC, at any version, or whose key is in `ignored_addons`, is skipped; the rest fetch their manifest on the dependant's channel (the ordinary `AddonChannelStatus.Resolve` fallback), install with the row's progress bar and "installing <name> (needed by <addon>)" as its status, and are recorded like any install, a CurseForge one also as a `ProviderAddonRecord` so it becomes a normal row. A requirement that cannot be resolved, has no build or fails to install fails the dependant with "Could not install <name> (needed by <addon>): ..." (`AddonRequirementException`). `WowInstallViewModel.RefreshRequired` sets `AddonRowViewModel.RequiredBy` on every row an installed row requires, which hides Uninstall, Ignore and Hide on it as `AutoInstall` does. A curseforge:// link install asks steward-server's files route with `?versionType=` so the file's own manifest carries `requires`.

A catalogue row's behaviour comes from declarative fields steward-server fills on every row (`docs/upcoming/protected-addons.md`, "Declarative rows"), read onto `ManagedAddon` and resolved there, rather than from the `source` string: `manifest_auth` (`session` fetches the manifest with the `Steward` client, `ManifestNeedsSession`), `zip_auth` (parsed and unused; always `none`, since a signed zip URL carries its own token), `zip_relative` (whether a relative `zip` resolves against the manifest URL; an absolute `zip` is used as given either way, and a relative one on a row that is not `zip_relative` fails the install, `AddonUpdater.ZipUri`), `auto_install`, `updates_while_unreachable` (`MayUpdateWhileUnreachable`, read by `AddonCatalogue.UpdatesWhileUnreachable`), `source_label` (the Source column, `DisplaySource`) and `curseforge` (the CurseForge gate, the Local-scan exclusion, the zip folder union, the unknown-version read and download-failure reporting, `IsCurseForge`), plus `requires` above and `notice` (`{ icon, text }`, both optional, `AddonNotice`, cached in `state.json` and omitted when null), which `AddonRowViewModel` draws as a small icon button after the addon name on the Addons table row, with `text` as its tooltip: `icon` `lock` is the Fluent lock glyph (`E72E`) and any other value the info glyph (`E946`), so the wording is steward-server's to change. After every install or update of a row that `AddonThemeFile.AppliesTo` (it has a `notice`, `manifest_auth` `session` or the `Protected` source), `AddonRowViewModel.WriteThemeFile` writes `Core/Theme.lua` in each of that row's folders that already has one (the zips ship a placeholder with `ns.themeId = nil`) as exactly `local _, ns = ...` and `ns.themeId = "<Discord user id>"` (LF, UTF-8 without BOM, temp file then move, never outside the addon's own folder), using the signed-in user's `/api/me` `user.id`; it writes nothing when signed out and rewrites every row when `MainViewModel` sees the account change. The id identifies who fetched a protected addon if a copy is shared, which the catalogue `notice` text says to users; no UI, log line or state key names it beyond the file. A row without a field falls back to its `source` string as before, so an older server changes nothing; a `Protected` row without them reads as `manifest_auth` session, not `zip_relative`, `source_label` "Steward", no `updates_while_unreachable` and not `curseforge`. `Protected` is the source of every HoobiScripts addon served from steward-server's gated `/api/addons/protected/<id>/` routes, whose manifest needs the session and whose `zip` is an absolute signed URL fetched with the cookie-less `Addon` client and hash-verified like any other. This is the release after which a catalogue change needs no client update: a new kind of row is expressed in these fields, and a behaviour they cannot express is a client change that extends them rather than adding a `source` string.

`docs/design/addon-manager.md` is the built Addons page: one table per selected WoW install, listing every configured addon `VisibleAddons()` passes plus a Local row for every other folder in that install's `AddOns` holding its own TOC. A folder whose TOC names another unmanaged folder as a dependency folds into that folder's row instead of getting one of its own, resolved through chains to the root, so a DBM-style suite of folders reads as one row; a folder depending only on a configured addon still gets its own row. A folder's top-level TOC is picked by the install's client interface (`TocFile.InterfaceNumber(ClientVersion)`): among `<Folder>.toc` and every `<Folder>_*.toc`, the first whose `## Interface:` list holds that number wins, suffixed before base, and with no match or an unknown client interface the base TOC (else the first suffixed) is used (`LocalAddons.TopLevelToc`), since Questie's base TOC is an interface-0 stub and the client loads `Questie_Camelot.toc`. `LocalAddons.Scan` in `Steward.Core` builds the list and `WowInstallViewModel.RescanLocal` rebuilds it on startup, on Refresh, and after an install or uninstall on that install, never on the background pass. The table's column widths, `IsCompact` (the Channel column dropped) and `IsVersionStacked` are computed only from widths that do not change with those modes (`HomePage.MeasureVersionCell`): a managed row's Version need is its current version or "No releases yet", its "Released {relative}" line measured off the tree whether or not it shows, and its Channel cell, while the version pair's own width comes from `VersionFloor`; the mode-dependent elements (the released line, the folded channel chip, the wide and stacked pair) are never measured live. The cell measured as a whole made the released line count only outside compact mode, so at one width the table switched between the two layouts on every layout pass (`ColumnFitTests` sweeps the window width 1px at a time and fails on that).

An install added by hand whose folder is gone is kept and shown greyed as "Folder not found" rather than dropped (`docs/design/addon-manager.md`, Missing installs). `MissingInstalls.Detect` (Core) runs on startup and Refresh only, recording `missing_since` per path, and reports a path due for removal after 14 days when its drive root still exists; a path on an absent drive is never auto-removed. Whether the drive is present is `InstallVolume.IsPresent` (Core): the path root on Windows and macOS, and on Linux, where the root is always `/`, the deepest mount in `/proc/self/mountinfo` holding the path: the drive counts as absent when an `/etc/fstab` mount point deeper than that holds the path (a configured disk that is not mounted), or when only `/` holds a path under `/media`, `/run/media` or `/mnt` (an unmounted removable or hand-mounted disk), with mount points matched on whole segments and their octal escapes decoded. A disk mounted by hand outside those folders and not in `fstab` reads as on `/`, so its install can still be removed 14 days after it was unmounted. `MainViewModel.DetectMissingInstalls` removes the due ones through `RemoveInstall(path)`, the one removal path, which calls `AppStateStore.RemoveInstall` (every per-path key and both side files). A missing install (`WowInstall.IsMissing`, built by `WowInstalls.MissingFromPath`) gets no addon rows, no local scan, no `StewardSync.lua` write, no character push and no RestedXP card; selecting it shows a centred message with Remove, and a once-per-episode local banner (dismissal recorded in `dismissed_banners` under `missing-install|{path}|{missing_since ticks}`) offers Remove too. User-driven removals confirm through `AppDialogs` first.

A user can ignore updates for a configured addon on one install, from the row's overflow menu. The key is `AppStateStore.Key` (flavour path plus addon id) in `ignored_addons` in `state.json`; an installed ignored row reads "Updates ignored" in amber in its status column, with "Update available" beneath it when there is one, and is excluded from the Updates count, Update all and `AutoApplyAsync`. A user can also hide an addon they manage through CurseForge or WowUp, from the same menu. Hidden ids live in `hidden_addons` in `state.json`, global rather than per install, and hidden rows are excluded from counts, auto-apply, Update all and the default and Updates views; the Hidden segment in the table's toolbar shows them again with a Hidden pill so they can be unhidden. Neither Ignore nor Hide is offered on an `AutoInstall` addon. Release channels are edited in the row's own channel dialog rather than on the Settings page.

The manifest for an addon+channel is `{ManifestBaseUrl}latest-{channel}.json`; the release zip resolves relative to that manifest URI, so an absolute `zip` URL is used as-is. A CurseForge manifest may carry a structured `changelog` (`ChangelogBlock` headings, paragraphs and depth-indented items whose `ChangelogRun`s may hold an http(s) `href`), which `ChangelogDialog` renders; a manifest without one shows its plain `notes` lines as depth-0 items (`Changelogs.For`). A manifest fetch sends `Cache-Control: no-cache` only from a manual Refresh (`RefreshAsync` passing `noCache` through `CheckAsync` to `AddonUpdater.ProbeChannelsAsync`), never from startup, the background pass or a retry; steward-server serves a CurseForge manifest from its 15-minute cache otherwise, and on `no-cache` refetches one 60 seconds old or more. Manifest fetches are conditional: `AddonUpdater.FetchManifestAsync` keeps the `ETag` and the parsed manifest per manifest URL in a `ManifestCache` (in memory; one per `AddonUpdater`, `AddonUpdater.ManifestCache`, and one inside `AppUpdater` for the MSI manifest), sends `If-None-Match` on the next fetch and reuses the stored manifest on a `304`, the literal `null` of an empty channel included. A response without an `ETag` drops the entry, so a server that sends none is fetched in full every time, and a `304` with nothing stored is refetched without the header. The 404 refetch in `InstallRefetchingOn404Async` never revalidates (`revalidate: false`), since a stored protected manifest names a signed zip URL that may have gone, and the cache is cleared on sign-out and when the signed-in user changes. SHA-256 verification and the zip-slip guard are unchanged from the single-addon version. A row installs through `AddonUpdater.InstallRefetchingOn404Async`: a 404 on the zip refetches the manifest once and retries with the build it names, since a publish after the manifest fetch can delete the zip (steward-server keeps a replaced protected zip for an hour). An existing addon folder is only deleted when it holds its own top-level TOC as `LocalAddons.TopLevelToc` picks it, `<Folder>.toc` or a flavour-suffixed `<Folder>_<flavour>.toc` named after the folder itself (QuestieDB ships only flavour TOCs); a folder with neither is refused (`AddonUpdater.RemovalRefusal`). After every install or update, and on startup and Refresh for every installed, unhidden managed row (configured, GitHub-mirrored and CurseForge alike), `InGameIcon.EnsureAsync` gives the primary folder an in-game icon when none of its top-level TOCs carries a `## IconTexture:` line: the row's own icon URL is fetched with the `Addon` client (a row with no `icon_url` behind a session manifest, `ManagedAddon.IconNeedsSession`, such as BugGrabber, is skipped, since its `icon.png` answers only with the session cookie and logged a 401 on every start), scaled to 64x64 and written as `StewardIcon.tga` through `AvatarTga.Encode` (the bottom-left-origin layout `Avatar.tga` and StewardGuides' `Icon.tga` already load with in the Forever client), and `GeneratedAddonIcon` (Core) adds `## IconTexture: Interface\AddOns\<Folder>\StewardIcon` after the last `##` line of every top-level TOC byte for byte, so encoding and line endings are kept; Local and unadopted folders are never touched, since CurseForge fingerprint matching hashes the TOC, and a failed fetch or decode is logged and skipped.

## Auth: default-browser sign-in over a loopback callback

steward-server accepts exactly one credential, the `gg_session` cookie (`SessionAuthentication` in `src/Steward.Data/AdminAccess.cs`), with no bearer or API-key path, and exposes a desktop flow that hands that cookie's raw value to a local client. `SessionService` generates a verifier (base64url of 32 random bytes) and a challenge (lowercase hex SHA-256 of the ASCII verifier, matching Python's `hexdigest`), binds a listener, and opens `GET {BaseUrl}/api/auth/desktop?challenge=<challenge>&port=<port>` in the default browser. steward-server runs the Discord OAuth exchange and redirects the browser to `http://127.0.0.1:<port>/?code=<one-time code>`. The app then POSTs `{"code","verifier"}` to `{BaseUrl}/api/auth/desktop/exchange` and receives `{"token": "<gg_session value>"}`; the code is single-use with a 120-second TTL.

The listener is a `TcpListener` on `IPAddress.Loopback` with port 0. `HttpListener` cannot bind port 0 and its HTTP.sys prefix semantics need a fixed registered prefix, and Kestrel pulls an ASP.NET framework reference into a self-contained publish, so neither is used. The whole flow times out after 5 minutes. Every accepted connection gets the same fixed 200 HTML page telling the user the tab can be closed, including the favicon request the browser makes alongside the callback; `LoopbackCallback.WaitForTokenAsync` in `Steward.Core` runs that accept loop, `TryReadCode` decides which request line carries a code, and a rejected code keeps the listener waiting, so "click this link" relaunching the same URL from a second tab is safe. steward-server refuses a user who is in no Steward server by redirecting to `http://127.0.0.1:<port>/?error=not_member` (`TryReadError`): that ends the wait at once with `SignInRefusedException`, and the gate shows "You are not a member of a Steward server" as a sign-in failure rather than waiting out the 5-minute timeout. A code exchange answered `403` with a JSON body whose `error` is `not_member` (`StewardClient.HasErrorCode`, the body parsed rather than matched as text) throws the same `SignInRefusedException` and ends the wait the same way. Any other `error=` value, a request with neither `code` nor `error`, and a failed code exchange (a rejected code, a non-JSON body, an `HttpRequestException` or an HTTP timeout, but not `client_outdated`, which still ends the wait) keep the listener waiting until the timeout; when the timeout then arrives after an exchange that could not reach Steward API, `SessionService` throws that failure so the gate reads Unreachable rather than Timeout. Each accepted connection has its own 10-second read and write limit (`LoopbackCallback.ConnectionTimeout`), so a socket that connects and sends nothing cannot stall the listener. The sign-in URL reaches `MainViewModel` through an `IProgress<string>` created on the UI thread, and the view model alone owns the pending-URL state and clears it when the attempt ends: the wait resumes on the thread pool, and a6cf296's `PendingSignInUrlChanged` event raised there threw `RPC_E_WRONG_THREAD` from a WinUI binding inside the `finally`, discarding a token already exchanged with no error on the gate. A failure other than a timeout, cancel or unreachable API shows its message on the gate (`GateFailure.SignInFailed`).

steward-server slides the session to 30 days from last use on every authenticated request, with no absolute ceiling, and never re-issues the token; the app's own `/api/me` checks are what keep it alive. Removing a user's last seat on the guild panel deletes their sessions server-side, so a demotion reaches the app as a 401 on the next check rather than as `role: null`. The app persists the raw token itself (`session_token` in `%LocalAppData%\Steward\state.json`, through `SecretProtection`) rather than relying on the cookie jar as the store; the browser flow is only how the token is acquired, once, at sign-in. On Windows the value is a DPAPI `CurrentUser` blob. On Linux and macOS (`SecretProtection.Unix.cs`) it is an AES-GCM blob (`SecretSeal` in Core: 12-byte nonce, 16-byte tag, ciphertext) under one random 32-byte session key per user, so `state.json` never holds the raw token on any OS. The key is read once per run, from `secrets/session.key` in the data folder when that file exists, else from the keyring; when neither has it a new key goes to the keyring, else to that file (folder `0700`, file `0600`, set at creation, temp then move), and where it came from is logged. Since the file is read first, a key once written there stays the key, and a start never waits on a keyring. On Linux the keyring is the Secret Service, used only while `DBUS_SESSION_BUS_ADDRESS` is set: first over D-Bus directly (`Services/SecretServiceKeyring.Unix.cs` in `Steward.Desktop`, the `ISecretKeyring` that `Program.Unix.cs` sets as `SecretProtection.SecretService` before the app starts, through `Tmds.DBus.Protocol` on the session connection: `OpenSession` with the `plain` algorithm, `SearchItems`, `Unlock` with its `Prompt` and `Completed` signal when the item or the default collection is locked, `Item.GetSecret`, `ReadAlias("default")` and `Collection.CreateItem` with replace, the session closed after each call), then through the `secret-tool` CLI (Ubuntu's `libsecret-tools`), then the file. Both keyrings use service `Steward`, account `session-key`, label "Steward session key" and the base64 key as `text/plain`, so an item one wrote the other reads (verified 16 Oct 2026 with gnome-keyring 46 in WSL, both directions). A keyring that answers Unavailable (no bus, no service, a D-Bus error, no default collection) passes to the next, a lookup that times out ends the walk, and a failed store passes on; libsecret answers a missing bus with exit 1 and no output, the same as a missing item; on macOS it is the login Keychain through `security` (exit 44 is a missing item; stored with `security -i` so the key is not in argv; not yet run on a Mac). Each keyring call has a 5-second limit (the D-Bus one runs on the thread pool and is waited on, as `TrayHost` does). A lookup that times out (a locked keyring waiting on a prompt, or a dismissed unlock prompt; a headless gnome-keyring with a locked `login` collection answered in 5.04 s) keeps that run's sessions in memory only and creates nothing, so the stored key still works on the next run; a store that times out or fails, or a keyring that errors, falls back to the next keyring and then the file. `Tmds.DBus.Protocol` is in `Steward.Desktop`'s closure through Avalonia but not in `Steward.Presentation`'s, so the D-Bus client lives in Desktop and reaches `SecretProtection` through the `ISecretKeyring` interface; Desktop tests never set it, so they never touch a real keyring. A blob from one OS never reads on another, and a blob whose key is gone reads as a bad blob, which signs the user out.

The API origin is `https://api.hoobi.io/guild` (`Steward:BaseUrl`). `guild.hoobi.io` is the Static Web App hosting the SPA, and its navigation fallback answers every `/api/*` path with `index.html` and a 200, so a client pointed there sees HTML where it expects JSON rather than a 401.

Every privileged action re-checks `GET /api/me`: at startup, immediately before an update, on every `accessChanged` event, and from the 1-minute background pass, which skips it while the access event stream is live and a check ran within the last 15 minutes (jittered like the other fallbacks), so the per-minute call only runs while that stream is down. A 401 means the session is gone; the persisted token is cleared and the app drops to signed-out. Any other failure (a 502, a timeout) marks the API unreachable: the error bar shows the message with a Retry button, the Sync page is disabled, the account ring reads Reconnecting, both event streams keep running on their own reconnect loop rather than being cancelled, and the timer retries every minute instead of every fifteen until a check succeeds and clears the state. A 5xx or a transient failure (`TransientHttp.IsRetryable`: any 5xx, or what `TransientHttp.IsTransient` matches, so a refused or reset connection and a timeout too; an `IOException` counts only as an `HttpIOException`, one inside an `HttpRequestException` or one wrapping a `SocketException`, so a local file failure such as a read-only or locked AddOns folder is never retried through this queue) from any operation that sets the error bar (this check, an addon manifest probe, the CurseForge manifest check, the guild roster pull, auto-apply, the background pass, startup) shows "Steward APIs are temporarily unavailable." only once the failing spell has lasted 5 seconds, so a blip such as a server restart never flashes the bar (a one-shot grace timer started by the first retryable failure, not restarted by later ones, and stopped when every retry has succeeded; a failure that is not retryable shows its message at once), and queues that operation in `MainViewModel.ApiRetry.cs` (`ReportFailure`, keyed per operation), retried on `TransientHttp.Backoff` (1, 2, 4, 8 and 16 seconds, then every 30); the bar clears once every queued operation has succeeded, by its retry or by its own next run (`ResolveApiRetry`), the bar's Retry button or either event stream reaching ready runs the queue at once (`RetryApiNow`), and sign-out empties it. `StewardClient` puts the response status on every `HttpRequestException` it throws, so the 5xx check sees it. The directory pull, the banner fetch and the character push stay off the error bar; a transient failure there (a 502, 503 or 504, a refused or reset connection, a DNS failure or a timeout, `TransientHttp.IsTransient` in Core) keeps the last good data and marks that work due on the next 1-minute pass. No request is retried inside the HTTP pipeline. An authenticated response whose effective feature set is empty (nothing to do in the app at all) clears the session and drops the app to the gate with a "no Steward access" bar, the same treatment as a 401. This re-check keeps the UI truthful; it is not enforcement, since the zips themselves are served from a public Static Web App with no auth of their own. A role or flag change still reaches the app between those checks: while signed in, `MainViewModel` keeps one connection to `GET /api/events` (`StewardClient.StreamAccessEventsAsync`), open for every signed-in user regardless of feature, not just `steward` holders. Unlike the guild stream's `event: <type>` framing, this route (steward-server's per-user SSE endpoint, `EventStream` in `src/Steward.Api/EventStream.cs`) carries its frame type inside the JSON `data:` payload as `{"type": "<name>", ...}`, so `StreamAccessEventsAsync` reads it with `ServerSentEventReader.ReadFramesAsync` and parses `Data` rather than the SSE event field. An `accessChanged` frame queues `RecheckAuthorizationAsync` (debounced ~1 second; while a background pass is in flight the recheck waits for it to finish and then runs, rather than being dropped, since that pass may have read `/api/me` before the change or skipped it because the stream was live), and that recheck signs out on a 401 and applies the lost-access removal above, so a role or feature flag added or removed elsewhere reaches feature gating, addon rows, the Sync/Guides pages, guild features and the `me` dataset within seconds; every other frame type on this stream is ignored. The reconnect, backoff and idle-timeout rules are the same as the guild stream (`TransientHttp.Backoff`: 1, 2, 4, 8 and 16 seconds, then every 30, reset when the stream reaches ready; 60 seconds of silence counts as dropped, a 401 signs out, a 404 means an older server and the stream stays off for the run), except that a 403 or 429 only backs off and retries rather than stopping the stream, since this route has no guild scope to be denied on. None of it touches the error bar or `StatusMessage`.

Lost access removes addons the companion installed (`AccessLoss` in Core, `MainViewModel.LostAccess.cs`). Only a catalogue row whose `Source` is `Steward` or `Protected` and is not `curseforge` counts, and only on an install that has its install record in `installs` (so a manual copy is never touched); the folders removed are the record's `folders` plus the row's `folder_name`, through `AddonUpdater.Uninstall` and its TOC guard, and `WTF` saved variables are never touched. There is no download cache to clear: release zips go to a temp file that `InstallAsync` deletes. There are two triggers and no others. First, a `401` whose body is `{"error":"revoked"}` on any route of the `Steward` client (`SessionRevokedHandler`, beside `ClientOutdatedHandler`, buffers the body and only reports; the caller still throws `SessionExpiredException`): `SignOutTo` marks every such install due at once (`AccessLoss.Revoke`) before it clears the catalogue, then signs out as for any 401. The revoked mark (`SessionRevocation`) is set only while signed in, taken by the one sign-out it causes, and cleared whenever the signed-in state changes, so a `revoked` answer that arrives after sign-out never reaches a later manual sign-out or plain 401. Second, a successful parsed `/api/me` whose `addons` list is non-empty but no longer holds a row that the previous catalogue had: `RecheckAuthorizationAsync` records the first-missing time per install (`AccessLoss.Track`) and the row becomes due only on a later successful check at least 30 minutes after that time (`AccessLoss.Grace`). A record is dropped when the row reappears, when its install record is gone, or when its install is removed. Records live in `lost_access` in `state.json` (flavour path, id, name, source, folders, `first_missing`, `due`), so a restart neither resets nor skips the wait. A plain 401, a timeout, a network error, a 5xx, a body that does not parse, an empty or missing `addons` list and `NotAuthorized` never mark anything. Due removals run from `AccessLoss.RemoveDue` after every check, after sign-out and at startup before the session restore returns; an install whose WoW client is running (or whose row is busy) is skipped and retried when that process exits (`WowClient.WaitForExitAsync`), whether or not the user is signed in. Each removal shows "<Addon> was removed because your access ended" as a local banner while signed in, or in an InfoBar on the sign-in gate while signed out (`AccessRemovedNotice`, cleared on the next sign-in). A row that reappears in the catalogue reinstalls through the ordinary auto-install path.

steward-server retires a route this or an older build calls by answering it with `410 Gone` and `{"error": "client_outdated", "message": "<text for the user>"}`. No route is retired this way at present. `ClientOutdatedHandler` in `Steward.Core` is a `DelegatingHandler` on the `Steward` named client, so every request on it (`StewardClient`, the SSE streams and `AddonUpdater`'s CurseForge manifest fetches) passes through it: a 410 whose body carries `error: "client_outdated"` throws `ClientOutdatedException` with the server's `message` (a fixed sentence when `message` is missing or empty), and any other 410, unparseable body included, is returned unchanged. `ClientOutdatedException` derives from `HttpRequestException` with `StatusCode` 410, so a catch site that handles a network failure still handles it. The handler also calls `MainViewModel.ReportClientOutdated` on every such response, from whichever call hit it, which puts the app in `GateFailure.ClientOutdated`: the error bar shows the server's message with an "Update Steward" button in place of Retry, running the same Store path as a banner's `store_update` action (`CheckOrInstallAppUpdateAsync` for a packaged GitHub-release build, else the Store's Updates and downloads page), and the signed-out gate shows the same bar. The session and the persisted token are kept. While in that state the background pass skips the `/api/me` recheck, and everything behind it, until 15 minutes have passed since the last `client_outdated` answer. The state lasts for the rest of the run, since a successful `/api/me` recheck says nothing about the other retired route that raised it, and only a new sign-in resets it. Either SSE stream that receives `client_outdated` stops for the rest of the run, the same as a 404. `--client-outdated-preview` (`src/Steward.Presentation/Services/ClientOutdatedPreview.cs`) puts the app in that state with no network, honouring `--tray`, for UI verification.

`/api/me`'s `user.features` is a `string[]` of `guides`, `steward`, `sync`, `roster`, `professions`, `signups` and `addons`, the user's OVERALL grants across every guild. Access is gated on that set, never on `role`: a guild member can be granted `guides` by Discord role or user id on the server side, independent of holding an officer seat; `steward` comes only with an officer seat; `sync`, `roster`, `professions`, `signups` and `addons` can each be granted without one. `addons` is an officer default and is also derived server-side for anyone holding `sync` or `hoobiscripts`, alongside being manually grantable, and it is what the RestedXP, BugSack and BugGrabber addon rows are gated on. `role` global/admin is only the fallback used to derive the set when an older server sends no `features` field at all, in which case an officer gets every officer feature (`addons` included) and everyone else gets none; `role` is `"raider"` for a seatless caller holding any of `sync`/`roster`/`professions`/`signups`/`addons` in some guild, and treated exactly like a null role everywhere this app checks for an officer (`IsProfessionsOnlySync` and the rest all pattern-match "not global/admin", so `raider` already falls out the same way `null` does). `StewardClient.EffectiveFeatures` computes that user-level set from an `AdminMe`; `StewardClient.IsAuthorizing` treats `guides`, `steward`, `sync`, `roster`, `professions`, `hoobiscripts` and `addons` as each counting towards the app's access gate (`signups` alone does not, since nothing in the app reads it yet, and neither does `curseforge`, which the app no longer reads: CurseForge management follows `addons` and a setting). `MainViewModel` keeps the user-level set in `_features`, which drives `HasGuidesFeature`, `VisibleAddons()` and `IsAuthorized`.

Every `/api/me` guild entry also carries its own `features`, that guild's resolved set (`StewardClient.ResolveGuildFeatures`, falling back to the user-level set when a guild entry carries none, as from an older server), since an officer of one guild is a plain member of another. `MainViewModel` keeps the SELECTED guild's set in `_guildFeatures`, recomputed (`UpdateGuildFeatures`) whenever `_guildId` or the user-level set changes, and reads `HasStewardFeature`, `HasSyncFeature` and the roster/professions pulls (see Character sync) from it rather than from `_features`, so switching guild in the account menu immediately reflects that guild's own access: a push or a roster pull is only attempted for a guild whose features actually allow it, never left to a 403. `IsProfessionsOnlySync` (`HasSyncFeature` without `HasStewardFeature`) is therefore also per guild, so an officer granted `sync` on a server where they hold no seat pushes the professions-only payload there. The guides gate itself lives inside `RestedXpViewModel`, not in `MainViewModel`: it takes a `Func<bool> hasGuidesFeature` at construction (`() => HasGuidesFeature`) and checks it in `CheckAsync`, `RefreshSessionAsync`, the per-install saved-variable confirm, and before setting up each install's `FileSystemWatcher`, so a feature drop stops every one of those without a caller having to remember the gate; guides is not guild-scoped, so it stays on the user-level set. `IsGlobalAdmin` (`role == "global"`) is unrelated to any of this; it no longer gates anything since the `develop` addon channel it once gated was removed. A non-officer's `guilds` list is empty, except for a caller holding one of `sync`/`roster`/`professions`/`signups`, who gets the guilds they are a Discord member of and hold at least one of those in; steward-server still answers 403 on every other `/api/admin/` route below `me` for them, so admin-only roster and members stay officer-only. The guild is chosen from the Guild row of the account menu (opened from the account entry at the bottom of the navigation pane), which shows the selected guild and, with more than one guild, opens a nested custom `Flyout` to its right (`RightEdgeAlignedTop`) listing each guild's icon, name, "{n} member(s) · {role}" and a check on the current one, where the role is that guild's own ("Officer" when its resolved features include `steward`, else "Member"; `/api/me` carries no per-guild role, only the account-wide one), opening on hover after the system menu show delay like a `MenuFlyoutSubItem` (`MainWindow.AttachSubmenu`); with one guild the row is not interactive. When more than one guild comes back and the stored `guild_id` is not among them (first sign-in, or removed from the chosen guild), `MainViewModel.PromptForGuildAsync` shows `ChooseGuildDialog` once per recheck that finds it so, while the window is visible, with the first listed guild preselected (steward-server sorts the guild last saved through `PUT /api/me/guild` to the front of `guilds`, and `/api/me` carries no explicit "selected" marker, so the server's own remembered-or-first guild is the best available default); Continue stores the choice, matched by guild id since `Guilds` can be rebuilt while the dialog is open. A prompt that finds the window hidden (a `--tray` start) is deferred and runs from `MainWindow.ShowFromTray` (`MainViewModel.ResumeGuildPrompt`) instead of surfacing from an unrelated recheck; a prompt failure is logged rather than left to `UnobservedTaskException`. A user-driven guild switch also calls `PUT /api/me/guild` (`StewardClient.SetSelectedGuildAsync`) so steward-server starts a new device or browser on the same server; the app already has that guild locally, so a 404 (an older server), a 400, a 401 or a network failure is only logged and never surfaces on the error bar or signs the user out.

## Channels

Two release channels, named after what produces them in `hoobio/addons`: `release` (a tagged GitHub release of the addon) and `pre-release` (every push to the addon's `main`). The `develop` channel (every push to an addon's `develop` branch) was removed on 26 Sep 2026: the download site no longer publishes it, so probing it is pointless and it is gone from `AddonChannelStatus.Ordered`; an addon repo's own `develop` branch is unaffected. RestedXP has `release` and `pre-release` only, mapped to the GitHub release and prerelease flags steward-server's mirror reads. The channel is per addon, stored in `Channels` alongside the install-state records in the same `state.json`, defaulting to the first channel that has a release in the order `release`, `pre-release` (`AddonChannelStatus.Ordered`, also the picker order). When a more stable channel holds a build released after the one on the chosen channel, the row shows a notice naming it, so being on `pre-release` while a newer `release` exists is visible without switching. The rename from `stable`/`beta`/`unstable` was not migrated: a stored old channel name falls back with the "No releases on X any more" notice. A stored `development` or `develop` value is migrated to `pre-release` on load: `AppStateStore.MigrateDevelopChannel` rewrites it, alongside the `LegacyChannel` seed; if that addon has no `pre-release` build, the ordinary `Resolve` fallback drops to `release` instead and says so in the row's notice.

Each WoW install + addon pair records what was actually installed (version, channel, and the manifest's `sha256` and/or `sha1`, each under its own key), keyed by flavour path plus addon id. With no record, the addon's own `.toc` version is the fallback, which is the manual-install case. Update availability is plain string inequality between that recorded/TOC version and the channel manifest's version, not a semver comparison: versions like `0.5.0-beta.1` and `0.5.0-unstable.219da29` don't parse as `System.Version`, and switching channels has to be able to move the installed version in either direction.

## WoW install discovery

`WowInstalls` walks `.flavor.info` (product code) joined against the root `.build.info` (product to version) to find each flavour without a hardcoded product-to-folder map. The Blizzard registry key (`HKLM\...\World of Warcraft`) is not used as a discovery root by itself: on the dev machine it is hijacked by an unrelated Ascension install, so it is one candidate root among several, never the only one trusted.

The candidate roots differ per OS. On Windows they are the registry `InstallPath` and `World of Warcraft`, `Program Files\World of Warcraft` and `Program Files (x86)\World of Warcraft` on every fixed drive. On macOS they are `/Applications/World of Warcraft` and `~/Applications/World of Warcraft`, then the same drive scan. On Linux WoW runs only through Wine, so `WinePrefixes.WowRoots` (Core) adds `drive_c/Program Files (x86)/World of Warcraft` and `drive_c/Program Files/World of Warcraft`, each folder name matched ignoring case, in every one of these prefixes: `$WINEPREFIX` and `~/.wine` (Wine's default); the `prefix:` value of each Lutris game config in `$XDG_CONFIG_HOME/lutris/games/*.yml`, `$XDG_DATA_HOME/lutris/games/*.yml` (Lutris falls back to the data folder when the config one is missing) and the Flatpak `~/.var/app/net.lutris.Lutris/{config,data}/lutris/games/*.yml`; each folder one level under `~/Games` (where Lutris installs `battlenet` by default, an unconfirmed default), `~/Games/Heroic/Prefixes/default`, `~/Faugus`, `$XDG_DATA_HOME/bottles/bottles` and the Flatpak `~/.var/app/com.usebottles.bottles/data/bottles/bottles`; and `steamapps/compatdata/*/pfx` under `~/.steam/steam`, `$XDG_DATA_HOME/Steam` and the Flatpak Steam's `data/Steam` and `.local/share/Steam`. Nothing below those levels is searched. On Linux a flavour folder's `Interface/AddOns` is also matched ignoring case (`WowInstalls.AddOnsPath`, through `WinePrefixes.FindIgnoringCase`), both to accept the flavour folder and as the install's `AddOnsPath`, since a Wine prefix keeps whatever case the copy or tool wrote; with no such folder yet the path is the plain `Interface/AddOns`. Confirmed from each project's source or docs: Wine's default, the Lutris config folders and its wine runner's `game_config.get("prefix")`, the native Bottles folder, `~/Games/Heroic/Prefixes/default`, `~/Faugus` and the Flatpak Steam `data/Steam` compatdata. Unconfirmed and probed only because a miss costs nothing: the per-game folder layout under Heroic, Faugus and the Bottles Flatpak, the native Steam roots, the Flatpak Steam `.local/share/Steam` form and the macOS paths. A hand-added install takes a POSIX path as is. On 16 Oct 2026 a read-only bind of the Windows install at `~/Games/battlenet/drive_c/Program Files (x86)/World of Warcraft` in WSL showed the beta with its client version, the held live install and the beta's Local rows.

`WowClient` finds a running client per OS too. On Windows and macOS it reads `Process.MainModule` of a process named `Wow*` (on macOS also `World of Warcraft*`). On Linux the process is the Wine preloader (`comm` reads `wine`), so `WowClient.WineClients` reads `/proc/<pid>/cmdline` for the first argument whose file name is `Wow*.exe` and maps a Windows path through the process's own `WINEPREFIX`, else `STEAM_COMPAT_DATA_PATH/pfx`, else `$HOME/.wine` (`WinePrefixes.ToUnixPath`: `C:` to `drive_c`, `Z:` to `/`, other letters through `dosdevices`), falling back to `/proc/<pid>/cwd`; verified 16 Oct 2026 with Wine 11.0, where the argument was `C:\Program Files (x86)\World of Warcraft\_forever_\Wow.exe` and `WaitForExitAsync` returned for the non-child process. On Linux `AddonManagerApps` reads `$XDG_CONFIG_HOME/autostart/*.desktop` (skipping `Hidden=true` and `X-GNOME-Autostart-enabled=false`, and requiring the `Exec` file to exist) and each process's first argument and `APPIMAGE` variable, comparing names with the version, `.AppImage`, case and hyphens removed (`AddonManagerApps.AppKey`), so `WowUp-CF-2.24.0.AppImage` is WowUp-CF and never WowUp (WowUp's AppImage asset name and its `auto-launch` autostart are from its source; the running process names of CurseForge, WowUp and WowUp-CF on Linux are not confirmed); macOS checks running processes only. The "Open Battle.net" button runs `BattleNet.Launcher` (Core): the `battlenet:` handler's exe on Windows, `/Applications/Battle.net.app` on macOS (unconfirmed path), and `lutris:rungame/battlenet` on Linux when a Lutris `battlenet-<id>.yml` exists, which `xdg-open` hands to Lutris's `x-scheme-handler/lutris` (the button was seen on 16 Oct 2026; the launch itself was not run); with none it is hidden.

Discovery is filtered to `SupportedProducts` in `appsettings.json`, a product code to display name map, since the managed addons target World of Warcraft: Forever only. It holds the live client `wowf` (`_forever_`, "World of Warcraft: Forever", `Wow.exe`) and the beta `wow_classic_beta` (`_classic_beta_`), both at interface 16001 and both mapped to CurseForge version type 88568; `docs/forever-release.md` lists every value and what the beta's retirement touches. From 21 Oct 2026 (`ForeverLaunch.Date`, local date) `MainViewModel.EnsureSelection` moves a selection still on a beta install to a present `wowf` install once (`ForeverLaunch.MoveFromBeta`, recorded as `forever_selection_moved` in `state.json`), so a user who picks the beta again afterwards stays on it.

While a present `wow_classic_beta` install exists, a `wowf` install whose flavour path is not in `forever_copy_done` in `state.json` is held out of `Installs` (`ForeverCopy.IsGated`, applied in `MainViewModel.DiscoverInstalls`, which startup and Rescan both use, and held the same way by `MainViewModel.BrowseAsync` for a hand-added path): no picker entry, no rows, no auto-install, no character push, no guides and no local scan. A user with only the live client is never gated. While a beta install is present and no live install is found or held, a dismissible local banner, "Install World of Warcraft: Forever" (`dismissed_banners` key `forever-install`), points at the Battle.net app, where the live client is listed as "Stress Test". Its "Open Battle.net" action starts the exe named by the `battlenet:` protocol handler (`HKCR\battlenet\shell\open\command`, so a non-default install location is found), since a `battlenet://` link leaves a tray-minimised Battle.net hidden; with no handler or no exe at that path the banner has no button. `--forever-install-preview` shows the banner whatever the installs, and a dismissal in it records nothing. While the install is held, a local banner that cannot be dismissed, "Copy your addons to World of Warcraft: Forever", opens the copy wizard (`MainWindow.ShowForeverCopyAsync` through `AppDialogs`); Copy and "I'll do it myself" add the path to `forever_copy_done` and release the install (`MainViewModel.ApplyForeverGate`, also run on Refresh, so a beta that goes missing releases it too), and "Not now" changes nothing. Once released, the Addons page header shows "Sync from beta" while the live install is selected and a beta install is present, which opens the same wizard with Sync and Cancel. Both run `ForeverCopy.Sync`, a newer-wins sync that never deletes anything on the live install: a beta AddOns folder missing on live is copied whole (staged as `<Folder>.steward-copy` and moved into place), a folder on both that Steward does not manage on live (not a configured or catalogue folder, not StewardGuides, not a recorded CurseForge folder or a folder in any live install record) is updated file by file where the live file is missing or has an older `LastWriteTimeUtc`, and managed folders are left to Steward's own updates. `WTF\Account` is synced the same way at account level only, as two options: "Account saved variables" (`<account>\SavedVariables\*`, `*.bak` excluded, and `Steward.lua`, which holds the beta's characters that the live install would then push as its own) and "Account settings" (every other file directly in `<account>`); realm and character folders are never copied, since they are named after the beta's realms and characters. "Graphics, sound and narration" merges the beta's video, sound and screen narration CVars (an allowlist in `ForeverCopy`: `graphics*`, `raidGraphics*`, `RAID*`, `Sound_*`, `Gx*`, `maxFPS*`, `shadow*`, `lodObject*`, `accessibility*`, `showScreenNarrationDialog` and named video CVars) into the live `WTF\Config.wtf` line by line, replacing a differing value in place and appending a missing one, temp then move, and leaves every other line (portal, locale, cache counters, `hwDetect`, `videoOptionsVersion`) as it is. Its count is the CVars whose value differs, since the client rewrites `Config.wtf` on every exit and its date says nothing, and it starts checked only when the beta's file is newer. With no live `Config.wtf` it is disabled with "Start Forever once first" and nothing is written, since a file of graphics lines alone lacks the client's own detection markers. Each option shows its count, computed off the UI thread before the dialog opens, and an option with nothing newer is disabled and unchecked. The dialog's CheckBox glyphs are re-centred against their two-line labels in `Loaded`, since the template top-aligns them. The copy refuses while either client is running or a row on either install is busy, checked before the plan and again before the copy, which holds `AddonUpdater.AddOnsWriteLock` for the AddOns part. ## Self-update

A Store build updates through the Microsoft Store and an MSI build from the latest GitHub release's MSI (see MSI self-update below), and either installs its own update rather than only pointing at one. `AppInfo.IsPackaged` (`GetCurrentPackageFullName` answering anything but `APPMODEL_ERROR_NO_PACKAGE`) splits packaged from unpackaged. A packaged, GitHub-release build (`AppInfo.IsGitHubRelease`) checks the Store through `StoreContext.GetAppAndOptionalStorePackageUpdatesAsync`, with the window handle passed through `InitializeWithWindow` as a desktop app requires, on the startup pass, on Refresh and at most once an hour from the 1-minute background pass (`_lastStoreCheck`, wall-clock like `_lastGuideCheck`). On startup and on a "Check for updates" press only (the title bar command and the InfoBar/About card path both run `CheckOrInstallAppUpdateAsync`), the check is preceded by a forced Store scan scoped to Steward, `AppInstallManager.SearchForUpdatesAsync(App:StoreProductId, "")`: `StoreContext` otherwise only sees an update once the Store app has scanned for it on its own schedule. `AppInstallManager` is documented as gated behind a Microsoft-only private capability, but it runs unelevated from this full-trust process with no capability declared, verified 28 Sep 2026. The product-scoped scan alone does not refresh the Store's catalogue for a flight: verified 29 Sep 2026 against a published flight, `SearchForUpdatesAsync` returned no item twice (also with `AppUpdateOptions.AutomaticallyDownloadAndInstallUpdateIfFound`) and `StoreContext` still reported 0 updates afterwards. `AppInstallManager.SearchForAllUpdatesAsync()`, the Store app's own "Get updates", is the call that does: in that same run it threw on completion (`AggregateException`, cause not captured) yet still queued Steward in `AppInstallItems`, and the next `StoreContext` check then found the update. Because this call is exactly the Store app's Get updates, it also queues every other Store app's pending update on the machine, not just Steward's, so it only ever runs on an explicit "Check for updates" press: `ForceStoreScanAsync(scanAllApps: true)`, called from `CheckOrInstallAppUpdateAsync` (packaged GitHub-release build) and from the same direct press path for the dev package and the Debug build, runs it after the product-scoped scan, logs `AppInstallItems`'s count and whether Steward was queued, and swallows any exception from it into the log rather than `StatusMessage`. The startup pass and the background pass never request it. `RegisterApplicationRestart` runs before that scan (see below) because on 28 Sep 2026 `SearchForUpdatesAsync` returned a null `AppInstallItem` yet the Store still installed the update about a minute later, so the scan itself can close the app. When `StoreContext.CanSilentlyDownloadStorePackageUpdates` is true (the user has automatic app updates on and the connection is not metered) and no addon row is mid-update, an update found on any of those checks installs silently through `TrySilentDownloadAndInstallStorePackageUpdatesAsync`. Otherwise the InfoBar and About card's Install button call `RequestDownloadAndInstallStorePackageUpdatesAsync`, which raises Windows' own consent dialog. A `_storeInstall` field tracks whichever of the two is in flight: `CheckStoreUpdateAsync` skips starting a silent install while one is already running, and `InstallAppUpdateAsync` awaits the in-flight install instead of starting a second, so a silent install from the background pass and an explicit install from the button or a banner's Install action never race each other. Both paths call `RegisterApplicationRestart` first (`WindowsStore.RegisterRestartForStoreUpdate`, `--tray` when the main window is not visible and `--no-activate` when it is, `RESTART_NO_CRASH | RESTART_NO_HANG | RESTART_NO_REBOOT` so only an update restarts the app rather than a crash, hang or reboot too) so Windows closes Steward to apply the update and relaunches it rather than leaving it stopped. A failed or user-cancelled install falls back to opening the Store's Updates and downloads page (`ms-windows-store://downloadsandupdates`), since the product page of an installed app offers no update button; a cancelled install is silent otherwise. The InfoBar's action label reads "Install update". A banner's `store_update` action, while signed in, navigates to Settings, brings the About card into view with a short accent pulse and runs the About card's own `CheckOrInstallAppUpdateCommand` (when its `CanExecute` allows), so every build behaves as if the user pressed that button, progress included; signed out, it runs `CheckOrInstallAppUpdateAsync` for a GitHub-release build (Store or MSI) and opens the Updates and downloads page otherwise, so posting the banner before `StoreContext` has surfaced the update (or on a dev or Debug build) still does something rather than nothing. The ClientOutdated error bar's Update Steward button keeps that signed-out path. A Store failure goes to the status bar. A packaged, non-GitHub-release build (the dev package) and the Debug build never see an update: `AppUpdate` is null on both. The dev package and the Debug build (both non-`GitHubRelease`) still run the same forced Store scan on the same two triggers, since the scan targets the installed Store copy of Steward (`Hoobi.Steward_thayxpy3eqg0g`) rather than the running build: `ForceStoreScanAsync` skips `RegisterApplicationRestart` and every `StoreContext` call for these builds (they need the running process's own Store package identity), and instead logs the Store copy's installed version (`PackageManager.FindPackagesForUser`) before the scan and again two minutes after, without blocking the UI or touching `StatusMessage`, so the log shows whether the scan actually moved the Store copy. An MSI build (unpackaged but still `GitHubRelease=true`) is unaffected either way, since it never ran the scan before this and still does not.

An install in progress shows its progress in the app-update InfoBar and the About card: a determinate `ProgressBar` with "Downloading update… 42% (12.3 of 29.1 MB)" while downloading, an indeterminate one with "Installing update… Steward will restart" while deploying and "Waiting for the Microsoft Store…" while pending, with the Install button disabled and reading "Installing…". Three sources feed one `StoreUpdateProgress` (`Steward.Core`) held in `MainViewModel.AppUpdateProgress`: the `Progress` handler on both the explicit and the silent `IAsyncOperationWithProgress`, and the `StatusChanged` event of a `StoreQueueItem` of kind `Update` from `StoreContext.GetAssociatedStoreQueueItemsAsync`, looked for on every Store check while no install of the app's own is in flight and `StoreContext` reports an update, so an update the Store queued itself (after the forced scan, say) shows too; with no update reported the queue is not followed at all, since the finished install's queue item outlives the restart and, followed, held the relaunched app on "Installing update… Steward will restart" (a tester on 0.17.2, 29 Sep 2026). A queue item still waiting (paused, or active at `Pending`) is shown only while `StoreContext` reports an update, since on 29 Sep 2026 the Store kept a Pending item for Steward with no update behind it and the Install button stayed on "Installing…". `PackageDownloadProgress` covers the download from 0.0 to 0.8 and the install from 0.8 to 1.0, so the percentage is that value over 0.8 and anything at or past 0.8 reads as installing. Both sources report on a background thread, so each update is throttled to one per 250ms per phase and marshalled to the UI thread through the injected `IUiPlatform`, and a report queued before the install finished is dropped. Phase changes are logged as "Store update: <phase>" and the end as "Store update: finished <state>"; a completed install keeps the installing state until Windows closes the app, and a cancel or failure clears it. `--update-progress-preview` (`src/Steward.Presentation/Services/UpdateProgressPreview.cs`) fakes an available update and loops pending, download 0 to 100% and installing every 12 seconds or so through the same reporting path, with no network and no `StoreContext`, for UI verification.

An MSI build (`AppInfo.BuildName == "msi"`: unpackaged, on Windows, and `GitHubRelease=true`) updates itself from steward-server's mirror of this repo's GitHub releases. `AppUpdater.CheckMsiAsync` fetches `{Steward:BaseUrl}/api/addons/steward-companion/latest-release.json` anonymously on the `Addon` client through `AddonUpdater.FetchManifestAsync` (a 404 means no release), on the same triggers as the Store check: the startup pass, Refresh, a "Check for updates" press and at most hourly from the background pass (`_lastStoreCheck`). The manifest's `version` is the release tag (`v0.20.2`) and its `zip` the release's `.msi` asset. An update is a manifest version greater than `InstalledVersion` (`AppUpdater.IsNewer`, which is `AppVersion.IsNewer` in Core: semver precedence after a leading `v` and any `+` suffix are dropped, 3 or 4 numeric parts, a pre-release below its release and its dot-separated identifiers compared numerically where both are numbers, so `-preview.23` is above `-preview.9`, and a malformed side never counting as newer), and there is no pre-release channel, since no pre-release carries an MSI. The outcome is recorded in `app_update_check` like a Store check, so the About card reads "Up to date" or "An update is available" the same way, and the InfoBar reads "Steward {version} is available" with its changelog link on the release's tag page. Install is prompted only, never silent, and refused with a status message while an addon row is busy: `AppUpdater.DownloadMsiAsync` refuses a manifest version that is not 3 or 4 dot-separated numbers with an optional leading `v`, `-` suffix and `+` suffix of letters, digits, dots and hyphens (the version is part of the file name), then checks where the MSI comes from before downloading anything: the manifest's `zip` must be exactly `https://github.com/hoobio/steward-companion/releases/download/<tag>/<file>.msi` (default port, no user info, query or fragment, `AppUpdater.ReleaseAsset`), `<tag>` must equal the manifest `version` once a leading `v` or `V` is dropped from each, since steward-server's mirror writes `v0.21.2` and `hoobio/addons`' mirror `0.21.2` for the tag `v0.21.2` (so a manifest cannot point a higher version at an older genuine MSI), the manifest must carry a `sha256`, and the release asset's `digest` from `GET https://api.github.com/repos/hoobio/steward-companion/releases/tags/<tag>` (unauthenticated, on the cookie-less `Addon` client with `Accept: application/vnd.github+json` and a `User-Agent`, once per update; the asset matched by `name` and `browser_download_url`, the digest read as `sha256:<64 hex>`) must equal the manifest's `sha256`. A null or missing digest, any other mismatch, a GitHub API failure or a non-JSON answer throws `UpdateVerificationException`: nothing is installed, the failure is logged and the status bar reads "The Steward update could not be verified: ...". It then downloads the MSI to `%TEMP%\Steward-{version}.msi` through `AddonUpdater.DownloadAsync` (GitHub answers the download with a 302 to `release-assets.githubusercontent.com`, which the client follows; the digest check is what binds the bytes), with progress fed into `AppUpdateProgress` as "Downloading update… x% (a of b MB)", verifies the file against GitHub's digest through `AddonUpdater.VerifyChecksumAsync`, and `AppUpdater.InstallMsiAfterExit` starts a hidden `powershell.exe` hand-off (`InstallMsiScript`, run through `RunAfterExit`) that waits for this process to exit, runs `msiexec /i "<msi>" /qn /l*v "<data folder>\update.log"` through `-PassThru -Wait`, stops on an exit code other than `0` or `3010` (a reboot-required success) and only then deletes the MSI; every value it interpolates into single-quoted PowerShell is escaped with `.Replace("'", "''")`. The app quits through `QuitRequested` right after starting it. The script does not relaunch the app: `installer/Steward.wxs`'s `LaunchSteward` custom action runs after `InstallFinalize` whenever `UILevel < 5`, which a `/qn` install (`UILevel` 2) meets, and it starts the installed `Steward.App.exe` with no arguments, so the window shows after an update whether or not it was in the tray. A download or checksum failure goes to `StatusMessage` and clears the progress. The ClientOutdated bar's Update Steward button and a banner's `store_update` action run this same check-or-install path on an MSI build.

`hoobio/addons`'s mirror only considers a GitHub release that carries an `.msi` asset, and releases carry one again, so the next `hoobio/addons` publish (it has no schedule, and nothing here dispatches it) moves the `release` manifest to the latest MSI and a 0.11.0 install polling `addon.hoobi.io` self-updates to it once, after which it updates from steward-server's mirror as above.

Which path a build takes is `AppInfo.UpdateSource` (`AppUpdateSources.Resolve` in Core, from the OS, `IsPackaged` and `GitHubRelease`): `Store` for a packaged Windows release build, `Msi` for an unpackaged Windows release build, `ReleasePage` for a release build on Linux or macOS, under Wine, and for the unzipped portable exe on Windows (`AppInfo.IsPortableZip`, the `PortableZip` `AssemblyMetadata` that `desktop-builds.yaml` sets for the zip of a release and of a preview), and `None` for every non-release build. The outcome goes in `app_update_check` as for every check. The signed-out gate shows the same update bar as the Addons page: the title, the progress or the last status message, and the button. The patch reads the submission through `Get-StorePendingSubmission` (same script), which polls `submission get` (or `flights submission get`) every 30 seconds, up to 10 times, until it lists the uploaded `.msixupload` by `FileName`, and fails the job otherwise: on 4 Oct 2026 (0.20.2) `get` answered right after the upload with the last published submission, and patching and committing that shipped the previous release's package. The file-path form of `msstore publish` (a `.msixupload`/`.msixbundle` passed as the positional argument, not `-i <directory>`) is confirmed working: `hoobio/command-palette-bitwarden`'s `store-publish` job uses the identical `msstore publish $bundle -id $env:PRODUCT_ID --noCommit` form against a `.msixbundle` and succeeded (run 31148741706, job "Publish to Microsoft Store"). The patch goes through `msstore submission update`, not `submission updateMetadata`, because `updateMetadata` sends only availability, properties and listings (`MSStore.API/Models/UpdateMetadataRequest.cs` in `microsoft/msstore-cli`) and drops `PackageDeliveryOptions`, while `update` PUTs the whole submission. Both take their JSON inline as a positional argument with no file-input flag, so the patched submission JSON is read from disk and passed as `(Get-Content -Raw patched.json)`. Every release and flight submission sets `PackageDeliveryOptions.IsMandatoryUpdate` with `MandatoryUpdateEffectiveDate` at submission time, merged into the existing delivery options so rollout settings are kept. The Store does not enforce the flag: it only sets `StorePackageUpdate.Mandatory` for the app's own `Windows.Services.Store` code to act on. Pre-releases never reach the Store. `msstore` only updates an app that is already live in the Store, so the first submission has to be made by hand in Partner Center: submit a pre-release `.msixupload` there manually, and only publish the bridge GitHub release (the one that triggers `store-submit`) once that manual listing is live, since `store-submit` clones the live submission rather than creating the app's first one.

The "What's new in this version" listing field is filled from the being-released version's own `CHANGELOG.md` section, keeping only the Features and Bug Fixes entries and dropping every other conventional-commit type; `scripts/Get-StoreWhatsNew.ps1` strips each entry down to its plain description (scope, gitmoji and commit-hash link removed) and truncates at a bullet boundary to the Store's 1500-character `ReleaseNotes` limit, replacing the dropped entries with a closing "and N more changes" line. A version whose changelog section holds neither section returns "Minor improvements and fixes." rather than leaving the listing untouched. Every `feat` and `fix` commit therefore reaches Store users, so a commit that changes nothing a user of the installed app sees (the workflow, packaging, Store submission, the dev build) is typed `ci`, `build` or `chore`.

The `store-flight` job runs after every `build-msix` (a manual dispatch, and a release-please release run), because flight testers only ever receive flight packages and never the non-flighted submission (Partner Center's package flight ranking), so a release reaches them only as a flight too. On a release run it submits the same package `store-submit` does, built with `StorePreRelease` off, so the tester's build carries no " (Pre-release)" suffix. It runs only when both the `STORE_FLIGHT_ID` and `AZURE_CLIENT_ID` repo variables are set (the same Key Vault OIDC login, credential masking and `msstore reconfigure` steps as `store-submit`). It waits out and deletes any pending flight submission through the same `Wait-StoreSubmissionClear` helper `store-submit` uses, pointed at `msstore flights submission status/delete 9PBKMZFKZHKX <flightId>` instead of the plain `submission` form, publishes the flight build (`msstore publish <msixupload> -id 9PBKMZFKZHKX --flightId <flightId> --noCommit`, retried up to 3 times 60 seconds apart and re-running the wait first when it fails with "Error while creating flight submission"), marks it mandatory through `msstore flights submission get` and `msstore flights submission update`, and commits it (`msstore flights submission publish 9PBKMZFKZHKX <flightId>`), checking `$LASTEXITCODE` after every call except the delete. It patches no release notes. A run cancelled mid-sequence (a newer dispatch cancels an older dispatched run) leaves at worst a pending flight draft; the next run's wait-and-delete clears it before publishing again, so a flighted tester never sees a half-submitted build linger. Flight testers are a known user group managed by hand in Partner Center; this repo has no record of who is in it. The submission API only updates, deletes and commits submissions it created itself, so a draft started in Partner Center (including the empty one Partner Center makes alongside a new flight) makes the delete and `msstore publish` answer "created through the API" instead of clearing normally; `Wait-StoreSubmissionClear` stops the job immediately with `::error::` naming that submission's id rather than looping on it, since only a human can delete it in Partner Center before either Store job can run again. Both jobs carry a 90-minute `timeout-minutes` to give the 60-minute wait room alongside the rest of the job.

A named mutex (`Local\Steward.App`, acquired in `Program.Main` before `Application.Start`) enforces one running instance across every train, so the name is shared between the Store build and an MSI install still in the wild rather than stamped per channel. `InstanceCoordination` decides what a second launch does with it: a launch of the SAME train (Store/flight, MSI, the dev package, Debug, `AppInfo.Train` is `BuildName` with `prerelease` folded into `store` since a Store flight is the same package; the trains are `store`, `msi`, `preview`, `portable`, `dev` and `debug` on Windows and `linux`, `macos` and `debug` elsewhere) signals the running instance to come to the foreground (`Local\Steward.App.Show.<train>`, an `EventWaitHandle` the running instance waits on from a background thread and marshals to `MainWindow.ShowFromTray` on the UI thread) and exits without showing anything; a launch of a DIFFERENT train signals the running instance to quit (`Local\Steward.App.Quit`), waits up to 15 seconds for the global mutex, and on success shows a dismissible "Closed the &lt;train&gt; build automatically" info bar through the same banner mechanism as a server banner. Each running instance also holds `Local\Steward.App.Running.<train>`, probed with `EventWaitHandle.TryOpenExisting` rather than any file, since a file a packaged build newly creates lands in per-package virtualised storage that another train's process does not see. The signalled instance quits through its own tray Quit path (`MainWindow.QuitFromAnotherBuildAsync`), waiting up to 10 seconds for a busy addon row to finish first so it never blows the newcomer's 15-second budget. A same-train launch carrying a `curseforge://` link first writes the URI as one line to the running instance's per-train named pipe (`Steward.App.Link.<train>`, `PipeOptions.CurrentUserOnly`, a 5-second connect timeout, logged and skipped on failure) and then sets the show event; the running instance reads it on a background loop and hands it to `MainViewModel.ReceiveCurseForgeLinkAsync` on the UI thread. A different-train launch carries its link through the quit-and-take-over path and handles it as a cold start. Windows App SDK `AppInstance` redirection is not used, since the named events already decide which instance keeps running. `InstanceCoordination.Windows` also probes the old preview trains `store-avalonia`, `msi-avalonia`, `dev-avalonia` and `debug-avalonia`, so a pre-cutover preview still running is closed by the first current build that starts. On Linux and macOS (`InstanceCoordination.Unix.cs`) named events do not exist and `Local\` names one login session (two terminals each acquire it, verified 16 Oct 2026), so the mutex is `Steward.App` with `NamedWaitHandleOptions { CurrentUserOnly = true, CurrentSessionOnly = false }` (a lock under `/tmp/.dotnet-uid<uid>`, separate per user, freed when its owner is killed), and every signal goes through one Unix domain socket per train, `<train>.sock` in `$XDG_RUNTIME_DIR/steward`, else `<LocalApplicationData>/Steward/run`, a folder kept at mode 0700. A launch connects to its own train's socket and, when it answers, writes `link <uri>` (when it carries one) and `show` (unless started with `--tray` or `--no-activate`) as UTF-8 lines and exits; otherwise it sends `quit` to the first other `*.sock` that answers, waits up to 15 seconds for the mutex, then binds its own socket, deleting the file first, since a killed instance leaves it behind and a refused connection reads as not running. The running instance accepts on a background loop, reads each connection's lines within 10 seconds, ignores unknown lines and a link over 2048 characters, and marshals show, quit and link to the same UI-thread handlers as on Windows; lines sent before `ListenForSignals` wait in the listen backlog. Verified 16 Oct 2026 under Xvfb in WSL: a same-train second launch with a link exited in 0.06 seconds and the first logged the link and the show, a relaunch after `kill -9` started and answered, and an MSI-train launch closed the running Debug train and bound its socket in 0.1 seconds. `Mutex.WaitOne` throwing `AbandonedMutexException` counts as already acquired, since a Store update force-kills the old process without releasing it. A `WM_QUERYENDSESSION`/`WM_ENDSESSION` subclass on the window (`MainWindow`'s `Native.HookSessionEnd`) always quits outright, bypassing Close to tray, so a Store update's forced shutdown does not wait out a 30-second kill timeout.

`MainViewModel.CheckStoreUpdateAsync` catches every exception from the `StoreContext` call itself and routes it to `StatusMessage`, rather than relying on the caller's typed catch clauses, since a WinRT failure there is not guaranteed to be a `COMException`.

Every Store, package and startup-task WinRT call lives in `WindowsStore` (`StoreContext` and its update and queue APIs, `AppInstallManager`, `PackageManager`, `StartupTask`, `RegisterApplicationRestart`), and the launcher and data-folder calls in `WindowsShell` (`Launcher`, `ApplicationData`); `CurseForgeDefaultQuery` keeps the `IApplicationAssociationRegistration` call. `MainViewModel` keeps the orchestration, the progress reporting and every `StatusMessage`, and `WindowsStore.ToProgress` maps a `StorePackageUpdateStatus` to Core's `StoreUpdateProgress` (`UpdateProgressPreview` goes through it). Under Wine (`AppInfo.IsWine`) the Store scan, the Store update check and the startup task are skipped entirely. A creation step (`StoreContext.GetDefault`, `new AppInstallManager()`, `new PackageManager()`, `StartupTask.GetAsync`, or the association COM object) that fails with a `TypeLoadException`, `DllNotFoundException`, `EntryPointNotFoundException` or a `COMException` of `REGDB_E_CLASSNOTREG` (`0x80040154`) or `CLASS_E_CLASSNOTAVAILABLE` (`0x80040111`) (`WindowsStore.IsActivationFailure`) is logged once and turns that feature off for the run, with no `StatusMessage`; any other failure is reported and retried as before: a Store failure goes to `StatusMessage` and the next check tries again, and a startup task read failure shows "Could not read the Start with Windows setting". With the startup task off the toggle is disabled and reads "Start with Windows is not available on this system".

When packaged, "Open data folder" prefers `Windows.Storage.ApplicationData.Current.LocalCacheFolder.Path\Local\Steward` over the literal `%LocalAppData%\Steward` when that folder exists, through the shared `WindowsShell.DisplayDataFolder` helper: a packaged process's newly created files under `%LocalAppData%\Steward` land in that virtualised location, so pointing Explorer at the literal path would not show them; where the real folder already exists (the usual case, see Development install) no such folder is created and the literal path is shown. The About card shows the version and, on the line beneath, the update state; it does not show the install path. Every successful `StoreContext` or MSI manifest check records its outcome in `app_update_check` in `state.json` (the displayed version, whether an update was found, when), so a later launch of the same version reads "Up to date" or "An update is available" before its own check finishes; a different version reads "Not checked for updates yet" until one does. The dev and Debug builds never check for an update and say so on that line instead. The real `%LocalAppData%\Steward` path is unchanged for `state.json` and `update.log`, which the packaged and unpackaged builds still share.

The Start with Windows toggle shows distinct, disabled text for each locked `StartupTaskState`: `EnabledByPolicy` reads on with "Turned on by your organisation's policy", `DisabledByPolicy` reads off with "Turned off by your organisation's policy", and `DisabledByUser` reads off with "Turned off in Windows Settings > Apps > Startup".

A WinUI install that updates to this build sees the Avalonia rebuild's window chrome, menus and fonts (the bundled Hanken Grotesk, Cascadia Mono and Fluent UI System Icons in place of Segoe), and its MSIX no longer depends on the Windows App Runtime. The train, the data folder (`state.json`, the DPAPI secrets, the logs, `provider_addons.json`, `character_sync.json`), the session, the Run value, the Start menu shortcut, the `StartupTask` and the `curseforge` protocol carry over: the executable is still `Steward.App.exe`, the train names are those the WinUI build used, `SecretProtection` is the same `ProtectedData` call for the current user with no entropy, and the MSI keeps its `UpgradeCode`, so it upgrades in place.

0.11.0 was the MSI release that bridged existing installs across to the Store, through a Switch-to-Store banner since removed; releases after 0.20.2 attach an MSI again, and an MSI build updates itself from those releases as described under Self-update.

## Development install

Every `git push` from this clone builds HEAD and registers it as a second, side-by-side packaged app, so a developer always has a running build of `main` without touching the Store install. `scripts/Install-DevBuild.ps1` never touches the working tree: it exports the pushed commit with `git archive HEAD` into a scratch copy at `%LocalAppData%\Steward.Dev\src` (wiped first), builds the Avalonia app from that copy with `scripts/Build-DesktopMsix.ps1 -Identity Dev -Version <version.txt>.<git rev-list --count HEAD>` into `%LocalAppData%\Steward.Dev\build`, the identity being `Hoobi.Steward.Dev` with publisher `CN=Hoobi Dev` and both display names reading "Steward (Development)", and the commit count (capped at 65535) making each push a higher version, an in-place update. It stops a running `Steward.App` or `Steward.Desktop` from that folder, removes any registered `Hoobi.Steward.Dev` with `Remove-AppxPackage -PreserveApplicationData` (whatever its version, since a same-version register fails with 0x80073CFB), copies the layout to `%LocalAppData%\Steward.Dev\app` and registers it with `Add-AppxPackage -Register`, which Developer Mode accepts unsigned. A commit made while the build is running never ships the dev identity and `git status` stays clean throughout. The package is self-contained, so it needs no Windows App Runtime. The Start menu entry is "Steward (Development)"; the package family name is `Hoobi.Steward.Dev_<publisher-hash>`, distinct from the Store's `Hoobi.Steward_thayxpy3eqg0g`.

The single-instance mutex is `Local\Steward.App`, unconditional across every build (Store release, Store flight, MSI, the dev package and the Debug build), so the dev package and the Store package no longer run side by side: starting one while the other is running closes the running one first, per `InstanceCoordination` under Microsoft Store. The Store update check (`CheckStoreUpdateAsync`, via `StoreContext`) only runs when `AppInfo.IsGitHubRelease`, since a dev identity is never in the Store; a packaged non-GitHubRelease build reports no update rather than surfacing a Store error.

The manifest's `StewardStartup` `StartupTask` is scoped per package identity, so enabling Start with Windows for the dev package cannot collide with the Store package's own toggle: each autostarts independently with `--tray` if the user turns it on for that package.

A packaged full-trust app's writes under `%LocalAppData%` are virtualised only for newly created files and folders, which go to `%LocalAppData%\Packages\<PFN>\LocalCache\Local`; a file that already exists in the real `%LocalAppData%\Steward` is opened and modified in place ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes), "AppData operations on Windows 10, version 1903 and later"). The manifest declares no `desktop6:FileSystemWriteVirtualization` or unvirtualised resources. Verified 29 Sep 2026: the real `%LocalAppData%\Steward` holds `state.json`, `provider_addons.json`, `character_sync.json` and `logs\` (including `steward-dev-*` and `steward-store-*` files), while neither package's `LocalCache\Local` holds a `Steward` folder. The dev package therefore reads and writes the same `state.json` as the Store and unpackaged builds and starts signed in on a machine that is signed in elsewhere, and `WindowsShell.DisplayDataFolder` finds no `LocalCache\Local\Steward` and shows the literal path.

`.githooks/pre-push` triggers the build: a POSIX `sh` script that starts `scripts/Install-DevBuild.ps1` fully detached and hidden, then exits 0 immediately, so a slow or failing dev build never blocks or fails a push. Run `git config core.hooksPath .githooks` once per clone to pick it up; `.gitattributes` forces it to LF regardless of the checkout's `autocrlf` setting. Everything the script does is logged to `%LocalAppData%\Steward.Dev\install.log`.

## Git workflow

Commits go straight to `main` in the one working tree at `D:\steward-companion` and are pushed there; this repo uses no feature branches, no worktrees and no pull requests for its own work, and a subagent edits `main` in place. Conventional-commit subjects feed release-please, which opens the release PR itself. A session or subagent that does create a branch or worktree must delete it, locally and on origin, once its work is on `main` or abandoned and before it finishes; a branch or worktree found with no live owner is merged to `main` or deleted rather than left behind.

A push to `main` runs release-please and lint and tests only. A Store pre-release flight build for testers is a manual run of the `Build & Release` workflow (`gh workflow run build.yaml --ref main`), since each flight submission deletes the one still in certification and restarts certification from zero, which takes hours; a release-please release run builds and submits on its own. A change is built, tested and, where it is visible, UI-verified locally before it is pushed.

## Build and test gotchas

Tests are fast by rule. The Core suite (about 800 tests) runs in about 2 seconds, and a new test keeps it there: no `Thread.Sleep`/`Task.Delay` waits, no real network, no real WoW or `%LocalAppData%` paths (temp directories only), and no per-test setup heavier than building the object under test. A test that needs time passing uses an injected clock or timestamp, not a wait. While iterating, run the affected test class (`--filter-class` or `--filter`); the whole suite runs once before pushing. steward-server's integration tests follow the same rule, set out in its AGENTS.md.

`Steward.slnx` defines no `Release|x64` solution configuration, so a solution-level `dotnet build` must not pass `-p:Platform=x64`; the CI workflow builds the solution without it and publishes `Steward.Desktop.csproj` at project level with `-r win-x64`.

`global.json` pins the SDK to `10.0.203` with `rollForward: disable`, because `DOTNET_SDK_VERSION` in the workflow only says what `setup-dotnet` installs and the runner image ships newer SDKs that `dotnet` would otherwise pick; it also sets `test.runner` to `Microsoft.Testing.Platform`. The publish step retries up to three times, since NuGet restore on the runner can fail with a bare MSB4181 "RestoreTask returned false but did not log an error" and no cause (NuGet/Home#13460), as it did twice on 20 Sep 2026. On .NET SDK 10.0.203, `dotnet test <directory>` fails under that runner; the working form is `dotnet test --project <csproj>`, which is what the CI workflow uses.

With two TFMs, `dotnet test --project` runs one test process per TFM at once, so a test never writes a fixed name under the temp folder without isolation: `tests/Steward.Core.Tests/TempFolderFixture.cs` points `TMP`, `TEMP` and `TMPDIR` at a folder of its own per process, since `AppUpdater.DownloadMsiAsync` writes `Steward-<version>.msi` there. `-f net10.0` runs one TFM. On Linux the Core suite runs with the pinned SDK installed by `dotnet-install.sh --version 10.0.203` and passes in full (1084 tests, 16 Oct 2026), and the Desktop suite runs there under Xvfb (`DISPLAY` set, `-p:EnableWindowsTargeting=true`).

`Microsoft.Win32.Registry` is already in-framework on `net10.0-windows` and compiles on `net10.0`, where it throws off Windows, so every registry call is guarded with `OperatingSystem.IsWindows()`; adding it as an explicit `PackageReference` fails restore with `NU1510`. `WowInstalls.cs` uses `Microsoft.Win32.Registry` directly, and neither `.csproj` in this repo references the package.

CommunityToolkit.Mvvm's field-backed `[ObservableProperty]` triggers diagnostic `MVVMTK0045` in a UI project; the ViewModels here declare partial properties instead (`[ObservableProperty] public partial string? Foo { get; set; }`).

## Diagnostic logging

The app writes a daily-rolling diagnostic log to `%LocalAppData%\Steward\logs\steward-<build>-YYYYMMDD.log` (the same folder for a packaged build, which modifies the existing real folder in place), through `FileLoggerProvider` in `Steward.Core` (`src/Steward.Core/Diagnostics`), registered as an `ILoggerProvider` in `StewardServices.AddStewardServices` alongside the existing `Microsoft.Extensions.Hosting`/`Logging` setup. `<build>` (`AppInfo.BuildName`, derived from `IsPackaged`/`IsGitHubRelease`/`IsPreRelease`) is one of `prerelease`, `store`, `dev`, `msi`, `preview`, `linux`, `macos` or `debug`, so the Store release, a Store flight, the side-by-side dev package, an unpackaged MSI install and a Debug build never contend for the same file lock when several run at once. Each line is `<UTC ISO timestamp> <level> <category>: <message>`, with an exception's full `ToString()` (stack included) on the following line; writes are single-threaded behind a lock and flushed per line. `LogFileRetention.DeleteOlderThan` runs at startup and drops any `steward-*.log` file older than 14 days, across every build name. Minimum level is Information for `Steward.*` categories and Warning for `Microsoft.*`/`System.*` (`builder.Logging.AddFilter`).

Instrumented through `ILogger<T>` injected where the class is already resolved through DI (`MainViewModel`, `SessionService`, `AddonUpdater`, `RestedXpService`, `StewardGuildSyncApi`) or passed as a parameter to the one static call site that needs it (`GuildRosterSync.WriteIfChanged`): every start (one `Steward <version> starting (<build name>, <OS>, <arch>)` line, without which a signed-out start on a fresh profile wrote no line and so no file, since the file opens on the first write), sign-in (start, browser launch, callback received, code exchange, completion or failure), every `/api/me` recheck (authorized/401/unreachable, role, feature count), guild roster and character-directory pulls (counts, 403/404 handled quietly, 401), character pushes (accepted/rejected counts, 403/429/unreachable), both SSE event streams (connect, ready, drop with reason and backoff, give-up), banner fetches, Store update checks, addon manifest probes and installs (per addon and install path), `StewardSync.lua`/`StewardGuides` writes (written/skipped-unchanged/failed) and RestedXP session refresh failures. `Dispatcher.UIThread.UnhandledException`, `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` are hooked in `App.OnFrameworkInitializationCompleted` to log at Critical without changing how they are otherwise handled.

Never logged: the `gg_session` cookie/token, the sign-in code or PKCE verifier, RestedXP tokens or password, and any DPAPI blob; the sign-in URL is logged through `LogRedactor.PathOnly`, which drops its query string (the challenge and callback port) entirely rather than judging what in it is sensitive.

## UI verification

A change to anything visible is checked in the headless suite (`tests/Steward.Desktop.Tests`, including the UiPaths suite) before it is reported done; a clean build is not evidence that a view looks or behaves right. A live run on top of that launches the Debug app, which takes the foreground, so it waits for Hoobi's go-ahead. The sequence:

1. Stop any running Debug build of `Steward.Desktop` (`Get-Process Steward.Desktop -ea 0 | Where-Object Path -like 'D:\steward-companion\*' | Stop-Process`), since a running instance locks the exe and the build then fails on the copy step rather than on the code; installed builds run as `Steward.App`, so that process name is a Debug build only, and the path filter keeps a Debug build of another clone running.
2. `dotnet build Steward.slnx -c Debug`, then launch `src\Steward.Desktop\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Steward.Desktop.exe`. It shares `%LocalAppData%\Steward\state.json` with the installed build, so it starts signed in with real data.
3. Drive it from PowerShell with `tools\UiDriver.psm1`: `Start-UiApp`, `Find-UiElement` (UI Automation), `Invoke-UiClick`, `Write-UiValue`, `Show-UiElement`, `Move-UiScroll`, `Save-UiScreenshot`, and `Get-UiPopup` for a menu or flyout, which opens as its own top-level window. The scenario script for a given change is written per task in the scratchpad and is not checked in. `Find-UiElement -Where` calls its scriptblock with the element as the first positional argument, so a filter is written `{ param($el) $el.Current.Name -eq '...' }`; `$_` is unbound there and a `$_` filter never matches.
4. Read every screenshot. For motion (hover, press, open), `Measure-UiTransition` pen-hovers a point and captures the window in a loop for 250ms, returning each frame's sampled colour, so a flash shows up as a frame brighter than both ends.

The user works at this machine while an agent drives the app, so the driver moves no mouse cursor and sends no mouse or keyboard input. `Invoke-UiClick` goes through UI Automation patterns (Invoke, then Toggle, then SelectionItem, then ExpandCollapse) and throws when an element supports none of them; text goes through `ValuePattern` (`Write-UiValue`) and scrolling through `ScrollItemPattern` and `ScrollPattern`. Avalonia's Win32 automation peers serve the Invoke path, and `DialogCommandButton` handles Invoke for it (see Avalonia desktop app).

Captures use `PrintWindow` with `PW_RENDERFULLCONTENT` (`0x2`) on the window handle, so an overlapping window, the user's cursor and a snipping overlay never appear in them. `Save-UiScreenshot -Popup` captures a popup's own window the same way and draws it over the main window at its screen offset, and `-Rect` crops to a screen rectangle. Popup capture is not yet verified: a flyout opened through `InvokePattern` while another window held the foreground was not found by `Get-UiPopup`, likely light-dismissed on deactivation.

Hover uses synthetic pen input (`CreateSyntheticPointerDevice` with `PT_PEN`, then `InjectSyntheticPointerInput` with `POINTER_FLAG_INRANGE | POINTER_FLAG_UPDATE` and no `INCONTACT`), in `Move-UiPointer` and `Exit-UiPointer`, and a tap is `Invoke-UiPenTap` (hover, then a `DOWN | INCONTACT` frame, then an `UP` frame, then out of range). On 29 Sep 2026 none of these reached the WinUI build: the injection calls succeeded and `GetLastInputInfo` advanced, but a tap on an unselected filter tab and on either title bar button changed nothing and logged no `Flyout` line, a hover showed no `PointerOver`, and synthetic touch behaved the same. `GetCursorPos` read the same before and after each tap, so the cursor is left alone. Until a run shows pen input reaching the app, hover, transition and pen-tap checks wait for the user's go-ahead. Launching the app still takes the foreground once.

UI Automation's `InvokePattern` calls the control directly and skips non-client hit testing, so it cannot show whether a title bar button is clickable: a button sitting under the caption region still invokes. Title bar buttons are verified with a pen tap once that works.

## Design system

The house design system is `D:\hoobi-design` (React and Tailwind, no XAML output); its `AGENTS.md` "WinUI 3 conventions" table is the spec this app ports into `Styles/Resources.axaml` by hand. Controls, cards, pills, alerts and flyouts carry no border, and fill alone tells surfaces apart; the only strokes are hairline dividers. Corners are 4px on controls and 8px on surfaces and overlays. Related cards under one heading form a group: a `StackPanel` with `Spacing="1"`, so the page ground shows through as the hairline, and the `GroupTopCornerRadius`, `GroupMiddleCornerRadius` and `GroupBottomCornerRadius` resources on its cards, so only the group's outer corners are rounded. A plain list of commands is an Avalonia `MenuFlyout` of `MenuItem`s, whose presenter gets the tinted look globally. A dropdown whose rows hold more than a menu item can (the account card, the account menu's guild submenu rows of icon, name, member count and role) is a custom `Flyout` with `FlyoutPresenterClasses="Tinted"` (add `Flush` for no padding), an explicit `Placement` and rows with menu item metrics. Both presenters take their tinted acrylic from `Styles/Acrylic` (hoobi-design's Mirage flyout blur with a darker tint: `FlyoutAcrylicTintColor` at `TintOpacity` 0.575 over a snapshot of the page behind, blurred at a sigma of 24 and saturated 1.4, the solid `FlyoutAcrylicFallbackColor` while the main window is not active; the full recipe is under Avalonia desktop app), so a view sets no `Background` on a presenter. A tooltip sets no `ToolTip.Placement`, since `Styles/PopupPlacement` places every one.

Every dialog subclasses `FAContentDialog` and is shown through `AppDialogs.ShowAsync(dialog, TopLevel.GetTopLevel(this)!)` (`src/Steward.Desktop/Services/AppDialogs.cs`), which applies the `Steward` class (tinted `ContentDialogBackground`, 8px corners, accent primary button, 440px width), closes any open flyout first and queues a dialog behind one already open; a dialog sets no brushes of its own, only a width override where its content needs one, and `Styles/Dialogs.axaml` supplies the scrim, the gap above the buttons and the text box and combo box look. A `PrimaryButtonClick` that does work takes `args.GetDeferral()`, as `MainWindow.ShowForeverCopyAsync` does. Two WinUI header metrics are set by hand: a `ComboBox` header has `LineHeight` 20, so its `FieldHeader` takes `Margin="0,0,0,10"`, and `RadioButtons` keeps an empty header with an 8px bottom margin and spaces its rows 8px, so its port is an `ItemsControl` with `Margin="0,8,0,0"` over a one-column `UniformGrid` with `RowSpacing="8"`.

A button with a clear rest background uses the `SubtleFillColor*` brushes for rest, hover and pressed. The Button template animates its background through a `BrushTransition` that interpolates ARGB, and `Transparent` is `#00FFFFFF`, so a clear rest brush against an opaque hover colour fades through white. A fade is safe when both ends share RGB (transparent to `SubtleFillColor*`, all white) or both are dark; a button with a clear rest background therefore uses `SubtleFillColorTransparentBrush` against `SubtleFillColor*`, or `ControlFillColorTransparentBrush` against an opaque fill, and a per-button override of hover or press colours goes in `Button.Styles` against the template part (`Selector="Button:pointerover /template/ ContentPresenter#PART_ContentPresenter"`). Button themes are set with `Theme="{StaticResource ...}"`: `DefaultButtonStyle`, `AccentButtonStyle`, `CriticalButtonStyle`, `CautionButtonStyle`, `SubtleButtonStyle` and `MenuRowButtonStyle` (a full-width subtle row for a flyout list). The segmented control (the Addons filter tabs, the Settings auto-update choice) is a `ListBox` with `Theme="{StaticResource SegmentedStyle}"` (`Styles/Controls.axaml`): equal-width items in a `UniformGrid` on `SegmentedTrackBrush` (`#19000000`) at 4px corners, items 29px high at 13px with 11px side padding, hover and press on an inset `PART_Hover` with the subtle fills, and the selected item on `ControlFillColorDefaultBrush` with a 16x3 accent pill at the bottom; an item selects on release over it, not on press (`Styles/SegmentedSelection`, switched on by the theme). Its items fade from `ControlFillColorTransparentBrush` (`#001A1F2B`) to the opaque `ControlFillColorDefaultBrush` on selection, so the fade never passes through white. A `TextBlock` with `Classes="FieldHeader"` (13px, `TextControlHeaderForeground`, 8px below) sits above a `TextBox` or `ComboBox` in place of a `Header`, `Classes="FieldHeader ComboBox"` for a `ComboBox`; a `FontSize` is set when the control sets its own.

Text inside a filled box (a read-only value field, pill, chip, tile or button) is vertically centred in it: the box takes a fixed height (32px, `TextControlThemeMinHeight`, for anything sitting beside a `TextBox` or `Button`) and the `TextBlock` inside sets `VerticalAlignment="Center"`, never top-aligned text with padding standing in for centring. A read-only value shown where an editable one would be is a `TextBox` with `IsReadOnly="True"`, so it gets the same metrics as its neighbours. Checked in a screenshot, the ink's gap above and below is equal within 1px; top-aligned text in a box has been built and flagged more than once. Text in two fonts on one line (a mono version beside proportional text) is one `TextBlock` of `Run`s, so every part sits on one baseline; separate `TextBlock`s centre by box height and the mono part rides high.

## Roster sync

`docs/design/roster-sync.md` is the agreed contract between this app, steward-server and the Steward addon, and it is the source of truth for how the three interact. Read it before touching anything that crosses a repo boundary. It carries the direction of travel, the identity and linking rules, the steward-server endpoints in use, the confirmed Forever client API facts, and the per-repo branch rules.

The short version. steward-server holds the people, the addon holds the characters, and this app is the only party that can talk to both. `GET /api/admin/{guild_id}/roster` and `GET /api/admin/{guild_id}/members` already existed for the admin SPA and needed no server change; `AdminMe.Guilds` supplies the guild id. `GuildRosterMember` and `DiscordMember` in `SyncModels` carry them, `RosterNotes.Trim` drops the lone `Y` and `N` lines a steward-server note collects, and `StewardSyncFile` emits them as `["members"]` and `["discord"]` alongside the existing datasets. `StewardGuildSyncApi` is the only implementation and is registered directly, with no interface between it and its callers.

Pulls are event-driven. While signed in, a guild selected and the `steward` feature held (the same gate as the pull it drives), `MainViewModel` keeps one connection to `GET /api/admin/{guild_id}/events` (`StewardClient.StreamGuildEventsAsync`, a `text/event-stream` read line by line by `ServerSentEventReader` in Core), restarted on a guild switch and stopped on sign-out or loss of `steward`, and kept reconnecting while the API is unreachable. `ready` and each `roster-changed`, `members-changed` or `characters-changed` event queue `SyncRosterAsync`, debounced 2 seconds and never overlapping a pull already queued from the stream. A dropped connection reconnects after 1, 2, 4, 8 and 16 seconds, then every 30 (`TransientHttp.Backoff`), reset by the next `ready`; neither server honours `Last-Event-ID`, so a reconnect resumes through the full pull that `ready` already queues; 60 seconds with no line at all, pings included, counts as a dropped connection. A 404 means the server in front of the app predates the route, and the stream stays off for the rest of the run; a 403 stops it for that guild; a 401 signs out as everywhere else. None of these touch the error bar or `StatusMessage`. The 1-minute background pass keeps its roster pull and character push as the fallback: every pass while the stream is not connected, and at most every 15 minutes (`_lastGuildSync`, wall-clock) while it has received `ready` and is alive. This guild stream is scoped to `steward` holders and to roster/member/character changes only; the separate access-change stream every signed-in user gets, whatever its role, is under Auth.

The existing `RosterMember` record is the WoW guild roster the addon observes, not the steward-server roster of people. The two are different datasets and the names are deliberately distinct.

## Character sync

`docs/design/character-sync.md` is the agreed contract for this and the source of truth. `StewardSavedVariables` reads `StewardDB.characters`, `professions`, `catalogue` and `guildRanks` through the `LuaSavedVariables` parser into `CharacterObservation`, `CharacterProfessions`, `ProfessionCatalogue` and `GuildRanks` records. `realm` on a character and on `guildRanks` is the guild's realm as a compact key (`ClassicBetaPvP2`), and the optional `realmName` display name (`CharacterObservation.RealmName`, `GuildRanks.RealmName`, JSON `realmName`, omitted when null) is forwarded on `CharacterSyncEntry` and `GuildRanksSync` and included in the push-gate fingerprint like `realm`. While a `sync` feature is held, `MainViewModel` gzip-compresses each install's batch and posts it to `POST /api/sync/{guild_id}/characters` (steward-sync's canonical prefix; builds before it posted to `/api/guild/{guild_id}/characters/sync`, still served as a temporary alias) through `StewardClient`, gated by a fingerprint over the canonical data with `observedAt` and `scannedAt` stripped out; the signed `fp` values cover those timestamps, so a `/reload` that restamps them still pushes. Push records live in `%LocalAppData%\Steward\character_sync.json`, a file separate from `state.json` because an older Store build rewrote `state.json` without the sync key, verified 26 Sep 2026. Each `/api/me` guild entry may carry `sync_guild_names` (`AdminGuild.SyncGuildNames`), the WoW guild names that Discord guild accepts. One push routes each install's characters to every Discord guild they belong to rather than only the selected one: `CharacterPushRouting.Route` (Core, via `MainViewModel.CharacterRoutes`) takes every `/api/me` guild whose own resolved features (`StewardClient.ResolveGuildFeatures`) hold `sync`, in that guild's own mode (officer with `steward`, professions-only without), and for each one whose `sync_guild_names` is a non-empty list runs `CharacterSyncMapping.Scope`, which keeps characters whose trimmed `guild` matches a listed name case-insensitively, keeps `guildRanks` only for an officer guild listing its guild, and fingerprints only what it kept. A WoW guild on several lists goes to each, and a character on no list, a guildless one included, is skipped. The Sync page, its "Your characters" row and Sync now show whenever any guild can be pushed to (`MainViewModel.CanPushCharacters`), not only when the selected guild holds `sync`, and the row's last push time and error cover only the guilds the install's characters route to. A `/api/me` recheck that finds any guild's `sync_guild_names` or push mode changed queues a push and reloads the Sync page. When the selected guild's entry carries no `sync_guild_names` at all (an older server), everything goes to the selected guild only, as before. Every routed guild is pushed in turn inside the one in-flight push; a 403, 404 or 429 for one guild is handled as before for that guild and the rest still run, a 401 signs out, and the directory pull that follows a post stays on the selected guild. Push records, batch ids, per-character outcomes and the catalogue fingerprint are keyed by Discord guild id plus install (`AppStateStore.CharacterSyncKey`), so each guild's gate and diff are independent. A rejection reading `guild not allowed` (`CharacterSyncRejectionCopy.GuildNotAllowedReason`) counts as skipped, never as rejected (`CharacterPushRouting.StateOf`). A push runs on startup, on Refresh, from Sync now, whenever an install's `WTF\Account\**\Steward.lua` is written (the Sync page's `SavedVariablesWatcher`, debounced 1.5 seconds, calls `MainViewModel.SavedVariablesWrittenAsync`, which pushes and then reloads the page), and on the background pass as described under Roster sync. Pushes never overlap: a request made while one is in flight runs once more after it finishes, forced if any queued request was. `StewardSyncFile` writes each member's linked `main` character and the recipe `catalogue` into `StewardSync.lua` alongside the existing roster, loot and attendance datasets.

A `sync` holder with no officer seat (`MainViewModel.IsProfessionsOnlySync`) gets a narrower push: `CharacterSyncMapping.FilterToProfessionsOnly` keeps only the characters that have a `StewardDB.professions` entry, the request's `guildRanks` is left null, and the push is a per-character diff (`ProfessionsPushSelection` in Core): each character's professions fingerprint (`CharacterSyncMapping.ProfessionsFingerprint`, `observedAt`/`scannedAt` excluded) is recorded with its outcome in `character_sync.json`, and a push sends only characters whose fingerprint differs from the recorded one, plus the catalogue only when its fingerprint differs from the last accepted one. A rejected character is resent only when its data changes or, for a "not linked to you" rejection, when the pulled member roster now links that guid to the signed-in user; with nothing to send no request is made, and Sync now sends every character. Only the selected guild's push resends a "not linked to you" rejection on its own when the roster changes, since the roster pull is the selected guild's; another guild's resends when the character's data changes or on Sync now, and its rejection reads with the plain copy rather than the roster-based text. The catalogue itself still rides along, since a seatless caller's captured recipes may be new to the guild: steward-server inserts only the catalogue rows that do not already exist for such a caller and never modifies an existing row. Roster fields still ride along on each sent `CharacterSyncEntry`, since the server's validation requires them; steward-server ignores them for a seatless `sync` holder along with the guild ranks, and keeps professions only for guids linked to that user. No separate `professions` flag exists. The Sync page has one layout for an officer and a seatless `sync` holder alike; only the data behind each row differs. `SyncViewModel` builds, for the selected install, a "Guild roster" row (the selected guild's `roster` feature, or `steward`, where it also covers the admin roster, members and Discord pull) and a "Guild professions" row (`professions`, or `steward`, where it also covers the admin recipe catalogue), both pulls whose tick means `StewardSync.lua` on disk carries the last written fingerprint, then a "Your characters" push row that expands to the per-character states, collapsed by default and remembered per install for the session. The row reads "{n} characters synced to {m} servers" (singular forms for one), or "{n} characters for {m} servers, sending shortly" while any is unsent, where n counts distinct characters routed to at least one guild and m the guilds routed to; with no character on any guild's list it reads "No characters on a server's guild list". Across routed guilds a character is synced when every guild it went to accepted it, pending when any is pending, and rejected only for a real rejection (`CharacterPushRouting.Combine`). The expanded list shows the characters routed in professions-only mode with each one's professions-fingerprint state, and otherwise only the signed-in user's own characters, matched by Discord link rather than by name (`CharacterSyncMapping.IsOwnCharacter`: the pulled roster pin `DirectoryCharacter.LinkedUserId` for that guid when a roster pull is available, else the character's own `StewardDB.characters[guid].linkedUserId`, compared against the signed-in user's id), while the row's own count and status cover every routed character; an officer with no own characters on an install sees "No characters of yours on this install yet." in the expanded row. Loot and attendance have no rows: nothing syncs them yet. The generated-file card shows for both, since a non-officer's `StewardSync.lua` still holds `me` and whatever `directory` and `catalogue` sections were pulled. The saved-variables watcher and Sync now still push on the same triggers as the officer path.

Until the Forever launch (`ForeverSchedule.Launch`), a live `wowf` install reads no Steward saved variables (`ForeverLaunch.HasNoCharacters`, applied by `MainViewModel.ReadStewardSavedVariables` for the push, the Sync page and the routed-guild count), since nobody can play that client yet and any `Steward.lua` there is a copy of the beta's; its Sync page shows "World of Warcraft: Forever is not out yet" (`SyncViewModel.NotReleasedVisibility`) in place of the cards, the addon-missing and never-exported states and the journey row, and the install pushes no characters and uploads no journeys. Until the launch no install uploads journeys at all (`UploadJourneysAsync`), since steward-server stores none before it, and after it a journey is uploaded only with an hour of active play and 3 or more subzones (`JourneyQuality.IsWorthUploading`); one below that is recorded as `too_short` and looked at again when its file changes. An install with several WoW accounts has one `Steward.lua` per account: a duplicate guid across files resolves to the newest `observedAt`, and a guild's character observations (other players seen in a guild scan) are dropped from any file whose own scan of that guild (`guildRanks.observedAt` for that guild, else its newest character `observedAt`; guild matched by name plus the realm id in its characters' guids (`Player-<realmId>-<hex>`, stable across addon realm spellings such as `Classic Beta PvP` and `ClassicBetaPvP2`), falling back to the compact realm key or `realmName` when no guid carries one) is more than 24 hours older than the newest scan of it in any file, so a stale account never resends roster rows the server skips. A character with a `professions` or `gear` entry in that file is kept, as is every character of a guild only one file has seen (`StewardSavedVariables.Read`).

`StewardDB.professions[guid].fp` is a keyed integrity fingerprint the addon computes in game (every sync field, timestamps included, is signed this way, and a new sync field ships with its fingerprint in the same change; see "Integrity" in `docs/design/character-sync.md` for the formats, test vectors and what is still unsigned); `StewardSavedVariables` parses it into `CharacterProfessions.Fp` and the app forwards it untouched as `professions.fp` on that character's `CharacterSyncEntry`, and left out of the push-gate fingerprint like every other `fp`, since each signs a timestamp and would otherwise push on every restamp. See "Integrity" in `docs/design/character-sync.md`. `StewardDB.catalogue[profession].fp` is the same kind of fingerprint, one per profession's catalogue entry rather than per character; `StewardSavedVariables` parses it into `ProfessionCatalogue.Fp` and it is forwarded untouched as `fp` on that profession's entry in the push's `catalogue` object, on both the officer and professions-only push, and is left out of the push-gate fingerprint the same way. `StewardDB.characters[guid].fp` (`o1`) and `StewardDB.guildRanks.fp` (`r1`) sign the roster fields and guild ranks, `observedAt` included; `StewardSavedVariables` parses them into `CharacterObservation.Fp` and `GuildRanks.Fp`, and they are forwarded untouched as `fp` on the `CharacterSyncEntry` and on `GuildRanksSync`, left out of the push-gate fingerprint like the rest. Each recipe list and the bank carry their own signature: `recipeScans[profession]` (`{scannedAt, fp}`, `p1`) beside the professions entry, parsed into `CharacterProfessions.RecipeScans`, and `bank.fp` (`k1`), parsed into `GearBank.Fp`, both forwarded untouched in the same shape. Since every version now signs its timestamp (`v3`, `p1`, `g3`, `k1`, `c3`, `o1`, `r1`), a restamp changes each `fp`, so the push gate leaves every `fp` out alongside `observedAt` and `scannedAt` (`recipeScans` and the bank's `observedAt` included), and a `/reload` that changes no data pushes nothing. A fingerprint is computed only at the moment of observation, over only what that observation read from the game, and stored data is never re-signed: the addon never fingerprints data read back from `StewardDB`, a migration or merge drops or carries a fingerprint and never recomputes one, data carried over from an earlier observation keeps the `fp` and timestamp of its own capture, and a new synced field is signed at its capture point. The app keeps to the same rule by forwarding every `fp` and the values it signs exactly as read, never recomputing, merging or normalising them. The addon also writes `addonVersion` (its TOC `## Version`) on each of those entries; `StewardSavedVariables` parses it onto the same models and it is forwarded untouched as `addonVersion` on the character, `guildRanks`, professions, gear and catalogue objects (omitted when null), left out of the push-gate fingerprint like `fp`. steward-server names it in the rejection it gives a character whose fingerprint is missing (`written by an older Steward addon (<version>); log in on this character to refresh`, shown verbatim on the Sync page) and in the mismatch DM; a missing fingerprint raises no DM.

Every signed-in user whose install has the Steward addon gets a `me` dataset in `StewardSync.lua`, officer or not: `{ id, role?, features }` (`SyncMe` in `Steward.Core`, `role` omitted when null). `StewardGuildSyncApi.PullAsync` sets it on the officer's full payload from the same `AdminMe` the roster pull already fetched; `MainViewModel.WriteMe` writes a minimal payload holding only `me` (plus `directory`/`catalogue`, described below) for a non-officer, called from `RecheckAuthorizationAsync` whenever the signed-in user, role or feature set changes (comparing against the values captured before that check overwrites them) and skipped when `HasStewardFeature` is true, since the officer's own write already carries `me` and a second, roster-less write would wipe it. `SignOutTo` is the one sign-out path (the `SignOut` command delegates to it): for a non-officer it calls `WriteMe` with `me: null`; for an officer it caches the last full payload `SyncRosterAsync` wrote (`_lastOfficerPayload`) and rewrites it with `Me = null`, keeping the roster, members, discord and catalogue data rather than wiping it with a roster-less skeleton. `Steward.Sync.Me()`/`Steward.IsOfficer()` in `hoobio/Steward`'s `Core/Sync.lua` are the addon-side readers; `me.role` is a display gate only; it is not enforced client-side.

Three per-flag member routes replaced the old single directory endpoint: `GET /api/guild/{guild_id}/roster` (`roster` feature, `StewardClient.GetMemberRosterAsync`) gives `{people, characters}`; `GET /api/guild/{guild_id}/professions` (`professions`, `GetMemberProfessionsAsync`) gives `{professions, catalogue}`, each professions entry now also carrying `name` and `class_id`; `GET /api/guild/{guild_id}/recipes/catalogue` (`sync` or `professions`, `GetMemberCatalogueAsync`) gives `{catalogue}` alone. `MainViewModel.SyncDirectoryAsync` reads the SELECTED guild's own features (`_guildFeatures`, see Auth) to decide which of these to call, on startup, on Refresh, right after a character push actually posts to steward-server, and on the background pass at most every 15 minutes wall-clock (`_lastDirectorySync`, the same `GuildSyncFallbackInterval` as `_lastGuildSync`); a 403 or 404 on any of them is handled quietly, the same treatment as the events stream, no error bar. The results compose into a `SyncDirectory` (`_lastDirectory`, people/characters/professions, each nullable) and a separate `_lastMemberCatalogue`, carried into whichever payload gets written next, officer or not. `StewardSyncFile`'s `DirectoryToLua` writes `StewardSync.lua`'s `["directory"]` from only the sections actually fetched: `people`/`characters` as a pair when roster was pulled, `professions` (camelCase `classId`, plus every other key already camelCase: `mainGuid`, `linkedUserId`, `maxRank`; `recipes[profession]` is a schema-2 bare array of recipe ids, no per-recipe object) when professions was pulled, each omitted entirely otherwise, so the key is missing rather than an empty table when nothing was fetched. A non-officer's `["catalogue"]` dataset comes from `_lastMemberCatalogue` (`MemberCatalogueMapping.ToCatalogue`, from the professions response when pulled, else the standalone catalogue route), since they never call the officer-only `recipes/catalogue` endpoint under `/api/admin`; an officer keeps their catalogue from that admin call as before.

A `people` entry's optional `avatar_url` (`DirectoryPerson.AvatarUrl`) becomes `Avatars\<userId>.tga` in the addon folder and an `avatar` key on that person's `directory.people` entry, written only when the file exists after the write; `SyncDirectory.Avatars` carries the decoded images, `PersonAvatars` (Core) decides what to download and `StewardSyncFile.Write` writes and prunes the files, as `docs/design/roster-sync.md` describes. The last written URL per install and user id is `person_avatars` in `state.json`.

steward-server pins every character link (guid to Discord user id) rather than deriving it live, so an officer's re-map, unlink or reset shows up in `characters[].linked_user_id` on the next pull the same way a fresh match would. `StewardSync.lua` carries that pin as a top-level `["links"] = { [guid] = discordUserId, ... }`, a sibling of `me`, `directory` and `catalogue` rather than nested under `directory`, since `hoobio/Steward`'s `Core/Sync.lua` reads `payload.links` directly; one entry per character with a non-null `linked_user_id`, an unlinked guid simply absent. `StewardSyncFile.Render` writes it whenever `payload.Directory.Characters` is not null, the same roster pull that feeds `directory`'s own `people`/`characters`, so it is present exactly when they are and omitted when roster was not pulled. `roster` is an officer default feature (`StewardClient`'s `OfficerFeatures`), so `SyncDirectoryAsync` already runs the member roster route for an officer the same as for a raider holding `roster`; it is not gated on `HasStewardFeature`. `hoobio/Steward`'s `Core/Sync.lua` reads `links` in preference to note matching.

## Saved variables

Roster, loot and attendance read WoW SavedVariables files. Those files are one per addon per scope: everything under an addon's `## SavedVariables:` TOC directive lands in one shared account-level file at `WTF\Account\<ACCOUNT>\SavedVariables\<Addon>.lua` under the flavour folder, and `## SavedVariablesPerCharacter:` in a per-character file at `WTF\Account\<ACCOUNT>\<Realm>\<Character>\SavedVariables\<Addon>.lua`. Account folder names look like `54939295#1`, and the `.lua.bak` beside each file is ignored. On Forever the realm folder under an account is often a numeric id (`70`) rather than a realm name, and a character name containing a space has the space turned into a hyphen in its folder (`Hoobi Furry` on disk as `Hoobi-Furry`), confirmed 28 Sep 2026, so the per-character folder path cannot be reconstructed from `CharacterObservation.Name`/`Realm` and is not used to identify a character.

The reader is built, in `Steward.Core` with no UI on it yet. `LuaSavedVariables.Parse` is a recursive-descent parser for the client's own dump format: one global per `## SavedVariables:` entry, `["string"]`, `[123]` and bare identifier keys, strings with the client's escapes, numbers, booleans, `nil`, nested tables, array items, trailing commas and the `-- [n]` comments the client writes after array entries. Malformed input throws a `FormatException` naming the line and column. `StewardSavedVariables.FindFiles` locates the Steward files under a flavour path and `StewardSavedVariables.Read` maps them into a `SavedVariablesSnapshot` of roster, loot and attendance.

The Steward addon writes `StewardDB.characters`, `professions`, `catalogue` and `guildRanks` (see Character sync); it does not write the roster, loot and attendance tables below, so that schema is the contract the addon must write rather than a record of what it writes. The account file holds `StewardDB`:

```lua
StewardDB = {
["exportedAt"] = 1758260000,
["roster"] = { { ["name"] = "Hoobi", ["realm"] = "Nightslayer", ["class"] = "WARRIOR", ["level"] = 60, ["rank"] = "Officer", ["rankIndex"] = 1, ["note"] = "", ["officerNote"] = "", ["lastOnline"] = 1758250000 }, },
["loot"] = { { ["id"] = "3f2a...", ["at"] = 1758240000, ["player"] = "Hoobi", ["itemId"] = 19019, ["item"] = "Thunderfury", ["quality"] = 5, ["source"] = "Ragnaros", ["instance"] = "Molten Core" }, },
["attendance"] = { { ["id"] = "9c1b...", ["at"] = 1758230000, ["instance"] = "Molten Core", ["present"] = { "Hoobi", "Grug" } }, },
}
```

The per-character file holds `StewardCharDB` with `["exportedAt"]`, `["character"] = { ["name"], ["realm"], ["class"] }`, and `["loot"]` and `["attendance"]` arrays of the same record shapes, carrying what that character observed. Roster is account-level only and the reader takes it from `StewardDB` alone.

`exportedAt` is unix seconds, at the file level and on `at` and `lastOnline`. Loot and attendance records carry an `id` string, and where the same `id` appears in more than one file the copy from the newest `exportedAt` wins. Reading is tolerant: a missing table gives an empty list, a record missing a required field is skipped and counted in the snapshot's `Skipped`, and an absent `exportedAt` gives null.

The client only serialises saved variables at logout, exit or `/reload`, rewriting the whole file from memory, so any external write to that file while the client is running is lost on the next serialise. Data flow is therefore one direction per file: the app only reads the saved-variables file, and only writes a generated Lua file elsewhere in the addon folder, one the client never writes to, calling a function the addon exposes rather than assigning a raw global.

The generated-file writer is `StewardSyncFile` (`Interface\AddOns\Steward\StewardSync.lua`, written by calling `Steward.LoadSync({...})`), guarded by the same TOC-existence check as `RemoveExistingInstall` and written temp-then-move; `GuildRosterSync.WriteIfChanged` logs a failed write (`IOException`, `UnauthorizedAccessException` or the guard's `InvalidOperationException`) at Warning and records no fingerprint, so the next pass, Refresh or file change writes it again, and the failure never reaches the roster pull or startup that called it; the addon's own TOC must list `StewardSync.lua` for the client to load it, a dependency on the addon repo.

steward-server ports `StewardSyncFile` (with `LuaWriter`, `RosterNotes`, `MemberCatalogueMapping`, `AvatarTga` and `PersonAvatars.RequestUri`), `AddonThemeFile.Render` and `GeneratedAddonIcon.InsertDirective` into `src/Steward.Integrations/StewardSyncFile.cs`, `ProtectedAddons.ThemeFile` and `AddonBundle.cs` for its Mac addon bundle (`GET /api/addons/bundle/{guild_id}/Steward-AddOns.zip`), so a change to any of them is made on both sides, with the server fixtures (`tests/Steward.Tests/Fixtures/steward-sync*.lua`) regenerated from this repo's `StewardSyncFile.Render`.

Installing or updating the Steward addon replaces the whole folder, so `StewardSync.lua` and `Avatar.tga` go with it. Two things put them back. `StewardSyncFile.Write` embeds the payload fingerprint as a `fingerprint` key right after `writtenAt`, and `GuildRosterSync.WriteIfChanged` skips only when the file on disk carries that same fingerprint (and `Avatar.tga` exists when the payload has one), so the placeholder `StewardSync.lua` the addon zip ships is rewritten on the next pass; and `AfterStewardInstalled` rewrites the file the moment an install finishes, for the user who launches the game before that pass, through `MainViewModel.RestoreRosterAfterInstallAsync` for an officer and `WriteMe` for everyone else. `RestoreRosterAfterInstallAsync` rewrites that install from the last pulled officer payload when it is for the selected guild, so a batch that updates Steward on several installs makes no extra roster pull, and pulls through `SyncRosterAsync` only when there is none. `StewardGuidesAddon.Write` likewise skips only when the `Guides.lua` on disk carries a valid fingerprint and the same entries. `SyncViewModel.WriteGeneratedFileAsync` (the Write again button, and with an install the post-install hook) goes through those methods, which pull through `StewardGuildSyncApi`; the in-memory fake that once backed the Sync page, and wrote its fake dataset over the real roster, was removed on 27 Sep 2026.

`SavedVariablesFreshness` judges freshness from the saved-variables mtime against the running client's process start time from `WowClient`, and the Sync page is built (see Character sync). The addon side of the contract lives in `hoobio/Steward`'s `AGENTS.md`.

## RestedXP guides

`docs/design/restedxp-guides.md` is the verified contract for RestedXP's undocumented API and is the source of truth for it. Steward signs in against Keycloak directly (`RestedXp:Keycloak`, the `RestedXP-Prod` realm's token endpoint, public client `rxp-prod-login-client`, scope `openid offline_access`) rather than through the account backend's `/login/*` proxy, so the offline refresh token keeps the session across restarts: a password grant, plus `totp=<code>` on a second grant when Keycloak answers `invalid_grant` with an OTP description, and `grant_type=refresh_token` after that. `refresh_expires_in: 0` on an offline token means no expiry, so the stored refresh expiry is null and a null expiry never expires; the cookie's `expiresAt` is then 30 days out. Keycloak's offline session idles out 30 days after the last use, and a refresh slides it, so the on-demand refresh before a call plus the 3-hour check keep the idle window alive and a Steward run at all in any 30-day window never asks for the password again. Every authenticated call carries the `rxp_cross_auth_token` cookie built per request from the access token; the backends read only its `token` field. Guide content comes from `RestedXp:GuidesBaseUrl` (`https://rxpgcr.restedxp.com`), where `/addon/get-all-timestamps` and `/addon?guideName=...&bundleIndex=0` both need the cookie (the timestamps route answered 200 without one until it started answering 401 on 30 Sep 2026).

The password is used for the one password grant and never stored; it is held in memory by `RestedXpService` only between the sign-in step and the code step, and cleared after. The session (username, both tokens, the access expiry and the nullable refresh expiry) lives in `restedxp_session` in `state.json` through `SecretProtection`, the same treatment as `session_token` on every OS (a DPAPI blob on Windows, an AES-GCM blob under the same session key on Linux and macOS). The access token lasts 15 minutes, so a call refreshes whenever it has under a minute left; a bounded refresh token is renewed near its end, and a refresh that answers 400 clears the session and the card shows the signed-out state.

Timestamps are checked on the startup pass, on the manual Refresh and on the first background pass more than 3 hours plus a random 0 to 30 minutes after the last check (`_nextGuideCheckDue`, redrawn on every check, so copies restarted together by a Store update drift apart instead of polling RestedXP in step) (`_lastGuideCheck` in `MainViewModel`, wall-clock rather than a pass count, so the minute-by-minute retry while the guild API is unreachable does not speed it up). A guide is stale when the timestamp recorded in `restedxp_guides` (keyed like `AppStateStore.Key`, flavour path plus `productName`) is older than the server's. A downloaded string is cached at `%LocalAppData%\Steward\guides\<product>.txt` beside a `.json` holding its timestamp and BattleTag, so a regeneration costs no network call, and a failed download is not retried for 10 seconds. The sync is per install: every selected product is cached first, and the folder is rewritten when any cached string or the selection itself moved since the last write for that install.

The importer is a published addon, `StewardGuides` (built from `hoobio/HoobiScripts`, catalogue id `steward-guides`, parent `steward`, features `guides`, served at `https://addon.hoobi.io/steward-guides/`), and owns all the Lua: its TOC (`## Title: Steward: Guides`) loads `Guides.lua` then `Core.lua`, and the zip ships a placeholder `Guides.lua`. The companion writes only `Guides.lua`, through `StewardGuidesAddon.Write`, and never creates or deletes the folder. It writes only when `Interface\AddOns\StewardGuides\StewardGuides.toc` carries the line `## Title: Steward: Guides`; a missing folder or the old generated one (`## Title: Steward Guides`) returns `NotInstalled` and is left untouched, so the old generated addon keeps working until the catalogue install replaces it. `Guides.lua` is `local generation`, `local fingerprint` (SHA-256 of everything from `local guides` to the end), `local guides = { ... }` with each selected product's string as a `[==[...]==]` long-bracket literal, then `ns.generation = generation` and `ns.guides = guides`; a string that holds `]==]`, or ends in `]==` (which the closing bracket would complete), gets a longer level (`[===[...]===]` and so on) until neither can occur, and names and tags go through `LuaWriter.SerializeString`, which escapes quotes, backslashes and control characters (`AddonThemeFile.Render` does the same for the id). The safety is `StewardSyncFile`'s: temp-then-move and no `WTF` segment in the path. `NotInstalled` maps to `GuideSyncOutcome.NotInstalled` and `GuideRowState.None` (no pill) and records nothing in state.

The `steward-guides` row is installed and updated only while RestedXP is signed in and the install has RXPGuides (`MainViewModel.SyncRestedXpRows` sets `AddonRowViewModel.IsInstallGated`, which drops the row from its parent's rolled-up children, so the Steward group update skips it). After it installs or updates, `AddonRowViewModel` calls the after-install hook, which runs `RestedXpViewModel.RewriteAfterInstallAsync` and rewrites `Guides.lua` from the cached strings.

The addon's own `Core.lua` (in `hoobio/HoobiScripts`, not here) reads `ns.guides`. On `PLAYER_ENTERING_WORLD` plus 3 seconds it takes the RXPGuides addon object from `LibStub("AceAddon-3.0"):GetAddon("RXPGuides", true)` and hands each string to `guideImporter:ImportString`, the paste box's own path. Imports run one at a time: a second call while an import is in flight resets the first one's buffer, so the file waits for `importCoroutine` to be nil and `importBufferSize` to be 0 before the next. `StewardGuidesDB.imported` records the hash from each string's `|hash:` header once the importer's `importStatusHistory[1]` reads "Guides Loaded Successfully", and the app reads it for the row state. On that success the bootstrap also records, in `StewardGuidesDB.keys` under `<hash>|<faction>`, the `key` of every `RXPGuides.db.profile.guides` entry the import wrote (an entry whose table differs from the pre-import snapshot), and a later login skips that string when every recorded key is loaded in RXPGuides itself (`guideCache[key]`, or a `guides` entry carrying that key), printing nothing for it. Our own mark alone is never the skip condition: on 20 Sep 2026 a skip on it left the game with no guides, when RXPGuides on this client kept no imported guides between sessions (ClassicWoWCommunity/forever-bugs#34, fixed by 26 Sep 2026). Faction is in the key because RXPGuides only loads a cached guide whose `enabledFor` applies to the character. The importer writes its failures only into its own window, so the file surfaces them: any other `importStatusHistory[1]` is printed to chat as `Steward <name>: <status>` and kept in `StewardGuidesDB.status[hash]`, which a success clears, and a status holding "restart your game client" is retried once after 10 seconds before it is recorded. Each guide entry also carries the purchaser's `tag` from the cached download, and a guide whose tag differs from `BNGetInfo`'s BattleTag (case-insensitive) is recorded and skipped with "bought on <tag>, you are <playerTag>; not imported" rather than handed to an importer that would reject it silently; a nil BattleTag or an uninitialised RXPGuides is waited on every 5 seconds up to 6 times before the run gives up with a chat line. At file load the bootstrap also wraps the five `inventoryManager` predicates RXPGuides v4.11.x calls from its bag hook (`IsRightClickEnabled`, `IsBagAutomationEnabled`, `IsMerchantAutomationEnabled`, `IsJunkIconEnabled`, `GetModKey`) so they answer false while `settings.profile` is nil, because that hook throws "attempt to index field 'profile'" on a client where their initialisation has not run; the wrap is a no-op once the profile exists. The bootstrap also answers the Hoobi addon version check: a `ping` on the `HoobiVersion` addon-message prefix gets a whisper of `StewardGuides=<TOC Version>` (the app's informational version) back to the sender, the same responder Steward and HoobiScripts carry; the protocol is in `hoobio/Steward`'s `AGENTS.md`.

An import is confirmed from the addon's own saved variable, `WTF\Account\*\SavedVariables\StewardGuides.lua` (`StewardGuidesSavedVariables` in Core): the file lands at logout, exit or `/reload` carrying the `generation` the loaded `Guides.lua` set (unix ms of the write, emitted as `local generation` and recorded per install in `restedxp_guides_generation`) and the hashes and statuses it wrote. Per kept product there are four outcomes: an account file at the install's current generation with the string's hash marked reads `Up to date`; the same file carrying a `status` string for that hash reads `Failed` with that string as the row's message, and drops that product's `restedxp_guides` record so the next sync rewrites the folder; the same file with neither reads `Not finished`, an import cut short by a logout or `/reload` that the addon runs again on the next login; no file at that generation leaves the row `Written`. The pass runs at the end of every guide check, when a client exits, and when a `FileSystemWatcher` per install sees that saved variable written under `WTF\Account` (debounced 1.5 seconds, since the client writes it temp-then-rename), so a row reads `Up to date` seconds after the `/reload` or logout that follows the importing login; it reads files only.

The file is read at login or `/reload` and never written by the client, so there is no client-closed rule: the folder is regenerated whether or not the game is running. Several products can be kept per install (`restedxp_guide_choices`, flavour path to a list of `productName`, migrating an older single `restedxp_guide_choice` into a one-item list), defaulting to every owned product allowed on that install. `RestedXp:ProductPrefixes` in `appsettings.json` maps a WoW product code to the product-name prefixes allowed on it, `wow_classic_beta` to "Forever" today; a product outside its install's prefixes is never written there. The guide string's trailing minimum-version number is not checked here; the addon reports incompatibility in game.

## Banners

Server-driven banners let steward-server put a message in front of every user without a Steward release: `GET /api/banners` (no auth required, works signed in or out) answers `{"banners": [...]}`, each entry an id, a revision, a level, a title, a message and an optional set of gates and actions. `Banner` and `BannerAction` in `Steward.Core`'s `Banners.cs` are the parsed shape; `id` is documented as a string but has shipped as a JSON number (commit 5425bf8), so `BannerIdConverter` accepts either and normalises to a string, since dropping the banner over a type mismatch would be worse than the coercion. `BannerParsing.Parse` walks the array element by element and skips a malformed one on its own `JsonException` rather than failing the whole response; `StewardClient.GetBannersAsync` answers an empty list on a 404 (an older server with no route yet) and never signs the user out on a 401, since a banner check is not a privileged action like `/api/me`.

A banner's `level` (`info`, `success`, `warning`, `error`) and each action's `type` (`store_update`, `open_url`, `navigate`, `dismiss`) are read by `BannerLevels.Parse` and `BannerActions.Parse`, and an unknown or missing value degrades rather than throws: an unknown level renders as `info`, an unknown action type hides that button only, the rest of the banner still renders. A `store_update` action while signed in goes through `MainViewModel.HandleStoreUpdateBannerActionFromBannerAsync`: it sets a one-shot request (`TakeAppUpdateFocusRequest`, `AppUpdateFocusRequested`, the `EditInstallRequested` pattern), navigates to Settings, where `SettingsPage` scrolls `AboutCard` into view and pulses its background (a fresh `SolidColorBrush` whose `Color` animates to a dark accent and back in 1.6 seconds, the original brush restored on completion, so no fade passes through white), and executes `CheckOrInstallAppUpdateCommand`. `BannerFilter.Active` narrows the fetched set to what should actually show: not already dismissed at its current revision, in the app's release channel when the banner names any (`Channels` empty or absent means every channel), and the installed version inside `MinVersion`/`MaxVersion` when either is set, compared component-by-component as a 4-part version rather than parsed as `System.Version`, the same reasoning as the addon version comparison under Channels.

`MainViewModel.SyncBannersAsync` fetches on startup, on Refresh, and at most every 15 minutes wall-clock from the background pass (`_lastBannersSync`, the same `GuildSyncFallbackInterval` used elsewhere); a failed or malformed fetch (`HttpRequestException`, `TaskCanceledException`, `JsonException`) is swallowed and keeps the last good set rather than clearing the banners or surfacing an error, since a banner is never load-bearing. `RefreshBanners` re-applies the dismissal filter and rebuilds the `ObservableCollection<BannerViewModel>` (`Banners`, ordered highest severity first) whenever the fetched set or the dismissed set changes. Dismissing (`DismissBanner`) records `{id: revision}` in `dismissed_banners` in `state.json` (`AppState.DismissedBanners`); a banner is dismissible unless it sets `dismissible: false`, and a non-dismissible banner's own `dismiss` action, like every `dismiss` action, is ignored anyway, since the close button already covers it. A later revision of the same id is not dismissed by an older revision's record, so a banner can be brought back by editing it on the server.

`BannerList` (`Views/BannerList.xaml`) is the one `UserControl` every page hosts: a `DependencyProperty` `Banners` bound to `MainViewModel.Banners` (directly for the Addons and Settings pages, whose `ViewModel` is the `MainViewModel` itself, or through `ViewModel.Main.Banners` for Sync and Guides, whose page view models wrap it), rendering severity-tinted cards with inline actions to the right and a close `X` rather than a separate dismiss button. It sits in a dedicated row between that page's own header (title, subtitle, command buttons, unchanged) and its content, on every page, so banners push content down instead of overlaying it: the Addons page's 3-row `Grid` puts it in row 1 with the empty and loaded states both confined to row 2; Sync, Guides and Settings place it inline in their single scrollable `StackPanel`, immediately after the header row (Settings has no in-page header of its own, the title bar being the header per `docs/design/home-and-settings.md`, so its `BannerList` is the first child). An empty `Banners` collection renders as a zero-height `ItemsControl`, so an unpinged page never shows a gap.

A `navigate` action is gated per page (`MainViewModel.IsPageVisible`) so a banner never offers a button to a hidden page (Sync or Guides without the feature that unlocks it); `NavigateToPageTag`, wired in `MainWindow.axaml.cs`, selects the matching nav item. `--banners-preview` (`src/Steward.Presentation/Services/BannersPreview.cs`) seeds one banner per level with one action type each (including a non-dismissible `error` banner exercising every action kind) and calls `RescanCommand` so the Addons page also shows its populated, non-empty state, for network-free UI verification.

## Navigation

Every top-level page (`HomePage`, `SyncPage`, `GuidesPage`, `SettingsPage`) is a DI singleton registered in `App.axaml.cs`, constructor-injected with `MainViewModel`, and the shell shows one by assigning it to `PageHost.Content` in `MainWindow.ShowPage`, chosen by the nav item's `Tag` in `MainWindow.Navigate`, never by building a new page per visit. In the WinUI build a new page per visit left each discarded page's bound repeaters and lists subscribed to the shared `MainViewModel` collections, and on 28 Sep 2026 one of those threw a bare `COMException 0x80004005` from a `TableRows` removal after a few Settings round trips. Pages get no navigation callbacks, so a page reacts to its view model or to its own `Loaded`/`Unloaded` (the Settings page's pending Edit install request), and `ShowPage` plays the entrance animation itself. A new page is registered as a singleton and added to the tag switch in `MainWindow.Navigate`. The pattern and its tradeoffs are in `D:\earmark\docs\adr\navigation-singleton-pages.md`.

The window extends content into the title bar (see Avalonia desktop app for the drawn caption buttons). The title bar holds only the install picker (`InstallPicker`), in `InstallPickerHost`, which spans the column between the title and the caption buttons. `MainWindow.PositionInstallPicker` runs on every title bar `LayoutUpdated` and sets the picker's `InstallPickerOffset.X` so it is centred on the whole window, clamped to 8px from the title on the left and from the caption buttons' drag gutter on the right, so a narrow window slides it beside whichever it would overlap; when the column is narrower than the picker plus both gaps it sits right-aligned in the column. The picker is at least 32px high (40px with the countdown line, 4px lower) and vertically centred in the 48px (`TitleBarHeight`) title bar. Under the install label the picker reads the time to the launch ("{n days m hours}") in 11px secondary text (`LaunchCountdownText`, `ForeverSchedule.TitleCountdown`, refreshed every 30 seconds, "Live now" for `ForeverSchedule.LiveFor` (24 hours) after the launch, then gone; while it shows, the picker's `Countdown` class makes its icon 24px and gives it a 4px top margin, and without it the picker is one line at 32px with a 20px icon), and the bottom of its flyout lists each `ForeverSchedule.Events` entry still ahead: the stress test, name reservations and the launch at Blizzard's Americas and Oceania times (news.blizzard.com, read 21 Oct 2026), in local time with "Starts in" or "Ends in"; an entry with no stated end (the stress test) leaves the list once it starts, and name reservations, given only as ending on 3 Nov, end at 23:59 Pacific that day. The picker is collapsed while signed out, and shows on Settings too so the countdown is on every page. Its "Manage installs" item opens Settings and brings the Installs card into view (`SettingsPage.ShowInstalls`), since the singleton Settings page keeps its scroll offset between visits. The install flyout (260px) opens centred below the picker (`Placement="Bottom"`) and passes its dismissing press through to `InstallPicker` (`OverlayInputPassThroughElement`).

The account entry (`AccountButton`, the Discord avatar and name) is a plain `Button` in the pane's footer, directly above the Settings item, rather than a nav item, so opening it never changes the selected page. It takes the nav items' metrics (36px high, 4px inset and 4px from the Settings item, 4px corners, a 40px icon column holding the 24px avatar, the `NavigationViewItemBackground*` brushes), shows the avatar alone in the compact pane with the user name and live-updates state as its tooltip and automation name (`MainViewModel.AccountAutomationName`, only the parts that are set joined with ", ", so it reads the live-updates state alone before the user name loads), and is visible only while signed in, with the rest of the pane. `AccountFlyout` opens to its right with its bottom edge 8px above the window's (`MainWindow.PlaceAccountFlyout`, a `VerticalOffset` set in `Opening`), and the guild submenu keeps opening to the right of its row, top-aligned. The role pill sits right-aligned on the name line when it fits beside the name with an 8px gap, else below the handle (`MainWindow.PlaceRolePill`, on either one's `SizeChanged`).

## UI design

`docs/design/home-and-settings.md` is the agreed design for the settings page and the shell, and it is implemented. Four things in it were behaviour rather than view, and the doc remains the source of truth for each: the release channel is per addon (`AppState.Channels`, with `LegacyChannel` carrying the one-time migration), refresh probes every channel per addon (`release`, `pre-release`) so a channel with no release can be disabled, the default channel is the first one that has a release in that order, and the timer refreshes manifests as well as the role. Applying an update follows the game client. It no longer describes the Addons page or the Release channels card; `addon-manager.md` covers both.

`docs/design/addon-manager.md` is the agreed redesign of the Addons page into a general addon manager: one table for a selected install, an install picker with user labels and a required game version, release channels edited in a dialog from the row instead of on Settings, per-install Ignore, Local rows for unmanaged folders and an out of date TOC flag. Phase 1 is implemented and that doc is the source of truth for the Addons page; phase 2's Get addons dialog and CurseForge source are built (see Managed addons, and `curseforge.md` for everything CurseForge), and Wago is not. The install picker lives in the title bar, centred on the window and slid aside when that would overlap the title or caption buttons (see Navigation; hidden while signed out), and its one app-wide selection (`MainViewModel.SelectedInstall`, `selected_install`) scopes what the Addons, Sync and Guides pages show: `SyncViewModel.Installs` holds only the selected install, whose datasets and the "Guild data in game" row form one card with no install heading, and the Guides page shows `MainViewModel.SelectedGuide` as one grouped card (its product rows, then a `Guides.lua` row carrying Write again) under a single "{username} · {BattleTag} · checked {relative}" line with Sign out, or a "RestedXP Guides is not installed on {install}." card. Background work still covers every install.

`docs/design/guides-page.md` is the agreed design for the Guides page and the RestedXP sign-in dialog, and both are built against it; the doc stays the source of truth. The row control is a `CheckBox` and any number of owned products are kept per install, each checked row carrying its own pill; a product outside the install's client gate renders disabled and unchecked with a dim "Not for this client" line in place of the updated time. There is no "Waiting for game to close" state, since the generated addon is read at login or `/reload`. The `Guides` menu item shows only while RXPGuides is installed in some WoW install and a RestedXP session exists, and the sign-in entry point is a button on the RestedXP row of the Addons page; the page navigates back to Addons when either condition drops. The ninth state, `Needs a newer guide`, is rendered from `GuideSyncOutcome.NeedsNewerAddon`, which nothing sets yet: the service does not compare the written string's minimum addon version against the installed RXPGuides, so that state is reachable only through the preview. The product list (`/user-products` and the timestamps) is held in memory only, so until the first fetch of a session completes the card shows a "Loading your guides from RestedXP…" row with a `ProgressRing` (`RestedXpInstallViewModel.LoadingVisibility`, from `RestedXpViewModel.IsCatalogueLoading`: signed in, no catalogue yet (`RestedXpService.HasCatalogue`, cleared on sign-out), and no failure since that fetch started). A later Refresh or 3-hour check keeps the loaded rows in place with no loading row, a failed first fetch shows neither row beside its error, and "No guides on this account" shows only once a fetch has completed with no products (`IsCatalogueLoaded`). `--guides-preview=<scenario>` (`src/Steward.Presentation/Services/GuidesPreview.cs`) seeds the view models with a fake session and one of the page or dialog states, calls no network and writes no files, and is how the states are screenshotted without an account.

`docs/design/sync.md` is the original design for the Sync page, and the page and the shell it describes are built; `character-sync.md` and `roster-sync.md` are the source of truth for what the page syncs. Loot and attendance have no rows and no endpoints yet.

## Outstanding work

The tray icon, close-to-tray and minimise-to-tray are built, on Avalonia's `TrayIcon` (`MainWindow.CreateTrayIcon`: Open Steward, Check for updates and Quit, with the bundled icon). Two Behaviour cards in Settings decide it: `MinimizeToTray`, persisted as `keep_in_tray` in `state.json` and defaulting to true, sends a minimise to the tray instead of the taskbar, and `CloseToTray`, persisted as `close_to_tray` and defaulting to false, makes the X button hide instead of quit. The two share the old single `keep_in_tray` key so an existing state file keeps its minimise choice and gets the new close default. Restoring from the tray goes through `MainWindow.ShowFromTray`, which shows the window, restores it only when minimised (so a maximised window stays maximised), calls `Activate`, then `Native.ForceForeground`: Windows refuses `SetForegroundWindow` to a process that did not receive the last input event, and a tray click goes to explorer, so the call is wrapped in an `AttachThreadInput` to the foreground window's thread, with a `BringWindowToTop` inside it because the attached `SetForegroundWindow` activates the window without raising it. The tray icon's click handler is assigned in code, in `MainWindow.CreateTrayIcon`. Start with Windows is a third Behaviour card backed by the `Steward` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, pointing at the running exe with `--tray`; that argument hides the window to the tray on launch when `MinimizeToTray` is on, and otherwise shows it without taking the foreground (`MainWindow.ShowWithoutFocus`, the same path as `--no-activate`), since only a launch the user started should take focus. The registry is the only store for it. Off Windows the card reads "Start on login" ("Starts Steward in the tray when you sign in"), through `MainViewModel.StartWithWindowsHeader` and `StartWithWindowsDescription`, and `StartupRegistration.Unix.cs` writes the file that is its only store: on Linux the XDG autostart entry `$XDG_CONFIG_HOME/autostart/steward.desktop` (`~/.config` when that variable is unset or relative) with `Exec="<exe>" --tray` and `X-GNOME-Autostart-enabled=true`, on macOS the LaunchAgent `~/Library/LaunchAgents/io.hoobi.steward.plist` (label `io.hoobi.steward`, `ProgramArguments` the exe and `--tray`, `RunAtLoad`), both built by `StartOnLogin` in Core; turning it off deletes the file. `launchctl` is never called, since loading a `RunAtLoad` agent starts a second Steward at once and removing a loaded one stops the running one; the file alone takes effect at the next login. A write failure off Windows is logged and shown on the status bar. The card is enabled only in a GitHub release build: the workflow's `dotnet publish` passes `-p:GitHubRelease=true`, the csproj writes that property as `AssemblyMetadata`, and `AppInfo.IsGitHubRelease` reads it back from the entry assembly, the same as the other build flags and the informational version, since `AppInfo` itself does not live in the app's own assembly. A packaged build cannot use the Run key, since its HKCU writes are virtualised; there the card drives the manifest's `StewardStartup` `StartupTask` (which passes `--tray`) through `StartupTask.GetAsync`, `RequestEnableAsync` and `Disable`, and is always enabled except when the task reads `DisabledByUser`, `DisabledByPolicy` or `EnabledByPolicy`, which render the toggle disabled with a description pointing at Windows Settings. A non-GitHub-release build shows "(Development)" and a GitHub-release build stamped `StorePreRelease` shows "(Pre-release)" in the window title, tray tooltip and version label, as described under Microsoft Store. A settings window was cancelled and has since been revived as a settings page: see `docs/design/home-and-settings.md`.

Checking runs at startup and on every tick of a 1-minute `UiTimer` (`IUiPlatform.CreateTimer`, a `DispatcherTimer` in `AvaloniaPlatform`) in `MainViewModel`, re-checking `/api/me` alongside the manifests, unless a pass is still in flight; the guild roster pull and character push inside that pass drop to every 15 minutes while the guild event stream is connected, as described under Roster sync. A background pass skips busy rows and never re-orders `Installs` or `AddonRows`. The pass's longer intervals (the 15-minute guild, directory and banner fallbacks, the 30-minute CurseForge check and the hourly Store check) go through `MainViewModel.IsDue`, which stretches each by a per-run random 0 to 20% (`_intervalJitter`), so copies restarted together by a Store update fall out of step instead of hitting steward-server at once. Concurrent updates share one in-flight `/api/me` recheck (`EnsureAuthorizedForActionAsync`), serialise only the delete-and-extract step and `StewardSync.lua` writes on `AddonUpdater.AddOnsWriteLock`, and an install's Local rescan waits until none of its rows is busy. `MainViewModel.AutoApplyAsync` runs after every pass, on every tick and right after a watched client exits: each eligible row's `UpdateCommand` is executed, up to 4 at once (`RunBoundedAsync`, shared with Update all and Update all installs), skipping busy rows and rows whose last attempt failed until a new resolution arrives. A fourth Behaviour card, "Auto-update addons", gates this in one place, the top of `AutoApplyAsync`: `Always` applies whether or not the client is running (the original behaviour), `Out-of-game` skips a row while its install's `WowInstallViewModel.IsClientRunning` is true and catches up the moment that install's client exits, and `Never` returns before touching any row, including the `AutoInstall` install of a missing addon. The setting is `AppState.AutoUpdate`, persisted as `auto_update` in `state.json` with the values `always`, `out-of-game` and `never`, defaulting to `out-of-game`; `AppStateStore.ParseAutoUpdate` reads an unknown or missing value the same way. `WowClient.IsRunning` in Core judges whether an install's client is up, by matching any `Wow*` process whose main module sits under that install's flavour folder; it drives the running dot and the `/reload` hint a row shows after an update applied while the client was running, cleared when the client stops.
