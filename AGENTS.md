# Steward

.NET 10 WinUI 3 desktop app, public repo, ships as an unpackaged self-contained MSI (x64 only). The desktop half of Steward, a guild toolkit for World of Warcraft: it keeps the Steward addon current and will carry guild roster, loot history and attendance between the game and gigagrug, combining several officers' records into one view.

Updating is the whole of it today. It manages a set of addons rather than one, against their published release channels, reading admin state from gigagrug.

## Managed addons

`appsettings.json` holds an `Addons` array of `{ Id, FolderName, ManifestBaseUrl, AutoInstall?, Features? }` (`ManagedAddon` in `Steward.Core`), rendered in array order; `ManifestBaseUrl` is required. Three entries ship today: `steward` (`AutoInstall: true`, `Features: ["steward"]`), `hoobiscripts`, and `restedxp` (`ManifestBaseUrl: https://api.hoobi.io/guild/api/addons/restedxp/`, `Features: ["addons","guides"]`, since the RestedXP row also carries the Guides sign-in entry point). A configured addon with no manifest on any channel renders as "No releases yet" rather than as an error. Adding one is a config entry, nothing more: `AddonUpdater` takes the `ManagedAddon` and channel as parameters rather than hardcoding a folder name or manifest URL, and the UI iterates the configured list per WoW install.

`Features` defaults to `["addons"]` and names which of the signed-in user's `/api/admin/me` features make the addon appear at all: it is visible when the user holds any one of them. `MainViewModel.VisibleAddons()` is the one place the configured `Addons` list is filtered down to the addons the signed-in user's feature set covers, and every addon-list iteration (the manifest/release check, auto-apply, Update all, the Hidden addons toggle, `AddonChannels`) goes through it. Per-install rows are not fixed at construction: `WowInstallViewModel.SyncAddons` reconciles `AddonRows` against a given addon list, keeping the row instance for an addon still visible, adding one for an addon newly visible in its config-order position, and removing and unsubscribing one for an addon no longer visible. `MainViewModel.ReconcileFeatureGating` calls it on every install, prunes `_status`/`_releases` to the addons still visible and rebuilds `AddonChannels`, whenever `RecheckAuthorizationAsync` finds the feature set changed from the previous check; that covers a feature gained or lost mid-session and a start where gigagrug was unreachable and the set was still empty, since the next successful check is a change from empty. Each row's own `ensureAuthorized` also reconfirms its addon's feature is still held before an update runs, so an update queued just as the feature drops refuses rather than applying.

`AutoInstall` marks an addon the background pass installs when it is missing, under the same admin gate as auto-update; it cannot be hidden. No addon is sourced from the GitHub API from this app any more: RestedXP moved to gigagrug's own mirror of `RestedXP/RXPGuides`'s GitHub releases, served at its `ManifestBaseUrl` in the same `latest-{channel}.json` shape every other manifest-host addon uses, so `AddonUpdater` and `GetLatestAsync` have one code path for every addon. The mirror (`src/gigagrug/services/github_mirror/service.py` in `D:\gigagrug`) applies the selection rules gigagrug's own list of GitHub releases needs: `release` is the non-draft entry without the `prerelease` flag that has the latest `published_at` and `pre-release` the one with the flag that has the latest `published_at`, because the GitHub API's list order is not date order (on 20 Sep 2026 it returned `.95, .94, .92, .102, .100`, and taking the first entry reported the installed build as up to date). The `.zip` asset is the release and its `sha256` digest is the checksum, and the tag name is the version (RXPGuides stamps the same `v4.11.4` form into its TOC); a release lacking a `.zip` asset or a digest is skipped by the mirror rather than surfaced here. There is no `develop` channel for RestedXP: the mirror only ever answers `release` and `pre-release`, so a `develop` request 404s and reads as no release the same way an empty channel does for any other addon. The icon comes from the mirror's own `icon.png` route, which redirects to the repo owner's GitHub avatar, so a manifest-host addon's icon logic covers it without a branch.

A user can hide an addon they manage through CurseForge or WowUp from the row's overflow menu. Hidden ids live in `hidden_addons` in `state.json`, global rather than per install, and hidden rows are excluded from counts, auto-apply, Update all and the list; the "Hidden addons" toggle in the page header shows them again with a Hidden pill so they can be unhidden.

The manifest for an addon+channel is `{ManifestBaseUrl}latest-{channel}.json`; the release zip resolves relative to that manifest URI, so an absolute `zip` URL is used as-is. The manifest fetch sends `Cache-Control: no-cache` per request rather than trusting the Static Web App's own cache headers, since the SWA route's header behaviour for a nested path is unconfirmed. SHA-256 verification, the zip-slip guard, and the rule that an existing addon folder is only deleted when it holds that addon's own `.toc` are unchanged from the single-addon version.

## Auth: default-browser sign-in over a loopback callback

gigagrug accepts exactly one credential, the `gg_session` cookie (`auth_middleware`), with no bearer or API-key path, and exposes a desktop flow that hands that cookie's raw value to a local client. `SessionService` generates a verifier (base64url of 32 random bytes) and a challenge (lowercase hex SHA-256 of the ASCII verifier, matching Python's `hexdigest`), binds a listener, and opens `GET {BaseUrl}/api/auth/desktop?challenge=<challenge>&port=<port>` in the default browser. gigagrug runs the Discord OAuth exchange and redirects the browser to `http://127.0.0.1:<port>/?code=<one-time code>`. The app then POSTs `{"code","verifier"}` to `{BaseUrl}/api/auth/desktop/exchange` and receives `{"token": "<gg_session value>"}`; the code is single-use with a 120-second TTL.

The listener is a `TcpListener` on `IPAddress.Loopback` with port 0. `HttpListener` cannot bind port 0 and its HTTP.sys prefix semantics need a fixed registered prefix, and Kestrel pulls an ASP.NET framework reference into a self-contained WinUI publish, so neither is used. The whole flow times out after 5 minutes. Every accepted connection gets the same fixed 200 HTML page telling the user the tab can be closed, including the favicon request the browser makes alongside the callback; `LoopbackCallback.TryReadCode` in `Steward.Core` decides which request line carries a code.

gigagrug slides the session to 30 days from last use on every authenticated request, with no absolute ceiling, and never re-issues the token; the app's own `/api/admin/me` checks are what keep it alive. Removing a user's last seat on the guild panel deletes their sessions server-side, so a demotion reaches the app as a 401 on the next check rather than as `role: null`. The app persists the raw token itself (DPAPI-protected, `%LocalAppData%\Steward\state.json`) rather than relying on the cookie jar as the store; the browser flow is only how the token is acquired, once, at sign-in.

The API origin is `https://api.hoobi.io/guild` (`Gigagrug:BaseUrl`). `guild.hoobi.io` is the Static Web App hosting the SPA, and its navigation fallback answers every `/api/*` path with `index.html` and a 200, so a client pointed there sees HTML where it expects JSON rather than a 401.

Every privileged action re-checks `GET /api/admin/me`: at startup, immediately before an update, and on a 15-minute timer while the window is open. A 401 means the session is gone; the persisted token is cleared and the app drops to signed-out. Any other failure (a 502, a timeout) marks the API unreachable: the error bar shows the message with a Retry button, the Sync page is disabled, and the timer retries every minute instead of every fifteen until a check succeeds and clears the state. An authenticated response whose effective feature set is empty (nothing to do in the app at all) clears the session and drops the app to the gate with a "no Steward access" bar, the same treatment as a 401. This re-check keeps the UI truthful; it is not enforcement, since the zips themselves are served from a public Static Web App with no auth of their own.

`/api/admin/me`'s `user.features` is a `string[]` of `addons`, `guides` and `steward`. Access is gated on that set, never on `role`: a guild member can be granted `addons` and `guides` by Discord role or user id on the gigagrug side, independent of holding an officer seat, while `steward` comes only with an officer seat, and `role` global/admin is only the fallback used to derive the set when an older gigagrug server sends no `features` field at all (officer gets all three, everyone else gets none). `GigagrugClient.EffectiveFeatures` computes that set from an `AdminMe`. `MainViewModel` keeps it in `_features` and reads it through `HasGuidesFeature`/`HasStewardFeature` and `VisibleAddons()`; `IsAuthorized` is true whenever the set is non-empty. The guides gate itself lives inside `RestedXpViewModel`, not in `MainViewModel`: it takes a `Func<bool> hasGuidesFeature` at construction (`() => HasGuidesFeature`) and checks it in `CheckAsync`, `RefreshSessionAsync`, the per-install saved-variable confirm, and before setting up each install's `FileSystemWatcher`, so a feature drop stops every one of those without a caller having to remember the gate. `IsGlobalAdmin` (`role == "global"`) is unrelated to any of this and continues to be the only gate on the `develop` addon channel. A non-officer's `guilds` list is empty and gigagrug answers 403 on every `/api/admin/` route below `me` for them, so roster and members are officer-only.

## Channels

Three release channels, named after what produces them in `hoobio/addons`: `release` (a tagged GitHub release of the addon), `pre-release` (every push to the addon's `main`) and `develop` (every push to its `develop` branch). RestedXP has `release` and `pre-release` only, mapped to the GitHub release and prerelease flags gigagrug's mirror reads. The channel is per addon, stored in `Channels` alongside the install-state records in the same `state.json`, defaulting to the first channel that has a release in the order `release`, `pre-release`, `develop` (`AddonChannelStatus.Ordered`, also the picker order). When a more stable channel holds a build released after the one on the chosen channel, the row shows a notice naming it, so being on `pre-release` while a newer `release` exists is visible without switching. `develop` is offered only when `/api/admin/me` returns `role: "global"` exactly; `admin` sees release and pre-release. That gate is client-side only, same caveat as the admin re-check above: nothing stops a direct fetch of the develop manifest. The rename from `stable`/`beta`/`unstable` was not migrated: a stored old channel name falls back with the "No releases on X any more" notice. The later rename from `development` to `develop` is migrated: `AppStateStore.MigrateDevelopmentChannel` rewrites a stored `development` value to `develop` on load, alongside the `LegacyChannel` seed.

Each WoW install + addon pair records what was actually installed (version, channel, sha256), keyed by flavour path plus addon id. With no record, the addon's own `.toc` version is the fallback, which is the manual-install case. Update availability is plain string inequality between that recorded/TOC version and the channel manifest's version, not a semver comparison: versions like `0.5.0-beta.1` and `0.5.0-unstable.219da29` don't parse as `System.Version`, and switching channels has to be able to move the installed version in either direction.

## WoW install discovery

`WowInstalls` walks `.flavor.info` (product code) joined against the root `.build.info` (product to version) to find each flavour without a hardcoded product-to-folder map. The Blizzard registry key (`HKLM\...\World of Warcraft`) is not used as a discovery root by itself: on the dev machine it is hijacked by an unrelated Ascension install, so it is one candidate root among several, never the only one trusted.

Discovery is filtered to `SupportedProducts` in `appsettings.json`, a product code to display name map, since the managed addons target World of Warcraft: Forever only. Today that map holds one entry, the beta's `wow_classic_beta`; the release build joins as a second entry once its product code is known, and `docs/forever-release.md` lists every value and file that day touches.

## Branding

`src/Steward.App/Assets/Steward.ico` (16 through 256px, PNG-compressed frames) is the one source of the app's icon: `ApplicationIcon` stamps it on the exe, `AppWindow.SetIcon` puts it on the one window, and the wxs picks it out of the publish payload for `ARPPRODUCTICON` and the Start menu shortcut. WinUI 3 does not take the window icon from the exe on its own, so the `SetIcon` calls are load-bearing.

The MSI uses `WixUI_InstallDir` with the licence dialog skipped through two `Publish` overrides (the repo has no licence file), so the flow is Welcome, InstallDir, Ready, Progress, Exit. `installer/WixUIDialogBmp.bmp` (493x312, `#1d1d1d` left panel with the logo at 96px) and `installer/WixUIBannerBmp.bmp` (493x58, logo at the right) are generated from `Steward-256.png` with System.Drawing and checked in beside the wxs, the same treatment as earmark. The `.msi` file itself keeps the Windows Installer icon: only a bundle exe can carry its own. `build.yaml` passes `WixToolset.UI.wixext/5.0.2,WixToolset.Util.wixext/5.0.2` to the build step; the unversioned names resolve to a WiX 7 extension that fails against WiX 5.

## Self-update

The app is moving to the Microsoft Store, and the GitHub MSI is the bridge to it rather than a continuing channel: the next MSI release is the last, and a later change removes the MSI build, the MSI self-updater and the app channels. `App.IsPackaged` (`GetCurrentPackageFullName` answering anything but `APPMODEL_ERROR_NO_PACKAGE`) splits the two paths. A packaged build checks the Store through `StoreContext.GetAppAndOptionalStorePackageUpdatesAsync`, with the window handle passed through `InitializeWithWindow` as WinUI 3 requires, on the startup pass, on Refresh and at most once an hour from the 1-minute background pass (`_lastStoreCheck`, wall-clock like `_lastGuideCheck`); an available update shows the same InfoBar and About card button, both opening the product page `ms-windows-store://pdp/?productid=` plus `App:StoreProductId`, and the app channel control is hidden. A Store failure goes to the error bar like a manifest failure. Everything below this paragraph describes the unpackaged MSI build only; none of it runs packaged.

An unpackaged build also looks for the Store package on the same passes, through `PackageManager.FindPackagesForUser(string.Empty, "Hoobi.Steward_thayxpy3eqg0g")`, which works unelevated from an unpackaged process. With no Store package the Addons page shows "Steward is on the Microsoft Store" with a button opening the product page; with it installed the page shows "The Microsoft Store version is installed" with a Switch button. Switch starts the same hidden `powershell.exe` hand-off as the MSI update (`AppUpdater.SwitchToStoreAfterExit`, built by `SwitchToStoreScript`), which waits for this process to exit, runs `msiexec /x /qn` against every product code `WindowsInstaller.Installer.RelatedProducts` returns for the wxs `UpgradeCode`, logging to `update.log`, deletes the `Steward` Run value, and only then launches `shell:AppsFolder\Hoobi.Steward_thayxpy3eqg0g!App`, because the MSI's `taskkill` custom action targets `Steward.App.exe`, which is also the packaged exe's name. The app quits right after starting it.

`AppUpdater` in Core reads `{App:ManifestBaseUrl}latest-{channel}.json` (`https://addon.hoobi.io/steward-companion/`) through `AddonUpdater.FetchManifestAsync`, the same manifest fetch the manifest-host addons use, on the startup pass, on Refresh and on every 1-minute background pass; a 404 on a channel reads as no release rather than a fault, since the manifests appear only once the addons pipeline has mirrored a release. The `hoobio/addons` pipeline writes those two manifests from the GitHub release list (`operations/scripts/mirror-github-releases.sh`), so the `zip` is the release asset's own `browser_download_url` on GitHub and only the pointer is on the Static Web App: the MSI is 77MB and the site is a Free tier app with a 250MB ceiling. A `dispatch` job here fires `addon-released` at that repo after a release or pre-release is published, which is what refreshes them. The app's own update channel is a user setting, `app_channel` in `state.json`, defaulting to `release` and picked from a Segmented control under About on the settings page. On `release` the tag is compared as a `System.Version` against the assembly version normalised to three parts, because `Version` treats a missing fourth component as below zero. On `pre-release` the newest release and the newest prerelease are compared by published date and the later one is offered when its tag differs from the running informational version and its numeric part is not lower than the running version, since an older prerelease is stale rather than an update. A pre-release build on the `release` channel is offered the latest release whatever its number, so switching channels always lands on the release even when the pre-release is newer; that is a downgrade in Windows Installer terms, which is why `MajorUpgrade` sets `AllowDowngrades` (a pre-release MSI also carries the same numeric version as the release that follows it, which the same setting covers). `AllowDowngrades` alone is not enough: Windows Installer costs files before `RemoveExistingProducts` runs and never replaces a versioned file with a lower version, so on a downgrade the old product's removal then deletes the files the new one skipped. The 0.8.2 release lost its whole .NET runtime that way on every upgraded machine, because pinning the SDK to 10.0.203 dropped the bundled runtime from 10.0.12 to 10.0.7 while the MSI itself was complete. Two rules follow: the MSI sets `REINSTALLMODE=amus` so every file is written regardless of version (the folder holds nothing but our own files), and `RuntimeFrameworkVersion` in `Steward.App.csproj` pins the shipped runtime and is only ever raised. Changing the channel saves the setting and re-runs the check at once. The version label reads `AssemblyInformationalVersion` cut at `+`, so a tester sees the full `0.7.2-pre-release.5b65e5e`. An available update shows as an InfoBar on the Addons page and changes the About card's button to "Install update". Installing downloads the MSI to `%TEMP%`, verifies the GitHub digest, then starts a hidden `powershell.exe -EncodedCommand` that waits for this process to exit, runs `msiexec /i /qn` with a verbose log at `%LocalAppData%\Steward\update.log` and deletes the MSI; the app quits immediately after starting it. The MSI itself ends any running `Steward.App.exe` before `InstallValidate` through a `WixQuietExec` call to `taskkill /f /im`: `util:CloseApplication` sends WM_CLOSE, which a tray-parked instance cancels, and its terminate fallback never freed the files. It then launches the installed exe, after `InstallFinalize` when `UILevel < 5` and from the exit dialog's Finish button otherwise, so the dialog cannot take the foreground back off the window it just opened. That is why the hand-off script does not relaunch: a second launch would start a second instance. The MSI is per-user, so no elevation is involved. Development builds check and install too; the launch afterwards starts the installed build, not the one that was running. The workflow's `build-msi-wix` step loads `WixToolset.Util.wixext` pinned to the WiX tool version through its `extensions` input.

## Microsoft Store

The MSIX package identity, reserved in Partner Center, is `Hoobi.Steward` (PFN `Hoobi.Steward_thayxpy3eqg0g`), publisher `CN=D74C026B-1081-4787-BDE6-0CFA2F1EDD71`, Store ID `9PBKMZFKZHKX`. `src/Steward.App/Package.appxmanifest` carries that identity directly rather than a Dev/Release pair, because the Store build is release-only: there is no channel-identity stamping to do. The `desktop:StartupTask` extension (`TaskId="StewardStartup"`, `uap10:Parameters="--tray"`) covers Start with Windows for a Store install, the counterpart to the registry-based toggle the MSI build uses.

`build.yaml`'s `build-msix` job runs on every push to main, building with `GitHubRelease=true` set as an environment variable on the `build-msix-dotnet` step, since MSBuild reads env vars of a property's own name, with a second identical step retrying it once on failure (the same NuGet-restore flakiness `build-msi`'s publish step retries against). `build-msix-dotnet` only produces a bare `.msix`; the Store needs an app package upload file, so the job zips that `.msix` and renames it to `.msixupload` (the documented manual method), and uploads it as the `msixupload-x64` workflow artifact. It is never attached to a GitHub release and never signed there: the Store re-signs on submission. The manifest is stamped from `version.txt` directly, read the same way on every run rather than falling back to an open release-please PR's title the way `build-msi` does for its pre-release numbering: `version.txt` only changes when a release PR merges, so a non-release run always stamps the last released version and a release run always stamps the version just released. Stamping a non-release build with the *next* version (the open PR's title) would give a manually-submitted pre-release `.msixupload` the same numeric version the following real release later submits, which Partner Center rejects as a duplicate; the Store has no prerelease-suffix concept to tell the two apart the way the MSI's assembly version does.

The `store-submit` job runs only when release-please cut a release on that run, after the `release` job, and only when the `AZURE_CLIENT_ID` repo variable is set, using `microsoft/microsoft-store-apppublisher@v1.4` and the `msstore` CLI. The Store credentials live in the homelab Key Vault `hbicfgkvtaus01` as `msstore-tenant-id`, `msstore-client-id`, `msstore-client-secret` and `msstore-seller-id` (the client is the "Partner Center Uploads" Entra app with the Manager role), so any repo that publishes to the Store reads the same four; the job signs in through GitHub OIDC as the `github-hoobio-msstore` Entra app (repo variables `AZURE_CLIENT_ID` and `AZURE_TENANT_ID`, no subscription), which holds `Key Vault Secrets User` on those four secrets only and trusts `main` of each repo it has a federated credential for. The job masks each value, runs `msstore reconfigure`, then a delete-pending-submission, `msstore publish <msixupload> -id 9PBKMZFKZHKX --noCommit`, a release-notes patch, `msstore submission publish` sequence, checking `$LASTEXITCODE` after every `msstore` call except the delete (which resets it deliberately, since a missing pending draft is not a failure). The file-path form of `msstore publish` (a `.msixupload`/`.msixbundle` passed as the positional argument, not `-i <directory>`) is confirmed working: `hoobio/command-palette-bitwarden`'s `store-publish` job uses the identical `msstore publish $bundle -id $env:PRODUCT_ID --noCommit` form against a `.msixbundle` and succeeded (run 31148741706, job "Publish to Microsoft Store"). `submission updateMetadata` takes its JSON inline as a positional argument; the CLI has no file-input flag for it (confirmed against the Microsoft Learn command reference), so the patched submission JSON is still read from disk and passed as `(Get-Content -Raw patched.json)`. Pre-releases never reach the Store. `msstore` only updates an app that is already live in the Store, so the first submission has to be made by hand in Partner Center: submit a pre-release `.msixupload` there manually, and only publish the bridge GitHub release (the one that triggers `store-submit`) once that manual listing is live, since `store-submit` clones the live submission rather than creating the app's first one.

The "What's new in this version" listing field is filled from the being-released version's own `CHANGELOG.md` section, keeping only the Features and Bug Fixes entries and dropping every other conventional-commit type; `scripts/Get-StoreWhatsNew.ps1` strips each entry down to its plain description (scope, gitmoji and commit-hash link removed) and truncates at a bullet boundary to the Store's 1500-character `ReleaseNotes` limit. A version whose changelog section holds neither section returns "Minor improvements and fixes." rather than leaving the listing untouched.

A named mutex (`Local\Steward.App`, created in `Program.Main` before `Application.Start`) enforces one running instance; a second launch finds the mutex already held and exits immediately without showing a window. The same code runs in both the MSI and Store builds, so the name is shared between them rather than stamped per channel.

Both hand-off scripts (`AppUpdater.InstallScript` and `AppUpdater.SwitchToStoreScript`) escape every value they interpolate into single-quoted PowerShell with `.Replace("'", "''")`, and read each `msiexec` call's exit code through `-PassThru -Wait`; a non-zero code other than `3010` (a reboot-required success) stops the script before it removes the `Run` value or launches the replacement app, so a failed uninstall or install cannot silently leave both the old and new install in a broken state.

`MainViewModel.CheckStoreUpdateAsync` catches every exception from the `StoreContext` call itself and routes it to `StatusMessage`, rather than relying on the caller's typed catch clauses, since a WinRT failure there is not guaranteed to be a `COMException`. The Store-install check (`PackageManager().FindPackagesForUser`, behind `IsStoreAppInstalled`) runs at the start of `LoadAsync`, `RefreshAsync` and `RunBackgroundPassAsync`, before the gigagrug authorization check and unconditional on its result, so the MSI-to-Store migration banners still show when `addon.hoobi.io` is unreachable or the user is signed out.

When packaged, "Open data folder" and the About card's installed-path text prefer `Windows.Storage.ApplicationData.Current.LocalCacheFolder.Path\Local\Steward` over the literal `%LocalAppData%\Steward` when that folder exists, through the shared `App.DisplayDataFolder` helper: a packaged process's writes to `%LocalAppData%\Steward` land in that virtualised location, so pointing Explorer or the About text at the literal path would not show what is actually on disk. The real `%LocalAppData%\Steward` path is unchanged for `state.json` and `update.log`, which the packaged and unpackaged builds still share.

The Start with Windows toggle shows distinct, disabled text for each locked `StartupTaskState`: `EnabledByPolicy` reads on with "Turned on by your organisation's policy", `DisabledByPolicy` reads off with "Turned off by your organisation's policy", and `DisabledByUser` reads off with "Turned off in Windows Settings > Apps > Startup".

The Store is the app's only release channel going forward. The MSI stays in place only for the one release that bridges existing installs across; a later change removes the MSI path once that release has shipped.

## Development install

Every `git push` from this clone builds HEAD and registers it as a second, side-by-side packaged app, so a developer always has a running build of `main` without touching the Store install. `scripts/Install-DevBuild.ps1` never touches the working tree: it exports the pushed commit with `git archive HEAD` into a scratch copy at `%LocalAppData%\Steward.Dev\src` (wiped first), stamps a dev identity into that copy's `Package.appxmanifest`, `Hoobi.Steward.Dev` publisher `CN=Hoobi Dev`, both `DisplayName` elements reading "Steward (Development)", and the version from `version.txt`, and builds from there, so a commit made while the build is running never ships the dev identity and `git status` stays clean throughout. It builds a Release x64 MSIX the same way `build-msix` does in `build.yaml`, extracts the produced `.msix` (a zip container) to `%LocalAppData%\Steward.Dev\app`, and registers that loose layout with `Add-AppxPackage -Register`, which Developer Mode accepts unsigned. The MSIX is framework-dependent (`WindowsAppSDKSelfContained=false`), so it only runs on a machine with the Windows App Runtime installed. The Start menu entry is "Steward (Development)"; the package family name is `Hoobi.Steward.Dev_<publisher-hash>`, distinct from the Store's `Hoobi.Steward_thayxpy3eqg0g`.

The dev package runs side by side with the Store package, both able to be open at once. The single-instance mutex is `Local\Steward.App` when `App.IsGitHubRelease` (the Store and MSI builds, which both publish with `GitHubRelease=true`) and `Local\Steward.App.Dev` otherwise, so a dev build never contests the Store build's mutex and vice versa. The Store update check (`CheckStoreUpdateAsync`, via `StoreContext`) only runs when `App.IsGitHubRelease`, since a dev identity is never in the Store; a packaged non-GitHubRelease build reports no update rather than surfacing a Store error. The MSI-to-Store migration banner (`UpdateStoreAppInstalledState`) only ever ran for an unpackaged build, so it was already inert for a packaged dev build without any change here.

The manifest's `StewardStartup` `StartupTask` is scoped per package identity, so enabling Start with Windows for the dev package cannot collide with the Store package's own toggle: each autostarts independently with `--tray` if the user turns it on for that package.

Because the two packages carry different identities, Windows virtualises each one's writes to `%LocalAppData%\Steward` into its own per-package storage; the dev package does not see the Store package's `state.json` or session, and starts signed out on a machine that is signed in on the Store build. `App.DisplayDataFolder` reflects this: it points at the dev package's own virtualised folder, not the Store package's.

`.githooks/pre-push` triggers the build: a POSIX `sh` script that starts `scripts/Install-DevBuild.ps1` fully detached and hidden, then exits 0 immediately, so a slow or failing dev build never blocks or fails a push. Run `git config core.hooksPath .githooks` once per clone to pick it up; `.gitattributes` forces it to LF regardless of the checkout's `autocrlf` setting. Everything the script does is logged to `%LocalAppData%\Steward.Dev\install.log`.

## Git workflow

Commits go straight to `main` in the one working tree at `D:\steward-companion` and are pushed there; this repo uses no feature branches, no worktrees and no pull requests for its own work, and a subagent edits `main` in place. Conventional-commit subjects feed release-please, which opens the release PR itself.

## Releases

`build.yaml` publishes from every push to `main`. A newer push cancels the run still in progress for an older one (`concurrency` with `cancel-in-progress`), except that a run for a release-please merge (`chore(main): release ...`) sits in its own group, so a push behind it can never cancel the run that cuts the release and attaches its MSI. release-please runs first; `build-msi` waits on it and takes the numeric version from the open release-please PR's title (`chore(main): release 0.8.0`, the version the next merge would cut), falling back to `version.txt` when no release PR is open; that number is the MSI `ProductVersion`, and the assembly version passed to `dotnet publish` is `<number>-pre-release.<7-char sha>` unless release-please cut a release on that run. With no release cut, the `pre-release` job creates a GitHub Release flagged prerelease, tagged `v<that version>`, with the MSI renamed to match and notes generated from the last release, then deletes all but the five newest prereleases and their tags, so the app's 20-item release listing never fills with them. Merging the release PR has release-please create the release as a draft (`draft: true` in `release-please-config.json`), the MSI is attached, the notes are stacked back to the last minor, and only then is the draft published through `publish-github-release`, so a published release never lacks its MSI. release-please matches the latest release by exact manifest version string, so a `-pre-release.<sha>` tag never moves its changelog boundary. Pull requests run lint and tests only; the MSI is not built for the release PR. The `release: published` trigger is gone, since nothing downstream listens.

## Build and test gotchas

`Steward.slnx` defines no `Release|x64` solution configuration, so a solution-level `dotnet build` must not pass `-p:Platform=x64`; the CI workflow builds the solution without it and passes `-p:Platform=x64` only on the project-level `dotnet publish` of `Steward.App.csproj`.

`global.json` pins the SDK to `10.0.203` with `rollForward: disable`, because `DOTNET_SDK_VERSION` in the workflow only says what `setup-dotnet` installs and the runner image ships newer SDKs that `dotnet` would otherwise pick; it also sets `test.runner` to `Microsoft.Testing.Platform`. The publish step retries up to three times, since NuGet restore on the runner can fail with a bare MSB4181 "RestoreTask returned false but did not log an error" and no cause (NuGet/Home#13460), as it did twice on 20 Sep 2026. On .NET SDK 10.0.203, `dotnet test <directory>` fails under that runner; the working form is `dotnet test --project <csproj>`, which is what the CI workflow uses.

`Microsoft.Win32.Registry` is already in-framework on `net10.0-windows`; adding it as an explicit `PackageReference` fails restore with `NU1510`. `WowInstalls.cs` uses `Microsoft.Win32.Registry` directly, and neither `.csproj` in this repo references the package.

CommunityToolkit.Mvvm's field-backed `[ObservableProperty]` triggers diagnostic `MVVMTK0045` under WinUI; the ViewModels here declare partial properties instead (`[ObservableProperty] public partial string? Foo { get; set; }`).

## UI verification

A change to anything visible is launched and driven before it is reported done; a clean build is not evidence that a view looks or behaves right. The sequence:

1. Stop any running `Steward.App` (`Get-Process Steward.App -ea 0 | Stop-Process`), since a running instance locks the exe and the build then fails on the copy step rather than on the code.
2. `dotnet build Steward.slnx -c Debug`, then launch `src\Steward.App\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Steward.App.exe`. It shares `%LocalAppData%\Steward\state.json` with the installed build, so it starts signed in with real data.
3. Drive it from PowerShell with `tools\UiDriver.psm1`: `Start-UiApp`, `Find-UiElement` (UI Automation), `Invoke-UiClick`, `Write-UiValue`, `Show-UiElement`, `Move-UiScroll`, `Save-UiScreenshot`, and `Get-UiPopup` for a menu or flyout, which opens as its own top-level window. The scenario script for a given change is written per task in the scratchpad and is not checked in.
4. Read every screenshot. For motion (hover, press, open), `Measure-UiTransition` pen-hovers a point and captures the window in a loop for 250ms, returning each frame's sampled colour, so a flash shows up as a frame brighter than both ends.

The user works at this machine while an agent drives the app, so the driver moves no mouse cursor and sends no mouse or keyboard input. `Invoke-UiClick` goes through UI Automation patterns (Invoke, then Toggle, then SelectionItem, then ExpandCollapse) and throws when an element supports none of them; text goes through `ValuePattern` (`Write-UiValue`) and scrolling through `ScrollItemPattern` and `ScrollPattern`. Navigating between pages through the `NavigationViewItem` patterns is verified.

Captures use `PrintWindow` with `PW_RENDERFULLCONTENT` (`0x2`) on the window handle, so an overlapping window, the user's cursor and a snipping overlay never appear in them; the main window renders its WinUI content in full while another window covers it. `Save-UiScreenshot -Popup` captures a popup's own window the same way and draws it over the main window at its screen offset, and `-Rect` crops to a screen rectangle. Popup capture is not yet verified: a flyout opened through `InvokePattern` while another window held the foreground was not found by `Get-UiPopup`, likely light-dismissed on deactivation.

Hover uses synthetic pen input (`CreateSyntheticPointerDevice` with `PT_PEN`, then `InjectSyntheticPointerInput` with `POINTER_FLAG_INRANGE | POINTER_FLAG_UPDATE` and no `INCONTACT`), in `Move-UiPointer` and `Exit-UiPointer`. It is not yet verified that WinUI applies `PointerOver` from it or that it leaves the cursor where it is, and it hit-tests on screen, so the target has to be the topmost window at that point. Until a run confirms both, hover and transition checks wait for the user's go-ahead. Launching the app still takes the foreground once.

## Design system

The house design system is `D:\hoobi-design` (React and Tailwind, no XAML output); its `AGENTS.md` "WinUI 3 conventions" table is the spec this app ports into `App.xaml` by hand. ## Saved variables

Roster, loot and attendance read WoW SavedVariables files. Those files are one per addon per scope: everything under an addon's `## SavedVariables:` TOC directive lands in one shared account-level file at `WTF\Account\<ACCOUNT>\SavedVariables\<Addon>.lua` under the flavour folder, and `## SavedVariablesPerCharacter:` in a per-character file at `WTF\Account\<ACCOUNT>\<Realm>\<Character>\SavedVariables\<Addon>.lua`. Account folder names look like `54939295#1`, and the `.lua.bak` beside each file is ignored.

The reader is built, in `Steward.Core` with no UI on it yet. `LuaSavedVariables.Parse` is a recursive-descent parser for the client's own dump format: one global per `## SavedVariables:` entry, `["string"]`, `[123]` and bare identifier keys, strings with the client's escapes, numbers, booleans, `nil`, nested tables, array items, trailing commas and the `-- [n]` comments the client writes after array entries. Malformed input throws a `FormatException` naming the line and column. `StewardSavedVariables.FindFiles` locates the Steward files under a flavour path and `StewardSavedVariables.Read` maps them into a `SavedVariablesSnapshot` of roster, loot and attendance.

The Steward addon has no Lua yet, so the schema below is the contract the addon must write rather than a record of what it writes. The account file holds `StewardDB`:

```lua
StewardDB = {
["exportedAt"] = 1758260000,
["roster"] = { { ["name"] = "Hoobi", ["realm"] = "Nightslayer", ["class"] = "WARRIOR", ["level"] = 60, ["rank"] = "Officer", ["rankIndex"] = 1, ["note"] = "", ["officerNote"] = "", ["lastOnline"] = 1758250000 }, },
["loot"] = { { ["id"] = "3f2a...", ["at"] = 1758240000, ["player"] = "Hoobi", ["itemId"] = 19019, ["item"] = "Thunderfury", ["quality"] = 5, ["source"] = "Ragnaros", ["instance"] = "Molten Core" }, },
["attendance"] = { { ["id"] = "9c1b...", ["at"] = 1758230000, ["instance"] = "Molten Core", ["present"] = { "Hoobi", "Grug" } }, },
}
```

The per-character file holds `StewardCharDB` with `["exportedAt"]`, `["character"] = { ["name"], ["realm"], ["class"] }`, and `["loot"]` and `["attendance"]` arrays of the same record shapes, carrying what that character observed. Roster is account-level only and the reader takes it from `StewardDB` alone.

`exportedAt` is unix seconds, at the file level and on `at` and `lastOnline`. Loot and attendance records carry an `id` string, and where the same `id` appears in more than one file the copy from the newest `exportedAt` wins. Reading is tolerant: a missing table gives an empty list, a record missing a required field is skipped and counted in the snapshot's `Skipped`, and an absent `exportedAt` gives null.

The client only serialises saved variables at logout, exit or `/reload`, rewriting the whole file from memory, so any external write to that file while the client is running is lost on the next serialise. Data flow is therefore one direction per file: the app only reads the saved-variables file, and only writes a generated Lua file elsewhere in the addon folder, one the client never writes to, calling a function the addon exposes rather than assigning a raw global.

The generated-file writer is `StewardSyncFile` (`Interface\AddOns\Steward\StewardSync.lua`, written by calling `Steward.LoadSync({...})`), guarded by the same TOC-existence check as `RemoveExistingInstall` and written temp-then-move; the addon's own TOC must list `StewardSync.lua` for the client to load it, a dependency on the addon repo.

Installing or updating the Steward addon replaces the whole folder, so `StewardSync.lua` and `Avatar.tga` go with it. Two things put them back. `GuildRosterSync.WriteIfChanged` skips on an unchanged fingerprint only when both files are still on disk, so the next background pass rewrites them; and `AfterStewardInstalled` runs `MainViewModel.SyncRosterAsync` the moment an install finishes, for the user who launches the game before that pass. `SyncViewModel.WriteGeneratedFileAsync` (the Write again button and the post-install hook) goes through that same method rather than pulling from its own `IGuildSyncApi`, which is `InMemoryGuildSyncApi` by default and wrote the fake dataset over the real roster.

Still to come, in the commits after this one: the freshness judgement (the saved-variables mtime against the running client's process start time from `WowClient`, plus `exportedAt`) and the sync page itself. The addon side of the contract lives in `hoobio/Steward`'s `AGENTS.md`.

## RestedXP guides

`docs/design/restedxp-guides.md` is the verified contract for RestedXP's undocumented API and is the source of truth for it. Steward signs in against Keycloak directly (`RestedXp:Keycloak`, the `RestedXP-Prod` realm's token endpoint, public client `rxp-prod-login-client`, scope `openid offline_access`) rather than through the account backend's `/login/*` proxy, so the offline refresh token keeps the session across restarts: a password grant, plus `totp=<code>` on a second grant when Keycloak answers `invalid_grant` with an OTP description, and `grant_type=refresh_token` after that. `refresh_expires_in: 0` on an offline token means no expiry, so the stored refresh expiry is null and a null expiry never expires; the cookie's `expiresAt` is then 30 days out. Keycloak's offline session idles out 30 days after the last use, and a refresh slides it, so the on-demand refresh before a call plus the 3-hour check keep the idle window alive and a Steward run at all in any 30-day window never asks for the password again. Every authenticated call carries the `rxp_cross_auth_token` cookie built per request from the access token; the backends read only its `token` field. Guide content comes from `RestedXp:GuidesBaseUrl` (`https://rxpgcr.restedxp.com`), where `/addon/get-all-timestamps` is public and `/addon?guideName=...&bundleIndex=0` needs the cookie.

The password is used for the one password grant and never stored; it is held in memory by `RestedXpService` only between the sign-in step and the code step, and cleared after. The session (username, both tokens, the access expiry and the nullable refresh expiry) lives in `restedxp_session` in `state.json` as a DPAPI blob, the same treatment as `session_token`. The access token lasts 15 minutes, so a call refreshes whenever it has under a minute left; a bounded refresh token is renewed near its end, and a refresh that answers 400 clears the session and the card shows the signed-out state.

Timestamps are checked on the startup pass, on the manual Refresh and on the first background pass more than 3 hours after the last check (`_lastGuideCheck` in `MainViewModel`, wall-clock rather than a pass count, so the minute-by-minute retry while the guild API is unreachable does not speed it up). A guide is stale when the timestamp recorded in `restedxp_guides` (keyed like `AppStateStore.Key`, flavour path plus `productName`) is older than the server's. A downloaded string is cached at `%LocalAppData%\Steward\guides\<product>.txt` beside a `.json` holding its timestamp and BattleTag, so a regeneration costs no network call, and a failed download is not retried for 10 seconds. The sync is per install: every selected product is cached first, and the folder is rewritten when any cached string or the selection itself moved since the last write for that install.

The write is a generated addon, `StewardGuidesAddon` in Core: `Interface\AddOns\StewardGuides\` holding `StewardGuides.toc`, `Icon.tga` (an `EmbeddedResource` in `Steward.Core`, the Steward addon's own icon) and `Guides.lua`. The TOC carries `## Category: Hoobi`, `## Dependencies: RXPGuides`, `## IconTexture: Interface\AddOns\StewardGuides\Icon`, `## SavedVariables: StewardGuidesDB` and the app's informational version. Its `## Interface:` value is read from the installed `RXPGuides.toc` verbatim, comma-separated list and all, so the generated addon tracks the client's interface number through RXPGuides and a new client build needs no change here; a missing `RXPGuides.toc` throws rather than falling back. `Guides.lua` holds each selected product's string as a `[==[...]==]` long-bracket literal, and rendering throws when a string holds that terminator. The safety is `StewardSyncFile`'s: temp-then-move per file, no `WTF` segment in the path, and an existing `StewardGuides` folder is only replaced when its TOC carries Steward's own `## Title:` and `## Author:` lines.

On `PLAYER_ENTERING_WORLD` plus 3 seconds `Guides.lua` takes the RXPGuides addon object from `LibStub("AceAddon-3.0"):GetAddon("RXPGuides", true)` and hands each string to `guideImporter:ImportString`, the paste box's own path. Imports run one at a time: a second call while an import is in flight resets the first one's buffer, so the file waits for `importCoroutine` to be nil and `importBufferSize` to be 0 before the next. `StewardGuidesDB.imported` records the hash from each string's `|hash:` header once the importer's `importStatusHistory[1]` reads "Guides Loaded Successfully", and the mark is read by the app only: the bootstrap imports every string on every login, a few seconds of work, because RXPGuides on this client keeps no imported guides between sessions (ClassicWoWCommunity/forever-bugs#34) and a skip on our own mark left the game with no guides on 20 Sep 2026. The importer writes its failures only into its own window, so the file surfaces them: any other `importStatusHistory[1]` is printed to chat as `Steward <name>: <status>` and kept in `StewardGuidesDB.status[hash]`, which a success clears, and a status holding "restart your game client" is retried once after 10 seconds before it is recorded. Each guide entry also carries the purchaser's `tag` from the cached download, and a guide whose tag differs from `BNGetInfo`'s BattleTag (case-insensitive) is recorded and skipped with "bought on <tag>, you are <playerTag>; not imported" rather than handed to an importer that would reject it silently; a nil BattleTag or an uninitialised RXPGuides is waited on every 5 seconds up to 6 times before the run gives up with a chat line. At file load the bootstrap also wraps the five `inventoryManager` predicates RXPGuides v4.11.x calls from its bag hook (`IsRightClickEnabled`, `IsBagAutomationEnabled`, `IsMerchantAutomationEnabled`, `IsJunkIconEnabled`, `GetModKey`) so they answer false while `settings.profile` is nil, because that hook throws "attempt to index field 'profile'" on a client where their initialisation has not run; the wrap is a no-op once the profile exists.

An import is confirmed from the addon's own saved variable, `WTF\Account\*\SavedVariables\StewardGuides.lua` (`StewardGuidesSavedVariables` in Core): saving works on this client even though forever-bugs#34 breaks loading, so the file lands at logout, exit or `/reload` carrying the `generation` the loaded `Guides.lua` set (unix ms of the write, emitted as `local generation` and recorded per install in `restedxp_guides_generation`) and the hashes and statuses it wrote. Per kept product there are four outcomes: an account file at the install's current generation with the string's hash marked reads `Up to date`; the same file carrying a `status` string for that hash reads `Failed` with that string as the row's message, and drops that product's `restedxp_guides` record so the next sync rewrites the folder; the same file with neither reads `Not finished`, an import cut short by a logout or `/reload` that the addon runs again on the next login; no file at that generation leaves the row `Written`. The pass runs at the end of every guide check, when a client exits, and when a `FileSystemWatcher` per install sees that saved variable written under `WTF\Account` (debounced 1.5 seconds, since the client writes it temp-then-rename), so a row reads `Up to date` seconds after the `/reload` or logout that follows the importing login; it reads files only.

The file is read at login or `/reload` and never written by the client, so there is no client-closed rule: the folder is regenerated whether or not the game is running. Several products can be kept per install (`restedxp_guide_choices`, flavour path to a list of `productName`, migrating an older single `restedxp_guide_choice` into a one-item list), defaulting to every owned product allowed on that install. `RestedXp:ProductPrefixes` in `appsettings.json` maps a WoW product code to the product-name prefixes allowed on it, `wow_classic_beta` to "Forever" today; a product outside its install's prefixes is never written there. The guide string's trailing minimum-version number is not checked here; the addon reports incompatibility in game.

## Outstanding work

The tray icon, close-to-tray and minimise-to-tray are built, on `H.NotifyIcon.WinUI`. The `TaskbarIcon` lives in `MainWindow.xaml`, takes its `IconSource` from the filesystem path `App.IconPath` when unpackaged, because an unpackaged app cannot resolve `ms-appx:///`, and from `ms-appx:///Assets/Steward.ico` when packaged, because a packaged app cannot load a `BitmapImage` from a file path under `WindowsApps` (the Store build's first release showed a blank tray icon), and runs in `ContextMenuMode="SecondWindow"`. Two Behaviour cards in Settings decide it: `MinimizeToTray`, persisted as `keep_in_tray` in `state.json` and defaulting to true, sends a minimise to the tray instead of the taskbar, and `CloseToTray`, persisted as `close_to_tray` and defaulting to false, makes the X button hide instead of quit. The two share the old single `keep_in_tray` key so an existing state file keeps its minimise choice and gets the new close default. Restoring from the tray goes through `MainWindow.ShowFromTray`, which shows the `AppWindow`, restores it only when minimised (so a maximised window stays maximised), calls `Activate`, then `Native.ForceForeground`: Windows refuses `SetForegroundWindow` to a process that did not receive the last input event, and a tray click goes to explorer, so the call is wrapped in an `AttachThreadInput` to the foreground window's thread, with a `BringWindowToTop` inside it because the attached `SetForegroundWindow` activates the window without raising it. The tray icon's click commands are assigned in code rather than through `x:Bind`, since a `Window`'s bindings evaluate only once its content loads and a `--tray` launch never loads it. Start with Windows is a third Behaviour card backed by the `Steward` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, pointing at the running exe with `--tray`; that argument hides the window to the tray on launch when `MinimizeToTray` is on. The registry is the only store for it; the MSI does not remove the value on uninstall. The installer's exit dialog offers "Start Steward with Windows" through `WIXUI_EXITDIALOGOPTIONALCHECKBOX`, ticked by default, and Finish writes the same Run value through a `WixQuietExec` call to `reg.exe`; the checkbox is hidden on an upgrade, and silent installs never see it, so the self-updater cannot flip a user's choice. The card is enabled only in a GitHub release build: the workflow's `dotnet publish` passes `-p:GitHubRelease=true`, the csproj writes that property as `AssemblyMetadata`, and `App.IsGitHubRelease` reads it back. A packaged build cannot use the Run key, since its HKCU writes are virtualised; there the card drives the manifest's `StewardStartup` `StartupTask` (which passes `--tray`) through `StartupTask.GetAsync`, `RequestEnableAsync` and `Disable`, and is always enabled except when the task reads `DisabledByUser`, `DisabledByPolicy` or `EnabledByPolicy`, which render the toggle disabled with a description pointing at Windows Settings. Every other build shows "(Development)" in the window title, tray tooltip and version label. A settings window was cancelled and has since been revived as a settings page: see `docs/design/home-and-settings.md`.

Checking runs at startup and on every tick of a 1-minute `DispatcherQueueTimer` in `MainViewModel`, re-checking `/api/admin/me` alongside the manifests, unless a pass is still in flight. A background pass skips busy rows and never re-orders `Installs` or `AddonRows`. `MainViewModel.AutoApplyAsync` runs after every pass, on every tick and right after a watched client exits: each eligible row's `UpdateCommand` is executed in turn, skipping busy rows and rows whose last attempt failed until a new resolution arrives. A fourth Behaviour card, "Auto-update addons", gates this in one place, the top of `AutoApplyAsync`: `Always` applies whether or not the client is running (the original behaviour), `Out-of-game` skips a row while its install's `WowInstallViewModel.IsClientRunning` is true and catches up the moment that install's client exits, and `Never` returns before touching any row, including the `AutoInstall` install of a missing addon. The setting is `AppState.AutoUpdate`, persisted as `auto_update` in `state.json` with the values `always`, `out-of-game` and `never`, defaulting to `out-of-game`; `AppStateStore.ParseAutoUpdate` reads an unknown or missing value the same way. `WowClient.IsRunning` in Core judges whether an install's client is up, by matching any `Wow*` process whose main module sits under that install's flavour folder; it drives the running dot and the `/reload` hint a row shows after an update applied while the client was running, cleared when the client stops.
