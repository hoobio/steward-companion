# Steward

.NET 10 WinUI 3 desktop app, public repo, ships as an unpackaged self-contained MSI (x64 only). The desktop half of Steward, a guild toolkit for World of Warcraft: it keeps the Steward addon current and will carry guild roster, loot history and attendance between the game and gigagrug, combining several officers' records into one view.

Updating is the whole of it today. It manages a set of addons rather than one, against their published release channels, reading admin state from gigagrug.

## Managed addons

`appsettings.json` holds an `Addons` array of `{ Id, FolderName, ManifestBaseUrl, AutoInstall?, Features? }` (`ManagedAddon` in `Steward.Core`), rendered in array order; `ManifestBaseUrl` is required. Five entries ship today: `steward` (`AutoInstall: true`, `Features: ["sync"]`, so anyone holding the character-sync flag also gets the addon auto-installed, since it is what writes and reads the guild data that flag unlocks), `hoobiscripts` (`Features: ["hoobiscripts"]`, a flag held only by explicitly granted individuals rather than any officer default), and `restedxp`, `bugsack` and `buggrabber` (`Features: ["addons"]` each, a grantable flag held by officers by default and derived server-side for anyone holding `sync` or `hoobiscripts`, so the diagnostic and RestedXP rows show for the same population without each naming its own flag; the RestedXP row moving to `addons` is separate from the Guides page and sign-in entry point, which stay gated on `guides`). A configured addon with no manifest on any channel renders as "No releases yet" rather than as an error. Adding one is a config entry, nothing more: `AddonUpdater` takes the `ManagedAddon` and channel as parameters rather than hardcoding a folder name or manifest URL, and the UI iterates the configured list per WoW install.

`Features` defaults to empty, so an addon configured without it is never visible. It names which of the signed-in user's `/api/me` features make the addon appear at all: it is visible when the user holds any one of them. `MainViewModel.VisibleAddons()` is the one place the configured `Addons` list is filtered down to the addons the signed-in user's feature set covers, and every addon-list iteration (the manifest/release check, auto-apply, Update all, the Hidden addons toggle, `AddonChannels`) goes through it. Per-install rows are not fixed at construction: `WowInstallViewModel.SyncAddons` reconciles `AddonRows` against a given addon list, keeping the row instance for an addon still visible, adding one for an addon newly visible in its config-order position, and removing and unsubscribing one for an addon no longer visible; that removal only drops the row and its event subscription, never the addon's own folder on disk, since `AddonUpdater.RemoveExistingInstall` runs only from inside `InstallAsync`, itself only reachable through a visible row's own `UpdateCommand`. `MainViewModel.ReconcileFeatureGating` calls it on every install, prunes `_status`/`_releases` to the addons still visible and rebuilds `AddonChannels`, whenever `RecheckAuthorizationAsync` finds the feature set changed from the previous check; that covers a feature gained or lost mid-session and a start where gigagrug was unreachable and the set was still empty, since the next successful check is a change from empty. Each row's own `ensureAuthorized` also reconfirms its addon's feature is still held before an update runs, so an update queued just as the feature drops refuses rather than applying. Auto-apply and Update all only ever iterate `Installs[].AddonRows`, so a feature-hidden addon, having no row there at all, is never auto-installed, updated or touched by either.

`AutoInstall` marks an addon the background pass installs when it is missing, under the same admin gate as auto-update; it cannot be hidden. No addon is sourced from the GitHub API from this app any more: RestedXP moved to gigagrug's own mirror of `RestedXP/RXPGuides`'s GitHub releases, served at its `ManifestBaseUrl` in the same `latest-{channel}.json` shape every other manifest-host addon uses, so `AddonUpdater` and `GetLatestAsync` have one code path for every addon. The mirror (`src/gigagrug/services/github_mirror/service.py` in `D:\gigagrug`) applies the selection rules gigagrug's own list of GitHub releases needs: `release` is the non-draft entry without the `prerelease` flag that has the latest `published_at` and `pre-release` the one with the flag that has the latest `published_at`, because the GitHub API's list order is not date order (on 20 Sep 2026 it returned `.95, .94, .92, .102, .100`, and taking the first entry reported the installed build as up to date). The `.zip` asset is the release and its `sha256` digest is the checksum, and the tag name is the version (RXPGuides stamps the same `v4.11.4` form into its TOC); a release lacking a `.zip` asset or a digest is skipped by the mirror rather than surfaced here. There is no `develop` channel for RestedXP: the mirror only ever answers `release` and `pre-release`, so a `develop` request 404s and reads as no release the same way an empty channel does for any other addon. The icon comes from the mirror's own `icon.png` route, which redirects to the repo owner's GitHub avatar, so a manifest-host addon's icon logic covers it without a branch.

A user can hide an addon they manage through CurseForge or WowUp from the row's overflow menu. Hidden ids live in `hidden_addons` in `state.json`, global rather than per install, and hidden rows are excluded from counts, auto-apply, Update all and the list; the "Hidden addons" toggle in the page header shows them again with a Hidden pill so they can be unhidden.

The manifest for an addon+channel is `{ManifestBaseUrl}latest-{channel}.json`; the release zip resolves relative to that manifest URI, so an absolute `zip` URL is used as-is. The manifest fetch sends `Cache-Control: no-cache` per request rather than trusting the Static Web App's own cache headers, since the SWA route's header behaviour for a nested path is unconfirmed. SHA-256 verification, the zip-slip guard, and the rule that an existing addon folder is only deleted when it holds that addon's own `.toc` are unchanged from the single-addon version.

## Auth: default-browser sign-in over a loopback callback

gigagrug accepts exactly one credential, the `gg_session` cookie (`auth_middleware`), with no bearer or API-key path, and exposes a desktop flow that hands that cookie's raw value to a local client. `SessionService` generates a verifier (base64url of 32 random bytes) and a challenge (lowercase hex SHA-256 of the ASCII verifier, matching Python's `hexdigest`), binds a listener, and opens `GET {BaseUrl}/api/auth/desktop?challenge=<challenge>&port=<port>` in the default browser. gigagrug runs the Discord OAuth exchange and redirects the browser to `http://127.0.0.1:<port>/?code=<one-time code>`. The app then POSTs `{"code","verifier"}` to `{BaseUrl}/api/auth/desktop/exchange` and receives `{"token": "<gg_session value>"}`; the code is single-use with a 120-second TTL.

The listener is a `TcpListener` on `IPAddress.Loopback` with port 0. `HttpListener` cannot bind port 0 and its HTTP.sys prefix semantics need a fixed registered prefix, and Kestrel pulls an ASP.NET framework reference into a self-contained WinUI publish, so neither is used. The whole flow times out after 5 minutes. Every accepted connection gets the same fixed 200 HTML page telling the user the tab can be closed, including the favicon request the browser makes alongside the callback; `LoopbackCallback.WaitForTokenAsync` in `Steward.Core` runs that accept loop, `TryReadCode` decides which request line carries a code, and a rejected code keeps the listener waiting, so "click this link" relaunching the same URL from a second tab is safe. The sign-in URL reaches `MainViewModel` through an `IProgress<string>` created on the UI thread, and the view model alone owns the pending-URL state and clears it when the attempt ends: the wait resumes on the thread pool, and a6cf296's `PendingSignInUrlChanged` event raised there threw `RPC_E_WRONG_THREAD` from x:Bind inside the `finally`, discarding a token already exchanged with no error on the gate. A failure other than a timeout, cancel or unreachable API shows its message on the gate (`GateFailure.SignInFailed`).

gigagrug slides the session to 30 days from last use on every authenticated request, with no absolute ceiling, and never re-issues the token; the app's own `/api/me` checks are what keep it alive. Removing a user's last seat on the guild panel deletes their sessions server-side, so a demotion reaches the app as a 401 on the next check rather than as `role: null`. The app persists the raw token itself (DPAPI-protected, `%LocalAppData%\Steward\state.json`) rather than relying on the cookie jar as the store; the browser flow is only how the token is acquired, once, at sign-in.

The API origin is `https://api.hoobi.io/guild` (`Gigagrug:BaseUrl`). `guild.hoobi.io` is the Static Web App hosting the SPA, and its navigation fallback answers every `/api/*` path with `index.html` and a 200, so a client pointed there sees HTML where it expects JSON rather than a 401.

Every privileged action re-checks `GET /api/me`: at startup, immediately before an update, and on a 15-minute timer while the window is open. A 401 means the session is gone; the persisted token is cleared and the app drops to signed-out. Any other failure (a 502, a timeout) marks the API unreachable: the error bar shows the message with a Retry button, the Sync page is disabled, and the timer retries every minute instead of every fifteen until a check succeeds and clears the state. An authenticated response whose effective feature set is empty (nothing to do in the app at all) clears the session and drops the app to the gate with a "no Steward access" bar, the same treatment as a 401. This re-check keeps the UI truthful; it is not enforcement, since the zips themselves are served from a public Static Web App with no auth of their own. A role or flag change still reaches the app between those checks: while signed in and the API reachable, `MainViewModel` keeps one connection to `GET /api/events` (`GigagrugClient.StreamAccessEventsAsync`), open for every signed-in user regardless of feature, not just `steward` holders. Unlike the guild stream's `event: <type>` framing, this route (gigagrug's per-user SSE endpoint, `_handle_sse`/`_notify_sse_event` in `services/http_server/service.py`) carries its frame type inside the JSON `data:` payload as `{"type": "<name>", ...}`, so `StreamAccessEventsAsync` reads it with `ServerSentEventReader.ReadFramesAsync` and parses `Data` rather than the SSE event field. An `accessChanged` frame queues `RecheckAuthorizationAsync` (debounced ~1 second, skipped rather than overlapped when a check is already in flight), so a role or feature flag added or removed elsewhere reaches feature gating, addon rows, the Sync/Guides pages, guild features and the `me` dataset within seconds; every other frame type on this stream is ignored. The reconnect, backoff and idle-timeout rules are the same as the guild stream (5 seconds doubling to 5 minutes, 60 seconds of silence counts as dropped, a 401 signs out, a 404 means an older gigagrug and the stream stays off for the run), except that a 403 or 429 only backs off and retries rather than stopping the stream, since this route has no guild scope to be denied on. None of it touches the error bar or `StatusMessage`.

`/api/me`'s `user.features` is a `string[]` of `guides`, `steward`, `sync`, `roster`, `professions`, `signups` and `addons`, the user's OVERALL grants across every guild. Access is gated on that set, never on `role`: a guild member can be granted `guides` by Discord role or user id on the gigagrug side, independent of holding an officer seat; `steward` comes only with an officer seat; `sync`, `roster`, `professions`, `signups` and `addons` can each be granted without one. `addons` is an officer default and is also derived server-side for anyone holding `sync` or `hoobiscripts`, alongside being manually grantable, and it is what the RestedXP, BugSack and BugGrabber addon rows are gated on. `role` global/admin is only the fallback used to derive the set when an older gigagrug server sends no `features` field at all, in which case an officer gets every officer feature (`addons` included) and everyone else gets none; `role` is `"raider"` for a seatless caller holding any of `sync`/`roster`/`professions`/`signups`/`addons` in some guild, and treated exactly like a null role everywhere this app checks for an officer (`IsProfessionsOnlySync` and the rest all pattern-match "not global/admin", so `raider` already falls out the same way `null` does). `GigagrugClient.EffectiveFeatures` computes that user-level set from an `AdminMe`; `GigagrugClient.IsAuthorizing` treats `guides`, `steward`, `sync`, `roster`, `professions`, `hoobiscripts` and `addons` as each counting towards the app's access gate (`signups` alone does not, since nothing in the app reads it yet). `MainViewModel` keeps the user-level set in `_features`, which drives `HasGuidesFeature`, `VisibleAddons()` and `IsAuthorized`.

Every `/api/me` guild entry also carries its own `features`, that guild's resolved set (`GigagrugClient.ResolveGuildFeatures`, falling back to the user-level set when a guild entry carries none, an older gigagrug or `/api/admin/me`), since an officer of one guild is a plain member of another. `MainViewModel` keeps the SELECTED guild's set in `_guildFeatures`, recomputed (`UpdateGuildFeatures`) whenever `_guildId` or the user-level set changes, and reads `HasStewardFeature`, `HasSyncFeature` and the roster/professions pulls (see Character sync) from it rather than from `_features`, so switching guild in the picker immediately reflects that guild's own access: a push or a roster pull is only attempted for a guild whose features actually allow it, never left to a 403. `IsProfessionsOnlySync` (`HasSyncFeature` without `HasStewardFeature`) is therefore also per guild, so an officer granted `sync` on a server where they hold no seat pushes the professions-only payload there. The guides gate itself lives inside `RestedXpViewModel`, not in `MainViewModel`: it takes a `Func<bool> hasGuidesFeature` at construction (`() => HasGuidesFeature`) and checks it in `CheckAsync`, `RefreshSessionAsync`, the per-install saved-variable confirm, and before setting up each install's `FileSystemWatcher`, so a feature drop stops every one of those without a caller having to remember the gate; guides is not guild-scoped, so it stays on the user-level set. `IsGlobalAdmin` (`role == "global"`) is unrelated to any of this; it no longer gates anything since the `develop` addon channel it once gated was removed. A non-officer's `guilds` list is empty, except for a caller holding one of `sync`/`roster`/`professions`/`signups`, who gets the guilds they are a Discord member of and hold at least one of those in; gigagrug still answers 403 on every other `/api/admin/` route below `me` for them, so admin-only roster and members stay officer-only. A user-driven guild switch also calls `PUT /api/me/guild` (`GigagrugClient.SetSelectedGuildAsync`) so gigagrug starts a new device or browser on the same server; the app already has that guild locally, so a 404 (an older gigagrug), a 400, a 401 or a network failure is only logged and never surfaces on the error bar or signs the user out.

## Channels

Two release channels, named after what produces them in `hoobio/addons`: `release` (a tagged GitHub release of the addon) and `pre-release` (every push to the addon's `main`). The `develop` channel (every push to an addon's `develop` branch) was removed on 26 Sep 2026: the download site no longer publishes it, so probing it is pointless and it is gone from `AddonChannelStatus.Ordered`; an addon repo's own `develop` branch is unaffected. RestedXP has `release` and `pre-release` only, mapped to the GitHub release and prerelease flags gigagrug's mirror reads. The channel is per addon, stored in `Channels` alongside the install-state records in the same `state.json`, defaulting to the first channel that has a release in the order `release`, `pre-release` (`AddonChannelStatus.Ordered`, also the picker order). When a more stable channel holds a build released after the one on the chosen channel, the row shows a notice naming it, so being on `pre-release` while a newer `release` exists is visible without switching. The rename from `stable`/`beta`/`unstable` was not migrated: a stored old channel name falls back with the "No releases on X any more" notice. A stored `development` or `develop` value is migrated to `pre-release` on load: `AppStateStore.MigrateDevelopChannel` rewrites it, alongside the `LegacyChannel` seed; if that addon has no `pre-release` build, the ordinary `Resolve` fallback drops to `release` instead and says so in the row's notice.

Each WoW install + addon pair records what was actually installed (version, channel, sha256), keyed by flavour path plus addon id. With no record, the addon's own `.toc` version is the fallback, which is the manual-install case. Update availability is plain string inequality between that recorded/TOC version and the channel manifest's version, not a semver comparison: versions like `0.5.0-beta.1` and `0.5.0-unstable.219da29` don't parse as `System.Version`, and switching channels has to be able to move the installed version in either direction.

## WoW install discovery

`WowInstalls` walks `.flavor.info` (product code) joined against the root `.build.info` (product to version) to find each flavour without a hardcoded product-to-folder map. The Blizzard registry key (`HKLM\...\World of Warcraft`) is not used as a discovery root by itself: on the dev machine it is hijacked by an unrelated Ascension install, so it is one candidate root among several, never the only one trusted.

Discovery is filtered to `SupportedProducts` in `appsettings.json`, a product code to display name map, since the managed addons target World of Warcraft: Forever only. Today that map holds one entry, the beta's `wow_classic_beta`; the release build joins as a second entry once its product code is known, and `docs/forever-release.md` lists every value and file that day touches.

## Branding

`src/Steward.App/Assets/Steward.ico` (16 through 256px, PNG-compressed frames) is the one source of the app's icon: `ApplicationIcon` stamps it on the exe and `AppWindow.SetIcon` puts it on the one window. WinUI 3 does not take the window icon from the exe on its own, so the `SetIcon` call is load-bearing.

## Self-update

The Microsoft Store is the app's only update path, and the app installs its own Store update rather than only pointing at one. `App.IsPackaged` (`GetCurrentPackageFullName` answering anything but `APPMODEL_ERROR_NO_PACKAGE`) splits packaged from unpackaged. A packaged, GitHub-release build (`App.IsGitHubRelease`) checks the Store through `StoreContext.GetAppAndOptionalStorePackageUpdatesAsync`, with the window handle passed through `InitializeWithWindow` as WinUI 3 requires, on the startup pass, on Refresh and at most once an hour from the 1-minute background pass (`_lastStoreCheck`, wall-clock like `_lastGuideCheck`). On startup and on a "Check for updates" press only (the title bar command and the InfoBar/About card path both run `CheckOrInstallAppUpdateAsync`), the check is preceded by a forced Store scan scoped to Steward, `AppInstallManager.SearchForUpdatesAsync(App:StoreProductId, "")`: `StoreContext` otherwise only sees an update once the Store app has scanned for it on its own schedule. `AppInstallManager` is documented as gated behind a Microsoft-only private capability, but it runs unelevated from this full-trust process with no capability declared, verified 28 Sep 2026. `RegisterApplicationRestart` runs before that scan (see below) because on 28 Sep 2026 `SearchForUpdatesAsync` returned a null `AppInstallItem` yet the Store still installed the update about a minute later, so the scan itself can close the app. When `StoreContext.CanSilentlyDownloadStorePackageUpdates` is true (the user has automatic app updates on and the connection is not metered) and no addon row is mid-update, an update found on any of those checks installs silently through `TrySilentDownloadAndInstallStorePackageUpdatesAsync`. Otherwise the InfoBar and About card's Install button call `RequestDownloadAndInstallStorePackageUpdatesAsync`, which raises Windows' own consent dialog. A `_storeInstall` field tracks whichever of the two is in flight: `CheckStoreUpdateAsync` skips starting a silent install while one is already running, and `InstallAppUpdateAsync` awaits the in-flight install instead of starting a second, so a silent install from the background pass and an explicit install from the button or a banner's Install action never race each other. Both paths call `RegisterApplicationRestart` first (`Native.RegisterRestartForStoreUpdate` in `MainWindow.xaml.cs`, `--tray` when the main window is not visible, `RESTART_NO_CRASH | RESTART_NO_HANG | RESTART_NO_REBOOT` so only an update restarts the app rather than a crash, hang or reboot too) so Windows closes Steward to apply the update and relaunches it rather than leaving it stopped. A failed or user-cancelled install falls back to opening the Store's Updates and downloads page (`ms-windows-store://downloadsandupdates`), since the product page of an installed app offers no update button; a cancelled install is silent otherwise. The InfoBar's action label reads "Install update". A banner's `store_update` action runs `CheckOrInstallAppUpdateAsync` for a packaged, GitHub-release build and opens the Updates and downloads page otherwise, so posting the banner before `StoreContext` has surfaced the update (or on a dev/unpackaged build) still does something rather than nothing. The MSI migration banner still opens the product page, `ms-windows-store://pdp/?productid=` plus `App:StoreProductId`, where Steward is installed. A Store failure goes to the status bar. A packaged, non-GitHub-release build (the dev package) and an unpackaged build never see an update: `AppUpdate` is null on both. The dev package and the Debug build (both non-`GitHubRelease`) still run the same forced Store scan on the same two triggers, since the scan targets the installed Store copy of Steward (`Hoobi.Steward_thayxpy3eqg0g`) rather than the running build: `ForceStoreScanAsync` skips `RegisterApplicationRestart` and every `StoreContext` call for these builds (they need the running process's own Store package identity), and instead logs the Store copy's installed version (`PackageManager.FindPackagesForUser`, already used by `UpdateStoreAppInstalledState`) before the scan and again two minutes after, without blocking the UI or touching `StatusMessage`, so the log shows whether the scan actually moved the Store copy. An MSI build (unpackaged but still `GitHubRelease=true`) is unaffected either way, since it never ran the scan before this and still does not.

An unpackaged build (an MSI still in the wild from the 0.11.0 bridge release) looks for the Store package on the same passes, through `PackageManager.FindPackagesForUser(string.Empty, "Hoobi.Steward_thayxpy3eqg0g")`, which works unelevated from an unpackaged process. With no Store package the Addons page shows "Steward is on the Microsoft Store" with a button opening the product page; with it installed the page shows "The Microsoft Store version is installed" with a Switch button. Switch starts a hidden `powershell.exe` hand-off (`AppUpdater.SwitchToStoreAfterExit`, built by `SwitchToStoreScript`), which waits for this process to exit, runs `msiexec /x /qn` against every product code `WindowsInstaller.Installer.RelatedProducts` returns for the wxs `UpgradeCode` that shipped in that bridge MSI, logging to `update.log`, deletes the `Steward` Run value, and only then launches `shell:AppsFolder\Hoobi.Steward_thayxpy3eqg0g!App`, because the MSI's `taskkill` custom action targeted `Steward.App.exe`, which is also the packaged exe's name. The app quits right after starting it. `AppUpdater` in Core carries only this Switch-to-Store path and the shared `RunAfterExit`/`EscapeSingleQuoted` helpers now; the manifest-based MSI self-update check, download and install were removed once the Store became the only channel, and `App:ManifestBaseUrl` dropped from `appsettings.json` with them.

`hoobio/addons`'s mirror only considers a GitHub release that carries an `.msi` asset, so an MSI install polling `addon.hoobi.io` for `steward-companion` manifests stays on 0.11.0 (the last release built with one) without any change on that side; those installs are expected to move across through the Switch-to-Store banner instead of a further self-update.

## Microsoft Store

The MSIX package identity, reserved in Partner Center, is `Hoobi.Steward` (PFN `Hoobi.Steward_thayxpy3eqg0g`), publisher `CN=D74C026B-1081-4787-BDE6-0CFA2F1EDD71`, Store ID `9PBKMZFKZHKX`. `src/Steward.App/Package.appxmanifest` carries that identity directly rather than a Dev/Release pair, because the Store build is release-only: there is no channel-identity stamping to do. The `desktop:StartupTask` extension (`TaskId="StewardStartup"`, `uap10:Parameters="--tray"`) covers Start with Windows for a Store install, the counterpart to the registry-based toggle the MSI build uses.

`build.yaml`'s `build-msix` job runs on every push to main, building with `GitHubRelease=true` set as an environment variable on the `build-msix-dotnet` step, since MSBuild reads env vars of a property's own name, with a second identical step retrying it once on failure (the same NuGet-restore flakiness the publish step in a self-contained build would retry against). `build-msix-dotnet` only produces a bare `.msix`; the Store needs an app package upload file, so the job zips that `.msix` and renames it to `.msixupload` (the documented manual method), and uploads it as the `msixupload-x64` workflow artifact. It is never attached to a GitHub release and never signed there: the Store re-signs on submission. Every run stamps the manifest `<major>.<minor>.<run number>.0`, release and flight alike, and exposes it as the job's `version` output. On a release run the major.minor is `version.txt`'s own; on a non-release run it comes from the open release-please PR's title (`chore(main): release 0.12.0` gives `0.12`), falling back to `version.txt`'s major.minor when no release PR is open. The fourth part is always `0`, since the Store reserves it and requires it be `0` at build time, and every part is capped at 65535. `GITHUB_RUN_NUMBER` makes each package version strictly higher than every earlier one, release or flight, which the Store requires for a device to see it as an update: a release stamped with its plain `0.13.2.0` would sit below a tester's `0.13.248.0` flight, and the Store never downgrades. The plain release version (`version.txt`) is the job's separate `release-version` output, which `store-submit` uses to find the previous release and the changelog section; the app's own version label reads the assembly's informational version, also `version.txt`, so it shows `0.13.2` whatever the package version, except on a flight, where the "Read version" step's separate `display-version` output (the release-please PR's next full version plus `-pre.<run number>`, e.g. `0.14.1-pre.260`, falling back to `version.txt`'s version with the same suffix when no release PR is open) is stamped as a `StoreDisplayVersion` `AssemblyMetadata` and shown instead: `InstalledVersion` itself stays the plain numeric `version.txt` value on every build, since `BannerFilter.Active` parses it as a 3-part version and a `-pre` suffix would break that; the sync User-Agent instead reads `App.StoreDisplayVersion` when set, falling back to `InstalledVersion` otherwise, so gigagrug's logs show the flighted `-pre` version rather than the last release's. `version.txt` itself is untouched by a non-release run. `App.IsPreRelease` reads a matching `StorePreRelease` `AssemblyMetadata`, set to `true` only on a non-release `build-msix` run (mirroring how `GitHubRelease` is set), and the window title, tray tooltip and version label append " (Pre-release)" for a flighted build the same way they append " (Development)" for a packaged non-`GitHubRelease` build and " (Debug)" for the unpackaged one (`App.BuildName == "debug"`); the package manifest's `DisplayName` stays "Steward" either way, since the Store listing name does not change per flight.

The `store-submit` job runs only when release-please cut a release on that run, after the `release` job, and only when the `AZURE_CLIENT_ID` repo variable is set, using `microsoft/microsoft-store-apppublisher@v1.4` and the `msstore` CLI. The Store credentials live in the homelab Key Vault `hbicfgkvtaus01` as `msstore-tenant-id`, `msstore-client-id`, `msstore-client-secret` and `msstore-seller-id` (the client is the "Partner Center Uploads" Entra app with the Manager role), so any repo that publishes to the Store reads the same four; the job signs in through GitHub OIDC as the `github-hoobio-msstore` Entra app (repo variables `AZURE_CLIENT_ID` and `AZURE_TENANT_ID`, no subscription), which holds `Key Vault Secrets User` on those four secrets only and trusts `main` of each repo it has a federated credential for. The job masks each value, runs `msstore reconfigure`, then a delete-pending-submission, `msstore publish <msixupload> -id 9PBKMZFKZHKX --noCommit`, a release-notes and mandatory-update patch, `msstore submission publish` sequence, checking `$LASTEXITCODE` after every `msstore` call except the delete (which resets it deliberately, since a missing pending draft is not a failure). Before that delete, `scripts/Wait-StoreSubmissionClear.ps1`'s `Wait-StoreSubmissionClear` polls `msstore submission status 9PBKMZFKZHKX` every 2 minutes for up to 60 minutes while the status is `CommitStarted`, `PreProcessing`, `PendingPublication`, `Publishing` or `Release`, since a delete against a submission still in one of those refuses rather than clearing it; a `PendingCommit` draft or a submission in `Certification` is deleted straight away, the newest push replacing it (observed 28 Sep 2026, run 259: `msstore flights submission delete` printed "Submission in its current state cannot be deleted" and then a false "✅ Existing submission deleted!" anyway, because `msstore`'s delete helper only treats the Ingestion API's own "created in Partner Center" error as a real failure and reports success for every other case regardless of what the API actually did). The same helper treats "cannot be deleted" in the delete output as not deleted and goes back to waiting, and stops the job immediately with `::error::` naming the submission id (`msstore` prints `Found ... Submission with Id '<id>'`) whenever any `msstore` output says a submission "can only update, delete, and commit ... created through the API", since only a human deleting it in Partner Center clears that one. `msstore publish` itself is retried up to 3 times, 60 seconds apart and re-running the wait first, when it fails with "Error while creating submission". The file-path form of `msstore publish` (a `.msixupload`/`.msixbundle` passed as the positional argument, not `-i <directory>`) is confirmed working: `hoobio/command-palette-bitwarden`'s `store-publish` job uses the identical `msstore publish $bundle -id $env:PRODUCT_ID --noCommit` form against a `.msixbundle` and succeeded (run 31148741706, job "Publish to Microsoft Store"). The patch goes through `msstore submission update`, not `submission updateMetadata`, because `updateMetadata` sends only availability, properties and listings (`MSStore.API/Models/UpdateMetadataRequest.cs` in `microsoft/msstore-cli`) and drops `PackageDeliveryOptions`, while `update` PUTs the whole submission. Both take their JSON inline as a positional argument with no file-input flag, so the patched submission JSON is read from disk and passed as `(Get-Content -Raw patched.json)`. Every release and flight submission sets `PackageDeliveryOptions.IsMandatoryUpdate` with `MandatoryUpdateEffectiveDate` at submission time, merged into the existing delivery options so rollout settings are kept. The Store does not enforce the flag: it only sets `StorePackageUpdate.Mandatory` for the app's own `Windows.Services.Store` code to act on. Pre-releases never reach the Store. `msstore` only updates an app that is already live in the Store, so the first submission has to be made by hand in Partner Center: submit a pre-release `.msixupload` there manually, and only publish the bridge GitHub release (the one that triggers `store-submit`) once that manual listing is live, since `store-submit` clones the live submission rather than creating the app's first one.

The "What's new in this version" listing field is filled from the being-released version's own `CHANGELOG.md` section, keeping only the Features and Bug Fixes entries and dropping every other conventional-commit type; `scripts/Get-StoreWhatsNew.ps1` strips each entry down to its plain description (scope, gitmoji and commit-hash link removed) and truncates at a bullet boundary to the Store's 1500-character `ReleaseNotes` limit, replacing the dropped entries with a closing "and N more changes" line. A version whose changelog section holds neither section returns "Minor improvements and fixes." rather than leaving the listing untouched. Every `feat` and `fix` commit therefore reaches Store users, so a commit that changes nothing a user of the installed app sees (the workflow, packaging, Store submission, the dev build) is typed `ci`, `build` or `chore`.

The `store-flight` job runs on every push to `main`, a release-please merge included, after `build-msix`, because flight testers only ever receive flight packages and never the non-flighted submission (Partner Center's package flight ranking), so a release reaches them only as a flight too. On a release run it submits the same package `store-submit` does, built with `StorePreRelease` off, so the tester's build carries no " (Pre-release)" suffix. It runs only when both the `STORE_FLIGHT_ID` and `AZURE_CLIENT_ID` repo variables are set (the same Key Vault OIDC login, credential masking and `msstore reconfigure` steps as `store-submit`). It waits out and deletes any pending flight submission through the same `Wait-StoreSubmissionClear` helper `store-submit` uses, pointed at `msstore flights submission status/delete 9PBKMZFKZHKX <flightId>` instead of the plain `submission` form, publishes the flight build (`msstore publish <msixupload> -id 9PBKMZFKZHKX --flightId <flightId> --noCommit`, retried up to 3 times 60 seconds apart and re-running the wait first when it fails with "Error while creating flight submission"), marks it mandatory through `msstore flights submission get` and `msstore flights submission update`, and commits it (`msstore flights submission publish 9PBKMZFKZHKX <flightId>`), checking `$LASTEXITCODE` after every call except the delete. It patches no release notes. A run cancelled mid-sequence (a newer push already cancels an older `build`-group run) leaves at worst a pending flight draft; the next run's wait-and-delete clears it before publishing again, so a flighted tester never sees a half-submitted build linger. Flight testers are a known user group managed by hand in Partner Center; this repo has no record of who is in it. The submission API only updates, deletes and commits submissions it created itself, so a draft started in Partner Center (including the empty one Partner Center makes alongside a new flight) makes the delete and `msstore publish` answer "created through the API" instead of clearing normally; `Wait-StoreSubmissionClear` stops the job immediately with `::error::` naming that submission's id rather than looping on it, since only a human can delete it in Partner Center before either Store job can run again. Both jobs carry a 90-minute `timeout-minutes` to give the 60-minute wait room alongside the rest of the job.

A named mutex (`Local\Steward.App`, acquired in `Program.Main` before `Application.Start`) enforces one running instance across every train, so the name is shared between the Store build and an MSI install still in the wild rather than stamped per channel. `InstanceCoordination` decides what a second launch does with it: a launch of the SAME train (Store/flight, MSI, the dev package, Debug, `App.Train` folding a Store flight into `store` since they are the same package) signals the running instance to come to the foreground (`Local\Steward.App.Show.<train>`, an `EventWaitHandle` the running instance waits on from a background thread and marshals to `MainWindow.ShowFromTray` on the UI thread) and exits without showing anything; a launch of a DIFFERENT train signals the running instance to quit (`Local\Steward.App.Quit`), waits up to 15 seconds for the global mutex, and on success shows a dismissible "Closed the &lt;train&gt; build automatically" info bar through the same banner mechanism as a server banner. Each running instance also holds `Local\Steward.App.Running.<train>`, probed with `EventWaitHandle.TryOpenExisting` rather than any file, since packaged builds get separate virtualised storage. The signalled instance quits through its own tray Quit path (`MainWindow.QuitFromAnotherBuildAsync`), waiting up to 10 seconds for a busy addon row to finish first so it never blows the newcomer's 15-second budget. `Mutex.WaitOne` throwing `AbandonedMutexException` counts as already acquired, since a Store update force-kills the old process without releasing it. A `WM_QUERYENDSESSION`/`WM_ENDSESSION` subclass on the window (`MainWindow`'s `Native.HookSessionEnd`) always quits outright, bypassing Close to tray, so a Store update's forced shutdown does not wait out a 30-second kill timeout.

The `SwitchToStoreScript` hand-off escapes every value it interpolates into single-quoted PowerShell with `.Replace("'", "''")`, and reads the `msiexec` call's exit code through `-PassThru -Wait`; a non-zero code other than `3010` (a reboot-required success) stops the script before it removes the `Run` value or launches the replacement app, so a failed uninstall cannot silently leave both the old and new install in a broken state.

`MainViewModel.CheckStoreUpdateAsync` catches every exception from the `StoreContext` call itself and routes it to `StatusMessage`, rather than relying on the caller's typed catch clauses, since a WinRT failure there is not guaranteed to be a `COMException`. The Store-install check (`PackageManager().FindPackagesForUser`, behind `IsStoreAppInstalled`) runs at the start of `LoadAsync`, `RefreshAsync` and `RunBackgroundPassAsync`, before the gigagrug authorization check and unconditional on its result, so the MSI-to-Store migration banners still show when `addon.hoobi.io` is unreachable or the user is signed out.

When packaged, "Open data folder" and the About card's installed-path text prefer `Windows.Storage.ApplicationData.Current.LocalCacheFolder.Path\Local\Steward` over the literal `%LocalAppData%\Steward` when that folder exists, through the shared `App.DisplayDataFolder` helper: a packaged process's writes to `%LocalAppData%\Steward` land in that virtualised location, so pointing Explorer or the About text at the literal path would not show what is actually on disk. The real `%LocalAppData%\Steward` path is unchanged for `state.json` and `update.log`, which the packaged and unpackaged builds still share.

The Start with Windows toggle shows distinct, disabled text for each locked `StartupTaskState`: `EnabledByPolicy` reads on with "Turned on by your organisation's policy", `DisabledByPolicy` reads off with "Turned off by your organisation's policy", and `DisabledByUser` reads off with "Turned off in Windows Settings > Apps > Startup".

The Store is the app's only release channel. 0.11.0 was the one MSI release that bridged existing installs across, through the Switch-to-Store banner described under Self-update; no later release builds an MSI.

## Development install

Every `git push` from this clone builds HEAD and registers it as a second, side-by-side packaged app, so a developer always has a running build of `main` without touching the Store install. `scripts/Install-DevBuild.ps1` never touches the working tree: it exports the pushed commit with `git archive HEAD` into a scratch copy at `%LocalAppData%\Steward.Dev\src` (wiped first), stamps a dev identity into that copy's `Package.appxmanifest`, `Hoobi.Steward.Dev` publisher `CN=Hoobi Dev`, both `DisplayName` elements reading "Steward (Development)", and the version from `version.txt`, and builds from there, so a commit made while the build is running never ships the dev identity and `git status` stays clean throughout. It builds a Release x64 MSIX the same way `build-msix` does in `build.yaml`, extracts the produced `.msix` (a zip container) to `%LocalAppData%\Steward.Dev\app`, and registers that loose layout with `Add-AppxPackage -Register`, which Developer Mode accepts unsigned. The MSIX is framework-dependent (`WindowsAppSDKSelfContained=false`), so it only runs on a machine with the Windows App Runtime installed. The Start menu entry is "Steward (Development)"; the package family name is `Hoobi.Steward.Dev_<publisher-hash>`, distinct from the Store's `Hoobi.Steward_thayxpy3eqg0g`.

The single-instance mutex is `Local\Steward.App`, unconditional across every build (Store release, Store flight, MSI, the dev package and the Debug build), so the dev package and the Store package no longer run side by side: starting one while the other is running closes the running one first, per `InstanceCoordination` under Microsoft Store. The Store update check (`CheckStoreUpdateAsync`, via `StoreContext`) only runs when `App.IsGitHubRelease`, since a dev identity is never in the Store; a packaged non-GitHubRelease build reports no update rather than surfacing a Store error. The MSI-to-Store migration banner (`UpdateStoreAppInstalledState`) only runs for the MSI build (unpackaged and `IsGitHubRelease`), so it is inert for a packaged dev build and for a Debug build alike.

The manifest's `StewardStartup` `StartupTask` is scoped per package identity, so enabling Start with Windows for the dev package cannot collide with the Store package's own toggle: each autostarts independently with `--tray` if the user turns it on for that package.

Because the two packages carry different identities, Windows virtualises each one's writes to `%LocalAppData%\Steward` into its own per-package storage; the dev package does not see the Store package's `state.json` or session, and starts signed out on a machine that is signed in on the Store build. `App.DisplayDataFolder` reflects this: it points at the dev package's own virtualised folder, not the Store package's.

`.githooks/pre-push` triggers the build: a POSIX `sh` script that starts `scripts/Install-DevBuild.ps1` fully detached and hidden, then exits 0 immediately, so a slow or failing dev build never blocks or fails a push. Run `git config core.hooksPath .githooks` once per clone to pick it up; `.gitattributes` forces it to LF regardless of the checkout's `autocrlf` setting. Everything the script does is logged to `%LocalAppData%\Steward.Dev\install.log`.

## Releases

`build.yaml` publishes from every push to `main` that touches something other than Markdown, `docs/`, `tools/`, `.githooks/` and `scripts/Install-DevBuild.ps1` (`paths-ignore` on both `push` and `pull_request`); a release-please merge always runs, since it changes `version.txt` and the manifest alongside `CHANGELOG.md`. ## Build and test gotchas

`Steward.slnx` defines no `Release|x64` solution configuration, so a solution-level `dotnet build` must not pass `-p:Platform=x64`; the CI workflow builds the solution without it and passes `-p:Platform=x64` only on the project-level `dotnet publish` of `Steward.App.csproj`.

`global.json` pins the SDK to `10.0.203` with `rollForward: disable`, because `DOTNET_SDK_VERSION` in the workflow only says what `setup-dotnet` installs and the runner image ships newer SDKs that `dotnet` would otherwise pick; it also sets `test.runner` to `Microsoft.Testing.Platform`. The publish step retries up to three times, since NuGet restore on the runner can fail with a bare MSB4181 "RestoreTask returned false but did not log an error" and no cause (NuGet/Home#13460), as it did twice on 20 Sep 2026. On .NET SDK 10.0.203, `dotnet test <directory>` fails under that runner; the working form is `dotnet test --project <csproj>`, which is what the CI workflow uses.

`Microsoft.Win32.Registry` is already in-framework on `net10.0-windows`; adding it as an explicit `PackageReference` fails restore with `NU1510`. `WowInstalls.cs` uses `Microsoft.Win32.Registry` directly, and neither `.csproj` in this repo references the package.

CommunityToolkit.Mvvm's field-backed `[ObservableProperty]` triggers diagnostic `MVVMTK0045` under WinUI; the ViewModels here declare partial properties instead (`[ObservableProperty] public partial string? Foo { get; set; }`).

## Diagnostic logging

The app writes a daily-rolling diagnostic log to `%LocalAppData%\Steward\logs\steward-<build>-YYYYMMDD.log` (the packaged build's virtualised equivalent, same as `state.json`), through `FileLoggerProvider` in `Steward.Core` (`src/Steward.Core/Diagnostics`), registered as an `ILoggerProvider` in `HostBuilderExtensions` alongside the existing `Microsoft.Extensions.Hosting`/`Logging` setup. `<build>` (`App.BuildName`, derived from `IsPackaged`/`IsGitHubRelease`/`IsPreRelease`) is one of `prerelease`, `store`, `dev`, `msi` or `debug`, so the Store release, a Store flight, the side-by-side dev package, an unpackaged MSI install and a Debug build never contend for the same file lock when several run at once. Each line is `<UTC ISO timestamp> <level> <category>: <message>`, with an exception's full `ToString()` (stack included) on the following line; writes are single-threaded behind a lock and flushed per line. `LogFileRetention.DeleteOlderThan` runs at startup and drops any `steward-*.log` file older than 14 days, across every build name. Minimum level is Information for `Steward.*` categories and Warning for `Microsoft.*`/`System.*` (`builder.Logging.AddFilter`).

Instrumented through `ILogger<T>` injected where the class is already resolved through DI (`MainViewModel`, `SessionService`, `AddonUpdater`, `RestedXpService`, `GigagrugGuildSyncApi`) or passed as a parameter to the one static call site that needs it (`GuildRosterSync.WriteIfChanged`): sign-in (start, browser launch, callback received, code exchange, completion or failure), every `/api/me` recheck (authorized/401/unreachable, role, feature count), guild roster and character-directory pulls (counts, 403/404 handled quietly, 401), character pushes (accepted/rejected counts, 403/429/unreachable), both SSE event streams (connect, ready, drop with reason and backoff, give-up), banner fetches, Store update checks, addon manifest probes and installs (per addon and install path), `StewardSync.lua`/`StewardGuides` writes (written/skipped-unchanged/failed) and RestedXP session refresh failures. `Application.UnhandledException`, `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` are hooked in `App.OnLaunched` to log at Critical without changing how they are otherwise handled.

Never logged: the `gg_session` cookie/token, the sign-in code or PKCE verifier, RestedXP tokens or password, and any DPAPI blob; the sign-in URL is logged through `LogRedactor.PathOnly`, which drops its query string (the challenge and callback port) entirely rather than judging what in it is sensitive.

## UI verification

A change to anything visible is launched and driven before it is reported done; a clean build is not evidence that a view looks or behaves right. The sequence:

1. Stop any running Debug build of `Steward.App` (`Get-Process Steward.App -ea 0 | Where-Object Path -like 'D:\steward-companion\*' | Stop-Process`), since a running instance locks the exe and the build then fails on the copy step rather than on the code; the plain process name also matches the Store and dev-package builds, which the path filter excludes, after killing the Store app by mistake on 26 Sep 2026.
2. `dotnet build Steward.slnx -c Debug`, then launch `src\Steward.App\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Steward.App.exe`. It shares `%LocalAppData%\Steward\state.json` with the installed build, so it starts signed in with real data.
3. Drive it from PowerShell with `tools\UiDriver.psm1`: `Start-UiApp`, `Find-UiElement` (UI Automation), `Invoke-UiClick`, `Write-UiValue`, `Show-UiElement`, `Move-UiScroll`, `Save-UiScreenshot`, and `Get-UiPopup` for a menu or flyout, which opens as its own top-level window. The scenario script for a given change is written per task in the scratchpad and is not checked in.
4. Read every screenshot. For motion (hover, press, open), `Measure-UiTransition` pen-hovers a point and captures the window in a loop for 250ms, returning each frame's sampled colour, so a flash shows up as a frame brighter than both ends.

The user works at this machine while an agent drives the app, so the driver moves no mouse cursor and sends no mouse or keyboard input. `Invoke-UiClick` goes through UI Automation patterns (Invoke, then Toggle, then SelectionItem, then ExpandCollapse) and throws when an element supports none of them; text goes through `ValuePattern` (`Write-UiValue`) and scrolling through `ScrollItemPattern` and `ScrollPattern`. Navigating between pages through the `NavigationViewItem` patterns is verified.

Captures use `PrintWindow` with `PW_RENDERFULLCONTENT` (`0x2`) on the window handle, so an overlapping window, the user's cursor and a snipping overlay never appear in them; the main window renders its WinUI content in full while another window covers it. `Save-UiScreenshot -Popup` captures a popup's own window the same way and draws it over the main window at its screen offset, and `-Rect` crops to a screen rectangle. Popup capture is not yet verified: a flyout opened through `InvokePattern` while another window held the foreground was not found by `Get-UiPopup`, likely light-dismissed on deactivation.

Hover uses synthetic pen input (`CreateSyntheticPointerDevice` with `PT_PEN`, then `InjectSyntheticPointerInput` with `POINTER_FLAG_INRANGE | POINTER_FLAG_UPDATE` and no `INCONTACT`), in `Move-UiPointer` and `Exit-UiPointer`. It is not yet verified that WinUI applies `PointerOver` from it or that it leaves the cursor where it is, and it hit-tests on screen, so the target has to be the topmost window at that point. Until a run confirms both, hover and transition checks wait for the user's go-ahead. Launching the app still takes the foreground once.

## Design system

The house design system is `D:\hoobi-design` (React and Tailwind, no XAML output); its `AGENTS.md` "WinUI 3 conventions" table is the spec this app ports into `App.xaml` by hand. ## Roster sync

`docs/design/roster-sync.md` is the agreed contract between this app, gigagrug and the Steward addon, and it is the source of truth for how the three interact. Read it before touching anything that crosses a repo boundary. It carries the direction of travel, the identity and linking rules, the gigagrug endpoints in use, the confirmed Forever client API facts, and the per-repo branch rules.

The short version. gigagrug holds the people, the addon holds the characters, and this app is the only party that can talk to both. `GET /api/admin/{guild_id}/roster` and `GET /api/admin/{guild_id}/members` already existed for the admin SPA and needed no server change; `AdminMe.Guilds` supplies the guild id. `GuildRosterMember` and `DiscordMember` in `SyncModels` carry them, `RosterNotes.Trim` drops the lone `Y` and `N` lines a gigagrug note collects, and `StewardSyncFile` emits them as `["members"]` and `["discord"]` alongside the existing datasets. `GigagrugGuildSyncApi` is the only implementation and is registered directly, with no interface between it and its callers.

Pulls are event-driven. While signed in, the API reachable, a guild selected and the `steward` feature held (the same gate as the pull it drives), `MainViewModel` keeps one connection to `GET /api/admin/{guild_id}/events` (`GigagrugClient.StreamGuildEventsAsync`, a `text/event-stream` read line by line by `ServerSentEventReader` in Core), restarted on a guild switch and stopped on sign-out, loss of `sync` or an unreachable API. `ready` and each `roster-changed`, `members-changed` or `characters-changed` event queue `SyncRosterAsync`, debounced 2 seconds and never overlapping a pull already queued from the stream. A dropped connection reconnects after 5 seconds, doubling to 5 minutes and reset by the next `ready`; 60 seconds with no line at all, pings included, counts as a dropped connection. A 404 means the gigagrug in front of the app predates the route, and the stream stays off for the rest of the run; a 403 stops it for that guild; a 401 signs out as everywhere else. None of these touch the error bar or `StatusMessage`. The 1-minute background pass keeps its roster pull and character push as the fallback: every pass while the stream is not connected, and at most every 15 minutes (`_lastGuildSync`, wall-clock) while it has received `ready` and is alive. This guild stream is scoped to `steward` holders and to roster/member/character changes only; the separate access-change stream every signed-in user gets, whatever its role, is under Auth.

The existing `RosterMember` record is the WoW guild roster the addon observes, not the gigagrug roster of people. The two are different datasets and the names are deliberately distinct.

## Character sync

`docs/design/character-sync.md` is the agreed contract for this and the source of truth. `StewardSavedVariables` reads `StewardDB.characters`, `professions`, `catalogue` and `guildRanks` through the `LuaSavedVariables` parser into `CharacterObservation`, `CharacterProfessions`, `ProfessionCatalogue` and `GuildRanks` records. While a `sync` feature is held, `MainViewModel` gzip-compresses each install's batch and posts it to `POST /api/guild/{guild_id}/characters/sync` through `GigagrugClient`, gated by a fingerprint over the canonical data with `observedAt` and `scannedAt` stripped out, so a `/reload` that only restamps those fields pushes nothing. Push records live in `%LocalAppData%\Steward\character_sync.json`, a file separate from `state.json` because an older Store build rewrote `state.json` without the sync key, verified 26 Sep 2026. A push runs on startup, on Refresh, from Sync now, from an install's own Send now, whenever an install's `WTF\Account\**\Steward.lua` is written (the Sync page's `SavedVariablesWatcher`, debounced 1.5 seconds, calls `MainViewModel.SavedVariablesWrittenAsync`, which pushes and then reloads the page), and on the background pass as described under Roster sync. Pushes never overlap: a request made while one is in flight runs once more after it finishes, forced if any queued request was. `StewardSyncFile` writes each member's linked `main` character and the recipe `catalogue` into `StewardSync.lua` alongside the existing roster, loot and attendance datasets.

A `sync` holder with no officer seat (`MainViewModel.IsProfessionsOnlySync`) gets a narrower push: `CharacterSyncMapping.FilterToProfessionsOnly` keeps only the characters that have a `StewardDB.professions` entry, the request's `guildRanks` is left null, and the push is a per-character diff (`ProfessionsPushSelection` in Core): each character's professions fingerprint (`CharacterSyncMapping.ProfessionsFingerprint`, `observedAt`/`scannedAt` excluded) is recorded with its outcome in `character_sync.json`, and a push sends only characters whose fingerprint differs from the recorded one, plus the catalogue only when its fingerprint differs from the last accepted one. A rejected character is resent only when its data changes or, for a "not linked to you" rejection, when the pulled member roster now links that guid to the signed-in user; with nothing to send no request is made, and Sync now and Send now send every character. The catalogue itself still rides along, since a seatless caller's captured recipes may be new to the guild: gigagrug inserts only the catalogue rows that do not already exist for such a caller and never modifies an existing row. Roster fields still ride along on each sent `CharacterSyncEntry`, since the server's validation requires them; gigagrug ignores them for a seatless `sync` holder along with the guild ranks, and keeps professions only for guids linked to that user. No separate `professions` flag exists. The Sync page reflects the mode: `SyncViewModel` builds, per install and instead of Roster/Loot/Attendance, a "Guild roster" row (only with the selected guild's `roster` feature) and a "Guild professions" row (only with `professions`), both pulls whose tick means `StewardSync.lua` on disk carries the last written fingerprint, then a "Your characters" push row that expands to the per-character states, collapsed by default when every character is synced and remembered per install for the session; the generated-file card shows for this user too, since their `StewardSync.lua` holds `me` and whatever `directory` and `catalogue` sections were pulled. The saved-variables watcher and Sync now still push on the same triggers as the officer path.

`StewardDB.professions[guid].fp` is a keyed integrity fingerprint the addon computes in game; `StewardSavedVariables` parses it into `CharacterProfessions.Fp` and the app forwards it untouched as `professions.fp` on that character's `CharacterSyncEntry`, included in the push-gate fingerprint like every other professions field so a changed `fp` triggers a push. See "Integrity" in `docs/design/character-sync.md`. `StewardDB.catalogue[profession].fp` is the same kind of fingerprint, one per profession's catalogue entry rather than per character; `StewardSavedVariables` parses it into `ProfessionCatalogue.Fp` and it is forwarded untouched as `fp` on that profession's entry in the push's `catalogue` object, on both the officer and professions-only push, and is included in the push-gate fingerprint the same way.

Every signed-in user whose install has the Steward addon gets a `me` dataset in `StewardSync.lua`, officer or not: `{ id, role?, features }` (`SyncMe` in `Steward.Core`, `role` omitted when null). `GigagrugGuildSyncApi.PullAsync` sets it on the officer's full payload from the same `AdminMe` the roster pull already fetched; `MainViewModel.WriteMe` writes a minimal payload holding only `me` (plus `directory`/`catalogue`, described below) for a non-officer, called from `RecheckAuthorizationAsync` whenever the signed-in user, role or feature set changes (comparing against the values captured before that check overwrites them) and skipped when `HasStewardFeature` is true, since the officer's own write already carries `me` and a second, roster-less write would wipe it. `SignOutTo` is the one sign-out path (the `SignOut` command delegates to it): for a non-officer it calls `WriteMe` with `me: null`; for an officer it caches the last full payload `SyncRosterAsync` wrote (`_lastOfficerPayload`) and rewrites it with `Me = null`, keeping the roster, members, discord and catalogue data rather than wiping it with a roster-less skeleton. `Steward.Sync.Me()`/`Steward.IsOfficer()` in `hoobio/Steward`'s `Core/Sync.lua` are the addon-side readers; `me.role` is a display gate only; it is not enforced client-side.

Three per-flag member routes replaced the old single directory endpoint: `GET /api/guild/{guild_id}/roster` (`roster` feature, `GigagrugClient.GetMemberRosterAsync`) gives `{people, characters}`; `GET /api/guild/{guild_id}/professions` (`professions`, `GetMemberProfessionsAsync`) gives `{professions, catalogue}`, each professions entry now also carrying `name` and `class_id`; `GET /api/guild/{guild_id}/recipes/catalogue` (`sync` or `professions`, `GetMemberCatalogueAsync`) gives `{catalogue}` alone. `MainViewModel.SyncDirectoryAsync` reads the SELECTED guild's own features (`_guildFeatures`, see Auth) to decide which of these to call, on startup, on Refresh, right after a character push actually posts to gigagrug, and on the background pass at most every 15 minutes wall-clock (`_lastDirectorySync`, the same `GuildSyncFallbackInterval` as `_lastGuildSync`); a 403 or 404 on any of them is handled quietly, the same treatment as the events stream, no error bar. The results compose into a `SyncDirectory` (`_lastDirectory`, people/characters/professions, each nullable) and a separate `_lastMemberCatalogue`, carried into whichever payload gets written next, officer or not. `StewardSyncFile`'s `DirectoryToLua` writes `StewardSync.lua`'s `["directory"]` from only the sections actually fetched: `people`/`characters` as a pair when roster was pulled, `professions` (camelCase `classId`, plus every other key already camelCase: `mainGuid`, `linkedUserId`, `maxRank`; `recipes[profession]` is a schema-2 bare array of recipe ids, no per-recipe object) when professions was pulled, each omitted entirely otherwise, so the key is missing rather than an empty table when nothing was fetched. A non-officer's `["catalogue"]` dataset comes from `_lastMemberCatalogue` (`MemberCatalogueMapping.ToCatalogue`, from the professions response when pulled, else the standalone catalogue route), since they never call the officer-only `recipes/catalogue` endpoint under `/api/admin`; an officer keeps their catalogue from that admin call as before.

gigagrug pins every character link (guid to Discord user id) rather than deriving it live, so an officer's re-map, unlink or reset shows up in `characters[].linked_user_id` on the next pull the same way a fresh match would. `StewardSync.lua` carries that pin as a top-level `["links"] = { [guid] = discordUserId, ... }`, a sibling of `me`, `directory` and `catalogue` rather than nested under `directory`, since `hoobio/Steward`'s `Core/Sync.lua` reads `payload.links` directly; one entry per character with a non-null `linked_user_id`, an unlinked guid simply absent. `StewardSyncFile.Render` writes it whenever `payload.Directory.Characters` is not null, the same roster pull that feeds `directory`'s own `people`/`characters`, so it is present exactly when they are and omitted when roster was not pulled. `roster` is an officer default feature (`GigagrugClient`'s `OfficerFeatures`), so `SyncDirectoryAsync` already runs the member roster route for an officer the same as for a raider holding `roster`; it is not gated on `HasStewardFeature`. `hoobio/Steward`'s `Core/Sync.lua` reads `links` in preference to note matching.

## Saved variables

Roster, loot and attendance read WoW SavedVariables files. Those files are one per addon per scope: everything under an addon's `## SavedVariables:` TOC directive lands in one shared account-level file at `WTF\Account\<ACCOUNT>\SavedVariables\<Addon>.lua` under the flavour folder, and `## SavedVariablesPerCharacter:` in a per-character file at `WTF\Account\<ACCOUNT>\<Realm>\<Character>\SavedVariables\<Addon>.lua`. Account folder names look like `54939295#1`, and the `.lua.bak` beside each file is ignored.

The reader is built, in `Steward.Core` with no UI on it yet. `LuaSavedVariables.Parse` is a recursive-descent parser for the client's own dump format: one global per `## SavedVariables:` entry, `["string"]`, `[123]` and bare identifier keys, strings with the client's escapes, numbers, booleans, `nil`, nested tables, array items, trailing commas and the `-- [n]` comments the client writes after array entries. Malformed input throws a `FormatException` naming the line and column. `StewardSavedVariables.FindFiles` locates the Steward files under a flavour path and `StewardSavedVariables.Read` maps them into a `SavedVariablesSnapshot` of roster, loot and attendance.

The Steward addon has no Lua yet, so the schema below is the contract the addon must write rather than a record of what it writes. The account file holds `StewardDB`:

```lua
StewardDB = {
["exportedAt"] = 1758260000,
["roster"] = { { ["name"] = "Hoobi", ["realm"] = "Nightslayer", ["class"] = "WARRIOR", ["level"] = 60, ["rank"] = "Officer", ["rankIndex"] = 1, ["note"] = "", ["officerNote"] = "", ["lastOnline"] = 1758250000 }, },
["loot"] = { { ["id"] = "3f2a...", ["at"] = 1758240000, ["player"] = "Hoobi", ["itemId"] = 19019, ["item"] = "Thunderfury", ["quality"] = 5, ["source"] = "Ragnaros", ["instance"] = "Molten Core" }, },
["attendance"] = { { ["id"] = "9c1b...", ["at"] = 1758230000, ["instance"] = "Molten Core", ["present"] = { "Hoobi", "Grug" } }, },
}
```

The per-character file holds `StewardCharDB` with `["exportedAt"]`, `["character"] = { ["name"], ["realm"], ["class"] }`, and `["loot"]` and `["attendance"]` arrays of the same record shapes, carrying what that character observed. Roster is account-level only and the reader takes it from `StewardDB` alone.

`exportedAt` is unix seconds, at the file level and on `at` and `lastOnline`. Loot and attendance records carry an `id` string, and where the same `id` appears in more than one file the copy from the newest `exportedAt` wins. Reading is tolerant: a missing table gives an empty list, a record missing a required field is skipped and counted in the snapshot's `Skipped`, and an absent `exportedAt` gives null.

The client only serialises saved variables at logout, exit or `/reload`, rewriting the whole file from memory, so any external write to that file while the client is running is lost on the next serialise. Data flow is therefore one direction per file: the app only reads the saved-variables file, and only writes a generated Lua file elsewhere in the addon folder, one the client never writes to, calling a function the addon exposes rather than assigning a raw global.

The generated-file writer is `StewardSyncFile` (`Interface\AddOns\Steward\StewardSync.lua`, written by calling `Steward.LoadSync({...})`), guarded by the same TOC-existence check as `RemoveExistingInstall` and written temp-then-move; the addon's own TOC must list `StewardSync.lua` for the client to load it, a dependency on the addon repo.

Installing or updating the Steward addon replaces the whole folder, so `StewardSync.lua` and `Avatar.tga` go with it. Two things put them back. `StewardSyncFile.Write` embeds the payload fingerprint as a `fingerprint` key right after `writtenAt`, and `GuildRosterSync.WriteIfChanged` skips only when the file on disk carries that same fingerprint (and `Avatar.tga` exists when the payload has one), so the placeholder `StewardSync.lua` the addon zip ships is rewritten on the next pass; and `AfterStewardInstalled` rewrites the file the moment an install finishes, for the user who launches the game before that pass, through `MainViewModel.SyncRosterAsync` for an officer and `WriteMe` for everyone else. `StewardGuidesAddon.Write` likewise skips only when `Guides.lua`, the TOC and `Icon.tga` all match what it would write. `SyncViewModel.WriteGeneratedFileAsync` (the Write again button and the post-install hook) goes through that same method, which pulls through `GigagrugGuildSyncApi`; the in-memory fake that once backed the Sync page, and wrote its fake dataset over the real roster, was removed on 27 Sep 2026.

Still to come, in the commits after this one: the freshness judgement (the saved-variables mtime against the running client's process start time from `WowClient`, plus `exportedAt`) and the sync page itself. The addon side of the contract lives in `hoobio/Steward`'s `AGENTS.md`.

## RestedXP guides

`docs/design/restedxp-guides.md` is the verified contract for RestedXP's undocumented API and is the source of truth for it. Steward signs in against Keycloak directly (`RestedXp:Keycloak`, the `RestedXP-Prod` realm's token endpoint, public client `rxp-prod-login-client`, scope `openid offline_access`) rather than through the account backend's `/login/*` proxy, so the offline refresh token keeps the session across restarts: a password grant, plus `totp=<code>` on a second grant when Keycloak answers `invalid_grant` with an OTP description, and `grant_type=refresh_token` after that. `refresh_expires_in: 0` on an offline token means no expiry, so the stored refresh expiry is null and a null expiry never expires; the cookie's `expiresAt` is then 30 days out. Keycloak's offline session idles out 30 days after the last use, and a refresh slides it, so the on-demand refresh before a call plus the 3-hour check keep the idle window alive and a Steward run at all in any 30-day window never asks for the password again. Every authenticated call carries the `rxp_cross_auth_token` cookie built per request from the access token; the backends read only its `token` field. Guide content comes from `RestedXp:GuidesBaseUrl` (`https://rxpgcr.restedxp.com`), where `/addon/get-all-timestamps` is public and `/addon?guideName=...&bundleIndex=0` needs the cookie.

The password is used for the one password grant and never stored; it is held in memory by `RestedXpService` only between the sign-in step and the code step, and cleared after. The session (username, both tokens, the access expiry and the nullable refresh expiry) lives in `restedxp_session` in `state.json` as a DPAPI blob, the same treatment as `session_token`. The access token lasts 15 minutes, so a call refreshes whenever it has under a minute left; a bounded refresh token is renewed near its end, and a refresh that answers 400 clears the session and the card shows the signed-out state.

Timestamps are checked on the startup pass, on the manual Refresh and on the first background pass more than 3 hours plus a random 0 to 30 minutes after the last check (`_nextGuideCheckDue`, redrawn on every check, so copies restarted together by a Store update drift apart instead of polling RestedXP in step) (`_lastGuideCheck` in `MainViewModel`, wall-clock rather than a pass count, so the minute-by-minute retry while the guild API is unreachable does not speed it up). A guide is stale when the timestamp recorded in `restedxp_guides` (keyed like `AppStateStore.Key`, flavour path plus `productName`) is older than the server's. A downloaded string is cached at `%LocalAppData%\Steward\guides\<product>.txt` beside a `.json` holding its timestamp and BattleTag, so a regeneration costs no network call, and a failed download is not retried for 10 seconds. The sync is per install: every selected product is cached first, and the folder is rewritten when any cached string or the selection itself moved since the last write for that install.

The write is a generated addon, `StewardGuidesAddon` in Core: `Interface\AddOns\StewardGuides\` holding `StewardGuides.toc`, `Icon.tga` (an `EmbeddedResource` in `Steward.Core`, the Steward addon's own icon) and `Guides.lua`. The TOC carries `## Category: Hoobi`, `## Dependencies: RXPGuides`, `## IconTexture: Interface\AddOns\StewardGuides\Icon`, `## SavedVariables: StewardGuidesDB` and the app's informational version. Its `## Interface:` value is read from the installed `RXPGuides.toc` verbatim, comma-separated list and all, so the generated addon tracks the client's interface number through RXPGuides and a new client build needs no change here; a missing `RXPGuides.toc` throws rather than falling back. `Guides.lua` holds each selected product's string as a `[==[...]==]` long-bracket literal, and rendering throws when a string holds that terminator. The safety is `StewardSyncFile`'s: temp-then-move per file, no `WTF` segment in the path, and an existing `StewardGuides` folder is only replaced when its TOC carries Steward's own `## Title:` and `## Author:` lines.

On `PLAYER_ENTERING_WORLD` plus 3 seconds `Guides.lua` takes the RXPGuides addon object from `LibStub("AceAddon-3.0"):GetAddon("RXPGuides", true)` and hands each string to `guideImporter:ImportString`, the paste box's own path. Imports run one at a time: a second call while an import is in flight resets the first one's buffer, so the file waits for `importCoroutine` to be nil and `importBufferSize` to be 0 before the next. `StewardGuidesDB.imported` records the hash from each string's `|hash:` header once the importer's `importStatusHistory[1]` reads "Guides Loaded Successfully", and the mark is read by the app only: the bootstrap imports every string on every login, a few seconds of work, kept from when RXPGuides on this client kept no imported guides between sessions (ClassicWoWCommunity/forever-bugs#34, confirmed fixed by the user on 26 Sep 2026): a skip on our own mark left the game with no guides on 20 Sep 2026, and the re-import stays cheap enough that dropping it buys nothing. The importer writes its failures only into its own window, so the file surfaces them: any other `importStatusHistory[1]` is printed to chat as `Steward <name>: <status>` and kept in `StewardGuidesDB.status[hash]`, which a success clears, and a status holding "restart your game client" is retried once after 10 seconds before it is recorded. Each guide entry also carries the purchaser's `tag` from the cached download, and a guide whose tag differs from `BNGetInfo`'s BattleTag (case-insensitive) is recorded and skipped with "bought on <tag>, you are <playerTag>; not imported" rather than handed to an importer that would reject it silently; a nil BattleTag or an uninitialised RXPGuides is waited on every 5 seconds up to 6 times before the run gives up with a chat line. At file load the bootstrap also wraps the five `inventoryManager` predicates RXPGuides v4.11.x calls from its bag hook (`IsRightClickEnabled`, `IsBagAutomationEnabled`, `IsMerchantAutomationEnabled`, `IsJunkIconEnabled`, `GetModKey`) so they answer false while `settings.profile` is nil, because that hook throws "attempt to index field 'profile'" on a client where their initialisation has not run; the wrap is a no-op once the profile exists. The bootstrap also answers the Hoobi addon version check: a `ping` on the `HoobiVersion` addon-message prefix gets a whisper of `StewardGuides=<TOC Version>` (the app's informational version) back to the sender, the same responder Steward and HoobiScripts carry; the protocol is in `hoobio/Steward`'s `AGENTS.md`.

An import is confirmed from the addon's own saved variable, `WTF\Account\*\SavedVariables\StewardGuides.lua` (`StewardGuidesSavedVariables` in Core): the file lands at logout, exit or `/reload` carrying the `generation` the loaded `Guides.lua` set (unix ms of the write, emitted as `local generation` and recorded per install in `restedxp_guides_generation`) and the hashes and statuses it wrote. Per kept product there are four outcomes: an account file at the install's current generation with the string's hash marked reads `Up to date`; the same file carrying a `status` string for that hash reads `Failed` with that string as the row's message, and drops that product's `restedxp_guides` record so the next sync rewrites the folder; the same file with neither reads `Not finished`, an import cut short by a logout or `/reload` that the addon runs again on the next login; no file at that generation leaves the row `Written`. The pass runs at the end of every guide check, when a client exits, and when a `FileSystemWatcher` per install sees that saved variable written under `WTF\Account` (debounced 1.5 seconds, since the client writes it temp-then-rename), so a row reads `Up to date` seconds after the `/reload` or logout that follows the importing login; it reads files only.

The file is read at login or `/reload` and never written by the client, so there is no client-closed rule: the folder is regenerated whether or not the game is running. Several products can be kept per install (`restedxp_guide_choices`, flavour path to a list of `productName`, migrating an older single `restedxp_guide_choice` into a one-item list), defaulting to every owned product allowed on that install. `RestedXp:ProductPrefixes` in `appsettings.json` maps a WoW product code to the product-name prefixes allowed on it, `wow_classic_beta` to "Forever" today; a product outside its install's prefixes is never written there. The guide string's trailing minimum-version number is not checked here; the addon reports incompatibility in game.

## Banners

Server-driven banners let gigagrug put a message in front of every user without a Steward release: `GET /api/banners` (no auth required, works signed in or out) answers `{"banners": [...]}`, each entry an id, a revision, a level, a title, a message and an optional set of gates and actions. `Banner` and `BannerAction` in `Steward.Core`'s `Banners.cs` are the parsed shape; `id` is documented as a string but has shipped as a JSON number (commit 5425bf8), so `BannerIdConverter` accepts either and normalises to a string, since dropping the banner over a type mismatch would be worse than the coercion. `BannerParsing.Parse` walks the array element by element and skips a malformed one on its own `JsonException` rather than failing the whole response; `GigagrugClient.GetBannersAsync` answers an empty list on a 404 (an older gigagrug with no route yet) and never signs the user out on a 401, since a banner check is not a privileged action like `/api/me`.

A banner's `level` (`info`, `success`, `warning`, `error`) and each action's `type` (`store_update`, `open_url`, `navigate`, `dismiss`) are read by `BannerLevels.Parse` and `BannerActions.Parse`, and an unknown or missing value degrades rather than throws: an unknown level renders as `info`, an unknown action type hides that button only, the rest of the banner still renders. `BannerFilter.Active` narrows the fetched set to what should actually show: not already dismissed at its current revision, in the app's release channel when the banner names any (`Channels` empty or absent means every channel), and the installed version inside `MinVersion`/`MaxVersion` when either is set, compared component-by-component as a 4-part version rather than parsed as `System.Version`, the same reasoning as the addon version comparison under Channels.

`MainViewModel.SyncBannersAsync` fetches on startup, on Refresh, and at most every 15 minutes wall-clock from the background pass (`_lastBannersSync`, the same `GuildSyncFallbackInterval` used elsewhere); a failed or malformed fetch (`HttpRequestException`, `TaskCanceledException`, `JsonException`) is swallowed and keeps the last good set rather than clearing the banners or surfacing an error, since a banner is never load-bearing. `RefreshBanners` re-applies the dismissal filter and rebuilds the `ObservableCollection<BannerViewModel>` (`Banners`, ordered highest severity first) whenever the fetched set or the dismissed set changes. Dismissing (`DismissBanner`) records `{id: revision}` in `dismissed_banners` in `state.json` (`AppState.DismissedBanners`); a banner is dismissible unless it sets `dismissible: false`, and a non-dismissible banner's own `dismiss` action, like every `dismiss` action, is ignored anyway, since the close button already covers it. A later revision of the same id is not dismissed by an older revision's record, so a banner can be brought back by editing it on the server.

`BannerList` (`Views/BannerList.xaml`) is the one `UserControl` every page hosts: a `DependencyProperty` `Banners` bound to `MainViewModel.Banners` (directly for the Addons and Settings pages, whose `ViewModel` is the `MainViewModel` itself, or through `ViewModel.Main.Banners` for Sync and Guides, whose page view models wrap it), rendering severity-tinted cards with inline actions to the right and a close `X` rather than a separate dismiss button. It sits in a dedicated row between that page's own header (title, subtitle, command buttons, unchanged) and its content, on every page, so banners push content down instead of overlaying it: the Addons page's 3-row `Grid` puts it in row 1 with the empty and loaded states both confined to row 2; Sync, Guides and Settings place it inline in their single scrollable `StackPanel`, immediately after the header row (Settings has no in-page header of its own, the title bar being the header per `docs/design/home-and-settings.md`, so its `BannerList` is the first child). An empty `Banners` collection renders as a zero-height `ItemsControl`, so an unpinged page never shows a gap.

A `navigate` action is gated per page (`MainViewModel.IsPageVisible`) so a banner never offers a button to a hidden page (Sync or Guides without the feature that unlocks it); `NavigateToPageTag`, wired in `MainWindow.xaml.cs`, selects the matching `NavigationViewItem`. `--banners-preview` (`Services/BannersPreview.cs`) seeds one banner per level with one action type each (including a non-dismissible `error` banner exercising every action kind) and calls `RescanCommand` so the Addons page also shows its populated, non-empty state, for network-free UI verification.

## UI design

`docs/design/home-and-settings.md` is the agreed design for the Addons page, the settings page and the shell, and it is implemented. Four things in it were behaviour rather than view, and the doc remains the source of truth for each: the release channel is per addon (`AppState.Channels`, with `LegacyChannel` carrying the one-time migration), refresh probes all three channels per addon so a channel with no release can be disabled, the default channel is the highest one that has a release ordered `stable`/`beta`/`unstable`, and the timer refreshes manifests as well as the role. Applying an update follows the game client.

`docs/design/addon-manager.md` is the agreed redesign of the Addons page into a general addon manager: one table for a selected install, an install picker with user labels and a required game version, release channels edited in a dialog from the row instead of on Settings, per-install Ignore, Local rows for unmanaged folders and an out of date TOC flag. It is not implemented; phase 1 is this repo only and phase 2 (Get addons, CurseForge and Wago sources) is blocked on gigagrug. Until phase 1 lands, `home-and-settings.md` describes what is built.

`docs/design/guides-page.md` is the agreed design for the Guides page and the RestedXP sign-in `ContentDialog`, and both are built against it; the doc stays the source of truth. The row control is a `CheckBox` and any number of owned products are kept per install, each checked row carrying its own pill; a product outside the install's client gate renders disabled and unchecked with a dim "Not for this client" line in place of the updated time. There is no "Waiting for game to close" state, since the generated addon is read at login or `/reload`. The `Guides` menu item shows only while RXPGuides is installed in some WoW install and a RestedXP session exists, and the sign-in entry point is a button on the RestedXP row of the Addons page; the page navigates back to Addons when either condition drops. The ninth state, `Needs a newer guide`, is rendered from `GuideSyncOutcome.NeedsNewerAddon`, which nothing sets yet: the service does not compare the written string's minimum addon version against the installed RXPGuides, so that state is reachable only through the preview. `--guides-preview=<scenario>` (`Services/GuidesPreview.cs`) seeds the view models with a fake session and one of the page or dialog states, calls no network and writes no files, and is how the states are screenshotted without an account.

`docs/design/sync.md` is the agreed design for a third page, moving roster, loot and attendance between SavedVariables and the guild API. It is not implemented and it is blocked on two things outside this repo: the Steward addon publishes no manifests, and the sync endpoints do not exist. The endpoint table in that doc is provisional and marked as such. Its shell change replaces the `Frame` in `MainWindow.xaml` with a `NavigationView` in `LeftCompact` mode and moves Settings to the footer item.

## Outstanding work

The tray icon, close-to-tray and minimise-to-tray are built, on `H.NotifyIcon.WinUI`. The `TaskbarIcon` lives in `MainWindow.xaml`, takes its `IconSource` from the filesystem path `App.IconPath` when unpackaged, because an unpackaged app cannot resolve `ms-appx:///`, and from `ms-appx:///Assets/Steward.ico` when packaged, because a packaged app cannot load a `BitmapImage` from a file path under `WindowsApps` (the Store build's first release showed a blank tray icon), and runs in `ContextMenuMode="SecondWindow"`. Two Behaviour cards in Settings decide it: `MinimizeToTray`, persisted as `keep_in_tray` in `state.json` and defaulting to true, sends a minimise to the tray instead of the taskbar, and `CloseToTray`, persisted as `close_to_tray` and defaulting to false, makes the X button hide instead of quit. The two share the old single `keep_in_tray` key so an existing state file keeps its minimise choice and gets the new close default. Restoring from the tray goes through `MainWindow.ShowFromTray`, which shows the `AppWindow`, restores it only when minimised (so a maximised window stays maximised), calls `Activate`, then `Native.ForceForeground`: Windows refuses `SetForegroundWindow` to a process that did not receive the last input event, and a tray click goes to explorer, so the call is wrapped in an `AttachThreadInput` to the foreground window's thread, with a `BringWindowToTop` inside it because the attached `SetForegroundWindow` activates the window without raising it. The tray icon's click commands are assigned in code rather than through `x:Bind`, since a `Window`'s bindings evaluate only once its content loads and a `--tray` launch never loads it. Start with Windows is a third Behaviour card backed by the `Steward` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, pointing at the running exe with `--tray`; that argument hides the window to the tray on launch when `MinimizeToTray` is on. The registry is the only store for it. The card is enabled only in a GitHub release build: the workflow's `dotnet publish` passes `-p:GitHubRelease=true`, the csproj writes that property as `AssemblyMetadata`, and `App.IsGitHubRelease` reads it back. A packaged build cannot use the Run key, since its HKCU writes are virtualised; there the card drives the manifest's `StewardStartup` `StartupTask` (which passes `--tray`) through `StartupTask.GetAsync`, `RequestEnableAsync` and `Disable`, and is always enabled except when the task reads `DisabledByUser`, `DisabledByPolicy` or `EnabledByPolicy`, which render the toggle disabled with a description pointing at Windows Settings. A non-GitHub-release build shows "(Development)" and a GitHub-release build stamped `StorePreRelease` shows "(Pre-release)" in the window title, tray tooltip and version label, as described under Microsoft Store. A settings window was cancelled and has since been revived as a settings page: see `docs/design/home-and-settings.md`.

Checking runs at startup and on every tick of a 1-minute `DispatcherQueueTimer` in `MainViewModel`, re-checking `/api/me` alongside the manifests, unless a pass is still in flight; the guild roster pull and character push inside that pass drop to every 15 minutes while the guild event stream is connected, as described under Roster sync. A background pass skips busy rows and never re-orders `Installs` or `AddonRows`. `MainViewModel.AutoApplyAsync` runs after every pass, on every tick and right after a watched client exits: each eligible row's `UpdateCommand` is executed in turn, skipping busy rows and rows whose last attempt failed until a new resolution arrives. A fourth Behaviour card, "Auto-update addons", gates this in one place, the top of `AutoApplyAsync`: `Always` applies whether or not the client is running (the original behaviour), `Out-of-game` skips a row while its install's `WowInstallViewModel.IsClientRunning` is true and catches up the moment that install's client exits, and `Never` returns before touching any row, including the `AutoInstall` install of a missing addon. The setting is `AppState.AutoUpdate`, persisted as `auto_update` in `state.json` with the values `always`, `out-of-game` and `never`, defaulting to `out-of-game`; `AppStateStore.ParseAutoUpdate` reads an unknown or missing value the same way. `WowClient.IsRunning` in Core judges whether an install's client is up, by matching any `Wow*` process whose main module sits under that install's flavour folder; it drives the running dot and the `/reload` hint a row shows after an update applied while the client was running, cleared when the client stops.
